# Designing a fork-first hypervisor for AI agents

The design the evidence supports is a microhypervisor: a small Rust core at EL2 (AArch64) or VMX/SVM root (x86-64) that owns only vCPUs, second-stage page tables, interrupt and timer virtualization, scheduling and the IOMMU, with one deprivileged VMM per sandbox, a Linux driver VM for physical NIC and NVMe, and an identical virtio-only, firmware-free guest contract on both architectures. Its one differentiating feature should be copy-on-write fork and snapshot restore implemented directly on stage-2/EPT page tables, because every agent-sandbox provider surveyed already "boots" by restoring a snapshot and each has had to build its own userfaultfd handler and chunk store around KVM to do it. The honest counter-case is strong: minimal Linux + KVM + a Rust VMM delivers ≤125 ms boots and ≤5 MiB overhead today, and no operator whose reasoning was found (AWS, Oxide, Firecracker's authors, Microsoft) chose to write a new privileged hypervisor for general Linux guests. A new type-1 is therefore justified only by two things KVM cannot offer: a guest-reachable privileged surface of roughly 10–15 KSLOC instead of a general-purpose host kernel, and fork/CoW/sharing as kernel primitives rather than Linux-mm workarounds. AArch64 is the simpler architecture for the CPU, memory and interrupt core and the harder one for platform I/O (SMMUv3, GIC ITS, ACPI/IORT), and Graviton offers no nested virtualization, so the Arm product needs bare metal while x86 can be developed and even deployed nested. The researchers' unsourced planning estimate is 3–5 engineers, 9–15 months to a credible dual-architecture prototype and 2–3 years to something trustworthy with hostile multi-tenant code. Three gaps limit confidence: no VM-exit cost measurement on any current server CPU, thin Arm-specific security evidence, and no independent benchmark of snapshot restore or fork across any VMM.

A note on evidence. The underlying notes label each claim as fetched from a primary source, taken from a search snippet or secondary write-up, recalled without re-fetching, or the researcher's own inference. This report keeps those labels where they change how much weight a claim can bear: "snippet", "secondary", "vendor claim", "recalled" and "estimate" below mean exactly that. Design recommendations are inferences unless a source is attached.

## Agent sandboxes are idle, stateful computers that start by restore

The market has converged on KVM microVMs with snapshot restore as the create path. E2B runs one Firecracker microVM per sandbox; templates are pre-booted snapshots in object storage, memory is served lazily through `userfaultfd`, the root filesystem is a CoW overlay, and a live sandbox can be forked into up to **100 copies** ([E2B infra README](https://raw.githubusercontent.com/e2b-dev/infra/main/README.md)). Modal, long a gVisor shop, shipped a Cloud Hypervisor-based VM runtime in October 2026 because customers needed Docker stacks, local databases, GUI environments and kernel-level work, and one customer could not mount FUSE under gVisor ([Modal](https://modal.com/blog/vm-sandboxes-agent-computers)). Fly's Sprites pre-stage pools of empty VMs because a Machine create "can take over a minute", and treat checkpoint/restore as a metadata shuffle over chunked object storage ([Fly](https://fly.io/blog/design-and-implementation/)). An independent May 2026 study confirms the engine classes actually in the field: Firecracker, Cloud Hypervisor, libkrun, gVisor and runc ([arXiv 2606.08433](https://arxiv.org/html/2606.08433v1)). Only Edera, which reuses the Xen core, runs a type-1 for agent isolation, and its published start times are slow: +740 ms over Docker's 381 ms in a paper by Edera-affiliated authors ([arXiv 2501.04580](https://arxiv.org/abs/2501.04580), snippet). The combination of a type-1 core, a full Linux guest and millisecond snapshot/fork appears unoccupied, which is an inference from a survey that did not cover every vendor.

The workload differs from serverless functions in ways that set the design priorities. One practitioner sizes a coding agent at 2 vCPU / 8 GiB RAM / 40 GiB disk and reframes cost as vCPU plus shared base memory plus dirty RAM plus dirty disk; in their Firecracker deployment a 4 GiB base memory file had only **49 MiB physically allocated**, and three guests showed 35% PSS/RSS against an ideal 33% ([Cortex](https://builders.cortex.io/blog/sandboxing-agents-part-2/)). CodeSandbox found that a resumed VM typically touches only 300–400 MB even when the guest reports 3–4 GB in use ([CodeSandbox](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3), 2022). Agents checkpoint constantly: Fly reports that the pre-installed Claude Code "checkpoints aggressively without being asked" ([Fly](https://fly.io/blog/design-and-implementation/)). Idle memory and disk dominate cost, so pause-to-zero, cheap fork and memory reclaim matter more than kernel boot time. No source quantified production session lengths, idle ratios or fork fan-out; the sizing above is one team's model.

The baseline to match is Firecracker's specification: **≤125 ms** from `InstanceStart` to guest `/sbin/init`, **≤5 MiB** VMM overhead for a 1 vCPU / 128 MiB guest, and guest CPU above 95% of bare metal, stated for both x86 and Graviton2 metal hosts ([Firecracker SPECIFICATION.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/SPECIFICATION.md)). Sub-100 ms figures in this market are restore figures and are all self-reported: Blaxel's ~25 ms resume ([Blaxel](https://blaxel.ai/platform/sandboxes), vendor claim, snippet), Morph's <250 ms branch ([Morph](https://cloud.morph.so/docs/developers), vendor claim, snippet), and Marc Brooker's statement that Firecracker restores "in as little as 4 ms (or about 10 ms for a full decent-sized Linux system)" ([Brooker](https://brooker.co.za/blog/2022/11/29/snapstart/), snippet, architecture unstated). Reasonable targets for a new design, which are the researchers' synthesis rather than sourced requirements, are restore-to-first-instruction in the low tens of milliseconds, fork cost proportional to dirty pages with fan-out of at least 100, low single-digit MiB fixed overhead per VM, and an unmodified Linux guest that runs Docker, FUSE, cgroups v2 and network namespaces.

The pain points with the KVM stack are about state, not boot, and they define what a purpose-built hypervisor could fix. Firecracker's diff snapshots are still developer preview, mostly not directly resumable, and dirty tracking "negates most huge page benefits"; snapshots must resume on identical hardware and software; clones resume with the same MAC, IP, entropy and tokens, which the docs call insecure unless mitigated; vsock connections die on restore ([Firecracker snapshot docs](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/snapshotting/snapshot-support.md)). Free page reporting and virtio-mem arrived only in v1.14, with reporting labelled developer preview ([Firecracker CHANGELOG](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)), and a proposed VFIO GPU passthrough implementation rejected balloon and memory hotplug when passthrough is enabled ([Firecracker PR #6245](https://github.com/firecracker-microvm/firecracker/pull/6245), snippet). Every serious user builds a private fault handler and chunk store; Cortex notes that memory "lacked an NBD-style boundary" ([Cortex](https://builders.cortex.io/blog/sandboxing-agents-part-2/)).

The threat model has two halves, and a hypervisor addresses only one directly. Against tenant escape, the argument for a small core is structural: with KVM the whole host kernel is in the TCB, and the same study counted roughly 3,500 Linux kernel CVEs in 24 months against two each for Firecracker and Cloud Hypervisor ([arXiv 2606.08433](https://arxiv.org/html/2606.08433v1)). Against the agent as confused deputy, isolation does nothing: in Anthropic's internal red-team a phishing-style prompt got Claude to read `~/.aws/credentials` and POST them out in **24 of 25 tries**, and only egress controls and filesystem boundaries held ([Anthropic](https://anthropic.com/engineering/how-we-contain-claude)). The hypervisor's I/O boundary is where those controls belong.

## Both architectures supply the same primitives; ARM64 is the cleaner CPU and the harder platform

x86-64 and AArch64 both provide a deprivileged guest mode that traps to the hypervisor, hardware two-stage paging with tagged TLBs, hardware-assisted interrupt-controller virtualization and an IOMMU. They differ in how much mandatory surface comes with them. The table summarizes the mechanisms; rows marked "spec" are standard architectural facts the notes summarized from background knowledge with a link to the canonical specification, not re-read this session.

### ARM64 is the simpler core to bring up

A type-1 lives entirely at EL2 with banked registers, so guest entry is an exception return, there is no VMCS consistency checking, stage-2 uses the stage-1 table format, and guests boot from a flat devicetree with PSCI. The measured consequence, on old hardware, is a cheaper bare transition: **376 cycles** for a Xen/ARM hypercall round trip against roughly 1,230–1,300 on x86, and 71 cycles for virtual interrupt completion on Arm against about 1,500 on pre-APICv x86 ([ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf); X-Gene and Xeons of that era). The one shared-codebase data point agrees: NOVA carries **11,008 SLOC for Arm and 13,996 for x86** (release 24.17, secondary), and now includes SMMUv3, ITS and LPI support ([NOVA FOSDEM 2026 slides](https://fosdem.org/2026/events/attachments/SUMHNW-nova/slides/267403/nova_-_fo_yup0qhf.pdf)). Bao boots Linux guests on Arm in 8,423 SLoC ([RTAS 2023](https://arxiv.org/abs/2303.11186)).

VHE is not required for a hypervisor that natively occupies EL2, but the notes recommend writing for `HCR_EL2.E2H=1` because it lets EL2 host its own EL0 processes, which is exactly what per-VM user-mode VMMs need; this point comes from background knowledge of the architecture, not a fetched source. The measured lesson from KVM's VHE redesign is about lazy state switching, not VHE itself: restructuring register save/restore out of the per-exit path cut a hypercall from 3,181 to 752 cycles on a Cortex-A57, while merely enabling VHE gave 3,181 to 3,045 ([Linaro SFO17-403](https://static.linaro.org/connect/sfo17/Presentations/SFO17-403%20Optimizing%20the%20Design%20and%20Implementation%20of%20KVM_ARM.pdf), 2017).

### ARM64 is the harder platform

Everything outside the CPU costs more on Arm. Servers boot with UEFI and ACPI under SystemReady SR while boards and QEMU use devicetree, so the hypervisor needs both front ends ([kernel.org ACPI on Arm](https://docs.kernel.org/6.16/arch/arm64/arm-acpi.html)). PCIe MSIs arrive as LPIs through the ITS, a driver with command queues and memory tables shared with hardware, and DMA isolation needs SMMUv3. Two well-resourced projects remain unfinished exactly here: pKVM's kernel documentation lists DMA isolation via IOMMU as **unimplemented** and the feature as "experimental ... subject to breaking changes" ([pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html)), and Xen's ACPI boot on Arm is experimental with IORT handling the remaining blocker ([xen-devel, Aug 2025](https://lists.xen.org/archives/html/xen-devel/2025-08/msg01497.html)). The hypervisor is also a client of EL3 firmware it cannot replace, using PSCI over SMC for secondary cores and reset.

Snapshot and fork are harder on Arm in three specific places. First, a virtual ITS keeps its tables in guest RAM: KVM's save operation writes them into guest memory, so the save itself dirties pages, and restore order is strict ([KVM vGIC ITS docs](https://docs.kernel.org/virt/kvm/devices/arm-vgic-its.html)). Second, there is no deployed PML analogue; the baseline is stage-2 write protection, and splitting a live 2 MiB block requires break-before-make unless FEAT_BBM level 2 is present ([eager-split series](https://lore.kernel.org/all/Y3Qms0lbCiLFJvG+@google.com/T/), secondary). Third, register state is wider and less stable: Firecracker states that arm64 snapshots cannot be restored across GIC versions ([Firecracker snapshot docs](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/snapshotting/snapshot-support.md)). For CoW fork the missing PML costs nothing, because fork needs the write fault anyway to copy the page; hardware logging only helps incremental snapshots.

The deployment asymmetry is a go-to-market constraint. AWS nested virtualization on virtual instances covers Intel families only, and Arm's own guidance says nested virtualization needs FEAT_NV2 on a bare-metal host and "isn't available inside a standard VM" ([AWS, Feb 2026](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-ec2-nested-virtualization-on-virtual); [Arm learning path](https://learn.arm.com/learning-paths/servers-and-cloud-computing/nested-virtualization/)). On x86 the product can run nested on commodity cloud VMs; on Arm it must own EL2 on Graviton `.metal`, Ampere-class bare metal or owned hardware. Even on x86, no nested offering exposes a real IOMMU, and AWS and GCP name only KVM and Hyper-V as supported L1 hypervisors ([EC2 user guide](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nested-virtualization.html), snippet), so a nested deployment has to trust its driver VM more than the bare-metal design does.

### Mandate a modern baseline on both

The cheapest way to shrink the core is to refuse old hardware, the trade bhyve made when it "was designed to require hardware virtualisation features (VT-x, EPT)" ([Oxide RFD 26](https://rfd.shared.oxide.computer/rfd/26)). The notes' recommended floors are inferences. On x86: EPT/NPT, VPID/ASID, unrestricted guest, x2APIC with APICv on Intel or x2AVIC on Zen 4+, TSC-deadline and invariant TSC, VT-d/AMD-Vi with interrupt remapping, UEFI-only boot. On Arm: Armv8.2+ written for E2H=1, 16-bit VMID, GICv3 with the system-register interface and no GICv2 path, GICv4.1 as an optional accelerator, SMMUv3, PSCI over SMC, UEFI+ACPI hosts, and the 4 KiB granule so one page-table walker serves both. These floors remove shadow paging, real-mode emulation, a general instruction emulator and PIC/PIT/IOAPIC emulation. Which of these features Graviton3/4, Axion, Cobalt and AmpereOne actually expose to bare-metal software was not confirmed from primary sources.

### Exit frequency matters more than exit cost, and the cost data is old

With nested paging, large pages and tagged TLBs, NOVA reported more than 99% of native performance in 2010 ([NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)); forcing 4 KiB stage-2 pages on Arm cost up to about 20% on MiBench ([RTAS 2023](https://arxiv.org/abs/2303.11186)). The levers are therefore second-stage huge pages, hardware interrupt virtualization and tickless guests. The newest verified per-exit numbers are from 2010–2017. The notes' planning budget of roughly 1,000–2,000 cycles for a bare x86 round trip including post-2018 mitigations, 3,000–6,000 for an exit handled by a same-core user VMM and 10,000+ for a cross-VM hop is an **estimate, not a measurement**; a 2025 blog's "200–800 cycles" for Neoverse N1 came without data and should not be quoted. Measure with kvm-unit-tests on target hardware before committing to any number.

## A microhypervisor with per-VM VMMs fits churn, but KVM is the honest baseline

Small type-1 hypervisors fall into three families. Static partitioners (Bao at 8.4 KSLoC, Jailhouse at 9.9 KSLoC) have no scheduler and no dynamic VM lifecycle. Control-domain systems (Xen at 67 KSLoC for a minimal Arm dom0less build, Hyper-V, ESXi) are the only true type-1s proven at cloud scale. Microhypervisors (NOVA, seL4 with a user-level VMM at 14.8 K + 40 K SLoC) keep roughly 10–15 KSLOC privileged and run one unprivileged VMM per VM ([RTAS 2023](https://arxiv.org/abs/2303.11186)). The third family fits "many mutually distrusting, short-lived guests" because a VMM compromise or crash is contained to one VM. Nothing in the first or third family is known to run thousands of short-lived Linux guests in production, and no VM create-rate measurements exist for NOVA or seL4.

The cost of the split is measurable and tolerable if interrupts stay out of it. In NOVA's 2010 evaluation an average handled exit cost about 3,900 cycles, of which the round trip to the user-mode VMM was about 600, or **15%**; 59% was emulation that would happen anywhere ([NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)). The warning is seL4's CAmkES VMM, where every interrupt goes kernel to VMM to kernel and latency reaches 9,400 ns against about 840 ns for Bao and 200 ns native; with GIC direct injection it returns to near native ([RTAS 2023](https://arxiv.org/abs/2303.11186)). The split that follows: vCPU run loop, stage-2 fault fast path, vGIC/LAPIC and timer virtualization, scheduler and IOMMU programming in the core; virtio device models, boot loading and snapshot orchestration in the per-VM VMM; physical NIC and NVMe in a driver VM.

Control-plane design decides whether churn scales. LightVM showed that Xen's bottleneck for fast creation was XenStore and the dom0 toolstack, not the hypervisor; replacing them with shared-memory device setup and pre-created VM shells produced 2.3 ms unikernel boots and 8,000 VMs per host ([LightVM, SOSP 2017](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf); never upstreamed). seL4's VMM added 65% to Linux guest boot in user-level capability setup ([RTAS 2023](https://arxiv.org/abs/2303.11186)). Per-VM setup must be O(1) with no global registry or lock, and a capability model makes teardown of a dead VM's resources a single revoke.

### The device driver problem has one answer with broad evidence

No general-purpose type-1 except ESXi writes its own broad driver set. Xen uses dom0 and driver domains, Hyper-V the root partition ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/architecture)), ACRN a Linux Service VM ([kernel.org ACRN docs](https://docs.kernel.org/virt/acrn/introduction.html), snippet), and AWS moved device models onto Nitro cards ([AWS Nitro whitepaper](https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/the-nitro-system-journey.html)). The viable path is a Linux driver VM that owns the NIC and NVMe through IOMMU passthrough and serves virtio backends to sandboxes. Its historical cost is real: Xen's I/O-out latency through dom0 was 11,262 cycles on x86 against 560 for KVM ([ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)), so shared-ring batching matters; no post-2020 controlled comparison of driver-domain, in-host vhost and VF passthrough was found. SR-IOV per sandbox is the performance escape hatch, but the notes judge that VF count limits and pinned guest memory defeat density, overcommit and CoW snapshots. The design work that is actually new is making the driver VM less privileged than dom0: it owns devices and serves backends but cannot map arbitrary guest memory.

### The case against building it

The case against a new type-1 deserves to be stated at full strength. Firecracker's authors "chose to keep KVM, but entirely replace QEMU" for implementation cost and because Linux's scheduler and memory manager are well proven; the result was about 50 KLOC of Rust, about 3 MB of overhead per VM against 13 MB for Cloud Hypervisor and 131 MB for QEMU, and up to 150 microVM creations per second per host ([Firecracker NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)). Oxide's guiding principle was to "choose software that is already close to being what we need"; it rejected Xen for its "large and complicated (by dom0) codebase" and never evaluated writing a hypervisor ([Oxide RFD 26](https://rfd.shared.oxide.computer/rfd/26)). Microsoft's new Rust work (OpenVMM, Hyperlight) is VMM-level on an existing hypervisor ([OpenVMM](https://github.com/microsoft/OpenVMM), snippet). The projects that did build small cores show how the second half stalls: Hedron remains Intel-only with a mirror-only repository after a decade ([Hedron README](https://github.com/cyberus-technology/hedron)); seL4's x86 VMM path still needs non-mainline Microkit patches ([libvmm](https://github.com/au-ts/libvmm), snippet); pKVM's protected guests landed in Linux 7.1 as "very experimental" after work Will Deacon described as "somewhat languishing upstream" ([linux-arm-kernel, Jan 2026](https://lists.infradead.org/pipermail/linux-arm-kernel/2026-January/1091563.html), snippet). Beyond that, the notes' inference is that performance parity is the best case, since exits cost the same hardware transition, and that a new core forfeits perf, eBPF, cgroups, kdump, THP, userfaultfd and io_uring and takes on every future CPU-vulnerability mitigation alone.

The case for it is narrower and rests on two points. A guest-to-host escape in KVM lands in ring 0 of a general-purpose kernel, and 2026 supplied a concrete example of the host kernel being the weak layer: a host IPv4 networking flaw reachable through virtio-net checksum metadata, found during a challenge against Vercel's Firecracker sandbox, was neither a KVM nor a Firecracker bug ([CSO Online](https://www.csoonline.com/article/4237999/kvm-escape-exposes-broader-attack-surface-in-linux-networking.html), secondary; the CVE number reported for it looks unusual and is unverified). In a microhypervisor that network backend sits in a deprivileged component. Second, the workload is narrow (Linux guests, virtio only, no legacy), which is the condition under which a small purpose-built system is feasible, and fork/CoW/sharing can be kernel objects. One caveat belongs with the security argument: a small TCB is not automatically a hardened one, and it needs the same speculation mitigations.

| Option | Time to first useful host (estimate) | Isolation story | Main risk |
|---|---|---|---|
| 1. New Rust type-1 + Linux driver VM + reused Rust VMM | 9–15 months to prototype; 2–3 years to production | Smallest privileged core; team owns every bug and mitigation | Schedule, hardware long tail, bus factor |
| 2. NOVA/Hedron or seL4 + own VMM | 6–12 months if Intel-only is acceptable (Hedron); long on x86 for seL4 | Proven microhypervisor design; seL4's proofs exclude VT-x | Thin communities, GPLv2 cores, x86 immaturity |
| 3. Xen core + Rust toolstack (Edera's path) | 3–6 months | Real type-1 with a long advisory history and active process | dom0 privilege, weak CoW snapshot culture; krata lists aarch64 at 10–30% |
| 4. Minimal Linux + KVM + Firecracker or Cloud Hypervisor | Weeks | Large ring 0 mitigated by jailer, seccomp, minimal config | Host kernel attack surface |
| 5. pKVM-style deprivileged host | Not available on x86 | Attractive in theory | arm64-only and experimental |

The table is the researchers' assessment; the times are unsourced estimates, and licences other than Hedron's GPLv2 were not verified ([Hedron README](https://github.com/cyberus-technology/hedron); [krata](https://www.github.com/edera-dev/krata), snippet; [seL4 verified configurations](https://docs.sel4.systems/projects/sel4/verified-configurations.html)). The position this report takes: ship on option 4 first with a VMM whose hypervisor interface is abstracted, as Cloud Hypervisor's already is across KVM and MSHV ([Phoronix](https://www.phoronix.com/news/Cloud-Hypervisor-26.0), snippet), and build option 1 underneath the same VMM and control plane only if the type-1 boundary and native fork are genuine product requirements. The driver VM in option 1 is then the option-4 host image minus KVM. Option 3 is the fastest real type-1 on x86 but unproven on Arm by its main proponent, and pKVM on Arm would split the two architectures into different TCB stories. With ARM64 confirmed as a target, option 1 is the only one that yields a single design on both.

## Converge the guest ABI and make fork a stage-2 primitive

### One device set, two boot contracts

The proven minimal device model is virtio-blk, virtio-net, virtio-vsock, a console, an entropy source, a paravirtual or architectural clock, a reset signal, and in-kernel interrupt controller and timer emulation. Firecracker's original set was exactly this, with a partial i8042 "used only to signal the host that the guest requested a reboot" ([Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)); its entire virtio-block implementation was about 1,400 lines of Rust ([Firecracker NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)). The portability rule the notes derive is to converge the guest rather than the host: the same virtio devices and no firmware on both architectures, so the per-VM VMM is almost entirely shared and only boot-info generation and CPU-feature policy differ.

Transport is a deliberate choice. virtio-mmio is the smallest code and on Arm needs only one SPI per device through the GICv3 distributor, avoiding the virtual ITS and its guest-memory tables entirely. virtio-pci gives per-queue MSI-X and hotplug, but Firecracker's opt-in PCI transport, added in v1.13, is where its 2026 out-of-bounds write occurred while the MMIO default was unaffected ([AWS bulletin 2026-015](https://aws.amazon.com/security/security-bulletins/2026-015-aws)). Start with virtio-mmio on both architectures, with split virtqueues plus EVENT_IDX and indirect descriptors. If PCI becomes necessary on Arm, the notes suggest an SPI-backed MSI frame as lower complexity than a virtual ITS, an inference no source compared.

Boot is direct on both. On x86 use the PVH entry or the 64-bit boot protocol with an uncompressed kernel; the Firecracker paper measured about 40 ms for decompression, up to 70 ms for serial console output, and 900 ms extra for a stock Ubuntu kernel probing absent legacy devices ([Firecracker NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)). The guest kernel config must match the device model exactly. On Arm the contract is smaller: load `Image` at `text_offset` above a 2 MiB-aligned base, pass the DTB address in `x0`, enter at EL1 with the MMU off; there is no in-kernel decompressor and the devicetree is the whole platform description ([Booting AArch64 Linux](https://docs.kernel.org/arch/arm64/booting.html)). The protocol requires the image to be cleaned to the point of coherency, which is easy to miss when image pages are mapped CoW from a shared copy. PSCI `SYSTEM_OFF/RESET` replaces the x86 reset stub. Cold-boot floors for a real Linux guest sit around 100–150 ms and are dominated by guest work (2020 data); nothing published breaks down a modern kernel's boot, and no arm64-specific boot or restore latency was found. Cold boot matters for template builds; the create path is restore.

### Fork on page tables, not on files

KVM practice is to keep guest RAM as a file, restore by `MAP_PRIVATE` or userfaultfd, and layer CoW with reflinks and shared mappings. A hypervisor that owns the second-stage tables can do what Xen's VM fork does: "creating a domain with an empty memory space and a parent domain specified from which to populate the memory when necessary" ([xen-devel VM forking series](https://lore.kernel.org/xen-devel/cover.1584981438.git.tamas.lengyel@intel.com/), secondary summary; a 0.011 s fork-reset figure is reported, creation time was not retrieved). The notes' design generalizes this. Pause the parent's vCPUs, write-protect its leaf entries or share page-table subtrees with reference counts, create the child with an empty or subtree-shared table, copy vCPU and virtio state, and resume both; a write fault allocates and copies 4 KiB, a read fault in a lazy child maps the shared frame read-only. Fork cost is then proportional to page-table pages touched rather than guest RAM, with no memory file, no user-space fault round trip and no page-cache duplication. This is a design inference; no implementation measured it.

Three choices follow. Use 2 MiB mappings for read-mostly template memory shared across clones and 4 KiB for private memory, because a huge page must either be copied whole on first write or split; on Arm, split at fork time or under a per-VM pause because of break-before-make. Make the dirty-tracking backend pluggable (write-protect faults everywhere, PML on Intel, HDBSS when it arrives), since it is needed only for incremental snapshots. And build working-set prefetch only for restore from cold or remote storage, where REAP cut cold-start delay about 3.7x and FaaSnap improved on REAP by up to 3.5x ([REAP](https://infoscience.epfl.ch/record/283308/files/asplos21-reap.pdf); [FaaSnap](https://www.sysnet.ucsd.edu/~voelker/pubs/faasnap-eurosys22.pdf); ratios from summaries); same-host forks from a resident parent do not need it.

Identity is part of the fork primitive. VMGenID reseeds the kernel PRNG on Linux 5.18+ via ACPI and 6.10+ via devicetree, and VMClock exposes a generation counter to userspace, but application-level state is still duplicated ([Firecracker snapshot docs](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/snapshotting/snapshot-support.md)). On Arm the hypervisor sets `CNTVOFF_EL2` per VM so the virtual counter continues from the snapshot value; there is no kvm-clock, so wall-clock correction comes from the guest agent or the VMClock page. The portable state format must exclude host handles, version vCPU state per feature, and pin a per-template CPU feature mask; on Arm that means sanitized ID registers and explicit SVE vector-length policy. Snapshot files are untrusted input: Firecracker's carry only a CRC64 against accidental corruption and operators must add authentication and encryption ([Firecracker snapshot docs](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/snapshotting/snapshot-support.md)).

### Memory elasticity, storage, network and the control channel

Free page reporting returns guest-freed blocks continuously at roughly 0.2–1.7% overhead in the original 2020 measurements, but only at `pageblock_order` granularity ([LWN](https://lwn.net/Articles/808807/)); virtio-mem resizes in 2 MiB units ([virtio-mem](https://virtio-mem.gitlab.io/)). In a fork-native design, releasing a page is unmapping a stage-2 entry. The rule to enforce is that re-faulting a guest-freed page yields zeros, never the parent's stale content. A 2026 Firecracker advisory covers restores using the file memory backend together with a balloon or virtio-mem device ([AWS bulletin 2026-169](https://aws.amazon.com/security/security-bulletins/2026-169-aws/), secondary; the bulletin was not read and the reported CVE identifier is unverified), and the notes infer, without confirmation, that it is this bug class. Elasticity, huge pages and snapshots must be designed together; hypervisor swap is the same machinery as diff snapshots and can wait.

Every platform examined gives the guest a plain virtio-blk root and implements CoW below it. E2B uses a read-only template plus a per-sandbox CoW cache served over NBD, sealed into a diff on pause, with chunks fetched lazily from object storage ([E2B ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)). The design that follows is a chunked CoW block layer keyed by the same snapshot ID as memory, so fork is atomic across both and a disk fork is a metadata operation, with discard support so deleted files release overlay chunks. Keep filesystem sharing out of the default profile: a 2026 Kata Containers virtio-fs flaw allowed guest-root to host-root escape when virtiofsd ran as root unsandboxed ([OSV](https://osv.dev/vulnerability/CVE-2026-47243), secondary), and vhost-user devices complicate snapshots.

For networking, every clone should keep the same guest MAC and IP with identity held hypervisor-side at the virtual switch port, which mirrors Firecracker's per-clone namespace-plus-NAT recipe without its setup cost ([Firecracker network-for-clones.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/network-for-clones.md)). E2B pools network slots (namespace, veth, tap, nftables), which implies that setup is expensive relative to restore, though no figure was published ([E2B ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)). Because agent traffic is mostly outbound HTTPS, terminating guest traffic in a deprivileged network service with proxy-mediated egress puts allowlists, credential injection and logging in one place; SNI/Host filtering alone is bypassable. Software virtio-net at 15–25 Gb/s per core in 2020 already exceeds the need ([Firecracker NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)).

The control channel should be vsock to a small guest agent offering exec with PTY, file operations and snapshot hooks. E2B's envd shows the surface and one optimization worth copying: sandbox create now blocks on a single held `/init` request instead of a retry loop ([E2B ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)). The protocol must be connectionless on restore, with the host reconnecting and delivering a "you were forked, new identity is X" message.

Backend placement is the least-sourced part of this design; the notes treat it as analysis, not established fact. The recommended hybrid keeps tiny fixed-function devices (vsock transport, console, RNG, clock pages) and the CoW block mapping in or near the core so the fork path involves no external process, and puts networking and object-storage access in a deprivileged service domain reached over virtio through pre-shared bounce regions, which avoids a backend mapping that bypasses CoW and dirty tracking.

## Security comes from structure: nothing to emulate, nothing mapped, everything bounded

Escapes cluster in device emulation, complex per-VM memory logic and instruction emulation; the bare VT-x/SVM path is rarely the culprit. The only quantitative breakdown found is dated: of Xen's core-hypervisor advisories through 2017, memory management accounted for 25.69%, CPU virtualization 21.53% and instruction emulation 13.19%, and isolating per-VM logic would have contained 107 of 144 ([Shi et al., NDSS 2017](https://dev.ndss-symposium.org/wp-content/uploads/2017/09/ndss2017_02A-4_Shi_paper.pdf)). The structural response is to leave those categories out of the core: no shadow paging, no PV MMU, no in-core instruction decoder, no grant-table machinery, no compatibility enlightenments. Nested virtualization recurs as an escape source, from the 2021 AMD nested-SVM escape ([Project Zero](https://googleprojectzero.blogspot.com/2021/06/an-epyc-escape-case-study-of-kvm.html)) to a 2026 KVM shadow-MMU use-after-free reported to need nested virtualization exposed by the host ([Ubuntu](https://ubuntu.com/blog/januscape-linux-vulnerability-mitigations-available), secondary; trigger not verified against the kernel commit). It should be off by default, which trades against the "optional nested virtualization" wish from the workload side.

Rust removes most memory corruption but not the residue. Firecracker's 2026 virtio-PCI flaw was triggered by a guest changing queue configuration after activation; sources disagree on whether it is a VMM crash or host code execution ([AWS bulletin 2026-015](https://aws.amazon.com/security/security-bulletins/2026-015-aws); [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-5747)). A Cloud Hypervisor flaw let a guest with a raw disk forge a QCOW2 header to exfiltrate host files, a pure logic bug ([INCIBE](https://www.incibe.es/en/incibe-cert/early-warning/vulnerabilities/cve-2026-27211), secondary). Rust also does not prevent double-fetch on memory shared with an untrusted party ([NCC Group](https://www.nccgroup.com/research/rustproofing-linux-part-44-shared-memory/)). The rules that follow: forbid device reconfiguration after activation, forbid image-format autodetection, treat guest memory as volatile bytes copied in once and validated, confine `unsafe` to a few small crates, and make guest-reachable paths panic-free, since with `panic=abort` every guest-reachable panic in the core is a host DoS. One caution on identifiers: an additional Cloud Hypervisor virtio-block CVE appears only in a single preprint, and several 2026 CVE numbers in press coverage look malformed, so this report does not rely on them.

Availability is a security property here. In the same Xen data **61.81%** of core vulnerabilities led to host DoS, through live locks, infinite loops, false `BUG_ON`s and resource exhaustion ([Shi et al., NDSS 2017](https://dev.ndss-symposium.org/wp-content/uploads/2017/09/ndss2017_02A-4_Shi_paper.pdf)). Every hypercall and exit handler needs a static bound or explicit preemption; a guest-reachable assertion kills the VM, not the host; all memory consumed on a VM's behalf is charged to a quota fixed at creation. Per-VM VMMs give crash containment for free, and "kill and recreate from snapshot" is acceptable recovery for sandboxes. For lifetimes of minutes to hours, drain-and-reboot is a simpler patch strategy than live update, whose Linux building blocks (KHO in 6.16, LUO in 6.19) still lacked guest-memory preservation outside RFC in 2026 ([LPC 2025 slides](https://lpc.events/event/19/contributions/2052/attachments/1729/4180/LPC'25%20Live%20Update%20Orchestrator.pdf); [RFC](https://lkml.indiana.edu/2605.2/02485.html)). A hung type-1 has no OS beneath it, so a hardware watchdog and host fencing are required.

Transient execution demands a structural defense because the disclosures do not stop: L1TF, MDS, Retbleed, Downfall, Inception, BHI, and in 2025 Training Solo, whose Indirect Target Selection issue also breaks hypervisor isolation, and VMScape, in which a guest steers branch prediction in the host's userspace VMM ([VUSec Training Solo](https://vusec.net/projects/training-solo); [Linux VMSCAPE docs](https://docs.kernel.org/admin-guide/hw-vuln/vmscape.html)). The most valuable decision is to be secret-free by construction: no direct map of all RAM, per-vCPU state mapped only while that vCPU runs, guest memory never mapped in the core. Microsoft Research's Xen prototype reported performance comparable to baseline ([MSR](https://www.microsoft.com/en-us/research/uploads/prod/2022/07/sf-hypervisor.pdf), authors' figures, 2022), while Linux's equivalent direct-map removal for guest memory was still under review in April 2026 ([LKML v12](https://lkml.iu.edu/2604.2/07630.html)). A new core gets this cheaply; a retrofit does not. VMScape applies directly to the per-VM VMM, which is why each VMM must hold only its own guest's secrets. Add tenant-keyed core scheduling so SMT siblings never run different tenants, predictor and buffer flushes at trust-boundary crossings, minimum-microcode enforcement at boot, per-VM CPU feature masking, and base-memory sharing scoped to one tenant's template with no cross-tenant deduplication ([Flip Feng Shui](https://www.usenix.org/conference/usenixsecurity16/technical-sessions/presentation/razavi), 2016). The mitigation list in the notes is x86-centric; the Arm equivalents surface only as SMCCC workaround discovery and an errata table, with no Arm-specific research behind them.

Verification is now within a small team's reach for the core, and Arm is ahead. Atmosphere verified a Rust microkernel with Verus in under 2.5 person-years at a 3.32:1 proof-to-code ratio ([Atmosphere, SOSP 2025](https://mars-research.github.io/doc/2025-sosp-atmo.pdf)); AWS verified its Rust Nitro Isolation Engine in Isabelle/HOL and ships it on Graviton5 ([AWS Compute Blog](https://aws.amazon.com/blogs/compute/aws-nitro-isolation-engine-formally-verifying-the-hypervisor-in-the-aws-nitro-system/)); pKVM's executable specification, used as a runtime oracle, found critical bugs without a full proof ([Memarian et al.](https://www.cl.cam.ac.uk/~pes20/Stuff/exec-spec-paper.pdf)). seL4's verified configurations include AArch64 at EL2 but have no VT-x coverage on x86 and exclude IOMMU and boot everywhere ([seL4 verified configurations](https://docs.sel4.systems/projects/sel4/verified-configurations.html)). A realistic plan is to prove the highest-value invariants first (no frame mapped into two tenants, hypervisor memory never guest-mapped), model-check `unsafe` blocks and virtqueue parsers, and run an executable spec as a fuzzing oracle.

Agent-specific containment sits around the VM, not in it. The documented 2025–2026 "sandbox escapes" of coding agents mostly abused what crosses the boundary: a prompt-injected agent writes a workspace file that a trusted tool outside the sandbox later acts on ([BleepingComputer](https://www.bleepingcomputer.com/news/security/cursor-codex-gemini-cli-antigravity-hit-by-sandbox-escapes/)). Vendors have converged on proxies outside the sandbox that inject credentials so the secret never enters the VM ([Docker](https://docs.docker.com/ai/sandboxes/security/credentials/); [Vercel](https://vercel.com/blog/security-boundaries-in-agentic-architectures)), and Anthropic's lesson that an allowlist is a capability grant, not just a destination filter, applies to any of them ([Anthropic](https://anthropic.com/engineering/how-we-contain-claude)). The platform should provide default-deny egress enforced outside the guest, per-destination credential injection with narrow scopes, no long-lived secrets in images or snapshots, a quarantined export path for artifacts, and flow logs recorded outside the guest. Confidential computing (SEV-SNP, TDX, CCA) protects a guest from the host, the reverse of this threat, and conflicts with overcommit and cheap snapshots; defer it but keep explicit shared regions for virtqueues. Secure and measured boot, attestation and IOMMU hardening are necessary but rest almost entirely on inference in the notes.

## Bring up AArch64 on QEMU first and keep x86 one milestone behind

### Language and reuse

Rust `no_std` is the default for new hypervisors, with one caveat: `build-std` remains unstabilized in 2026, so a custom target means a pinned nightly ([Rust project goals 2026](https://goals.rust-lang.org/2026/build-std.html)). The Arm crate stack is the stronger one because Google maintains `smccc` (SMCCC 1.4 and PSCI 1.1), `arm-gic`, `aarch64-paging` and `aarch64-rt` for pKVM firmware work ([smccc](https://docs.rs/crate/smccc/0.2.1); [osdemo](https://lib.rs/crates/osdemo); snippets); expect to write the vGIC, SMMUv3 and ITS drivers and, on x86, the VMCS/VMCB layer. Build the EL2 core without FP/SIMD: a solo developer's 30K-line `no_std` EL2 hypervisor lost hours to a debug build that turned `read_volatile` into NEON instructions trapped by EL3 firmware ([users.rust-lang.org](https://users.rust-lang.org/t/30k-lines-of-no-std-rust-a-bare-metal-arm64-hypervisor-that-replaces-googles-hafnium-spmc/139497)).

No drop-in `no_std` device stack exists. rust-vmm assumes a hosted Unix environment ([vm-memory](https://github.com/rust-vmm/vm-memory)), so it is reference material in the core but works unchanged in a Linux service VM. The most leveraged reuse is therefore to shape the hypervisor's control ABI like KVM's or MSHV's and add a third backend to an existing Rust VMM. The lowest-effort first step runs per-sandbox VMMs as processes in the service VM behind a `/dev/<hv>` device, as ACRN's HSM and `/dev/mshv` do; moving them to EL0/ring-3 processes on the hypervisor is the better isolation end state and requires a small user-mode runtime. The tension should be explicit: VMMs in the service VM make that VM a shared TCB slice, which is the property the microhypervisor design exists to remove.

### One codebase, two architectures

Dual-architecture hypervisors are normal (Xen, KVM, Bao, seL4, NOVA, AxVisor), and so is a second architecture that lags for years: krata lists aarch64 at 10–30%, libvmm's x86 trails its Arm support, Hedron never gained AMD ([krata](https://www.github.com/edera-dev/krata), snippet; [Hedron README](https://github.com/cyberus-technology/hedron)). The seam the notes recommend has an architecture-neutral core (frame allocator, VM and vCPU lifecycle, scheduler, guest address-space manager with CoW and sharing, control ABI) over a small set of per-arch interfaces: a vCPU `run()` returning a portable exit enum (decoded MMIO access, hypercall, halt/WFI, shutdown), a second-stage page-table interface served by one generic 4-level walker parameterized by entry format, host and virtual interrupt controllers, IOMMU, platform discovery from a shared static-table ACPI parser plus FDT on Arm, and guest boot. Virtual interrupt controllers, CPU feature filtering, vector state, mitigations and SMP boot will not unify and should not be forced.

Earlier text in the notes treated ARM64 as a late port; the confirmed scope supersedes that. The recommended order is Arm first for the first guest on QEMU `virt` with EL2 enabled, x86 started no later than the Arm Linux boot, and neither architecture more than one milestone ahead. The reasoning is that an abstraction designed against EL2's explicit trap bits and syndrome-decoded MMIO stays small when stretched over VMX and SVM, while one designed around the VMCS leaks x86 notions into the portable core. The counter-argument should weigh on staffing: x86 has three back ends (VMX, SVM and their differing interrupt virtualization), cheaper and more plentiful bare metal, and hardware-accelerated nested development, while Arm development runs on slow TCG or physical boards. No published experience report compares the two orders.

| Stage | AArch64 (estimate) | x86-64 (estimate) |
|---|---|---|
| Boot, print, memory, discovery, SMP | A0–A3: EL2 entry, EL2 MMU, ACPI+FDT, GICv3, PSCI; about 6–9 weeks | M0–M2: UEFI, x2APIC, ACPI, AP startup; about 5–9 weeks |
| First guest instruction and memory | A4: `HCR_EL2`, stage-2, `ERET`; 1–2 weeks | M3–M4: VMXON/VMCS or VMCB, EPT/NPT; 4–7 weeks; most first attempts stall here |
| Linux to initramfs shell, 1 vCPU | A5: Image + DTB, PSCI, ID-register sanitization; 3–5 weeks | M5: PVH or bzImage, CPUID/MSR filtering, clock; 4–8 weeks |
| Interrupt virtualization | A6: vGICv3 list registers, distributor emulation; 4–6 weeks plus long tail | M6: APICv/AVIC, injection rules; 4–8 weeks plus long tail |
| SMP guests | A7: 2–3 weeks | M7: 3–6 weeks |
| virtio | Shared | 6–12 weeks |
| IOMMU and passthrough | A9: SMMUv3 + ITS; 8–14 weeks | M9: VT-d/AMD-Vi; 6–12 weeks |
| Hardening | RAS, errata, SVE/SME policy | Machine check, microcode, mitigations |

Every duration is the researchers' estimate for 2–3 experienced engineers, drawn from background engineering knowledge and unverified against sources. Their ordering carries the useful signal: Arm reaches a Linux shell in roughly 9–16 weeks against 13–24 on x86, the vGIC is comparable to x86 interrupt work, and SMMUv3 plus ITS is larger than VT-d. Skip GICv4 for version one. The rule that prevents drift is to have the second architecture's "boot, print, enter guest, exit" in CI before the first architecture's virtio or IOMMU work begins, and to gate every core change on both builds.

### Tooling and testing

Day-to-day development runs in emulation. On Arm, QEMU `virt` with `virtualization=on` exposes EL2, selectable GIC versions and an SMMUv3 under TCG on any x86 runner ([QEMU virt docs](https://www.qemu.org/docs/master/system/arm/virt), snippet). On x86, nested KVM is available on GitHub-hosted runners, though GitHub calls nested virtualization "not officially supported" ([GitHub changelog](https://github.blog/changelog/2024-04-02-github-actions-hardware-accelerated-android-virtualization-now-available/), snippet), and whether three levels work there is untested. Bochs is worth keeping for VMX because it prints why a VM entry failed; real hardware reports bad guest state only as exit reason 33 without saving the state ([Hypervisor-101-in-Rust](https://tandasat.github.io/Hypervisor-101-in-Rust/hypervisor-setup-and-operation-cycle/testing-with-bochs.html), snippet). Emulation hides errata and is more forgiving than silicon, so real hardware is needed from the IOMMU milestone: one recent Intel and one AMD EPYC generation, and one SystemReady Arm server, since boards are devicetree-only and lack server-class SMMUv3/ITS. How SystemReady servers behave for a non-Linux EL2 payload is untested in the notes, and provider availability was not verified.

The test stack should be built in from the first commit. Compile the core as a host library with a mocked CPU for unit and property tests; put fuzz harnesses on every exit handler, hypercall and virtqueue parser; run kvm-unit-tests, which also runs on non-KVM targets ([KVM Forum 2020](https://kvm-forum.qemu.org/2020/kvm-unit-tests_%20When%20KVM%20doesn%27t%20mean%20_KVM_.pdf), snippet), and XTF-style guests as conformance; and add snapshot-based full-system fuzzing at the VM-exit interface in the style of HyperPill, which found 26 bugs across QEMU, Hyper-V and macOS Virtualization Framework without hypervisor-specific hooks ([HyperPill](https://www.usenix.org/conference/usenixsecurity24/presentation/bulekov)). Reconfigure-after-activate bugs need sequence-aware fuzzing. An independent study found no microVM engine among the products it examined with a continuous public fuzzer, and observed deployments pinned to vulnerable VMM versions for more than a year ([arXiv 2606.08433](https://arxiv.org/html/2606.08433v1)); both are cheap ways to stand out. A fast loop is achievable: the solo Rust EL2 project runs 34 suites in about 5 seconds under QEMU ([users.rust-lang.org](https://users.rust-lang.org/t/30k-lines-of-no-std-rust-a-bare-metal-arm64-hypervisor-that-replaces-googles-hafnium-spmc/139497)).

### Effort calibration

The sourced part of the calibration is code size: privileged cores are small (NOVA 11–14 KSLOC per architecture, Bao 8.4 K, ACRN about 40 K by design, a solo Rust EL2 hypervisor at 30 K), and total systems are not (seL4's VMM alone is 40 K; Firecracker was about 50 KLOC at publication). The rest is the researchers' judgment with no source: 3–5 strong systems engineers; 3–6 months to a single-vCPU Linux guest; 9–15 months to SMP guests, virtio through a service VM, IOMMU and a usable API; 2–3 years to a system fit for untrusted multi-tenant fleets; and dual-architecture support adding roughly 40–60% to core effort, concentrated in vCPU, interrupt-controller, IOMMU and platform code, with at least one owner per architecture. No team sizes or elapsed times for NOVA, ACRN, Bao, Firecracker or Edera were found, so these figures cannot be checked against precedent. The stall points the notes predict are the I/O story, the hardware and firmware long tail, interrupt bugs that appear only under load, the continuous stream of CPU-vulnerability mitigations, feature-parity pressure, unbudgeted operational tooling, and loss of the one or two people who understand the world-switch code.

## What the evidence does not yet support

Several load-bearing numbers do not exist in the research. No VM-exit round-trip measurement was found for Sapphire Rapids, Zen 4/5, Neoverse N1/N2/V1/V2 or AmpereOne; the newest verified data is 2016–2017 on X-Gene and Cortex-A57, and none of it includes post-2018 mitigations. No independent benchmark compares snapshot restore or fork fan-out across VMMs, and no head-to-head compares a microhypervisor with Firecracker/KVM on the same hardware. No arm64-specific microVM boot or restore latency was published. No data covers microhypervisor stability or create rates under heavy churn, per-VM network setup cost, or nested-virtualization overhead on AWS's 2026 offering.

Arm-specific security coverage is thin. The vulnerability history, mitigation list and fuzzing literature in the notes are overwhelmingly x86; nothing was gathered on Arm speculative-execution mitigations beyond their SMCCC discovery interface, on SMMUv3 or ITS attack research, or on Arm CCA. The Arm material on VHE register redirection, timers, break-before-make, HAFDBS and SMMUv3 internals comes from background knowledge because the Arm guide could not be fetched. Which GIC version, NV2, HAFDBS, ECV and BBM levels the major Arm server parts expose to bare-metal software is unconfirmed, as is the state of nested virtualization in late-2026 mainline KVM/arm64 and on Axion or Cobalt.

Three design areas rest mostly on reasoning: device-backend placement and cross-VM virtio transport in a type-1; secure boot, attestation and IOMMU hardening; and scheduler design for thousands of mostly idle vCPUs. The CVE record needs care: the Firecracker PCI and jailer advisories were read from AWS bulletins, but other 2026 identifiers come from press or a single preprint and some appear malformed. Whether Edera offers snapshot or fork was not established, and licences for most candidate bases were not verified.

## Conclusion

The research changes the question from "how do I build a small hypervisor" to "which two things justify building one". Reaching a booting Linux guest is the easy part on both architectures, and on AArch64 it is a matter of weeks. The hard and valuable parts are the ones KVM users already struggle with, namely fork-consistent memory, disk and identity, and the ones no small type-1 has finished, namely Arm server I/O through SMMUv3 and ITS and a driver VM that serves backends without being able to read every guest. A project that treats fork-on-stage-2 and a secret-free core as the product, and everything else as borrowed (Linux for drivers, an existing Rust VMM for devices, a KVM-shaped ABI to connect them), has a defensible reason to exist. A project that sets out to write a faster Firecracker does not, because performance parity is the best it can achieve.

ARM64 as a first-class target sharpens this rather than complicating it. It supplies the cleaner model to design the portable core against, the stronger Rust crate base and the verification precedents, and it removes the nested-cloud shortcut, which forces an early decision about bare-metal supply. Two cheap experiments should precede any commitment: measure exit and fork-fault costs with kvm-unit-tests on one Graviton `.metal` or Ampere host and one current x86 server, and prototype stage-2 CoW fork inside an existing small hypervisor to see whether the restore and density gains over userfaultfd-based KVM designs are large enough to pay for a two-to-three-year build.
