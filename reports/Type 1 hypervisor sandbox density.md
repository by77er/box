# Dense agent sandboxes reclaim backing, not capacity

The design the evidence supports keeps every sandbox's guest-visible RAM, vCPU count and disk size fixed and generous, and makes the hypervisor stop *backing* whatever is not in use: unbacked until touched, shared with a template until written, handed back when the guest frees it, compressed when cold, and written out when idle. Memory is the binding resource once CPU is oversubscribed, on the evidence of three operators, so most of the design effort belongs there. On the three ingredients named in the brief: the classic memory balloon is the wrong primary tool (about 1 GiB/s, unverifiable, and it turns late deflation into guest OOM kills) and should survive only as a size-zero device that carries free page reporting and statistics, plus an emergency cache squeeze. Copy-on-write is the foundation for both memory and disk, at 4 KiB granularity, but it protects only what the template already held; the guest page cache that grows after fork is the largest leak, and it needs its own mechanisms (in-guest proactive reclaim, a shared read-only base mapped by DAX). Optimized disk writes mean a 4 KiB-granular CoW block layer under guest ext4, with a flush that is honest and cheap because it lands on power-loss-protected NVMe, and with deduplication and compression moved off the write path to checkpoint upload. CPU density is the easier half: published fleets run 5x to 10x vCPU overcommit for mostly idle guests, provided idle guests generate almost no wakeups and waking vCPUs are scheduled within about 2 ms. Compared with the earlier architecture report, three things change: cold-memory compression and hibernation move from "can wait" to core; the disk CoW map moves out of the hypervisor core into the storage VM; and virtio-mem is demoted to a growth and hard-cap mechanism. Nearly every capacity number that follows from this design is an estimate, and no published system combines these mechanisms with measured sandboxes-per-host, so the report ends with what a prototype must measure before any ratio is promised.

A note on evidence. The research notes label each claim as fetched from a primary source, taken from a snippet or secondary summary, recalled without re-checking, or the researcher's own inference. This report keeps those distinctions where they change the weight a claim can bear: "snippet", "secondary", "recalled", "vendor claim", "preprint" and "estimate" mean exactly that, and design recommendations are inferences unless a source is attached. The report builds on the earlier architecture work (a Rust microhypervisor core that owns stage-2/EPT tables, one deprivileged VMM per sandbox, a Linux driver/storage VM, virtio-only firmware-free guests, and CoW fork and snapshot restore as kernel primitives) and does not re-derive it.

## Memory binds first, so density is a memory problem with a CPU side-condition

Three independent operator sources agree on which resource runs out. AWS's Firecracker paper states that an idle slot consumes only memory, that memory is roughly 40% of server capital cost (a 2020 figure), and that "our goal is to sell all the memory we buy" ([Firecracker NSDI'20](https://css.csail.mit.edu/6.566/2023/readings/firecracker.pdf)). Azure's Coach study of more than a million VMs found CPU the packing bottleneck 69% of the time without oversubscription, and memory the bottleneck (49%) once CPU is oversubscribed; it also found memory contention can degrade performance up to **4.3x**, far worse than CPU contention's worst case ([Coach](https://arxiv.org/html/2501.11179v2)). The one agent-sandbox fleet with published telemetry, DeepSeek's DSec (an arXiv preprint from September 2026), reports that about **90% of sandboxes use at most 5% of their requested CPU** while memory, page cache and writable state stay pinned across turns; its nodes peaked at 524 microVMs and ran stably at 800 on 1.5 TB machines, and the paper names memory, not CPU, as the limiter ([DSec](https://arxiv.org/html/2609.22978v1)). The practical reading is that CPU overcommit degrades gracefully and memory overcommit does not, which is why the usability guardrails later in this report are stricter for memory.

Where the memory goes in a development sandbox is also reasonably well evidenced. A resumed CodeSandbox VM typically touched only 300 to 400 MB while the guest reported 3 to 4 GB in use ([CodeSandbox](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3), 2022). Cortex found 49 MiB physically allocated against a 4 GiB base memory file on a first canary, and also that "a 4 GiB guest could pull several GiB of pages into host RAM once real workloads ran" ([Cortex](https://builders.cortex.io/blog/sandboxing-agents-part-2/)). After a clang build in a 16 GiB VM, the page cache "occupies a substantial part of the guest's total memory" and blocks reclaim ([HyperAlloc, EuroSys'25](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)). Across Meta's services, an average of 35% of container memory was untouched for five minutes ([TMO, ASPLOS'22](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)). So the memory to recover falls into four pools with different mechanisms: never-touched memory (lazy allocation), memory identical to a template (CoW), guest-free and guest-cache memory (reporting and cache control), and cold private memory (compression, swap, hibernation).

That decomposition is the reason the usual definition of overcommit, the sum of configured guest RAM over host RAM, is close to meaningless here. A 4 GiB guest that costs 100 MiB of private frames makes the ratio look enormous without saying anything about risk. The quantity to admit and schedule against is **committed private memory**: per-VM private resident frames plus compressed bytes plus page tables plus VMM overhead, with shared pools (templates, base images) charged once. This is the notes' definition, an inference, and the rest of the report uses it.

## Verdict on ballooning: keep the device, retire the balloon

### The classic balloon is slow, unverifiable and aimed at the wrong quantity

The measured case against the balloon as the main elasticity path is consistent across sources. On QEMU/KVM with Linux 6.1, virtio-balloon shrinks touched memory at **0.95 GiB/s** and grows it back at 2.3 GiB/s, because each 4 KiB page is allocated and discarded individually; it was the only mechanism in that study that significantly hurt a single-threaded guest while resizing ([HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)). An independent measurement attributes 81% of balloon reclaim latency to VM exits ([Squeezy, EuroSys'26 preprint](https://arxiv.org/html/2411.12893v2)). The Linux driver inflates in arrays of at most 256 pages and sleeps 200 ms after a failed allocation ([virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c)); Firecracker's documentation adds that the VMM cannot control inflation speed, that `deflate_on_oom` does not cover kernel-internal allocations or large requests and is "a crash safeguard, not a routine mechanism", that 4 KiB discards fragment mappings (its Linux host panics at the VMA limit after roughly 128 MiB of scattered discards), and that because a compromised driver can misreport everything, hosts "must be ready for the Firecracker process to use all memory it was given at boot" ([Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)). With huge-page-backed guests, inflation frees nothing at all.

The deeper objection is about what a balloon controls. A balloon shrinks the guest's usable capacity, so a controller has to choose a safe target, and every shipping controller found picks it conservatively: ChromeOS equalises headroom with a learned 400 MiB critical margin and a second policy that caps guest cache in tiers as the host tightens ([ChromeOS concierge, R117](https://cos.googlesource.com/third_party/platform2/+/refs/heads/release-R117/vm_tools/concierge/balloon_policy.cc), 2023 source); Hyper-V keeps a 20% buffer above committed memory ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/dynamic-memory), snippet). The Tide preprint argues that for agents such a target "does not exist", because tool memory spikes are known only at run time ([Tide](https://arxiv.org/abs/2609.40082)). A sandbox whose balloon has not deflated when `cargo build` starts gets an OOM kill, which is exactly the surprise the brief rules out.

The verdict is to ship the virtio-balloon device with the balloon at size zero. The device is still useful: it is the stock carrier for free page reporting, and its statistics queue gives an agent-less pressure signal (guest Linux 6.12 added `OOM_KILL`, `ALLOC_STALL`, and direct and asynchronous scan and reclaim counters; there is no PSI field) ([Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)). Inflation remains available as one rung of the host pressure ladder, used ChromeOS-style to cap the page cache of the idlest guests, bounded by a margin and reversed immediately on any pressure signal. If a balloon is ever used routinely it should work in 2 MiB units, which the HyperAlloc authors measured at about 140x faster; stock Linux has no such balloon, so this means a guest patch.

### Free page reporting is the cheap default, and it plateaus

Free page reporting is the mechanism that should do the routine work. The guest keeps pages on its own free list and tells the host about free blocks; the host drops the backing; a later allocation simply faults. Give-back therefore needs no protocol step. In the HyperAlloc evaluation, default reporting (2 MiB order, 2 s delay) cut a clang build's memory footprint by **34%** against a static 16 GiB VM at 0.15% CPU overhead, and the kernel suspends reporting by itself when a zone's free memory nears its low watermark ([HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf); [mm/page_reporting.c](https://github.com/torvalds/linux/blob/master/mm/page_reporting.c)). Upstream direction favours it too: in a February 2026 thread David Hildenbrand recommended extending reporting with pause and continue controls over extending free page hinting, which Firecracker still ships as a developer preview because the specification lets a guest reuse a hinted range before the host has processed it ([LKML, Feb 2026](https://lkml.iu.edu/hypermail/linux/kernel/2602.1/04796.html)).

Reporting has two limits that matter for this workload. It sees only free blocks of pageblock order, and it is blind to the page cache. After the build finished, artifacts were deleted and the whole cache was dropped, reporting shrank the VM only to **8 GiB**, where an allocator-level design reached 1.9 GiB; the gap is buddy-allocator fragmentation below 2 MiB. Lowering the reporting order to 4 KiB recovered more (42%) but raised runtime by 19% through the stock virtqueue path ([HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)). On coding-agent trajectories specifically, the Tide preprint used Firecracker plus reporting as its baseline and reported 34 to 45% lower backing memory with harness-declared memory phases. That is one small study with one trajectory per task, not peer reviewed, and the notes flag that its tables were read through a summarising tool, so it supports "reporting alone leaves a lot behind" and no more ([Tide](https://arxiv.org/abs/2609.40082)).

In this hypervisor a reported block becomes an unmapped stage-2 range, and the earlier report's rule holds with one sharpening from the density notes: the entry must go to an explicit **absent-zero** state in the VM's own layer, never back to "inherited from parent", or a forked guest would read stale template contents in a freshly allocated page. Reporting at 2 MiB keeps stage-2 block mappings intact; sub-2 MiB reporting forces block splits and belongs only in a deep idle pass. The notes' design inferences for cutting the low-order cost are a batched range hypercall in place of the 32-entry virtqueue report, host-controlled pause and order selection, and a compaction pass before each idle reporting pass so that 2 MiB blocks exist. None of these has a measurement behind it yet.

Guest configuration matters as much as the device. `init_on_free=1` makes the guest zero a page, the host discard it and the host zero it again on re-fault, and the first of those writes breaks CoW sharing on a page that was about to be given away; non-zero page poisoning is incompatible with reporting. The guest should run with `init_on_free=0`, no poisoning, and ideally `init_on_alloc=0`, relying on the hypervisor's zero-on-fault guarantee. A 2026 kernel series adds a "host already zeroed this" flag so the guest can skip its own zeroing; its merge status is unconfirmed ([LWN](https://lwn.net/Articles/1073887/), snippet). No source measured the cost of these settings in microVM guests, so the saving is argued from mechanism.

### Page-cache control is the missing half of elasticity

None of the elasticity devices evicts page cache; something has to make the guest do it. The best-documented controller is Meta's Senpai, which reclaims through the stateless `memory.reclaim` interface in proportion to how far pressure-stall (PSI) time sits below a 0.1% threshold, runs every 6 seconds, caps each step at 1% of the workload, costs 0.05% of CPU, and saved 20 to 32% of memory fleet-wide. The kernel was changed alongside it to reclaim only file cache for as long as no refaults occur ([TMO](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)). The in-kernel alternative is DAMON_RECLAIM, with a default minimum age of 120 s, quotas of 10 ms and 128 MiB per second, an optional PSI-driven quota autotuner and a `skip_anon` switch ([kernel docs](https://docs.kernel.org/admin-guide/mm/damon/reclaim.html)). DSec reports that DAMON plus balloon free page reporting cut time-integrated host memory by 21.2% ([DSec](https://arxiv.org/html/2609.22978v1)).

The recommended recipe, which is the notes' inference and has not been measured inside VMs in combination with reporting, is an in-guest loop run by the platform's agent: PSI-gated proactive reclaim of cold file cache, then compaction, then a reporting pass. It should be aggressive when the sandbox is idle (vCPUs halted, PSI zero) and Senpai-gentle or off while a tool runs. `drop_caches` is a blunt idle-time or pre-snapshot action only, since it discards the hot build cache the next command needs. Guest zram for cold anonymous memory is a plausible addition, but no source compares it with host-side compression, and the hypervisor-side tier described below works without guest cooperation.

### virtio-mem grows guests and caps hostile ones; it does not shrink busy ones

virtio-mem unplugs at about 34 GiB/s when memory is already free and movable, but Squeezy measured 617 ms to reclaim 512 MiB and almost 2.5 s for 2 GiB from a loaded guest, with timeouts and partial reclaim under pressure and more than 2x slowdown of co-located work. An attempt to drive it as an automatic reclaimer produced the worst footprint of the automatic techniques, and a more aggressive variant "was unable to resize the VM fast enough to prevent OOMs" ([Squeezy](https://arxiv.org/html/2411.12893v2); [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)). Plug is cheap, 35 to 45 ms per operation. Hotplugging 16 GiB costs about 262 MiB of boot memory for the memory map, and the movable-to-kernel zone ratio should stay near 3:1 to 4:1 ([Firecracker memory-hotplug.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/memory-hotplug.md); [virtio-mem guide](https://virtio-mem.gitlab.io/user-guide/user-guide-linux.html)). The verdict: use virtio-mem, if at all, to raise a sandbox's ceiling on demand and to enforce a verifiable hard cap. The simpler option for a hypervisor that owns stage-2 is to boot the guest at its full entitlement with a hypervisor-enforced resident limit, accepting about 1.56% of configured RAM in `struct page` metadata.

### The policy that removes surprise OOMs

The rule the notes derive from Senpai's asymmetry ("adaptation to workload expansion is immediate", contraction takes minutes) is the central usability decision of this report: **never shrink guest-visible capacity as the primary mechanism.** Keep `MemTotal` at the entitlement and reclaim backing. A burst then needs no host round trip to begin; allocations succeed from the guest free list and fault frames in at roughly 4 GiB/s in the QEMU measurements, a figure that is host fault-in speed and has not been measured on a purpose-built type-1. The risk moves from the guest (OOM kill) to the host frame pool (exhaustion), where the hypervisor can answer with back-pressure and freezing instead of killing. The supporting design inference is a pre-zeroed frame pool sized for the simultaneous burst across sandboxes and refilled from idle guests.

### Purpose-built interfaces come later, in tiers

Three research prototypes bound what a co-designed guest interface could add. HyperAlloc shares allocator state with the hypervisor and shrinks 362x faster than the balloon with 17% lower footprint than reporting, but requires replacing the guest page allocator and does not address the page cache ([HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)). Squeezy makes hot-unplug lifetime-aware and reclaims 2 GiB in 127 ms ([Squeezy](https://arxiv.org/html/2411.12893v2)). Tide lets the agent harness declare memory phases ([Tide](https://arxiv.org/abs/2609.40082)). All three attack lifetime mixing inside 2 MiB blocks, none has production deployment evidence, and Tide is a single preprint. The notes order the work by guest intrusiveness: stock kernel plus configuration plus agent first; then a small custom device for reporting control, a pushed pressure channel and batched discards; then guest memory-management patches; and harness-declared intent only if the platform controls the harness.

## Verdict on copy-on-write: the foundation, with a known leak

### Sparse, lazy, zero-aware memory comes before sharing

The largest and cheapest saving is never allocating what was never written. Zero pages were 38% of memory in Difference Engine's mixed snapshot ([Difference Engine, OSDI'08](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/gupta/gupta_html/)), and the CodeSandbox and Cortex figures above show how little of a restored guest is touched. In a stage-2-owning hypervisor this is a sparse per-VM map in which "zero/absent" costs no frame and no table page, a first write takes a pre-zeroed frame, and zero pages are detected wherever contents are read anyway (compression, hibernate write-out, template sealing). The latency face of lazy allocation is one stage-2 fault per first touch; the notes estimate about a second of fault overhead spread across a build that touches 2 GiB, using an unsourced 1 to 2 µs rule of thumb, and propose fault-around for active VMs as the knob. That cost needs measuring.

### Fork from sealed templates, populate stage-2 lazily

The earlier report made fork-on-stage-2 the differentiating primitive; the density notes add numbers and a simplification. Xen's VM fork creates a child with an empty second-stage table and a parent pointer in about **745 µs**, with reset in about 111 µs, on a 2017 laptop CPU (slides and a cover letter, read as snippets) ([Lengyel, Xen VM fork](https://www.slideshare.net/tklengyel/vm-forking-and-hypervisorbased-fuzzing-with-xen)). The data structures needed are small: a refcounted frame table; immutable layers that map guest frame numbers to a frame, a zero mark, "absent here" or an on-disk extent; one writable top layer per VM; and a parent chain walked only on faults and flattened in the background. Sharing second-stage page-table subtrees between forks, which the earlier report listed as an option, is possible but has no production precedent; the notes recommend lazy population first, since a clone that touches 300 MB needs about 0.6 MiB of leaf tables, and shared read-only subtrees later for immutable regions only. This is a sharpening, not a reversal.

How much sharing persists is the weakest part of the evidence. CodeSandbox reported clones sharing more than 90% of the source's data, and Cortex a ΣPSS/ΣRSS of 35% across three guests against a 33% ideal; both are point values near fork time. **No source publishes a divergence-over-time curve for long-lived development sandboxes.** Older identical-VM studies are the nearest proxy: Difference Engine saved about 40% for kernel-compile VMs, its lowest homogeneous result and the closest to a coding workload.

### What CoW does not protect

The notes' mechanism analysis, an inference but a well-grounded one, is that long-run divergence is dominated by the guest page cache, not anonymous memory. Every file a guest reads from a virtio-blk disk is copied into a guest page that was free in the template, so a `git clone`, a package install and a build write gigabytes of guest-physical memory that is private from the hypervisor's point of view even when half of it is byte-identical across sandboxes. CoW protects the template's resident set and nothing else. Other sharing breakers are guest THP collapse and compaction (which rewrite frames), `init_on_free`, and free-list churn. The countermeasures are configuration: guest transparent huge pages at `madvise`, proactive compaction off except before sealing a template, no in-guest KSM, no guest swap; and a template-sealing procedure that drops unwanted cache, compacts once and zeroes free memory so that everything not deliberately warm is absent.

### A shared read-only base through DAX removes the biggest duplicate, at a price

Mapping an immutable image into every guest as a DAX device makes its file data exist once on the host and never in guest RAM. Firecracker's virtio-pmem documentation measured two 128 MB VMs sharing a 100 MB image at a worst case of about 356 MB instead of 456 MB, and a 24 MB double-caching penalty without DAX ([Firecracker pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)). DSec reports virtio-pmem/DAX cut peak host memory by **40.2%**, while peak CPU rose from 26.5% to 41.4% ([DSec](https://arxiv.org/html/2609.22978v1)). A vendor blog claims moving a Next.js base image out of the memory snapshot onto a read-only EROFS base cut memory from 4 GB to 1 GB; that is a vendor claim, and the fetched page is ambiguous about which product it describes ([Blaxel](https://blaxel.ai/blog/sandbox-snapshot-hibernate-resume-ai-agents)).

The costs are specific. The guest allocates `struct page` metadata of about 1.56% of the device size up front; a September 2026 patch series aimed explicitly at AI-sandbox microVMs reduces this and is not confirmed merged ([LWN](https://lwn.net/Articles/1092485/)). DAX requires uncompressed image data, and EROFS chunk deduplication cannot be applied under FSDAX; dm-verity cannot protect DAX mappings ([EROFS at LPC 2025](https://lpc.events/event/19/contributions/2238/attachments/1902/4089/LPC2025_erofs.pdf)). Every sandbox mapping the same frame can run cache-timing probes on it, which Firecracker's documentation calls out as a side channel. And read-only enforcement has failed in practice: under KVM a guest write to a read-only pmem mapping is discarded on x86-64 and stops the VM on aarch64, and a secondary write-up of CVE-2026-24834 describes a Kata guest whose DAX-mapped root device became writable because the guest probe path cleared the read-only flag ([cvereports](https://cvereports.com/reports/CVE-2026-24834), secondary; the advisory itself was not read).

The two research strands disagree on how far to take this, and the disagreement is worth stating. The memory notes rank a DAX-mapped EROFS base with an overlay upper layer third in value, ahead of reporting. The storage notes recommend a single CoW virtio-blk root as the default, because guest overlayfs copies whole files on first write, complicates nested Docker, and because forking from a warm memory snapshot already shares the page cache that existed at fork time. The reconciliation this report adopts is the storage notes' layout with the memory notes' mechanism: one CoW virtio-blk ext4 root per sandbox, plus additional read-only DAX devices for large, read-mostly, public content (toolchains, language runtimes, package caches), with read-only enforced as a stage-2 permission so the guest driver's opinion is irrelevant, public images shared across tenants and tenant-private images shared only within a tenant. Whether more of the base should move into DAX depends on a number nobody has published: how much page cache a forked single-root sandbox duplicates after fork.

### Deduplication: by construction, zero pages, and template-relative only

Scanning deduplication recovers real memory. VMware's production samples reclaimed 7 to 33%, and Difference Engine found 13% non-zero sharable pages on top of 38% zero pages ([Waldspurger, OSDI'02](https://research.cs.wisc.edu/areas/os/Qual/papers/vmware-memory.pdf); [Difference Engine](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/gupta/gupta_html/)). It also has a security record that ended cross-tenant use: write timing on a merged page reveals whether another VM holds identical content; Flip Feng Shui combined merging with Rowhammer to corrupt a victim's page without writing to it, and its authors recommended disabling memory deduplication; VMware turned inter-VM sharing off by default through per-VM salting in 2014 ([VUSec](https://vusec.net/projects/flip-feng-shui); [Broadcom KB](https://knowledge.broadcom.com/external/article/318959/security-considerations-and-disallowing.html); both read as snippets). The scan is not free either: Linux KSM's advisor defaults target a 200-second full pass capped at 70% of a core ([KSM docs](https://docs.kernel.org/admin-guide/mm/ksm.html)).

The safe policy the notes derive, as inference, has four levels. Zero-page elimination is always on. Template-relative re-sharing (a private page found equal to the page at the same guest frame number in its own ancestor layer is dropped and re-pointed) costs one comparison against a known candidate, needs no cross-VM index, and falls out of diffing at hibernate time. Content-hash matching against a trusted public base-image corpus is optional, and the hypervisor-owned frame always becomes the backing copy so that no tenant-supplied frame ever backs another tenant's mapping. Arbitrary cross-tenant merging stays off. The claim that zero-page-only dedup is immune because the backing frame is hypervisor-chosen is the researcher's reasoning; the Flip Feng Shui paper's mitigation text could not be fetched to confirm it.

### Huge pages: by region, not globally

Two-megabyte second-stage mappings bought 3 to 22% in VMware's Nehalem-era EPT evaluation, and misaligned guest and host sizes give no TLB benefit (both snippets; [VMware EPT evaluation](https://www.cs.miami.edu/~burt/learning/Csc521.121/docs/Perf_ESX_Intel-EPT-eval.pdf); [Gemini](https://cs.hofstra.edu/~jshan/papers/xgemini.pdf)). No 2023 to 2026 measurement on current server cores was found, so the gain for build workloads is unknown. The density cost is concrete: a 2 MiB private mapping copies 512 times more on first write after fork, carries one accessed bit and one dirty bit for the whole block, hides zero sub-pages, and must return from compression or swap whole. Firecracker's own guidance is that dirty tracking "negates most huge page benefits" ([Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)). The policy is therefore regional: 2 MiB (or larger) read-only blocks for DAX windows and for intact, contiguous template extents, split to 4 KiB on first write with no data copy; 4 KiB for private guest RAM by default; and opportunistic promotion only for hot, fully private, fully populated ranges of active VMs, demoted when the VM goes idle. This confirms the earlier report's "2 MiB for shared template memory, 4 KiB for private" and adds promotion and demotion. On Arm, splitting a block needs break-before-make unless FEAT_BBM level 2 is present (recalled, not verified), which raises the cost of "start huge, split on write" there. Guests should use 4K pages on both architectures: with 64K pages the pageblock is 512 MiB and the reporting driver special-cases itself down to 2 MiB ([virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c)), CoW and dirty granularity coarsen by 16x, and a 4K-block image cannot be DAX-mapped.

### Cold memory: compress, then write out, then hibernate to zero

This is where the density research most changes the earlier report, which said hypervisor swap "can wait". Fleet evidence says a fifth to a third of memory is cold even in busy services: Google found 32% cold at a 120 s threshold and offloads to a compressed tier at about 6 µs per access, governed by a promotion-rate limit of 0.2% of the working set per minute (read through a detailed secondary summary) ([far memory, ASPLOS'19](https://blog.acolyer.org/2019/05/22/sw-far-memory/)); Meta's figures are above. Sandboxes are idler than services. And whole-VM hibernation is what sandbox providers already ship, with a visible weak spot: E2B documents about **4 s of pause per GiB of RAM**, about 1 s to resume, and nodes refusing a pause with HTTP 503 while a previous snapshot is still being written ([E2B persistence](https://docs.e2b.dev/sandbox/persistence)). Fly resumes suspended Machines in "a few hundred ms", restricts the feature to 2 GB guests, and notes that suspension "does not free capacity in a region" ([Fly suspend/resume](https://docs.fly.io/reference/suspend-resume)). Vendor claims of sub-25 ms standby resume exist and are unverified ([Blaxel](https://blaxel.ai/blog/sandbox-snapshot-hibernate-resume-ai-agents)).

The design the notes propose, as inference, is one page-state machine per guest frame: absent-zero, inherited from a layer, mapped private, compressed, on NVMe. Lazy restore, swap, compression and hibernation are then transitions in one map with one fault path, which is the earlier report's "swap is the same machinery as diff snapshots" taken to its conclusion. Idleness comes from hardware accessed bits in stage-2 leaf entries, scanned per VM over populated private entries only; on Arm cores without hardware access-flag management the fallback is VMware-style statistical sampling (100 random pages per 30 s) ([Waldspurger](https://research.cs.wisc.edu/areas/os/Qual/papers/vmware-memory.pdf)). Guests get no swap device, which removes the classic double-paging problem. The piece that could beat the incumbents is continuous background cleaning: cold private pages are compressed or written while the VM runs, so hibernating at idle flushes only the recently dirtied remainder and pause cost tracks the dirty rate, not RAM size. On wake, pages are stored in the order of the last recorded working set and prefetched as one sequential read while the vCPU runs; the notes compute that faulting a 300 to 400 MB working set serially at 4 KiB from NVMe would take on the order of 8 to 15 s against a fraction of a second sequentially, an arithmetic estimate. Hibernated extents hold tenant secrets and need per-VM encryption.

The honest status: no public description was found of a production microVM platform doing per-page hypervisor swap or compression of running guests; Google's and Meta's numbers are for containers; the compression ratio to budget (2.5x on private non-zero pages) comes from Sabre's diff-snapshot figure via a vendor blog and Google's recalled 3x; and the notes' wake targets (under 50 ms from the local compressed tier, under 300 ms from local NVMe, about 1 s remote) are targets, not results.

## Verdict on disk writes: 4 KiB CoW under guest ext4, with an honest cheap flush

### Keep the filesystem in the guest

The strongest measured lever is architectural. Modal, moving the same image from virtio-fs to virtio-blk with guest ext4, measured `bun install` at 12.5 s against 1.07 s, SQLite speedtest1 at 543 s against 43 s, pgbench read-write at 8.3k against 18.8k TPS, and 100,000 `chown` calls at 9.87 s against 0.21 s ([Modal](https://modal.com/blog/vm-sandbox-filesystem)). This confirms the earlier report's rule to keep filesystem sharing out of the default profile, and adds the performance reason to the security one. The guest filesystem should be ext4, which is what every surveyed platform runs in the guest; a copy-on-write guest filesystem would turn every overwrite into a fresh host allocation.

### CoW granularity sets write amplification

No same-hardware benchmark compares first-write cost across qcow2, dm-thin, reflink files, zvols, SPDK lvols and ublk backends; this is a stated gap. What the sources agree on is the shape: the first write to a shared unit costs a parent read, a write of the whole unit and a metadata update. The unit sizes are documented: dm-thin's floor is 64 KiB ([kernel docs](https://docs.kernel.org/admin-guide/device-mapper/thin-provisioning.html)), SPDK lvol clusters default to 4 MiB ([SPDK](https://spdk.io/doc/logical_volumes.html)), Ubicloud's ubiblk copies 1 MiB stripes ([ubiblk](https://github.com/ubicloud/ubiblk)), and Cortex's 16 MiB chunks mean "a session that dirties 20 chunks adds at most 320 MiB". qcow2 with 4K subclusters gave its author 10 to 15 times more IOPS on first writes over a populated backing file ([Igalia](https://blogs.igalia.com/berto/2020/12/03/subcluster-allocation-for-qcow2-images/), 2020). The 2025 to 2026 platforms that describe their design in detail converged elsewhere: an immutable chunked base plus a per-VM sparse overlay with a 4 KiB presence bitmap (DigitalOcean, Modal) ([DigitalOcean](https://www.digitalocean.com/blog/microvm-architecture)). At 4 KiB matching the guest block size, a full-block write never reads the parent, and a 100 GiB disk needs about a 3.2 MiB bitmap per layer (arithmetic).

The design follows. The guest sees one thin-provisioned virtio-blk root with 4096-byte logical and physical block sizes advertised, so no sub-block read-modify-write exists. Each overlay generation is an identity-mapped sparse file with a three-state map per 4 KiB block: absent (read the parent), present, and zero. The third state is DigitalOcean's rule that zeroing must set the presence bit or old parent data reappears, and it is what lets guest `fstrim` shrink both local usage and the next uploaded diff. Sealed generations stack and are compacted in the background; the published form is always a flat manifest so restore cost is independent of history.

### fsync: honest and cheap instead of ignored

Current providers make fsync fast by not honouring it. Firecracker's default `Unsafe` cache mode does not advertise the flush feature at all, E2B's published configuration uses it on both drives, and DigitalOcean states that "a local write can be acknowledged before the host disk is durable" ([Firecracker block-caching.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/api_requests/block-caching.md); [E2B](https://e2b.dev/blog/scaling-firecracker-using-overlayfs-to-save-disk-space); [DigitalOcean](https://www.digitalocean.com/blog/microvm-architecture)). The hardware makes a better answer available. A January 2026 measurement found fsync at **1.6 µs** on a Samsung PM9A3 and 12.4 µs on an Intel D7-P5520, both enterprise drives with power-loss protection, against 2,974 µs on a consumer Samsung 990 Pro ([Small Datum](https://smalldatum.blogspot.com/2026/01/ssds-power-loss-protection-and-fsync.html)). LSVD showed the software pattern: a local journal makes commits durable, upload is asynchronous and batched, and the result was up to 4x faster than bcache on sync-heavy workloads with all committed writes recovered after a crash ([LSVD, EuroSys'22](https://rs3lab.github.io/assets/papers/2022/hajkazemi-aschenbrenner:lsvd.pdf)).

The recommendation is to advertise FLUSH and complete it after a group-committed sync of a small write-ahead log on power-loss-protected NVMe in the storage VM, with data written straight to the overlay using direct I/O. Local fsync then survives guest crash, VMM restart and host power loss; durability against host loss is the checkpoint to object storage. A per-sandbox policy can drop FLUSH for explicitly disposable sandboxes. This path is the researcher's design and **has no public precedent among the surveyed sandbox providers**, and no group-commit design for virtio-blk flush across VMs was found, so the fsync latency a database in the guest actually sees is a prototype measurement. Guest mount defaults of `noatime,lazytime` and a longer ext4 commit interval reduce host writes without weakening fsync; their effect is unmeasured.

### Reclamation, dedup and compression belong off the hot path

Space comes back through DISCARD and WRITE_ZEROES on the virtual disk and an agent-driven `fstrim` on idle and before each checkpoint, in preference to the `discard` mount option; no measurement compares the two through a thin layer. Deduplication belongs at the immutable chunk layer. AWS Lambda flattens images deterministically to ext4, splits them into fixed 512 KiB chunks, and reports that about **80% of newly uploaded functions add zero unique chunks**, with a median of 2.5% unique chunks for the rest ([Lambda, ATC'23](https://www.usenix.org/system/files/atc23-brooker.pdf)). Inline dedup under live overlays costs throughput: one secondary benchmark put OpenZFS at a 25% penalty with fast dedup and 50% with legacy ([Klara](https://klarasystems.com/?p=22086), snippet). So dirty chunks are hashed against the parent manifest and a global index at upload, zero chunks are skipped, chunks are zstd-compressed in the object tier, and the hot local overlay stays uncompressed. Hashing at upload also removes identical rewrites that a dirty bitmap would count. The notes suggest 128 to 256 KiB object chunks, smaller than Lambda's because sandbox diffs are scattered small writes; that is a judgment call, and **no block-level dedup or compression ratio for developer workspaces has been published**. Shared package caches should be additional read-only content-addressed devices, never a writable shared filesystem.

### Checkpoints, transport and fairness

A combined memory and disk checkpoint needs no guest filesystem freeze: with vCPUs stopped, the storage service seals overlay generation N, records virtqueue state, opens N+1 and resumes, and upload runs in the background; DigitalOcean describes this sequence and commits a checkpoint only when every artifact is published. A fork seals and opens two new generations under one snapshot ID shared with memory. This is where the density research revises the earlier report, which placed the CoW block mapping "in or near the core" so that fork involved no external process. The storage notes conclude that atomicity needs only a synchronous "seal generation N" call to the storage service while vCPUs are paused, so the bitmap and manifest logic can live in the storage VM and stay out of the hypervisor's trusted base. Both positions are analysis; neither was measured.

On the data path, the per-VM VMM should not proxy requests. Virtqueues are shared directly between guest and storage VM, the hypervisor brokers notifications, and a per-VM pre-shared bounce region keeps the storage VM from mapping general guest RAM, as the earlier report already recommended. The nearest published performance evidence is SPDK vhost-user-blk at about 91% of bare NVMe and roughly a million IOPS per backend core (2021 slides, snippet) ([KVM Forum 2021](https://kvm-forum.qemu.org/2021/Changpeng%20Liu%26Ben%20Walker_High%20Performance%20NVMe%20Virtualization%20with%20SPDK%20and%20vfio-user.pdf)). No measurement of a guest-to-backend-VM virtio-blk path on a type-1 microhypervisor exists in the research. Fairness is enforced in the storage service with per-device token buckets and weighted-fair dequeue, charging CoW parent reads and flushes to the VM that caused them, and capping checkpoint and hydration I/O separately; CodeSandbox once wrote about 1 GiB/s of memory snapshots from hibernation alone ([CodeSandbox](https://codesandbox.io/blog/how-we-scale-our-microvm-infrastructure-using-low-latency-memory-decompression), snippet), which is why memory checkpoints must be incremental and compressed for drive endurance as well as speed.

## CPU: idle guests must cost nothing, and bursts must run within 2 ms

### Idle cost is mostly self-inflicted

The only modern quantitative source on idle microVM cost is a single GitHub issue thread, so it is a case study, not a benchmark. On Firecracker with a 6.12 guest and 2 vCPUs, an idle sandbox generated about 102 host vCPU wakeups per second and 5.79 millicores; 43 of those wakeups came from the guest agent polling a child process every 25 ms. Fixing only the agent brought it to about 14 to 26 wakeups per second and **2.54 millicores**. Disabling tickless idle raised wakeups to 2,043 per second ([mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802)). LightVM's 2017 result brackets it: a trimmed Linux guest held about 1% of a machine for 1,000 guests, a stock Debian about 25% ([LightVM](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)). Host halt polling is the other trap: the kernel documentation warns it "can push CPU utilization to 100% on an otherwise idle machine" ([KVM halt polling](https://docs.kernel.org/virt/kvm/halt-polling.html)).

The design consequences are inferences from that small evidence base. The guest agent must have no periodic timers, with heartbeats driven from the host, which can read vCPU state directly. The guest kernel must be tickless at idle. Halt polling in the hypervisor's own scheduler should be per-VM and budgeted, never applied to a guest idle for more than a few milliseconds. And the hypervisor should offer a state between running and hibernated: vCPUs descheduled and guest timers masked with memory resident, entered transparently when only housekeeping timers are pending and left on virtio activity, with a paravirtual time adjustment so watchdogs do not fire. No product publishes a latency for such a state. A paravirtual tick in the style of Paratick, which cut exits by up to 80% in its evaluation, removes the x86 timer-programming exits on each idle transition; on Arm the guest-owned virtual timer avoids those exits already, a recalled point ([Paratick](https://web.njit.edu/~dingxn/papers/paratick.pdf)).

### Published overcommit ratios, and where latency breaks

The published operating points are 10x in production and over 20x tested for Lambda (2020; the memory notes could not confirm whether the wording covers memory as well as CPU) ([Firecracker NSDI'20](https://css.csail.mit.edu/6.566/2023/readings/firecracker.pdf)), a hard cap of 5 sandbox vCPUs per node vCPU on AWS's November 2026 EKS sandbox product (secondary reporting) ([InfoQ](https://www.infoq.com/news/2026/11/aws-nitro-sandboxes-eks/)), and about 26% more VMs for general-purpose Azure workloads under Coach. A secondary article describing DSec as "50x overcommitted" is not supported by the paper text the researchers read. Firecracker's authors frame the ratio as a statistical bet whose efficiency improves with the square root of the number of uncorrelated workloads, and they note that workloads of one customer behave as one workload. That makes correlated bursts, one tenant fanning out hundreds of agents that all build at once, the main hazard, and tenant anti-affinity across hosts the main defence.

The metric that predicts interactive pain is the time a runnable vCPU waits on the host run queue. With two 32-vCPU VMs sharing 32 cores, p95 tail latency rose up to **20x** as that wait grew from 2 ms to 16 ms ([vSched, EuroSys'25](https://cs.hofstra.edu/~jshan/papers/vsched.pdf)). DSec's priority experiment gives the remedy: a latency-sensitive workload slowed 45.2% beside best-effort load with no controls and at most 3.4% when best-effort work ran in a strict idle class; adding SMT core scheduling made it 17.3%, worse than priority alone ([DSec](https://arxiv.org/html/2609.22978v1)).

### Few vCPUs, a two-class scheduler, and SMT-less hardware where possible

Lock-holder preemption, stalled TLB shootdowns and co-scheduling problems all need at least two vCPUs to exist; paravirtual fixes help (PV TLB flush gave +78% and +132% on ebizzy at 2x and 3x overcommit in 2017 patches, snippet) but are x86/KVM-centric ([LKML](https://lkml.iu.edu/hypermail/linux/kernel/1712.1/03584.html)). The structural answer, an inference, is to default sandboxes to one or two vCPUs and widen only during bursts, either by exposing more vCPUs and telling the guest how many are currently backed or by hot-add; no source compares the two. For multi-vCPU guests the hypervisor should export a per-vCPU preempted flag and steal time on both architectures, which on arm64 must be designed in.

The scheduler shape the notes synthesise (not drawn from one source, and no head-to-head comparison of schedulers for thousands of mostly idle VMs exists) is per-core run queues with work stealing, a wake-up boost for vCPUs returning from a long sleep, a token-bucket budget per sandbox and per tenant so a compile cannot pose as interactive indefinitely, strict two-level priority, and hierarchical fairness from tenant to sandbox to vCPU. SMT is a real capacity tax: AWS's sandbox product loses "roughly half the advertised vCPUs" to core scheduling on SMT instances, while one-thread-per-core Arm parts and x86 E-core parts avoid the question. On SMT x86 the microhypervisor should pair siblings only within a trust domain. Tag space needs attention at density on Arm, where an 8-bit VMID covers 255 VMs; 16-bit VMIDs and generation-based allocation to runnable VMs are the notes' requirement (the VMID widths are recalled; the allocator design is from a KVM patch thread read as a snippet) ([KVM/arm64 VMID allocator](https://lore.kernel.org/all/Yef65ng6pQK5yZDa@arm.com/T/)). Reclaim itself costs CPU, as DSec's DAX result shows, so reclaim work runs in the batch class and is charged to the tenant.

## The combined design, the build order and the gates on overcommit

### One design, restated by resource

For memory: guests boot once per template with 4K pages and a density-tuned kernel configuration; clones fork with lazy stage-2 population over refcounted layers; unbacked and zero states cost nothing; a size-zero balloon device carries 2 MiB free page reporting into an absent-zero state; the in-guest agent runs PSI-gated cache reclaim and compaction when idle; public read-mostly content sits on stage-2-enforced read-only DAX devices in 2 MiB blocks; private RAM is mapped at 4 KiB, aged by accessed bits, compressed and then written to NVMe under a promotion-rate limit; idle sandboxes soft-hibernate and then leave RAM entirely; only zero-page and template-relative dedup run across the fleet. For disk: one virtio-blk ext4 root over a 4 KiB three-state overlay in the storage VM, direct I/O, an honest group-committed flush on power-loss-protected NVMe, `fstrim` before checkpoints, and seal-then-upload checkpoints with hashing, dedup and zstd at upload into a flat manifest. For CPU: an event-driven agent, tickless guests, a paused-resident idle state, one or two vCPUs by default, a two-class token-bucket scheduler and burstable vCPU semantics.

### Build order

The notes rank mechanisms by saving and certainty against complexity. Combining the memory, elasticity and storage rankings gives the order below; the ordering is the researchers' judgment, and the evidence column says how much of each row rests on measurement.

| Order | Mechanism | What it removes | Strength of evidence |
|---|---|---|---|
| 1 | Sparse lazy allocation, explicit zero state, density guest config, event-driven agent | Configured-but-untouched RAM; idle CPU burn | Strong for the saving (CodeSandbox, Cortex); idle CPU from one case study |
| 2 | Template fork with 4 KiB CoW and lazy stage-2; 4 KiB three-state disk overlay under ext4 | Template resident set per clone; base image per disk | Fork cost from Xen snippets; persistence of sharing unmeasured |
| 3 | Free page reporting at 2 MiB with absent-zero semantics; balloon at size zero with stats | Guest-freed memory | Measured (34% on a build), with a known plateau |
| 4 | In-guest PSI-gated cache reclaim, compaction, pressure reporting to the host | Cold guest page cache; fragmentation gap | Senpai and DAMON measured in containers; the VM combination unmeasured |
| 5 | Honest cheap flush on PLP NVMe; fstrim; upload-time dedup and zstd | Slow fsync or lost durability; diff bloat | Device latencies measured; flush path has no precedent |
| 6 | Read-only DAX devices for shared public content | Duplicate page cache of base content | Firecracker docs and one preprint; CPU cost and side channel noted |
| 7 | Accessed-bit aging, compressed tier, NVMe tier, background cleaning | Cold private memory; seconds-per-GiB pause | Container fleets only; no per-page microVM precedent |
| 8 | Soft and hard hibernate with working-set-ordered prefetch | Idle sandboxes' RAM | Product baselines exist; targets unproven |
| 9 | Admission on private memory, pressure ladder, two-class scheduler with budgets | Unsafe overcommit | Policy inference from Coach, Google, Meta, DSec |
| 10 | 2 MiB promotion for hot private RAM, shared stage-2 subtrees, custom reporting device, guest mm patches | TLB cost; residual fragmentation | Research prototypes; no current huge-page measurement |

Admission control and the pressure ladder are listed ninth because they need the earlier mechanisms' counters, but a conservative version (no overcommit of private memory, freeze on exhaustion) has to exist from the first multi-tenant deployment. Explicitly not recommended: cross-tenant content scanning, sub-page patching, 2 MiB-only guest RAM, guest swap, routine balloon inflation, virtio-fs on the root or workspace path, and inline dedup or compression under live overlays.

### Guardrails and metrics that gate overcommit

The proven control pattern is to reclaim only while a guest pressure signal is at or near zero, back off within one control period, and make expansion immediate. The gates below combine published thresholds with the notes' starting points; where a threshold is the researchers' proposal it is marked, and none of them is an operator-published sandbox SLO, because none was found.

| Gate | Signal | Starting threshold | Basis |
|---|---|---|---|
| Stop guest reclaim | Guest memory PSI `some`; balloon-stat `ALLOC_STALL`, direct-reclaim, `OOM_KILL` deltas | PSI above roughly 0.1 to 1%, or any non-zero delta; hold off tens of seconds | Senpai's 0.1% target is published; the band and hold-off are proposals |
| Thrash guard | Refaults and major faults after each reclaim step | Any refault raises that guest's protected floor | TMO's rationale for its 6 s period; the floor rule is a proposal |
| Limit offload | Promotion rate from compressed and NVMe tiers | 0.2% of working set per minute | Google's published limit, via secondary summary |
| CPU contention | Run-queue wait of runnable vCPUs | p99 wake-to-run under 1 to 2 ms; alert at 5% of wall time | vSched's 2 ms knee and VMware's 5% CPU Ready line (snippet); the SLO is a proposal |
| User-visible latency | Synthetic exec round trip per host; reference build slowdown on canaries | Build slowdown at most 1.2 to 1.5x at p95 | Proposal |
| Admission | Sum of working-set estimates, idle floors, shared pools and a burst reserve against RAM | Reserve sized to the measured P99 one-minute growth | Proposal, after Coach's P95 windows and guaranteed/oversubscribed split |
| Incident counter | In-guest OOM kills; sandbox freezes | Every OOM kill is a platform incident | Proposal |

When the host itself runs short, the notes' ladder runs from invisible to visible: drop clean shared pages that can be re-read; compress and then write out cold private pages of idle guests; squeeze the idlest guests' cache with the balloon; soft-hibernate idle sandboxes, longest idle first; stall the allocation faults of the fastest-growing sandboxes; freeze active low-priority sandboxes with state intact; refuse or redirect new and waking sandboxes. The last resort is a freeze, never an OOM kill, which is possible because the hypervisor owns the memory and always has a consistent state to pause. One finding supports brief freezes over migration: up to 88.1% of memory overloads in an oversubscribed cloud lasted under two minutes (2011, snippet) ([Overdriver](https://researcher.draco.res.ibm.com/publications/overdriver-handling-memory-overload-in-an-oversubscribed-cloud--1)). Red Hat's 2025 warning stands as the counterweight: at 25% memory oversubscription without the right mechanisms, VMs get killed by the OOM killer ([Red Hat](https://developers.redhat.com/articles/2025/04/24/evaluating-memory-overcommitment-openshift-virtualization), snippet). Waking a hibernated sandbox is an admission event, and mass hibernation must be rate-limited because snapshot I/O is itself a bottleneck, as E2B's 503 responses show.

### What changes relative to the earlier architecture report

The architecture stands: nothing in the density research argues against the microhypervisor core, per-VM VMMs, the storage VM or the virtio-only guest. Seven recommendations move. Hypervisor swap and compression were deferred and are now a core tier, built on the same layer map as diff snapshots. Dirty tracking was "needed only for incremental snapshots" and is now also needed for background cleaning, alongside accessed-bit scanning for idle tracking, so both belong in the portable page-table abstraction from the start. The disk CoW map moves from "in or near the core" to the storage VM behind a synchronous seal call. Page-table subtree sharing is deferred in favour of lazy population. virtio-mem changes from a resize mechanism to a growth and hard-cap mechanism, with guest capacity otherwise fixed. The zero-on-refault rule becomes an explicit absent-zero page state that also governs hibernation and discard on disk. And the Xen fork figure the earlier report could not retrieve is now available as about 745 µs to create, from slides. Two earlier positions are reinforced with new evidence: 4K-page guests on both architectures, and no filesystem sharing on the root path. The scheduler, which the earlier report listed as resting on reasoning, now has DSec and vSched data behind its priority and latency targets, though still no comparison of scheduler designs.

### What the prototype must measure

The capacity arithmetic in the notes is explicitly an estimate: if an active sandbox averages 300 to 500 MiB private and a soft-hibernated one 20 to 60 MiB compressed, a 512 GiB host holds on the order of 500 to 1,000 active plus several thousand hibernated sandboxes. Every input to that sentence is unmeasured for this design. The measurements that turn it into a plan are these. First, private memory per sandbox against time since fork (one minute, one hour, one day), idle and under a scripted agent workload, split into anonymous memory, page cache and kernel; this is the single most important missing number. Second, what an idle forked guest dirties over ten minutes, and its idle wakeup rate and millicores on both architectures. Third, how much reporting returns from a mostly idle long-lived guest, and how much the reclaim-compact-report sequence adds. Fourth, page-cache duplication after fork with a single CoW root against a DAX layout. Fifth, compressibility of the private set, post-wake working-set size and its stability between wakes. Sixth, latencies: stage-2 fault, CoW break, decompress fault, frame fault-in rate, fork, pause and wake, plus NVMe throughput in a wake storm. Seventh, 4 KiB against 2 MiB stage-2 mappings on build workloads per CPU family. Eighth, storage: 4K write and fsync latency at queue depth one from guest to NVMe through the storage VM, the first-write penalty after fork, diff size per checkpoint at 4 KiB against 64 KiB granularity, dedup and zstd ratios of real diffs, and pause time attributable to sealing. Ninth, run-queue wait and exec latency as overcommit rises, with correlated bursts injected.

## What the evidence does not support

The combination has no published end-to-end precedent with measured density. The closest public designs (Cortex, E2B, CodeSandbox, DigitalOcean) are KVM and Firecracker systems built on userfaultfd and host page cache, and none publishes sandboxes per host. No sandbox operator has published a memory overcommit ratio, interactive latency thresholds, incident data on balloon- or reporting-induced stalls, per-VM IOPS budgets, or burst-correlation statistics; "mostly idle" rests on one preprint's CPU telemetry.

Several numbers this report leans on are old or thin. The huge-page benefit is from roughly 2009 hardware. Core-scheduling overheads are from 2019 to 2020 prototype kernels. Paravirtual lock and TLB results are from 2017. The idle-guest cost is one GitHub issue. Tide and DSec are preprints, and Tide's numbers in particular should be re-read from the paper before being quoted further. Fault costs of 1 to 2 µs and Arm details (VMID width, hardware access-flag support on specific cores, break-before-make levels) are recalled, not verified. There are no arm64 measurements of reporting, ballooning, idle guests, DAX or virtio-blk backends anywhere in the research.

Four interactions are flagged by the researchers as the likeliest sources of bugs, none with a published treatment for this stack: free page reporting against CoW layers and hibernation (the zero-versus-inherited rule); DAX window identity against snapshot, fork and image garbage collection, since guest page tables in a memory snapshot point into the window and the same image version must reappear at the same address; accessed-bit tracking against shared table subtrees; and block splitting on Arm without FEAT_BBM2.

## Conclusion

The brief named three ingredients and the research returns three different answers. Ballooning is the one whose obvious form should be dropped: its job is done better by a guest that keeps its full capacity and a hypervisor that stops backing what the guest is not using. Copy-on-write is necessary and insufficient: it makes fork nearly free and shares what existed at fork time, and then the page cache quietly undoes it unless cache control and a shared read-only base are built alongside. Optimized disk writes turn out to be less about speed tricks than about granularity and honesty: 4 KiB CoW so small writes stay small, and a flush that is cheap enough on the right drives to be real.

The less expected result is where the usability guarantee comes from. It does not come from tuning any single reclaim mechanism but from a division of responsibility that only a hypervisor owning the second-stage tables can offer: the guest never sees its capacity shrink, the host absorbs the risk, and the host's worst response to exhaustion is a brief freeze of a low-priority sandbox, not a killed process. That property, more than any sandboxes-per-host figure, is the density argument for this design over a KVM-based one, and it is testable early. A prototype that forks from a template, reports free pages into an absent-zero state and records private memory against time under a scripted agent workload will show within weeks whether the dominant terms are the ones this report predicts, and that curve should decide how much of the later machinery is worth building.
