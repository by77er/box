## 1. virtio-balloon in depth (mechanics, stats, speed, pathologies, auto-balloon controllers)

### Takeaway
The classic balloon is the only mechanism that can *force* a Linux guest to shed page cache, but it is slow (about 1 GiB/s shrink, 2.3 GiB/s grow at 4 KiB granularity), exit-heavy, unverifiable, and it destroys 2 MiB host mappings; every shipping controller (ChromeOS, Hyper-V, Proxmox) therefore sizes it conservatively from "free + reclaimable cache minus a safety margin" and backs off on a guest pressure signal. For a new design it should be a slow, bounded "cache squeezer" and safety valve, not the main elasticity path.

### Cited Findings

Mechanics (Linux guest driver, mainline at fetch time)
- Inflate allocates guest pages one at a time and sends PFNs in arrays of at most 256 (`VIRTIO_BALLOON_ARRAY_PFNS_MAX 256`); when allocation fails the driver sleeps 200 ms (`msleep(200)`) and retries; the deflate-on-OOM notifier releases 256 pages per OOM notification (`VIRTIO_BALLOON_OOM_NR_PAGES 256`, notifier priority 80). [F] — [linux drivers/virtio/virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c)
- Firecracker's doc confirms the same from the VMM side: the guest "retries allocation when below target, sleeping 0.2 seconds after each failure" and prints `Out of puff!`; Firecracker "cannot control inflation or deflation speed, which is set by the guest kernel"; if inflation stalls, the operator should reset the target near the achieved size to stop CPU-heavy retries. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)
- `deflate_on_oom`: applies only to physical page allocations for guest processes; it does **not** cover kernel-internal allocations, requests larger than what the balloon holds, or allocations refused up-front by overcommit heuristics (`vm.overcommit_memory=0`). Firecracker calls it a crash safeguard, not a routine mechanism: repeated use is CPU-intensive, worse if the balloon is still inflating toward target. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)
- Cloud Hypervisor: balloon `size` is subtracted from guest RAM; `deflate_on_oom` (default off) lets the guest shrink the balloon to 0; `free_page_reporting` (default off) works with `size=0`; stats queue is offered whenever a balloon exists, read via `ch-remote balloon-stats`. [F] — [Cloud Hypervisor docs/balloon.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/balloon.md)

Stats queue (what a controller can see)
- Classic stats: `SWAP_IN`, `SWAP_OUT`, `MAJFLT`, `MINFLT`, `MEMFREE`, `MEMTOT`, `AVAIL` (MemAvailable), `CACHES` (reclaimable without extra I/O), `HTLB_PGALLOC`, `HTLB_PGFAIL`. Added in Linux v6.12: `OOM_KILL`, `ALLOC_STALL` (allocations entering the slow/direct reclaim path), `ASYNC_SCAN`, `DIRECT_SCAN`, `ASYNC_RECLAIM`, `DIRECT_RECLAIM`. Reclaim efficiency = reclaimed/scanned; Firecracker cites `sar` guidance that below about 30% indicates difficulty. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md); stat list confirmed in [virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c)
- There is **no PSI stat** in the virtio-balloon stats queue; the closest are `ALLOC_STALL`, `DIRECT_SCAN/RECLAIM` and `OOM_KILL` counters (deltas between polls). [F] — [virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c)
- Firecracker polls stats on a fixed `stats_polling_interval_s`; stats cannot be enabled after boot if not enabled pre-boot; stats "come from the guest and are only indicative"; do not rely solely on them for control decisions. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)

Speed (measured, QEMU/KVM, Linux 6.1, 20 GiB VM shrunk to 2 GiB and back, 10 runs)
- virtio-balloon shrink of touched memory: **0.95 GiB/s**; grow (deflate): **2.3 GiB/s**; hypercalls are batched (256 pages) but each 4 KiB page is individually allocated and individually `madvise`d. A reimplemented 2 MiB "virtio-balloon-huge" is 143x faster shrinking and 139x faster growing. HyperAlloc: 344.8 GiB/s shrink (362x virtio-balloon). [F] — [HyperAlloc, EuroSys'25](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Return + re-touch ("return+install", i.e. give-back including re-faulting): best candidates reach only about **4-4.2 GiB/s** (virtio-balloon-huge 4.2, virtio-mem and HyperAlloc 4.0) versus 17 GiB/s for touching already-mapped memory; i.e. host-side fault-in, not the protocol, bounds give-back speed. [F] — [HyperAlloc, EuroSys'25](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Interference: with STREAM in the guest, 4 KiB balloon shrinking is the only mechanism that significantly hurts a single-threaded guest; at full load HyperAlloc's 1st-percentile memory bandwidth is 2.3x that of virtio-balloon; the STREAM run finishes about 8.9 s later under virtio-balloon resizing. [F] — [HyperAlloc, EuroSys'25](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Independent measurement (Squeezy, Linux 6.6): balloon reclamation latency is dominated by VM exits (81% on average); virtio-mem was 2.34x faster than the balloon on average; ballooning causes host CPU spikes while serving exits. [F] — [Squeezy, EuroSys'26 (arXiv 2411.12893v2)](https://arxiv.org/html/2411.12893v2)

Huge-page interaction
- Linux guests inflate the traditional balloon at most 1 MiB at a time, so on hugetlbfs-backed guests inflation never covers a whole 2 MiB page and frees nothing; worse, inflating pages the host has not yet backed can *increase* host usage (zeroing allocates a huge page). Firecracker recommends hinting/reporting instead of the balloon with huge pages. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)
- 4 KiB balloon discards on a `File`-backed (snapshot-restored, private mapping) guest split VMAs: up to 2 extra VMAs per non-contiguous discard; default `vm.max_map_count` 65530 is hit after roughly 32K non-contiguous 4 KiB discards (about 128 MiB), panicking Firecracker. This is a Linux-host artifact, but the analogue in a type-1 design is second-stage page-table fragmentation (2 MiB block mappings split to 4 KiB). [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)

Trust model
- A balloon cannot be enforced: Firecracker lists what a compromised driver can violate (exact page consumption, accurate `actual`, no reuse of inflated pages, correct stats) and says hosts "must be ready for the Firecracker process to use all memory it was given at boot". PFNs are validated; discarded ranges read as zero; private snapshot-file mappings are replaced with anonymous mappings so old snapshot contents cannot be read back. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)

Auto-balloon controllers
- **ChromeOS concierge (crosvm; source at release R117, 2023 — dated)**, two policies:
  - `BalanceAvailableBalloonPolicy`: `guest_available = free + disk_caches`; `balloon_delta = (guest_above_critical − host_above_critical) / 2` where each "above critical" is available minus a critical margin; guest critical margin starts at **400 MiB** and is learned downward; balloon capped at 3/4 of guest RAM; acts only if a side is within 1 MiB of critical or the delta exceeds 1% of a margin. I.e. it equalises headroom between host and guest.
  - `LimitCacheBalloonPolicy` (ARCVM): reads guest `/proc/zoneinfo` watermarks; targets guest free memory of `totalreserve + ~315 MiB` (`MAX_OOM_MIN_FREE = 322,560 KiB`, tied to Android LMKD's min-free) and, as host memory tightens through "reclaim / moderate / critical" tiers, inflates to cap the *guest page cache* at a per-tier target, never inflating past `guest_cache − target_cache`. On an LMKD kill request arriving over vsock (`DeflateBalloonToSaveProcess`) it deflates by `min(proc_size, responsive_max_deflate_bytes)` if tier limits allow, instead of letting the app be killed. [F] — [platform2 vm_tools/concierge/balloon_policy.cc (R117)](https://cos.googlesource.com/third_party/platform2/+/refs/heads/release-R117/vm_tools/concierge/balloon_policy.cc)
- **Hyper-V Dynamic Memory**: target = committed guest memory plus a buffer (default example 20%: 1000 MB committed gives about 1200 MB assigned); "pressure" = committed/assigned, so a 20% buffer targets about 83%; sustained above 85% is flagged; separate Startup and Minimum RAM, with Smart Paging (disk-backed) bridging restarts when Minimum < Startup. The control input is guest **committed memory**, not free memory. [S] — [Microsoft Learn: Dynamic Memory](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/dynamic-memory); [Hyper-V performance: memory](https://learn.microsoft.com/en-us/archive/blogs/neales/hyper-v-performance-memory)
- **VMware ESX** (2002, dated but foundational): balloon makes the guest OS run its own reclaim; hypervisor decides *how much* using sampled working-set estimates and an **idle memory tax** (default 75%, an idle page costs 4x an active one, `k = 1/(1−τ)`). [S] — [Waldspurger, OSDI'02](https://www.usenix.org/legacy/event/osdi02/tech/waldspurger/waldspurger_html/node1.html)
- Reported cost of ballooning in that paper: a ballooned VM ran dbench 1.4% to 4.4% slower than a VM booted with the smaller size. [R] — [Waldspurger, OSDI'02](https://www.usenix.org/legacy/event/osdi02/tech/waldspurger/waldspurger_html/node1.html)
- **Proxmox auto-ballooning**: `pvestatd` balloons VMs toward their configured minimum only when host RAM use exceeds about 80%, proportionally by "shares". [R] — [Proxmox: Dynamic Memory Management](https://pve.proxmox.com/wiki/Dynamic_Memory_Management)
- **Google working-set reporting (WSR)** for virtio-balloon: RFC series by Yuanchu Xie / T.J. Alumbaugh, v1 May 2023 through v4 Nov 2024; adds `VIRTIO_BALLOON_F_WS_REPORTING` with two virtqueues (host configures bins/requests a report; guest sends reports on request or under memory pressure); histograms of memory by idle age, built on MGLRU generations (`CONFIG_LRU_GEN=y`, `CONFIG_WORKINGSET_REPORT`). Search results did not show it merged upstream; crosvm's balloon device source already defines working-set ops. [S] — [LKML v4 workingset reporting](https://lkml.iu.edu/hypermail/linux/kernel/2411.3/03646.html); [RFC v2 virtio-balloon WS reporting](https://lkml.indiana.edu/2306.2/06348.html); [crosvm balloon.rs](https://crosvm.dev/doc/src/devices/virtio/balloon.rs.html)

### Inferences
- A "safe balloon target" formula consistent with all of the controllers above: `inflate_by = max(0, MemAvailable − margin)` where `MemAvailable ≈ S_AVAIL` (or `MEMFREE + CACHES`), margin on the order of max(300-400 MiB, 10-20% of guest RAM), step-limited, and immediately reversed when `ALLOC_STALL`/`DIRECT_RECLAIM`/`MAJFLT` deltas become non-zero or `OOM_KILL` increments. ChromeOS's 400 MiB / 315 MiB margins and Hyper-V's 20% buffer are the two empirically shipped anchors.
- At 0.95 GiB/s shrink and 2.3 GiB/s grow, a 4 GiB swing takes seconds of guest CPU and exits. That is acceptable for idle-time squeezing but not for burst give-back; the burst path must not involve deflating a 4 KiB balloon. Either the balloon should already be mostly deflated when a burst starts (hard), or memory is held back some other way (reported-free pages, section 2) so that give-back is just a fault.
- For a custom hypervisor the balloon should operate on 2 MiB (or pageblock-order) units when it operates at all: 139-143x faster and no second-stage mapping fragmentation. Stock Linux has no huge balloon; this needs a guest patch or (simpler) a different primitive.
- Because the balloon is unverifiable and the stats are guest-supplied, host admission control must budget for the *un-ballooned* size or have a hypervisor-enforced fallback (host-side swap/compression or pause-to-snapshot), exactly as Firecracker advises.

### Gaps
- Android AVF/pKVM balloon policy, Kata's balloon/reclaim settings, MOM/oVirt rules, Xen autoballoon/tmem: not fetched. Recalled but unverified: Kata exposes a `reclaim_guest_freed_memory` option that turns on free page reporting, and Xen tmem was removed around Xen 4.13; do not cite without checking.
- Balloon compaction (movable balloon pages) and its measured effect on guest THP availability: no numbers found.
- No measured data on balloon-induced guest swap storms; guests in this design would normally have no swap, so the failure mode is OOM-kill instead.
- Whether virtio-balloon WSR was merged in 2025-2026 kernels was not confirmed.

## 2. Free page reporting (and free page hinting)

### Takeaway
Free page reporting is cheap (about 0.15% CPU overhead) and automatic, and cut a clang build's memory footprint by 34% in the HyperAlloc evaluation, but it only sees free blocks of pageblock order (2 MiB) and is blind to the page cache: after a build, even with the cache fully dropped, the VM stayed at 8 GiB (vs 1.9 GiB for an allocator-level design) because of buddy fragmentation. Lowering the order to 4 KiB recovers more (42%) at a 19% runtime cost with the stock virtqueue protocol, so a custom hypervisor benefits from a cheaper transport, not just a lower order.

### Cited Findings

Kernel mechanics (mainline at fetch time)
- `page_reporting_order` is a module parameter (mode 0644, i.e. runtime-writable via sysfs / settable on the kernel command line as `page_reporting.page_reporting_order=`); if unset it takes the driver's order, else `pageblock_order`. Capacity (batch size) is capped at `PAGE_REPORTING_CAPACITY` (32 entries per report in the stock kernel; the HyperAlloc authors varied it 32 to 512). [F] — [linux mm/page_reporting.c](https://github.com/torvalds/linux/blob/master/mm/page_reporting.c); [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Reporting is skipped for a zone unless free memory exceeds `low_wmark + (capacity << page_reporting_order)` (a built-in "do not report when the guest is tight" guard); each pass processes a budget of `nr_free / (capacity × 16)` batches per free list; isolate-type free lists are skipped. [F] — [mm/page_reporting.c](https://github.com/torvalds/linux/blob/master/mm/page_reporting.c)
- Reporting starts 2 seconds after registration and 2 seconds after any sufficiently high-order free; while a batch is being reported the pages are withheld from the allocator and returned to the free list afterward. [S] — [kernel docs: Free Page Reporting](https://docs.kernel.org/mm/free_page_reporting.html)
- Firecracker: `free_page_reporting: true` at PUT `/balloon`, pre-boot only; guest needs `CONFIG_PAGE_REPORTING`; "keep `page_reporting_order` at 9 or higher" so reported ranges match backing page size; with hugetlbfs backing Firecracker cannot free sub-2 MiB ranges and zeroes them instead; "reporting runs continuously and cannot be stopped"; runtime impact "depends heavily on workload". [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)

Measured effectiveness (HyperAlloc paper, clang 16 build, 12 vCPU, 16 GiB VM, QEMU RSS sampled at 1 Hz)
- Default reporting (order 9, delay 2 s, capacity 32) reduces footprint (GiB·min) by **34%** vs a static 16 GiB VM, with CPU overhead 0.15 ± 0.42% (HyperAlloc: 0.51 ± 0.18%). All auto-reclaim techniques fall in a 24-45% range. [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Tuning: with order 9, delay (2 s down to 100 ms) and capacity (32 to 512) make no significant difference. With **order 0 (4 KiB)**, two configurations reach **42%** (d = 2 s, c = 512) but **increase runtime by 19%** with significantly higher user and system CPU. [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Page cache dominates what reporting cannot return: "By the end of compilation, the page cache occupies a substantial part of the guest's total memory. This prevents many poorly utilized huge pages from being freed and reclaimed." After deleting build artifacts and dropping the whole cache, virtio-balloon reporting shrinks the VM only to **8 GiB**, HyperAlloc to **1.9 GiB**. In a repeated Blender workload, after dropping the cache: **4.08 GiB** (reporting) vs **1.17 GiB** (HyperAlloc). [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Three 16 GiB VMs each building clang three times with 2 h idle gaps: footprint reduced 9.1% (reporting) vs 40% (HyperAlloc) when peaks coincide; with peaks offset by 40 min, peak demand falls from 40.74 GiB to 35.98 GiB (reporting: one extra VM fits in 48 GiB) or 28.11 GiB (HyperAlloc: two extra VMs fit). [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Agent-specific data point: Tide (arXiv preprint, Sept 2026) uses **Firecracker + free page reporting as its baseline** for coding-agent microVMs and reports 34-45% lower total backing memory than that baseline on Terminal-Bench trajectories (section 8); i.e. on agent workloads default reporting leaves at least a third of backing memory unreclaimed, per that one small study. [F] — [Tide, arXiv 2609.40082](https://arxiv.org/abs/2609.40082)

Free page hinting vs reporting (2026 upstream discussion)
- Hinting was designed for live migration; the guest allocates `MAX_PAGE_ORDER` blocks (`VIRTIO_BALLOON_HINT_BLOCK_ORDER`, about 4 MiB on x86) and holds them until a shrinker or a host "stop" releases them. [F] — [virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c); [LKML Feb 2026](https://lkml.iu.edu/hypermail/linux/kernel/2602.1/04796.html)
- Firecracker ships hinting as developer preview because the spec lets the guest reuse a hinted range before the host has processed it (host `MADV_DONTNEED` could then destroy live data); mitigation sketched with UFFD write-protect. A hinting run on a 1 GB VM takes about **200 ms**. Firecracker wants hinting because it is host-triggered and cancellable ("reclaim from idle VMs and cancel quickly if the VM gets new work"). Jack Thomson's Jan 2026 RFC adds wait-for-ACK semantics, costing about 30% longer hinting runs. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md); [LKML Feb 2026](https://lkml.iu.edu/hypermail/linux/kernel/2602.1/04796.html)
- David Hildenbrand's objections: hinting's allocations are unmovable so it cannot free memory in ZONE_MOVABLE/CMA; granularity is coarser (MAX_ORDER vs pageblock); hinted pages are not reusable until the shrinker runs. His recommendation: **extend free page reporting** (he floated a pause/continue control) rather than extend hinting. [F] — [LKML Feb 2026](https://lkml.iu.edu/hypermail/linux/kernel/2602.1/04796.html)

Status across VMMs (as of late 2026)
- Firecracker: reporting GA-ish and hinting dev-preview since v1.14 (previous notes); Cloud Hypervisor: `free_page_reporting=on` supported, default off. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md); [Cloud Hypervisor balloon.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/balloon.md)
- QEMU: `-device virtio-balloon-pci,free-page-reporting=on` since QEMU 5.1; libvirt `<memballoon ... freePageReporting='on'>`. [S] — [libvirt patch thread](https://lists.libvirt.org/archives/list/devel@lists.libvirt.org/thread/AO3GBVXU4Q3XXU2XDIZVSBJQWOIPAJFU/)

### Inferences
- Reporting recovers "free and contiguous" memory only. In a dev sandbox, most idle memory is page cache (not free) and post-burst free memory is fragmented below 2 MiB, so reporting alone will plateau well above the true working set. The HyperAlloc numbers (8 GiB vs 1.9 GiB after drop_caches) put the fragmentation loss at several GiB on a 16 GiB build VM.
- The 19% runtime cost at order 0 is a transport cost (per-4 KiB scatterlist entries, per-range host unmap, per-page re-fault), not inherent. A custom hypervisor can cut it by (a) reporting at an intermediate order (e.g. order 4-6, 64-256 KiB) only when the guest is idle, (b) switching order dynamically (`page_reporting_order` is runtime-writable; write 9 during bursts, lower when PSI is zero and CPU is idle), and (c) running compaction (`/proc/sys/vm/compact_memory`, or `vm.compaction_proactiveness`) before an idle-time reporting pass so order-9 blocks exist.
- Reporting's built-in guard (`low_wmark + capacity << order`) and the fact that reported pages stay on the guest free list make it the safest primitive: give-back is a plain second-stage fault with no guest protocol step. Cost of give-back is the fault-in rate (about 4 GiB/s in the QEMU measurements; a type-1 hypervisor with a pre-zeroed frame pool should beat that).
- A type-1 hypervisor that unmaps at 2 MiB granularity from a 2 MiB block mapping keeps large second-stage mappings intact when order is 9; any sub-2 MiB reporting forces block splits, so sub-2 MiB reclaim should be reserved for long-idle guests whose TLB efficiency no longer matters, and blocks should be re-collapsed on wake.
- Hinting's one real advantage (host-chosen timing) can be had with reporting plus a pause/resume control, which matches upstream direction and is trivial in a custom device.

### Gaps
- No source measured reporting on a *mostly idle* long-lived guest (how much trickles back over hours); all numbers are for builds/benchmarks.
- crosvm's free page reporting status and defaults were not verified this session.
- The exact reason the stock order-0 path is slow (exits vs madvise vs refault) is not broken down in the paper.

## 3. virtio-mem

### Takeaway
virtio-mem is the right tool for a verifiable hard cap and for growing a VM beyond its boot size, but unplug speed and success depend on migration: about 34 GiB/s when the memory is already free and movable, well under 1 GiB/s when pages must be migrated, with timeouts and partial reclaim under pressure. "Start small, grow on demand" is practical (plug is tens of ms); "shrink on idle via unplug" is not a substitute for cache control.

### Cited Findings
- Guest support: x86-64 (kdump-safe from v5.13), **arm64 from v5.18**, s390x from v6.13. Since v5.19 hot(un)plug works at pageblock granularity (2 MiB on x86-64 and on arm64 with 4K pages; 4 MiB before). `VIRTIO_MEM_F_UNPLUGGED_INACCESSIBLE` (v5.16) is required by hypervisors backing the device with huge pages. Limitations: hibernation unsupported, no driver reload, no defragmentation of the block layout, onlining policy must be set on the kernel command line. [F] — [virtio-mem Linux user guide](https://virtio-mem.gitlab.io/user-guide/user-guide-linux.html)
- ZONE_MOVABLE guidance: hotplugged memory onlined movable "can usually be unplugged reliably"; keep MOVABLE:KERNEL at or below about 3:1 to 4:1 (example: 24 GiB hotplugged onto an 8 GiB boot VM); alternative `memory_hotplug.online_policy=auto-movable memory_hotplug.auto_movable_ratio=301`. [F] — [virtio-mem Linux user guide](https://virtio-mem.gitlab.io/user-guide/user-guide-linux.html)
- Firecracker (v1.14+): separate hotpluggable pool starting fully unplugged; `block_size_mib` default 2, `slot_size_mib` default 128 (KVM slot that is fully protected from the guest once all its blocks are unplugged); min guest kernel 5.16 (x86-64) / 5.18 (aarch64); recommended `memhp_default_state=online_movable`; memmap cost 64 B per 4 KiB page from boot memory (**262 MiB of boot memory to hotplug 16 GiB**) unless `memory_hotplug.memmap_on_memory=1`, which does not work if everything is onlined MOVABLE; unplugged blocks are freed from the host immediately; not configurable on snapshot-restored VMs (restored config is used); unplug "requires the guest to cooperate and actually be able to find" blocks. [F] — [Firecracker memory-hotplug.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/memory-hotplug.md)
- Speed, favourable case (HyperAlloc paper; memory touched then freed, movable zone, no migration needed): unplug **34 GiB/s**, plug **102 GiB/s** (one hypercall per 2 MiB block), plug+touch 4 GiB/s. With VFIO passthrough unplug is 52% slower and plug 21x slower (pre-population/pinning). During unplug under a multi-threaded STREAM load virtio-mem perturbed the guest for about 10 s (worse than the balloon) because it unplugs in decreasing address order and must migrate used subblocks. [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Speed, unfavourable case (Squeezy paper; 32 memhog instances, memory in use): virtio-mem takes **617 ms to reclaim 512 MiB and almost 2.5 s for 2 GiB**; page migration is 61.5% and zeroing 24% of latency; migrations start to dominate once about 20% of VM memory is occupied; placement is random so latency is unpredictable; **under memory pressure it hits timeouts and reclaims less than requested**; the guest kthread burns a vCPU; co-located requests slow more than 2x during scale-down. Plug costs 35-45 ms for all function sizes. [F] — [Squeezy (arXiv 2411.12893v2)](https://arxiv.org/html/2411.12893v2)
- Conflict note: 34 GiB/s (HyperAlloc) vs about 0.8 GiB/s (Squeezy) for virtio-mem unplug is not a contradiction; the first unplugs already-free movable memory, the second unplugs from a loaded guest needing migration. The Squeezy number is the relevant one for reclaiming from a guest that still holds page cache.
- An attempt to drive virtio-mem as an automatic reclaimer (track free huge pages, resize in 1 GiB steps at 1 Hz) gave the *worst* footprint of the automatic techniques and 39.8% higher footprint than HyperAlloc with VFIO; a more aggressive variant tracking free base pages forced compaction/migration that "turned out to be too slow, and virtio-mem was unable to resize the VM fast enough to prevent OOMs". [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- Squeezy's fix (guest MM made aware of hotplugged regions; per-instance regions): 2 GiB reclaimed in **127 ms** regardless of utilisation, 10.9x faster than virtio-mem, about 3 ms exit overhead per 128 MiB chunk; at 70% host memory P99 is about 1.1x vs 3.15x for virtio-mem. Linux 6.6 patch, serverless-oriented. [F] — [Squeezy (arXiv 2411.12893v2)](https://arxiv.org/html/2411.12893v2)

### Inferences
- "Start small, grow on demand" works for agent sandboxes as a *ceiling* mechanism: boot with e.g. 1-2 GiB, plug in 128 MiB-1 GiB steps when the pressure signal fires (35-45 ms per plug, memory populated lazily). The 3:1-4:1 movable ratio limits growth to about 4-5x boot memory unless hotplugged memory is onlined to ZONE_NORMAL (then it is effectively never unpluggable) — acceptable if shrinking is done by reporting/cache control instead of unplug.
- Shrinking by unplug is mostly pointless when free page reporting already returns the same free 2 MiB blocks without migration; unplug adds value only for (a) a verifiable hard limit (slot protection) against a hostile guest and (b) removing the `struct page` overhead of a large never-used region.
- ZONE_MOVABLE cannot hold kernel allocations (slab, page tables), and a Docker/build-heavy guest generates many; too large a movable share produces guest OOMs with free memory available. Budget boot (ZONE_NORMAL) memory generously.
- A simpler equivalent for a custom hypervisor: boot the guest with its *maximum* RAM but a hypervisor-enforced resident limit, relying on reporting to keep the unused part unbacked (HyperAlloc's "large guest-physical memory but low hard limit" suggestion). Cost: `struct page` for the full size (1.56% = 64 B per 4 KiB) is resident from boot.

### Gaps
- The VEE'21 paper's own evaluation numbers were not retrieved (ACM page not fetched); the comparison numbers above come from two later independent papers.
- No published unplug success-rate statistics for long-lived, fragmented dev-style guests.
- virtio-mem with 16K/64K arm64 guests: only 2020-2021 mailing-list material found (section 7).

## 4. Controlling the guest page cache (the dominant idle consumer)

### Takeaway
None of the elasticity devices reclaims page cache by itself; something must push the guest to evict it. The best-documented controller is Meta's PSI-driven Senpai (target 0.1% "some" pressure, at most 1% of the workload per 6 s, 0.05% CPU) which found on average 35% of container memory cold past 5 minutes; inside a sandbox the same loop via `memory.reclaim`, or DAMON_RECLAIM with `min_age` of 30-120 s, followed by compaction and free page reporting, is the practical recipe.

### Cited Findings
- Evidence that cache is the problem for build workloads: after a clang build, page cache "occupies a substantial part of the guest's total memory" and blocks reclaim; HyperAlloc authors name exposing the page cache to the hypervisor ("shrink the VM from the outside") as the logical next step. [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- TMO/Senpai (Meta, ASPLOS'22): `reclaim_mem = current_mem × reclaim_ratio × max(0, 1 − PSI_some / PSI_threshold)`; production settings `reclaim_ratio = 0.0005`, `PSI_threshold = 0.1%`, run every **6 seconds** (chosen to leave time to observe refaults); the paper states the maximum step is 1% of workload size per period, so "reaction time to extreme contraction tends to be minutes", while "adaptation to workload expansion ... is immediate"; Senpai also watches IO PSI; reclaim CPU cost **0.05% of all CPU cycles**. [F] — [TMO, ASPLOS'22](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)
- Why a stateless knob: an early Senpai drove `memory.high`, which could block an expanding workload until the limit was raised; Meta added the stateless `memory.reclaim` cgroup file to the kernel for this purpose. [F] — [TMO, ASPLOS'22](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)
- Coldness data: across Meta applications, memory not touched within 5 minutes averages about 35% (range 19-62%); one profile: 50% used in the last 1 min, +8% in 2 min, +12% in 5 min, 30% cold beyond 5 min. [F] — [TMO, ASPLOS'22](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)
- Savings: 20-32% of total memory fleet-wide (7-19% from application containers, about 13% from sidecar/"memory tax"); zswap backend 7-12% of resident memory, SSD backend 10-19%; for the Web tier (4x compression ratio) zswap saved 13% vs 4% for SSD. [F] — [TMO, ASPLOS'22](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)
- File vs anon balance: the kernel was changed to reclaim **only file cache as long as no refaults occur**, and to start swapping as soon as file refaults begin, balancing by refault rate vs swap-in rate; PSI was changed to count stalls from refaults of recently evicted cache but not first-time reads. [F] — [TMO, ASPLOS'22](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)
- DAMON_RECLAIM (in-kernel proactive reclaim; module parameters under `/sys/module/damon_reclaim/parameters/`): defaults `min_age` 120 s, `quota_ms` 10 ms and `quota_sz` 128 MiB per `quota_reset_interval_ms` 1 s; watermarks deactivate it when free memory is above high or below low (falls back to normal LRU reclaim); `quota_mem_pressure_us` auto-tunes the quota toward a target PSI stall time; `skip_anon=Y` restricts it to file-backed pages; documented example: `min_age` 30 s, 1 GiB/s cap, active only between 20% and 50% free. [F] — [kernel docs: DAMON_RECLAIM](https://docs.kernel.org/admin-guide/mm/damon/reclaim.html)
- MGLRU-based working-set reporting (section 1) is the proposed host-visible signal for "how much of this guest is older than N seconds"; requires `CONFIG_LRU_GEN`. [S] — [LKML v4 workingset reporting](https://lkml.iu.edu/hypermail/linux/kernel/2411.3/03646.html)
- `memory.reclaim` exists as a cgroup v2 interface since Linux 5.19 (writing a byte count triggers reclaim from that cgroup; root-cgroup write reclaims system-wide). [R] — [kernel docs: cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)
- MGLRU merged in Linux 6.1; its `lru_gen` debugfs interface supports proactive reclaim and working-set estimation by generation age. [R] — [kernel docs: Multi-Gen LRU](https://docs.kernel.org/admin-guide/mm/multigen_lru.html)
- ChromeOS's `LimitCacheBalloonPolicy` is a shipped example of using balloon pressure specifically to cap guest page cache at tiered targets as the host tightens. [F] — [balloon_policy.cc (R117)](https://cos.googlesource.com/third_party/platform2/+/refs/heads/release-R117/vm_tools/concierge/balloon_policy.cc)
- Host-side alternative (hypervisor-managed swap), from a Huawei system for cloud VMs skimmed incidentally: about 30% of server memory in their data centers is not accessed; their userspace swapper beats Linux kernel swapping by up to 25% (best-effort cold reclaim) and 30% (limited memory), and up to 71% of a VM's memory was reclaimable for one workload (Kafka). Only the abstract/intro and scattered result lines were read. [F, partial] — [Flexible Swapping for the Cloud, arXiv 2409.13327](https://www.arxiv.org/pdf/2409.13327)

### Inferences
- Technique ranking for dropping guest cache when both guest image and agent are controlled:
  1. **In-guest PSI-gated proactive reclaim** (Senpai loop against the root cgroup's `memory.reclaim`, or DAMON_RECLAIM with `skip_anon=Y`, `min_age` 30-120 s, PSI-autotuned quota). Evicts by coldness, self-limits via refault pressure, never blocks expansion. Needs no host involvement; pair with reporting so evicted pages actually leave the host.
  2. **Balloon squeeze to a cache target** (ChromeOS style) when the host is tight; coarser, forces eviction regardless of hotness, costs exits.
  3. **`drop_caches` via the agent** only as an idle/pre-snapshot action: it is indiscriminate (drops hot build caches, dentries/inodes with `3`), and the next `cargo build`/`npm test` pays cold-cache I/O. Use `echo 1` after `sync` only when the sandbox has been idle long enough that cache value is low, and prefer (1).
- Senpai's production step (≤1% per 6 s) is tuned for latency-critical services; an *idle* sandbox (agent waiting on the model, zero PSI, near-zero CPU) can use a far more aggressive ratio, tapering to Senpai-like gentleness while a tool is running. Idle detection is cheap for the hypervisor (vCPU halted/WFI time).
- The file-first rule from TMO maps directly: with no guest swap, reclaim only touches file cache and clean pages; adding **guest zram** lets cold anon (idle language servers, the agent harness) be compressed, at the cost of guest CPU on swap-in. zram inside the guest keeps the policy next to PSI and refault data and makes freed pages visible to reporting; host-side compression/swap is the non-cooperative backstop and is the only thing that works against a guest that ignores the protocol. (No fetched source compares the two directly.)
- Order of operations at idle: proactive reclaim → `compact_memory` → reporting pass (order 9, then optionally lower order) → hypervisor releases frames. Skipping compaction leaves the multi-GiB fragmentation gap measured by HyperAlloc.
- Dirty cache is not reclaimable until written back; virtio-blk writeback latency bounds how fast a post-`npm install` cache can be shed. Lower `dirty_background_bytes` / `dirty_expire_centisecs` in the guest image shortens the window (inference; no measured number).
- If the rootfs is a shared read-only image, DAX/virtio-pmem-style mapping of host page cache would remove that cache from guest RAM entirely and share it across sandboxes (density win orthogonal to reclaim; not researched here).

### Gaps
- No public measurement of Senpai/DAMON_RECLAIM running *inside* VMs combined with free page reporting, nor of page-cache share in coding-agent sandboxes specifically (Tide gives savings but not a cache breakdown).
- zram-in-guest vs zswap-at-host for microVMs: no primary comparison found.
- DAMON overhead numbers in small guests not retrieved.

## 5. Usability safeguards: detecting pressure, give-back latency, anti-thrash policy

### Takeaway
The proven pattern is: reclaim only while a guest pressure signal is at (near) zero, back off within one control period, and make expansion immediate and unconditional. PSI is the right signal but is not carried by virtio-balloon stats, so it has to come from the guest agent (or a custom device); the v6.12 balloon stats (`ALLOC_STALL`, `DIRECT_RECLAIM`, `OOM_KILL`) are a usable agent-less fallback.

### Cited Findings
- Senpai's asymmetry is explicit: contraction is rate-limited (minutes), "adaptation to workload expansion ... is immediate"; threshold 0.1% `some` memory pressure; IO PSI must be monitored too because refaults can hurt via the storage device rather than fault latency. [F] — [TMO, ASPLOS'22](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)
- PSI `some` = share of time at least one task is stalled on memory; `full` = all non-idle tasks stalled; exported as `/proc/pressure/memory` and per-cgroup `memory.pressure` with 10/60/300 s averages plus a cumulative `total` counter. [F for the some/full definition] — [TMO, ASPLOS'22](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)
- PSI supports userspace triggers: write a threshold and window (500 ms to 10 s) to the pressure file and `poll()` for events, so an agent can be woken within the window when stall time exceeds the threshold. [R] — [kernel docs: PSI](https://docs.kernel.org/accounting/psi.html)
- Balloon-stat pressure proxies available since guest Linux v6.12: `ALLOC_STALL`, `DIRECT_SCAN`, `DIRECT_RECLAIM` (a process stalled reclaiming for itself), `ASYNC_*` (kswapd), `OOM_KILL`. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)
- Free page reporting self-suspends when zone free memory is below `low_wmark + (capacity << order)`. [F] — [mm/page_reporting.c](https://github.com/torvalds/linux/blob/master/mm/page_reporting.c)
- Give-back latency numbers: reported/unplugged memory returns at fault-in speed, about 4 GiB/s via QEMU/KVM (vs 17 GiB/s for mapped memory); 4 KiB balloon deflate 2.3 GiB/s before faults; virtio-mem plug 35-45 ms per operation (Squeezy) and 102 GiB/s protocol-only (HyperAlloc); HyperAlloc return is 229 ns per 2 MiB frame (protocol only). [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf); [Squeezy](https://arxiv.org/html/2411.12893v2)
- Dynamically resized VMs are not free for the workload: Squeezy reports cold-start execution on a dynamically resized VM 3-35% slower than on a static VM, and one benchmark (BFS) 15% overhead during scale-up. [F] — [Squeezy](https://arxiv.org/html/2411.12893v2)
- Documented failure modes under aggressive reclaim: virtio-mem auto-resize too slow, causing guest OOMs (HyperAlloc experiment); virtio-mem timeouts and partial reclaim under pressure, plus more than 2x slowdown of co-located work (Squeezy); balloon inflate stall loops burning CPU and `deflate_on_oom` not covering kernel allocations (Firecracker); VMA-limit panic with fragmented discards on file-backed memory (Firecracker); a ChromeOS policy needing a learned "critical margin" because guests start killing apps below it. [F] — sources as cited in sections 1-3
- Hyper-V's shipped safety margin: 20% buffer above committed memory; alarm above 85% pressure. [S] — [Hyper-V performance: memory](https://learn.microsoft.com/en-us/archive/blogs/neales/hyper-v-performance-memory)
- Tide's argument specific to agents: balloon and virtio-mem "require a safe capacity target, which does not exist for bursty agent workloads"; tool memory spikes are only known at run time. [F] — [Tide, arXiv 2609.40082](https://arxiv.org/abs/2609.40082)

### Inferences (recommended policy)
- **Never shrink guest-visible capacity as the primary mechanism.** Keep the guest's MemTotal at its entitlement and reclaim *backing* (reported-free pages + evicted cache). Then a burst never needs a host round-trip to start: allocations succeed from the guest free list and fault in frames. This removes the "surprise OOM" class caused by a balloon/unplug that has not been undone in time. The host-side risk moves to frame-pool exhaustion, handled by admission control plus a backstop (below).
- **Host frame-pool headroom is the real latency guarantee.** At about 4 GiB/s fault-in, a compile that grows by 2 GiB in a second is fine if frames are available; keep a pre-zeroed free pool sized for the P99 simultaneous burst across sandboxes, refilled by squeezing idle guests. Zeroing in the background removes zeroing from the fault path.
- **Control loop (per guest, agent-reported PSI every 1-2 s, plus PSI trigger for sub-second wake):**
  - State IDLE (vCPUs halted > N s, PSI some = 0): aggressive in-guest reclaim of cold file cache (age ≥ 30-60 s), then compaction, then reporting at order 9; after minutes idle, deeper pass (lower reporting order, zram for cold anon); after tens of minutes, snapshot-and-release (previous notes).
  - State ACTIVE: reclaim off or Senpai-gentle; reporting at order 9 only.
  - Any of {PSI some avg10 > ~0.1-1%, `ALLOC_STALL`/`DIRECT_RECLAIM` delta > 0, `OOM_KILL` delta > 0, PSI trigger}: stop all reclaim immediately, deflate any balloon, hysteresis hold-off (tens of seconds) before reclaiming again. Asymmetric gains (fast up, slow down) prevent thrash.
- **Thrash guard:** track refault/major-fault rate after each reclaim step (TMO's reason for the 6 s period). If a step produces refaults, raise that guest's protected floor (learned working-set estimate, like ChromeOS's learned critical margin). Agent workloads are phased (idle → tool → idle), so remember the last burst's peak cache use and do not evict toolchain/build caches younger than the typical inter-tool gap.
- **Backstops for overcommit failure:** (1) balloon squeeze of the idlest guests to a cache cap; (2) hypervisor-side compression/swap of idle guests' pages; (3) pause-to-snapshot of the longest-idle sandboxes; (4) only then refuse/queue new sandboxes. An in-guest OOM kill should be treated as a platform incident and counted (`S_OOM_KILL`).
- Guest sysctls that reduce stall risk with reclaimed backing (inference, standard practice, not measured here): modest `vm.min_free_kbytes`/`watermark_scale_factor` increase so kswapd starts before direct reclaim; `vm.overcommit_memory` left at 0; no reliance on `deflate_on_oom` for correctness.

### Gaps
- No published incident reports or benchmarks from agent-sandbox operators (E2B, Modal, Daytona, etc.) on balloon/reporting-induced stalls or OOMs were found this session.
- Frame fault-in rate for a purpose-built type-1 hypervisor (vs the 4 GiB/s QEMU number) is unknown; needs measurement.
- PSI over a virtio device: no existing spec feature; WSR series reports "under memory pressure" but its trigger details were not read.

## 6. Guest zeroing/init costs (init_on_free, page poisoning) and interaction with reporting and CoW sharing

### Takeaway
Reported/ballooned pages come back as zero pages, so guest-side sanitisation that zeroes on free is redundant work and guest-side init-on-alloc touches every page of a freshly faulted block; non-zero page poisoning is incompatible with reporting. For density, build the guest kernel without poisoning, with `init_on_free=0`, and let the hypervisor's zero-on-fault provide the hygiene.

### Cited Findings
- The virtio-balloon driver negotiates `VIRTIO_BALLOON_F_PAGE_POISON` and writes a `poison_val` config field; it starts with 0 "representing general init" (the `init_on_free` case) and uses the `PAGE_POISON` byte pattern when page poisoning is enabled; the feature bit is cleared when neither `init_on_free` nor sanity-checked poisoning is in use. This exists so the host knows what content the guest expects in freed pages, for both hinting and reporting. [F for the driver code; S for the patch rationale] — [virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c); [Duyck patch](https://lore.kernel.org/kvm/20200211224646.29318.695.stgit@localhost.localdomain/)
- QEMU ignores free page reports when PAGE_POISON is negotiated with a non-zero poison value (discarding would return zeros where the guest expects the pattern); with `init_on_free` (poison value 0) reporting still works because discarded pages read as zero. [R] — [QEMU hw/virtio/virtio-balloon.c](https://gitlab.com/qemu-project/qemu/-/blob/master/hw/virtio/virtio-balloon.c)
- Discarded ranges read as zero until rewritten; on restored snapshots Firecracker replaces private file mappings with anonymous memory on discard so stale snapshot contents are not readable. [F] — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)
- Zeroing is a first-order cost in reclaim paths: 24% of virtio-mem unplug latency is "unnecessary zeroing of pages about to be unplugged". [F] — [Squeezy](https://arxiv.org/html/2411.12893v2)
- LLFree-based guests incurred about half as many EPT faults and TLB misses as buddy-allocator guests in the clang build because of contiguous allocation patterns. [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)

### Inferences
- `init_on_free=1`: guest zeroes on free, host discards, host zeroes again on re-fault: double zeroing, and the free-time zeroing *dirties* a page that might have been CoW-shared with a template, forcing a private copy just before it is given away. Disable it. `init_on_alloc=1` (a common distro default) zeroes at allocation: harmless for correctness but it writes the whole page, so each reused reported page costs fault + host zero + guest zero; with host zero-on-fault guaranteed, a guest patch/paravirt hint ("page known zero") could skip the second zeroing. No fetched number for this saving.
- CoW/snapshot interaction (extends the previous notes): for a forked guest, a reported page whose frame is still shared with the template must become a *zero* mapping, not revert to the template's content; discard therefore records "hole" state in the per-VM overlay. Freed-and-reused memory steadily diverges a clone from its template, so reporting does not restore sharing; only content-based dedup (KSM-style) or zero-page detection would, at CPU cost and with side-channel concerns.
- Diff snapshots benefit: reported holes need not be saved; an idle-time reporting pass before snapshot shrinks the image (CodeSandbox's 300-400 MB touched of 4 GiB is the scale of win; previous notes).
- Balloon/hinting-held pages are guest-allocated and unmovable, and block compaction; reporting leaves pages free. Another reason to prefer reporting.

### Gaps
- No measured cost of `init_on_alloc`/`init_on_free` in microVM guests with reporting was found.
- QEMU's exact poison handling was recalled, not re-read.

## 7. ARM64 specifics

### Takeaway
With 4K guest pages arm64 behaves like x86-64 (2 MiB pageblocks, 2 MiB virtio-mem blocks, order-9 reporting). With 64K pages the pageblock is 512 MiB, so the kernel special-cases reporting to order 5 (2 MiB) and virtio-mem block size balloons to 512 MiB; 4K guests are the density-friendly choice, and granularity must be designed against the *host* stage-2 page size as well.

### Cited Findings
- Mainline driver: "The default page reporting order is @pageblock_order, which corresponds to 512MB in size on ARM64 when 64KB base page size is used. The page reporting won't be triggered if the freeing page can't come up with a free area like that huge. So we specify the page reporting order to 5, corresponding to 2MB. It helps to avoid THP splitting if 4KB base page size is used by host." Applied under `CONFIG_ARM64 && CONFIG_ARM64_64K_PAGES`. The comment adds that ideally the order would follow the host's base page size, which the device does not currently communicate. [F] — [virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c)
- With 64K pages: `pageblock_order` 13 (512 MiB), `MAX_ORDER` 14; QEMU's virtio-mem defaults block size to THP size, 512 MiB in that configuration, and a 2020 qemu-devel thread questioned whether virtio-mem was worthwhile there. (2020-2021 sources; dated.) [S] — [Gavin Shan patch](https://lore.kernel.org/lkml/20210625042150.46964-5-gshan@redhat.com/); [qemu-devel thread](https://lists.gnu.org/archive/html/qemu-devel/2020-11/msg06204.html)
- virtio-mem guest support on arm64 since Linux 5.18; hot(un)plug granularity 2 MiB on aarch64 (4K pages) since 5.19; Firecracker requires aarch64 guest kernel ≥ 5.18 and, on hosts with pages larger than 32 KiB, slot sizes that are multiples of 64 host pages (4 MiB with 64 KiB pages). [F] — [virtio-mem user guide](https://virtio-mem.gitlab.io/user-guide/user-guide-linux.html); [Firecracker memory-hotplug.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/memory-hotplug.md)
- The classic balloon protocol counts in 4 KiB units regardless of guest page size (`VIRTIO_BALLOON_PFN_SHIFT`; one guest page = `PAGE_SIZE >> 12` balloon PFNs), so a 64K guest inflates in 64 KiB steps (16 PFNs per page). [F] — [virtio_balloon.c](https://github.com/torvalds/linux/blob/master/drivers/virtio/virtio_balloon.c)

### Inferences
- Granularity table (guest page / natural huge block): 4K → 2 MiB (order 9); 16K → 32 MiB PMD block (order 11); 64K → 512 MiB (order 13). For 16K guests the default reporting order (pageblock) would be 32 MiB unless overridden; set `page_reporting.page_reporting_order` explicitly (e.g. order 7 = 2 MiB at 16K). Only the 64K case is special-cased in the driver (this follows from the code above; 16K behaviour not directly verified).
- A hypervisor can only release whole stage-2 granules: a 4K guest on a 16K/64K-granule stage-2 cannot return less than 16/64 KiB; mixed sizes waste memory. Simplest: 4K stage-2 granule with 2 MiB block mappings and 4K guests on both architectures, giving one code path and identical tuning.
- Larger guest pages inflate page-cache footprint for small files (source trees, `node_modules`): a 1 KiB file costs 64 KiB of cache on a 64K kernel. For dev sandboxes dominated by many small files, 4K guests are materially denser irrespective of reclaim (inference; no measured number retrieved).
- Stage-2 unmap on arm64 needs break-before-make and TLBI broadcast; batch reclaim at 2 MiB to keep TLBI cost down (design inference).

### Gaps
- Current (2025-2026) arm64 defaults for pageblock order with `CONFIG_PAGE_BLOCK_ORDER`/contpte/mTHP were not checked; recent kernels allow configuring pageblock order independently, which could change the 64K numbers.
- No measurements of reporting/balloon performance on arm64 found.

## 8. What a purpose-built paravirtual memory interface could look like (research results and measured gains)

### Takeaway
Three recent lines of work bound the opportunity when both sides are controlled: sharing allocator state with the hypervisor (HyperAlloc: 362x faster shrink than balloon, 17% lower footprint than reporting, 1.9 GiB vs 8 GiB residual after a build); making hot-unplug lifetime-aware (Squeezy: 2 GiB in 127 ms); and letting the agent harness declare memory phases (Tide: 34-45% less backing memory than Firecracker + reporting on coding-agent trajectories). All three attack the same root cause: the buddy allocator mixes lifetimes inside 2 MiB blocks.

### Cited Findings
- **HyperAlloc (EuroSys'25, Linux 6.1 + QEMU 8.2 prototype)**. Design: guest uses the LLFree lock-free allocator whose per-frame/per-2 MiB state lives in memory shared with the hypervisor; the hypervisor reclaims free huge frames by flipping bits directly (no guest driver work) and scans for free-but-installed frames every 5 s ("soft" automatic reclamation); the guest allocator prefers non-evicted frames; re-use of an evicted frame issues an explicit *install hypercall at allocation time* (about 6% slower than an EPT fault in their QEMU path, but DMA-safe); a hard limit is separate from the soft one; if free memory is insufficient for a hard shrink the guest is asked to purge caches. Results: shrink 344.8 GiB/s touched (4.92 TiB/s untouched; 388 ns per untouched huge page), return 229 ns per huge page (84x virtio-mem, 26x balloon-huge); "no measurable impact" on STREAM/FTQ; clang footprint −17% vs reporting at 0.51% CPU overhead; post-build floor 1.9 GiB vs 8 GiB; Blender idle gaps −49% to −60% vs reporting (300 → 234 GiB·min overall); multi-VM numbers in section 2. Limits: requires replacing the guest page allocator; cannot grow beyond initial size (authors suggest large guest-physical space with a low hard limit, or hotplug); operates on 2 MiB units; does not address page cache (named as future work). [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf); code: [hyperalloc-linux](https://github.com/luhsra/hyperalloc-linux), [llfree-rs](https://github.com/luhsra/llfree-rs)
- LLFree side-benefit: per-type (movable/unmovable/huge) reservations of 16 MiB "trees" reduce huge-page fragmentation without active compaction; a few long-lived allocations such as page cache were observed to drive huge-frame fragmentation under the default policy. [F] — [HyperAlloc](https://sra.uni-hannover.de/Publications/2025/hyperalloc-eurosys25/wrenger_25_eurosys.pdf)
- **Squeezy (EuroSys'26; earlier preprint name "HotMem"; Linux 6.6)**. Identifies "obliviousness of the OS memory manager to the hotplugged memory" as the unplug bottleneck; assigns hotplugged regions per function instance so that when the instance exits the region is empty: no migration, no zeroing. 2 GiB in 127 ms (about 16 GiB/s), 10.9x faster than virtio-mem, negligible CPU, 7x higher reclaim throughput under FaaS load, 42.5-45% lower GiB·s than virtio-mem / HarvestVM-style baselines, P99 about 1.1x at 70% host memory. [F] — [Squeezy](https://arxiv.org/html/2411.12893v2)
- **Tide (arXiv preprint, 30 Sep 2026; Wu, Liao, Gu)**. Claim: in agent microVMs the idle harness and short-lived tool processes share pages/huge pages, so frequency- or footprint-based reclaim picks wrong pages, settles on wrong capacity, or splits THPs. Design: the harness declares per-phase memory intent through a user-space "arena" API; a guest-kernel allocator groups an arena's exclusive allocations into huge-page-aligned extents; a hypervisor extension (in Firecracker) maps extents to host backing and applies the declared action (e.g. drop when the tool exits, page out while waiting on the model) without changing guest capacity. Results on six Terminal-Bench tasks × three harnesses (OpenCode / OpenClaude / Codex): total backing memory 45.3% / 41.0% / 34.2% lower than Firecracker + free page reporting; 46.8% / 39.3% / 32.9% lower than HyperAlloc (which stayed within about ±3% of the baseline on these workloads); harness time +5.1% / +1.1% / +1.9%; SkillsBench tasks within 1.7% of baseline. Caveats: one trajectory per task, HyperAlloc run on QEMU vs Tide on Firecracker, no experimental comparison with balloon/virtio-mem/host swap, no reclaim latency reported, not peer reviewed as of fetch. [F] — [Tide, arXiv 2609.40082](https://arxiv.org/abs/2609.40082)
- Cloud Hypervisor `pvmemcontrol` (previous notes) is a shipped example of a guest→host madvise-like hint channel. [F, earlier session] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- Upstream direction for the standard interface: extend free page reporting (pause/resume), not hinting. [F] — [LKML Feb 2026](https://lkml.iu.edu/hypermail/linux/kernel/2602.1/04796.html)

### Inferences (design sketch for this hypervisor)
Tiered by guest-kernel intrusiveness; each tier is useful alone.
- **Tier 0, stock kernel + config + agent (ship first):** virtio-balloon with `F_REPORTING`, `F_STATS_VQ`, `F_DEFLATE_ON_OOM` (balloon normally size 0); guest built with `CONFIG_PAGE_REPORTING`, `CONFIG_LRU_GEN`, `CONFIG_PSI`, `CONFIG_DAMON_RECLAIM`, `CONFIG_COMPACTION`, zram; `init_on_free=0`, no page poisoning; 4K pages on both architectures. Agent implements the section-5 loop (PSI report over the control channel, `memory.reclaim`/DAMON, `compact_memory`, runtime `page_reporting_order` switching). Expected result per HyperAlloc's baseline: about one third footprint reduction on build workloads from reporting alone, more once cache is evicted and memory compacted at idle, bounded by fragmentation.
- **Tier 1, small custom virtio/hypercall device (no core-mm patch):**
  - reporting control: pause/resume and order selection from the host (replaces agent writes; matches Hildenbrand's suggestion);
  - a pressure channel: PSI some/full + refault + OOM counters pushed on PSI trigger (sub-second), replacing polling of balloon stats;
  - batched range hypercalls ("discard these N extents") instead of a virtqueue kick per 32-entry scatterlist, cutting the order-0 transport overhead that cost 19% runtime in QEMU;
  - a "zeroed on return" guarantee flag so the guest can skip `init_on_alloc` zeroing for pages it knows were discarded.
- **Tier 2, guest mm patches:** (a) shared free-state bitmap at 2 MiB (and optionally 64 KiB) granularity that the hypervisor reads and claims directly, HyperAlloc-style, removing the reporting delay and driver CPU, with install-on-fault rather than install hypercall since VFIO passthrough is out of scope for virtio-only guests; (b) lifetime-segregated allocation so tool/process memory lands in dedicated 2 MiB extents freed wholesale at exit (Squeezy/Tide idea; a cgroup-per-tool-invocation keyed arena would not need harness changes); (c) page-cache placement in dedicated extents so cache eviction yields whole blocks, addressing the fragmentation HyperAlloc observed from long-lived cache pages.
- **Tier 3, harness-declared intent (Tide):** only if the platform controls the agent harness; largest reported gain for agent workloads but least mature evidence.
- The single most valuable property to engineer for is that reclaim yields whole 2 MiB blocks: it preserves stage-2 block mappings, makes release O(1) per 2 MiB, and makes clone/snapshot bookkeeping coarse. Buddy-allocator fragmentation, not protocol speed, is what separates 8 GiB from 1.9 GiB in the measured case.
- A hypervisor-visible page cache (Xen tmem "cleancache"-like, or host-shared DAX for read-only image layers) would turn guest cache into host-evictable memory without guest pressure; mainline removed the cleancache/frontswap hooks, so this is Tier 2+ work with no current upstream path (recalled; not verified this session).

### Gaps
- Not researched this session (no citable facts): Hyperupcalls, Xen tmem, "memory harvesting VMs" (HarvestVM appears only as a Squeezy baseline), FaaSMem, Medes, application-driven vertical scaling papers. Their measured gains are therefore not reported here rather than recalled imprecisely.
- No production deployment evidence for HyperAlloc, Squeezy or Tide; all are research prototypes on Linux 6.1/6.6 or Firecracker forks.
- LLFree maintenance burden on current kernels (6.12+) and arm64 support of the HyperAlloc prototype were not checked.
- Tide's full evaluation tables were summarised by the fetch tool, not read line by line; the arXiv listing should be re-checked before quoting its numbers in a final report.
