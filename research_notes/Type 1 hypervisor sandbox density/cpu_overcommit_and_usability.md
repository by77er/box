## 1. Idle guest cost: wakeup sources, tick/timer virtualization, halt polling, measured idle rates

### Takeaway
An idle Linux microVM is not free by default: a recent (Nov 2026) Firecracker measurement shows ~100 host vCPU wakeups/s and ~5.8 millicores per idle 2-vCPU guest, dominated by the *guest agent's own polling loops*, not the kernel; after fixing the agent it fell to ~14–26 wakeups/s and ~2.5 millicores. The remaining floor is RCU, workqueues, vsock/virtio kworkers and compaction; host-side halt polling can silently turn "idle" into "burning a core" and must be off (or per-VM) on density hosts.

### Cited Findings

**Measured idle cost (most relevant numbers found)**
- [F] Firecracker, guest kernel 6.12.111, 2 vCPU / 512 MiB, 25 idle units (`sleep`), `CONFIG_HZ=1000`, `NO_HZ_IDLE` on, `NO_HZ_FULL` off, clockevent `lapic-deadline`, plain HLT idle with no cpuidle driver/halt polling: host wakeups per unit = `fc_vcpu 0` 55.2/s + `fc_vcpu 1` 47.8/s + VMM main thread 1.66/s (+ API thread 0). — [tinylabscom/mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802) (single project's issue thread; case study, closed 2026-11-24)
- [F] Attribution of the ~102 wakeups/s in that guest: guest-agent exec loop polling its child every 25 ms = 43.0/s; agent orphan reaper (200 ms sweep) = 5.0/s; other agent threads 4.9/s; kernel `events` workqueue 2.0–5.5/s; `rcu_preempt` 4.0–5.2/s; kcompactd (proactive compaction) 1.9/s; ksoftirqd 1.7–2.2/s; vsock interrupts 3.6–3.8/s; serial 0.4/s; function-call IPIs 11.3/s; reschedule IPIs 3.0–3.3/s. The CPU hosting the exec loop took 91–99 local-timer interrupts/s. — [mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802)
- [F] After fixing only the guest agent (no kernel change): single unit 7.7 + 6.5 = 14.2 vCPU wakeups/s; at 25-unit density 8.38 + 6.30 vCPU wakeups/s, 26.1 total wakeups/s per unit (was 114.7), and **idle host CPU per unit 5.79 m → 2.54 m (millicores)**. Remaining sources: vsock kworker 5.3/s, `rcu_preempt` 4.9/s, exec loop 4.6/s, agent thread 3.1/s, `events` wq 2.5/s, kcompactd 2.0/s, ksoftirqd 1.9/s, telemetry 1.6/s, vsock IRQs 4.6/s. — [mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802)
- [F] Boot-parameter experiments in the same issue: `nohz=off` raised vCPU wakeups from ~102/s to **2042.6/s** (i.e. a periodic HZ=1000 tick on 2 vCPUs); `sysctl.vm.compaction_proactiveness=0 sysctl.vm.stat_interval=60 tsc=reliable` only moved 102 → 95.6/s (kcompactd 1.9 → 0). `CONFIG_HZ=100` and `rcu_nocbs` were not measured. — [mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802)
- [F] LightVM (SOSP'17, Xen; dated): idle CPU for 1,000 guests — noop unikernel "a fraction of a percentage point" above Docker; Tinyx (minimal Linux) "maximum utilization of about 1% when running 1,000 guests"; stock Debian VM "about 25% for 1,000 VMs" because of out-of-the-box services. Conclusion: VM CPU use is on par with containers only if the guest is trimmed. — [LightVM paper](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)
- [F] LightVM: boot times stay close to Docker up to ~750 VMs (250 per core on the test machine); beyond that they rise because "even an idle, minimal Linux distribution such as Tinyx runs occasional background tasks", whereas idle containers/unikernels do not. — [LightVM paper](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)
- [F] Firecracker NSDI'20 gives no idle-CPU number; it only states "negligible overhead on CPU" and thousands of microVMs per host. — [Firecracker NSDI'20](https://css.csail.mit.edu/6.566/2023/readings/firecracker.pdf)
- [S] Old anecdote (dated, VMware forum): switching a CentOS 5 guest to a tickless kernel dropped it from ~1000 timer wakeups/s to 20–30/s (powertop in guest), with most of the remainder from guest tools rather than the tick. — [VMware community thread](https://communities.vmware.com/t5/VMware-Fusion-Discussions/Lower-power-consumption-from-Linux-guest-VMware-Tools-sucking/td-p/607145)

**Tick and timer virtualization**
- [F] Paratick (ICPP'21): with periodic ticks, "the running vCPU is suspended whenever a tick interrupt arrives for a descheduled vCPU, even if the latter is idle"; the host cost scales with Σ(n_vCPU × f_tick), which is the dominant overhead in overcommitted hosts where most vCPUs are idle. — [Paratick paper](https://web.njit.edu/~dingxn/papers/paratick.pdf)
- [F] Paratick: a tickless (NO_HZ idle) x86 guest must reprogram the tick on each idle entry/exit; each is a `TSC_DEADLINE` MSR write, hence a VM exit. Exit count ≈ 2 × (active-tick term + (1−L)·n_vCPU·t / T_idle). Worked example at 250 Hz, 16 pCPUs, 10 s: an idle 16-vCPU VM = 40,000 exits with periodic ticks vs ~0 tickless; 4 idle VMs = 160,000 vs ~0; but a workload blocking 1000×/s = 40,000 (periodic) vs 60,000 (tickless). Tickless wins only while average idle period > (tick period ÷ vCPUs sharing a pCPU). — [Paratick paper](https://web.njit.edu/~dingxn/papers/paratick.pdf)
- [F] Paratick cites prior work that guests may spend 15% of CPU time processing VM exits for frequently blocking workloads; its paravirtual "virtual scheduler tick" (host injects ticks on VM entry; guest stops programming tick timers) cut VM exits by up to 80%, raised throughput by up to 125% and cut runtime by up to 25% vs mainline Linux/KVM. — [Paratick paper](https://web.njit.edu/~dingxn/papers/paratick.pdf)
- [S] 2026 LKML thread: guests *without a cpuidle driver* fall back to the default idle path that stops the tick on every brief idle, causing repeated clockevent reprogramming, each a VM exit; a patch proposes stopping the tick only when average idle time exceeds a tick. — [sched/idle patch thread, March 2026](https://ratatoskr.run/linux-pm/2026/03/3445510/t)
- [R] On Arm the EL1 virtual timer (CNTV_*) is programmed by the guest without trapping; only expiry costs an exit (physical IRQ to the hypervisor, re-injected as a virtual IRQ), and WFI is trapped via HCR_EL2.TWI so the hypervisor can block the vCPU. So the "2 exits per idle transition for timer programming" x86 cost described by Paratick does not have a direct Arm equivalent. — [KVM/ARM ISCA'16 paper, timer/WFI discussion](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)
- [R] On x86, KVM mitigates the TSC-deadline exit with an exit fastpath for `MSR_IA32_TSC_DEADLINE` writes and by backing the guest LAPIC timer with the VMX preemption timer. — [KVM x86 timer docs](https://docs.kernel.org/virt/kvm/x86/timekeeping.html)

**HLT/WFI exiting vs halt polling**
- [F] KVM host halt polling: after a vCPU halts, the host busy-polls for up to `halt_poll_ns` before scheduling out; helps only when the guest resumes within "a few micro-seconds". Defaults: `halt_poll_ns` = `KVM_HALT_POLL_NS_DEFAULT` (per-arch), `halt_poll_ns_grow`=2, `halt_poll_ns_grow_start`=10000 ns, `halt_poll_ns_shrink`=2. Interval grows when a wakeup arrives shortly after the poll window ended, shrinks when block time exceeded the global max. — [kernel.org halt-polling doc](https://docs.kernel.org/virt/kvm/halt-polling.html)
- [F] Explicit caveat: a large `halt_poll_ns` "can push CPU utilization to 100% on an otherwise idle machine"; if wakeup periods are shorter than the global max, the host polls for the *full* block time. Polling only happens when no other task is runnable on that pCPU (so it is not a DoS vector, and it self-limits when the host is busy). `KVM_CAP_HALT_POLL` allows a per-VM override. — [kernel.org halt-polling doc](https://docs.kernel.org/virt/kvm/halt-polling.html)
- [R] Per-arch defaults: x86 `KVM_HALT_POLL_NS_DEFAULT` = 200,000 ns; arm64 = 500,000 ns. — [kernel source, arch/x86/include/asm/kvm_host.h](https://github.com/torvalds/linux/blob/master/arch/x86/include/asm/kvm_host.h)
- [F] Vendor blog (PandaStack; asserted, explicitly unmeasured — "I am deliberately not publishing a figure"): on a host of idle sandboxes, `fc_vcpu` threads showed "a steady, unmistakable slice of a core" from halt polling; Firecracker does not expose the per-VM `KVM_CAP_HALT_POLL` ceiling; recommendation is `halt_poll_ns=0` on density hosts and splitting the fleet into latency hosts (polling on) and density hosts (off). Suggested instrumentation: per-vCPU KVM stats `halt_successful_poll`, `halt_attempted_poll`, `halt_poll_success_ns`, `halt_poll_fail_ns`, `halt_wait_ns`. — [PandaStack halt-polling post](https://www.pandastack.ai/blog/firecracker-halt-polling-vcpu-idle-explained/)
- [F] Guest-side `cpuidle-haltpoll`: polls inside the guest before HLT (a successful poll avoids the exit entirely), tunables under `/sys/module/haltpoll/parameters/` (`guest_halt_poll_ns`), and writes a PV MSR so the host stops polling on its behalf; needs a CPUID PV hint or `force`. — [PandaStack halt-polling post](https://www.pandastack.ai/blog/firecracker-halt-polling-vcpu-idle-explained/) (secondary description; kernel doc: [cpuidle haltpoll](https://docs.kernel.org/virt/guest-halt-polling.html) [R])

**Per-VM host threads**
- [F] Firecracker's per-microVM thread set as observed: one `fc_vcpu N` thread per vCPU, one `firecracker` main/VMM thread, one `fc_api` thread; idle the VMM thread woke 1.66/s and the API thread 0/s. — [mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802)

### Inferences
- From the single measured case study: ~2.5 millicores per idle 2-vCPU guest ⇒ ~400 idle guests per core of pure idle burn, ~5.8 m ⇒ ~170 per core before agent tuning. LightVM's Tinyx figure (≈1% of the machine for 1,000 guests) is an order of magnitude better again and represents what a purpose-trimmed guest achieves; Debian-with-services (25% for 1,000) is the cautionary bound. The design target "idle guest ≤ ~1 millicore, ≤ ~10 wakeups/s per vCPU" looks reachable but needs the agent to be event-driven.
- The largest idle costs found are *self-inflicted by the in-guest agent* (25 ms poll loop = 43 of 102 wakeups/s). Since the platform controls the guest agent, the rule should be: no periodic timers in the agent at all (use pidfd/epoll/vsock blocking), and heartbeats driven from the host side (host can inspect vCPU state directly instead of asking the guest).
- Guest kernel knobs implied by the evidence (untested combination): `NO_HZ_IDLE` (never `nohz=off`), `HZ=100`/250, `vm.compaction_proactiveness=0`, long `vm.stat_interval`, no watchdogs (`nowatchdog`, `nosoftlockup`), `rcu_nocbs`/lazy RCU, a cpuidle driver or the "don't stop the tick for short idles" fix so short sleeps do not cost two timer exits, and one vCPU where possible (removes the 14/s function-call + reschedule IPIs seen above, which exist only because there is a second vCPU).
- For an own-scheduler type-1 hypervisor, halt polling should be a per-VM, budgeted mechanism: poll only for vCPUs that have recently been woken within microseconds (interactive burst in progress) and never for a guest that has been idle for > a few ms. A paravirtual tick (Paratick-style: hypervisor injects the tick on entry, guest never programs a tick timer) is cheap to do when both the hypervisor and guest kernel config are controlled, and removes the x86-only TSC-deadline exit pair on each idle transition. On Arm the guest-owned virtual timer already avoids the programming exits.
- An idle vCPU with no pending timer should be fully removed from run queues and timer wheels; cost then becomes a function of wakeup rate only. Timer coalescing/slack applied by the hypervisor to idle guests' timer deadlines (e.g. round to 10–50 ms when the guest has been idle for seconds) would batch the residual RCU/workqueue wakeups.

### Gaps
- No authoritative, peer-reviewed measurement of idle exit rate / host CPU per idle microVM on a modern kernel was found; the only quantitative modern source is one GitHub issue. Firecracker's own docs/paper give no number.
- No arm64-specific idle-guest measurements found (wakeups/s, WFI trap rate, timer IRQ cost on Graviton/Ampere).
- Effect of `CONFIG_HZ=100`, `rcu_nocbs`, `NO_HZ_FULL`, lazy RCU on idle guest exits: not measured in any source found.
- Intel "APIC timer virtualization" (hardware-assisted guest-owned LAPIC timer) — I recall patches circulating in 2025–2026 but could not verify status; not cited.
- The Paratick PDF did not yield measured idle-VM exits/s (its idle numbers are analytical).

## 2. vCPU overcommit in practice: published ratios and where latency degrades

### Takeaway
Published operating points span two regimes: general-purpose clouds oversubscribe CPU modestly (Azure Coach ≈ +26% VMs; Google ≈ +10–16% usable CPU; VMware folklore 1:1–3:1; AWS's new EKS Nitro Sandboxes caps at 5 vCPU per host vCPU), while serverless/agent-sandbox fleets with mostly idle guests go to ~10× in production (Lambda/Firecracker, tested >20×), supported by data that ~90% of agent sandboxes use ≤5% of requested CPU. Once CPU is oversubscribed, memory becomes the binding constraint.

### Cited Findings
- [F] Firecracker/Lambda: "We have tested memory and CPU oversubscription ratios of over 20x, and run in production with ratios as high as 10x, with no issues." (2020; dated) — [Firecracker NSDI'20, §6](https://css.csail.mit.edu/6.566/2023/readings/firecracker.pdf)
- [F] Firecracker/Lambda economics: idle slots consume memory only; "Memory makes up roughly 40% of the capital cost of typical modern server designs, so idle slots should cost 40% of the cost of busy slots", which "requires that resources (like CPU) are both soft-allocated and oversubscribed". Oversubscription is "a statistical bet": pick a compliance goal X (e.g. 99.99%) that a function gets all its resources with no contention; efficiency ∝ mean/Xth-percentile of use, which improves ≈ √N for N *uncorrelated* workloads — and workloads of the same application/customer/industry behave as one workload. — [Firecracker NSDI'20, §4.2](https://css.csail.mit.edu/6.566/2023/readings/firecracker.pdf)
- [F] DeepSeek DSec (arXiv Sept 2026; agent-sandbox fleet, containers + Firecracker microVMs): ~90% of sandboxes of both kinds use ≤5% of requested CPU on average; median lifetime 17.4 min (containers) / 15.5 min (microVMs), p99 > 3 h; ~3M sandboxes/day, ~380K peak concurrent, >5,000 creations/s on a ~160-node / 30K-core / ~250 TB DRAM scale unit; observed per-node peaks 1,048 containers and 524 microVMs, with stable operation seen at 3,200 containers or 800 microVMs per node (EPYC 9655 2×96c×2 SMT, 1.5 TB test nodes); memory, not CPU, is the limiter. The paper does not state a numeric CPU overcommit ratio. — [DSec paper](https://arxiv.org/html/2609.22978v1)
- [S] A secondary article headlines DSec as "50× overcommitted"; the primary paper text I read does not give that ratio — treat as unverified. — [secondary summary](https://ai.thesatyajit.com/articles/dsec-agent-sandbox)
- [F] AWS Nitro Sandboxes on EKS (launched Nov 2026; Firecracker microVM per pod): total sandbox vCPUs may not exceed **5× the node's vCPU count** (4-vCPU node → twenty 1-vCPU or five 4-vCPU sandboxes); the sandbox-count cap is halved on CPU-overcommit instance families; core scheduling prevents two sandboxes sharing SMT siblings "so roughly half the advertised vCPUs are usable" on SMT instances, Graviton unaffected; no snapshot/restore/live migration at launch. Comparison quoted: GKE microVM class reserves a fixed 250 mCPU + 130 MiB per pod. — [InfoQ, Nov 2026](https://www.infoq.com/news/2026/11/aws-nitro-sandboxes-eks/) (secondary reporting of AWS docs)
- [F] Azure Coach (ASPLOS'25; >1M VMs, two weeks of May 2024): most VMs average <50% CPU; per-VM CPU range (P95−P5) often reaches 60% whereas memory's is mostly within 30%; without oversubscription CPU is the packing bottleneck 69% of the time (memory 29%, network 2%); once CPU is oversubscribed the bottleneck shifts to memory (49%). — [Coach, arXiv 2501.11179](https://arxiv.org/html/2501.11179v2)
- [F] Coach design/results: each resource split into a guaranteed and an oversubscribed portion (example: 10-core/36 GB server hosting 14 cores/56 GB ≈ 30% oversubscription); P95 prediction over six 4-hour windows so the oversubscribed part is touched ≤ ~5% of the time; hosts up to ~26% more VMs; worst-case latency slowdown with fully oversubscribed VMs 2.35× (0.41→0.96 ms) vs ~10% under Coach's configuration; mitigations in order: local trimming/CPU-group readjustment, then evicting Spot VMs, then live migration as last resort; contention detection via EWMA (20 s horizon) + LSTM (5 min). — [Coach, arXiv 2501.11179](https://arxiv.org/html/2501.11179v2)
- [S] Google "Take it to the Limit" (EuroSys'21): Borg's default predictor overcommits CPU by a fixed ratio; machine-level peak predictors increased usable CPU capacity by 10–16% vs no overcommit in production. Autopilot (separate, limit-tuning) cut slack to 23% vs 46% for manually managed jobs. — [Google Research page](https://research.google/pubs/take-it-to-the-limit-peak-prediction-driven-resource-overcommitment-in-datacenters/), [Autopilot paper copy](https://homepages.dcc.ufmg.br/~cunha/teaching/20221/cloudcomp/readings/10-readings/rzadca20autopilot.pdf)
- [R] Resource Central (SOSP'17): a large fraction of Azure VMs have low CPU utilization (I recall ~60% of VMs averaging <20% CPU) and the paper used P95-utilization prediction to oversubscribe non-production VMs while keeping predicted physical utilization under a cap. Exact figures not re-verified. — [Resource Central paper](https://www.microsoft.com/en-us/research/publication/resource-central-understanding-predicting-workloads-improved-resource-management-large-cloud-platforms/)
- [S] VMware/Broadcom: CPU Ready baseline 5% per vCPU, 10% warning; co-stop healthy <1–3% per vCPU (thresholds differ between KB articles); high Ready + low co-stop ⇒ host-level vCPU overprovisioning, high Ready + high co-stop ⇒ oversized (too many vCPU) VMs. — [Broadcom KB 386180](https://knowledge.broadcom.com/external/article/386180), [Broadcom KB 421543](https://knowledge.broadcom.com/external/article/421543/esxi-host-cpu-usage-alarms-and-vm-perfor.html)
- [S] vCPU:pCPU "1:1 to 3:1 is no problem" is community/third-party guidance attributed to VMware; one white paper states there is "no universally agreed upon number". Could not confirm against an official VMware document. — [Demystifying CPU Ready](https://www.actualtechmedia.com/wp-content/uploads/2013/11/demystifying-cpu-ready.pdf), [Syneto help page](https://help.syneto.eu/en_US/vmware-virtual-machines/how-to-manage-virtual-cpus-in-vmware-esxi)
- [S] AWS burstable instances: instances earn credits below a per-vCPU baseline and spend them above it; t3.large baseline is 30% per vCPU; in Unlimited mode surplus credits are billed at a flat per-vCPU-hour rate if 24 h average exceeds baseline; T3/T3a/T4g launch in Unlimited mode and get no launch credits. — [AWS burstable key concepts](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-credits-baseline-concepts.html), [Unlimited mode](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-performance-instances-unlimited-mode-concepts.html)
- [R] Other T3 baselines per vCPU: nano 5%, micro 10%, small/medium 20%, large 30%, xlarge/2xlarge 40% (i.e. AWS's own bet is an implied 2.5×–20× CPU oversubscription for this class). — [AWS burstable key concepts](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-credits-baseline-concepts.html)
- [S] A self-hosted Firecracker platform's operator manual exposes soft/hard CPU overcommit ratios of 1.5×/2.0× as example config (configuration reference, not measurement). — [Compute operator manual](https://rashid2g.github.io/compute/)
- [F] Where latency degrades (controlled experiment): with two 32-vCPU VMs pinned on the same 32 cores (2:1), p95 tail latency of Tailbench workloads scaled "up to 20×" as vCPU latency (time a runnable vCPU waits on the host run queue) grew from 2 ms to 16 ms. — [vSched, EuroSys'25](https://cs.hofstra.edu/~jshan/papers/vsched.pdf)

### Inferences
- The right mental model is Firecracker's: ratio is not a constant but an outcome of (mean/peak of per-guest demand) and √N decorrelation. With DSec-like demand (90% of sandboxes ≤5% of request) the *mean-based* headroom is 20× or more; the practical ratio is set by burst correlation (e.g., one tenant fanning out 500 agents that all run `cargo build` at once) and by memory.
- A platform-level commitment in "vCPUs" should therefore be a burstable contract (guaranteed share + burst ceiling), like T-instances or Coach's guaranteed/oversubscribed split — not dedicated-core semantics. A defensible initial envelope from published points: 5× (AWS Nitro Sandboxes' hard cap for general pods) as conservative, 10× (Lambda production) as proven for mostly-idle workloads, >20× only with per-tenant decorrelation and working rebalancing.
- Correlated bursts from a single tenant are the main statistical hazard; placement should spread a tenant's sandboxes across hosts (anti-affinity) precisely because of the √N-uncorrelated assumption.

### Gaps
- No published overcommit ratios from E2B, Modal, Daytona, Morph, Cloudflare, Fly.io Sprites were found this session; their "vCPU" semantics (shared vs dedicated) remain undocumented here.
- No official VMware vCPU:pCPU number could be confirmed (only KB thresholds for Ready/co-stop).
- Resource Central numbers are recalled, not verified.
- Final ~20% of the DSec paper and Coach paper text was not read (fetch truncation).

## 3. Scheduler pathologies under overcommit and their fixes; 1-vCPU guests

### Takeaway
Multi-vCPU guests under overcommit suffer lock-holder/lock-waiter preemption, stalled IPIs/TLB shootdowns and "double scheduling"; paravirtual fixes help a lot (PV TLB flush: +78–132% on ebizzy at 2–3× overcommit) but are x86/KVM-centric and imperfect (PLE "helps in some workloads and hurts in others"). Each of these problems needs ≥2 vCPUs to exist, so few-vCPU guests sidestep them structurally.

### Cited Findings
- [F] vSched (EuroSys'25) taxonomy: a preempted vCPU is "inactive"; a task on it makes no progress; vCPU capacity is dynamic and asymmetric; run-queue latency inside the guest is extended by host-side vCPU latency. Known sub-problems: lock-holder preemption (LHP), lock-waiter preemption (LWP), blocked-waiter wakeup (BWW); the hypervisor mitigates LHP by preempting "excessively spinning vCPUs" (PLE). — [vSched](https://cs.hofstra.edu/~jshan/papers/vsched.pdf)
- [F] vSched: steal time is only observable while a vCPU is busy, so an idle low-capacity vCPU looks strong to the guest scheduler ("A low-capacity idle vCPU without steal time can appear to" be high capacity); vSched's guest-side probers + three policies (intra-VM harvesting = migrate a running task off a soon-to-be-inactive vCPU; biased vCPU selection = place small latency-sensitive tasks on low-latency vCPUs; relaxed work conservation = leave straggler vCPUs idle) gave up to 82% throughput gain (16-vCPU VM at 50% share per vCPU), 42% lower p95 on average, and in multi-tenant tests 1.6–2.3× lower latency and 18–69% more throughput vs CFS, at ~0.7% overhead. — [vSched](https://cs.hofstra.edu/~jshan/papers/vsched.pdf)
- [F] vSched: a task on a vCPU that is inactive 5 ms of every 10 ms is stalled 50% of the time by default; leaving low-capacity vCPUs idle (non-work-conserving) gave up to 43% / 30% higher throughput in their examples. — [vSched](https://cs.hofstra.edu/~jshan/papers/vsched.pdf)
- [S] PV TLB shootdown (KVM, Wanpeng Li, Dec 2017; dated): remote TLB flush does not wait for preempted vCPUs — KVM flushes when the vCPU next runs. ebizzy on 64-pCPU Xeon Gold 6142 with 64-vCPU VMs: +4% (1 VM), **+78% (2 VMs)**, **+132% (3 VMs)** (46799→48670, 23962→42691, 16152→37539). Same series adds the vCPU running/preempted state used for PV IPI decisions. — [PATCH v8 0/4 KVM: X86: Add Paravirt TLB Shootdown](https://lkml.iu.edu/hypermail/linux/kernel/1712.1/03584.html)
- [S] PLE is imprecise: "inaccurate at detecting spinlock spin operations, so its optimization helps some cases and hurts others"; a 2017 informal test (Linux 4.12, 28-CPU host, kernel compile at 200% overcommit) found plain test-and-set beat KVM PV spinlocks. — [KVM Paravirt Spinlocks Challenges and Status (blog)](https://clovertrail.github.io/jekyll/theme/2017/10/17/KVM-Paravirt-Spinlocks-Perf.html)
- [S] `vcpu_is_preempted(cpu)` (2016, KVM and Xen) lets spinlock/mutex optimistic-spin loops stop spinning on a preempted owner. — [commit 446f3dc8cc0a](https://mail-archive.com/linux-kernel@vger.kernel.org/msg1277496.html)
- [R] KVM x86 PV feature set relevant to overcommit: PV unhalt/kick for qspinlock (`KVM_FEATURE_PV_UNHALT`), steal time (`KVM_FEATURE_STEAL_TIME`), PV TLB flush (4.16), PV send-IPI (4.19), PV sched-yield (`KVM_HC_SCHED_YIELD`, 5.3), async PF; `KVM_HINTS_REALTIME` tells the guest vCPUs are never preempted and disables these. Defaults `ple_gap`=128, `ple_window`=4096 cycles. — [KVM CPUID PV features doc](https://docs.kernel.org/virt/kvm/x86/cpuid.html)
- [R] Arm64: PV steal time exists (since ~5.5, via SMCCC PV-time); WFE can be trapped (HCR_EL2.TWE) as the analogue of PLE and KVM/arm64 un-traps WFx when the pCPU has a single runnable task; I am not aware of upstream arm64 PV qspinlocks/`vcpu_is_preempted` (patch series existed). Verify. — [KVM arm64 PV time doc](https://docs.kernel.org/virt/kvm/arm/pvtime.html)
- [F] Paratick: in overcommit, tick interrupts for descheduled (even idle) vCPUs interrupt running vCPUs — a pathology that scales with total vCPU count rather than with load. — [Paratick](https://web.njit.edu/~dingxn/papers/paratick.pdf)
- [F] Empirical hint on vCPU-count cost in an idle guest: with 2 vCPUs the idle guest generated 11.3 function-call IPIs/s and ~3 reschedule IPIs/s — pure SMP housekeeping that vanishes with 1 vCPU. — [mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802)
- [S] UFO (cited by vSched) "provides VMs with the number of cores allocated, allowing the VM to optimize the number of online vCPUs for latency-critical tasks" — i.e. dynamically matching online vCPUs to actually-available cores is a published remedy. — [vSched related work](https://cs.hofstra.edu/~jshan/papers/vsched.pdf)

### Inferences
- LHP, LWP, BWW, stalled TLB shootdowns/IPIs, co-stop and capacity asymmetry all require ≥2 vCPUs. A 1-vCPU guest under overcommit just runs slower and with jitter — it cannot deadlock-spin against itself. This is the strongest (structural) argument for "default to 1–2 vCPUs and widen only during bursts".
- For multi-vCPU guests with a controlled guest kernel and an own hypervisor, the cheap, high-value PV set is: (a) per-vCPU "preempted" flag in a shared page (drives `vcpu_is_preempted`, PV TLB flush deferral and PV IPI skipping), (b) PV spinlock kick/wait or directed yield, (c) steal time, (d) a PV yield-to hint. On Arm these need to be designed in (not inherited from upstream arm64 Linux), which is feasible given the controlled guest kernel.
- A hypervisor-driven alternative to hot-add is "vCPU parking": expose N vCPUs but tell the guest (PV hint, as UFO/vSched do) how many are currently backed, so the guest scheduler stops using stragglers. This avoids CPU hotplug latency while delivering the 1-vCPU-like behaviour under contention. Gang/relaxed co-scheduling for the brief windows when a guest is truly parallel (build with `-jN`) is the complement.
- Interrupt delivery latency to a descheduled vCPU is bounded by the scheduler's wake-up preemption policy; for interactive sandboxes the dominant term is the host run-queue wait (the "vCPU latency" that produced the 20× p95 blow-up at 16 ms), not the injection mechanism.

### Gaps
- No measured data found on CPU hot-add/hot-remove latency and cost in microVMs (a PandaStack post on Firecracker vCPU hotplug exists but was not fetched). No quantitative evidence comparing "1 vCPU + hotplug" vs "N vCPUs + PV parking".
- No modern (2023–2026) benchmark of PV spinlocks/PLE on current hardware was found; the cited results are 2017.
- Timer skew/clock drift for long-descheduled vCPUs: not researched beyond Fly's note (section 6) that the clock can lag seconds after resume.
- arm64 PV-lock status is recalled only.

## 4. Scheduler design for many mostly-idle bursty VMs

### Takeaway
Published evidence favours: hard-prioritising latency-sensitive wakeups over batch (DSec: 45.2% latency inflation with no QoS vs ≤3.4% with a strict idle class), token-bucket burst budgets rather than flat caps, and treating SMT core-isolation as a real capacity tax (≈half the threads on AWS's sandbox product; up to 17–30% in early benchmarks) that SMT-less Arm and E-core x86 parts avoid entirely.

### Cited Findings
- [F] DSec two-class scheme: latency-sensitive (LS) vs best-effort (BE) sandboxes; BE runs under `SCHED_IDLE` and yields whenever LS is runnable; core scheduling (`PR_SCHED_CORE`) keeps BE off the SMT sibling of LS. Per-step latency inflation of an LS workload at 50% BE load: **45.2% with no QoS, ≤3.4% with `SCHED_IDLE` alone, 17.3% with `SCHED_IDLE` + core scheduling** (i.e. core scheduling made latency *worse* than SCHED_IDLE alone in their test). Residual interference: turbo frequency reduction, memory bandwidth, shared LLC. — [DSec paper](https://arxiv.org/html/2609.22978v1)
- [F] DSec placement: power-of-k-choices with per-edge final admission authority that can reject under critical pressure; stale placement estimates can overload nodes. — [DSec paper](https://arxiv.org/html/2609.22978v1)
- [F] Firecracker deliberately reuses the Linux scheduler (one thread per vCPU, cgroup cpu quotas per microVM) rather than a custom VM scheduler. — [Firecracker NSDI'20](https://css.csail.mit.edu/6.566/2023/readings/firecracker.pdf), [Firecracker design doc](https://github.com/firecracker-microvm/firecracker/blob/4a3e9bd76d9fc57a3538c1aeb7e5687de43a0efa/docs/design.md)
- [S] Xen Credit2: designed for "fairness, responsiveness and scalability", for "latency-sensitive workloads and very large systems"; run queues are configurable per core / socket / NUMA node / host (`credit2_runqueue=`), unlike Credit1's per-pCPU queues; a rate limit guarantees a vCPU a minimum run time before preemption (can be set to 0). — [Xen wiki: Credit2 Scheduler](https://wiki.xen.org/wiki/Credit2_Scheduler), [credit2 ratelimit patch](https://lore.kernel.org/all/578CC37A.7020701@citrix.com/T/)
- [R] Credit1 gives waking vCPUs a temporary BOOST priority and uses a 30 ms timeslice; Credit2 became Xen's default in 4.12 and replaces BOOST with credit-based preemption on wake (ratelimit default 1 ms). — [Xen wiki: Credit Scheduler](https://wiki.xenproject.org/wiki/Credit_Scheduler)
- [S] CFS bandwidth burst (`cpu.max.burst`): a group may accumulate unused quota up to the burst value and spend it later, bounded by unused slice per CPU; default 0 = no accumulation. — [kernel CFS Bandwidth Control doc](https://docs.kernel.org/scheduler/sched-bwc.html)
- [S] 2026 LKML proposal from Amazon (Fernand Sieber): expose `cpu.max.runtime` for explicit runtime-credit injection, allow burst > quota, and add a sched_ext callback when credits are injected — evidence AWS is moving toward credit/token-bucket CPU semantics in-kernel. Not confirmed merged. — [PATCH 0/2 sched/fair: expose cpu.max.runtime](https://lkml.iu.edu/2605.3/02004.html)
- [S] µslice (eBPF workshop 2026): a sched_ext scheduler doing CPU *pacing* for cgroups on fractional vCPU allocations with millisecond-scale workloads — releases a runnable task only when the cgroup's budget allows. — [µslice paper](https://cirrus.ece.ubc.ca/papers/ebpf26_uslice.pdf)
- [R] Linux: EEVDF replaced CFS's pick logic in 6.6 (lag-based fairness + per-task slice as latency hint; per-task custom slices via `sched_setattr` from ~6.12); sched_ext merged in 6.12. — [LWN: EEVDF scheduler](https://lwn.net/Articles/925371/), [kernel sched_ext doc](https://docs.kernel.org/scheduler/sched-ext.html)
- [S] Tableau (EuroSys'18): table-driven VM scheduler targeting high-density hosts with high throughput and predictable (bounded) scheduling latency. — [Tableau paper](https://people.mpi-sws.org/~bbb/papers/pdf/eurosys18.pdf)
- [F] vSched argues hypervisor-agnostic guest-side adaptation is necessary because stacked ("double") scheduling hides capacity/activity/topology from the guest. — [vSched](https://cs.hofstra.edu/~jshan/papers/vsched.pdf)
- [S] Core scheduling cost (all dated, 2019–2020 prototype kernels): Tim Chen's virtualization test ran at 96% of unmodified-kernel performance with core scheduling vs 87% for the alternative (SMT off); other tests showed 17–30% decline from forced idling; MySQL under overcommit: core scheduling up to −25% vs nosmt −15%; TPC-C in KVM: nosmt −49% vs core scheduling −25%; Linpack: nosmt −22% vs core scheduling ≈0%. Peter Zijlstra noted it was "far far worse" with many VM exits. The 5.14 doc warns it can be worse than SMT-off. — [LWN 820321](https://lwn.net/Articles/820321), [LWN 799454](https://lwn.net/Articles/799454/), [kernel core-scheduling doc](https://www.kernel.org/doc/html/v5.14/admin-guide/hw-vuln/core-scheduling.html), [LKML thread 2019](https://lkml.iu.edu/hypermail/linux/kernel/1904.3/03045.html)
- [F] AWS's 2026 sandbox product applies core scheduling so that two sandboxes never share SMT siblings, costing "roughly half the advertised vCPUs"; Graviton (one thread per core) is unaffected. — [InfoQ, Nov 2026](https://www.infoq.com/news/2026/11/aws-nitro-sandboxes-eks/)
- [R] seL4 MCS: scheduling contexts carry (budget, period) sporadic-server reservations, giving temporal isolation with capability-controlled CPU time; NOVA: priority-based round-robin scheduling contexts with donation/helping; BVT (Duda & Cheriton, SOSP'99): weighted fair sharing with a per-domain "warp" that lets latency-sensitive domains borrow against future allocation on wake-up. — [seL4 MCS tutorial](https://docs.sel4.systems/Tutorials/mcs.html), [NOVA EuroSys'10](https://hypervisor.org/eurosys2010.pdf), [BVT paper](https://dl.acm.org/doi/10.1145/319151.319169)

### Inferences
- Shape of a fit-for-purpose scheduler for this workload (synthesis, not from one source): (1) per-core run queues with wake-time placement on an idle core and work stealing — at 100–300 cores a global queue is a lock/cache disaster, and Credit2's choice of per-core/per-socket queues points the same way; (2) BVT-style wake-up warp / EEVDF-style short deadline for vCPUs that wake after a long sleep, so an exec or keystroke preempts a neighbour's compile within well under 1 ms — the vSched data says p95 scales with host run-queue wait, so the SLO should be on that wait; (3) token-bucket CPU budget per sandbox and per tenant (baseline share + burst bucket, T-instance/`cpu.max.burst` style), with interactive priority only while the bucket is non-empty so a compile cannot masquerade as interactive forever; (4) strict two-level priority (interactive/bursting-with-credit above batch/exhausted), matching DSec's 45% → 3.4% result; (5) hierarchical fairness tenant → sandbox → vCPU so one tenant's 500 sandboxes cannot out-vote others.
- A minimum-run-time ratelimit (Credit2's idea) matters at high density: with thousands of tiny wakeups, unconstrained wake-preemption thrashes caches; ~0.5–1 ms min-run plus a hard cap on wake latency is the usual compromise.
- SMT: DSec's own data shows core scheduling can cost more latency than it protects, and AWS's product loses half its threads. For a new design the cleaner options are (a) SMT-less hardware (Arm servers; Intel E-core Xeons) where the issue disappears, or (b) on SMT x86, schedule whole cores per VM/tenant inside the microhypervisor (it owns the scheduler, so core-granularity trust-domain pairing can be built in instead of bolted on), accepting that sibling threads are only shared within a trust domain.
- NUMA/cache affinity: because guests sleep for seconds between bursts, their cache state is cold on wake anyway; soft affinity to last core/LLC is worth keeping only for wake-ups within a few ms. Memory-side NUMA locality (which node holds the guest's pages) matters more than core affinity for builds.

### Gaps
- No head-to-head published comparison of Credit2 vs CFS/EEVDF vs sched_ext for thousands of mostly-idle VMs was found. No sched_ext scheduler specifically for vCPU threads at production scale was identified (µslice is a workshop paper).
- No recent (post-2021) quantitative core-scheduling overhead study found; all numbers are prototype-era.
- No published data on run-queue structure scalability at 192–288 cores for VM schedulers.
- Tableau and seL4/NOVA/BVT details are snippet/recalled; their quantitative results were not retrieved.

## 5. Usability metrics and SLOs; noisy neighbours; admission, placement, rebalancing

### Takeaway
Operators' published thresholds are few: VMware's CPU Ready ≥5% (watch) / ≥10% (act) per vCPU, Firecracker's "all resources with no contention X=99.99% of the time" compliance goal, and Coach's "oversubscribed portion used ≤5% of the time". Research shows the metric that predicts interactive pain is host run-queue wait of a runnable vCPU (2 ms → 16 ms gave up to 20× p95).

### Cited Findings
- [S] VMware/Broadcom thresholds: CPU Ready 5% baseline, 10% warning (per vCPU); co-stop <1–3% healthy. — [Broadcom KB 386180](https://knowledge.broadcom.com/external/article/386180), [Broadcom KB 421543](https://knowledge.broadcom.com/external/article/421543/esxi-host-cpu-usage-alarms-and-vm-perfor.html)
- [F] Firecracker/Lambda frames the SLO as a compliance percentile: functions get all needed resources with no contention X% (e.g. 99.99%) of the time. — [Firecracker NSDI'20 §4.2](https://css.csail.mit.edu/6.566/2023/readings/firecracker.pdf)
- [F] Coach: oversubscribed resources touched at most ~5% of the time by construction (P95 prediction); simulated ~1% CPU contention; contention detected by EWMA (20 s) and LSTM (5 min) predictors; mitigation ladder = local CPU-group adjustment → evict low-priority → live-migrate (last resort). — [Coach](https://arxiv.org/html/2501.11179v2)
- [F] vSched: p95 of latency-sensitive workloads rises up to 20× as host-side vCPU latency goes 2 → 16 ms; guest can estimate average vCPU inactive period from steal-time jumps (e.g. 60 ms stolen over 5 preemptions ⇒ 12 ms average inactive period). — [vSched](https://cs.hofstra.edu/~jshan/papers/vsched.pdf)
- [F] DSec noisy-neighbour numbers: LS per-step latency +45.2% at 50% BE load with no controls, ≤3.4% with strict priority; BE load still costs via turbo/memory-bandwidth/LLC. Metrics DSec tracks: live sandboxes per node, lifetime distribution, CPU and memory usage normalised to request, disk-write IOPS, peak concurrency, per-step latency, host CPU/memory; no explicit SLOs are stated. — [DSec paper](https://arxiv.org/html/2609.22978v1)
- [F] DSec overflow policy: burst to cloud VMs when on-prem utilisation exceeds 80%; ~200 cloud VMs absorb ~30% of peak overflow. — [DSec paper](https://arxiv.org/html/2609.22978v1)
- [F] Reclaim has a CPU cost: virtio-pmem/DAX cut peak host memory 40.2% but raised peak CPU from 26.5% to 41.4% in DSec's test; DAMON + balloon free-page reporting cut time-integrated host memory 21.2%. — [DSec paper](https://arxiv.org/html/2609.22978v1)
- [F] Coach: memory contention can degrade performance up to 4.3× (≈1.3× with proactive mitigation), far worse than CPU contention's worst case — i.e. CPU overcommit degrades gracefully, memory overcommit does not. — [Coach](https://arxiv.org/html/2501.11179v2)
- [F] Suggested host-side measurement practice: use per-VM cgroup `usage_usec`/`cpu.stat` and KVM halt-poll counters rather than sampling. — [PandaStack interrupts post (via search summary)](https://www.pandastack.ai/blog/microvm-interrupts-irq-tail-latency-explained/) [S]
- [R] Linux PSI (`/proc/pressure/{cpu,memory,io}`, per-cgroup `*.pressure`) reports `some`/`full` stall percentages over 10/60/300 s windows and supports poll()-able triggers; usable inside the guest and per-VM on a Linux host. — [kernel PSI doc](https://docs.kernel.org/accounting/psi.html)

### Inferences
- Proposed metric set for this platform (author's synthesis; thresholds are starting points derived from the cited numbers, not operator-published SLOs):
  - **vCPU run-queue delay** (time runnable-but-not-running) per sandbox: p50/p99/max per 10 s; this is the hypervisor's own "CPU Ready". Alert at ≥5% of wall time over 1 min (VMware's line); interactive SLO p99 wake-to-run < 1–2 ms (vSched's knee starts at 2 ms).
  - **Steal %** exported to the guest so in-guest tooling/PSI is truthful.
  - **Exec round-trip probe**: synthetic `true` exec through the real control path per sandbox class per host, p50/p99 (captures vsock + agent + scheduler + page-in). This is the user-visible metric.
  - **Guest PSI** cpu/memory/io `some avg10`, collected by the agent only when woken for other reasons (never a periodic timer — see §1).
  - **Burst slowdown**: reference build benchmark slowdown vs uncontended (canary sandboxes), target e.g. ≤1.2–1.5× at p95.
  - **Host-level**: runnable vCPUs per core distribution, fraction of time any core has >k runnable vCPUs, compliance percentile à la Firecracker ("% of sandbox-seconds with zero run-queue delay").
- Admission/placement: use peak-predictive packing (Google's machine-level peak predictor, Coach's time-window P95) rather than a static ratio; power-of-k-choices with host-side final admission (DSec) tolerates stale views; tenant anti-affinity preserves decorrelation; keep a CPU headroom reserve per host sized to the largest single-sandbox burst (e.g. N cores for an N-vCPU build).
- Rebalancing: since a sandbox is idle most of the time, "snapshot while idle, restore elsewhere" is a near-free migration primitive (no pre-copy convergence problem); prefer it over live migration, and trigger it from sustained run-queue-delay on the source host.

### Gaps
- No sandbox operator has published explicit interactive SLO thresholds (exec latency p99, wake latency) that I could find. Thresholds above are inference.
- No microVM-specific noisy-neighbour study with CPU-only interference beyond DSec's single chess-app experiment was found.
- PSI thresholds used in production (e.g. Meta's oomd/senpai-type settings) were not researched this session.

## 6. Paused/frozen states and auto-pause/wake behaviour

### Takeaway
Published wake latencies: Fly.io resumes a suspended Firecracker Machine in "a few hundred ms" (community reports ~100–250 ms) vs ~2+ s cold start; E2B resumes in ~1 s but pausing costs ~4 s per GiB of RAM; vendor-reported raw Firecracker snapshot load is 49–80 ms. Idle-but-running is the only state with zero wake latency, so its CPU cost (§1) decides how aggressively to pause.

### Cited Findings
- [F] Fly.io suspend: Firecracker snapshot of full VM state (CPU registers, memory, open file handles); resume "a few hundred ms" vs cold start "around 2+ seconds for common apps"; eligibility: ≤2 GB RAM (larger discouraged because suspend takes longer), no swap, no schedule; clock can lag a few seconds after resume until NTP syncs; network peers may have closed connections (ECONNRESET etc.); falls back to cold start on new deploy, host migration, lost/corrupted snapshot, maintenance, or exceeding a suspension threshold; suspended Machines are billed like stopped (storage only) but "suspension lowers cost but does not free capacity in a region"; suspending many machines at once is not recommended. — [Fly.io suspend/resume docs](https://docs.fly.io/reference/suspend-resume)
- [S] Fly Proxy autostop/autostart: proxy resumes suspended Machines on incoming requests (`auto_stop_machines = "suspend"`, `auto_start_machines = true`); an excess-capacity loop runs every few minutes and stops at most one Machine per region per pass; a start arriving mid-suspend cancels the memory copy and resumes the existing Firecracker process; community-reported resume ≈250 ms, later ≈100 ms (2024, dated). — [Fly autostop/autostart docs](https://fly.io/docs/launch/autostop-autostart), [Fly community: autosuspend](https://community.fly.io/t/autosuspend-is-here-machine-suspension-is-enabled-everywhere/20942), [start from suspending state](https://community.fly.io/t/machines-can-now-start-from-the-suspending-state/26623)
- [F] E2B persistence: pausing takes ~4 s per 1 GiB RAM; resuming takes ~1 s; pause saves filesystem + memory (processes, variables); filesystem-only pause reboots on resume; paused sandboxes kept indefinitely; while paused, services are unreachable and clients are disconnected (must reconnect after resume); a busy node can refuse a pause with HTTP 503; if `envd` is unresponsive the pause proceeds but resume requires reboot. — [E2B persistence docs](https://docs.e2b.dev/sandbox/persistence.md)
- [S] E2B auto-pause/auto-resume: `onTimeout: "pause"` pauses instead of killing at timeout; auto-resume is opt-in and triggered by HTTP traffic and SDK operations; a resumed sandbox gets a 5-minute minimum timeout; if the node is still finishing the previous snapshot, pause is retried for up to ~2 minutes. — [E2B auto-resume docs](https://www.e2b.dev/docs/sandbox/auto-resume)
- [F] DSec hibernation: containers — `docker pause` then `memory.swap.max` + `memory.reclaim` to push memory to swap, resume with `MADV_WILLNEED` prefetch then unpause; microVMs — save memory + execution state to a snapshot, terminate the Firecracker process, restore into a new process on resume. No latencies reported. — [DSec paper](https://arxiv.org/html/2609.22978v1)
- [F] Vendor-asserted Firecracker snapshot figures (PandaStack): snapshot create p50 179 ms, p99 ≈203 ms; `/snapshot/load` 49–80 ms. — [PandaStack post](https://www.pandastack.ai/blog/firecracker-halt-polling-vcpu-idle-explained/) (vendor claim, methodology not given)
- [F] AWS Nitro Sandboxes (Nov 2026) launched *without* snapshot/restore or live migration. — [InfoQ](https://www.infoq.com/news/2026/11/aws-nitro-sandboxes-eks/)
- [F] LightVM (2017): checkpoint/migration of a small unikernel VM over a 1 Gbps/10 ms link takes ~150 ms; instantiating a ClickOS VM ~10 ms. — [LightVM paper](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)

### Inferences
- State ladder for a mostly-idle sandbox, with costs assembled from the above plus §1 (the per-state CPU numbers for (b)–(d) are inference):
  - (a) **Idle-but-running**: ~1–6 millicores and ~15–100 host wakeups/s per guest today (tunable lower); wake latency = scheduler wake latency (µs–ms). Holds full memory.
  - (b) **vCPUs paused, memory resident** (hypervisor stops scheduling the vCPUs and masks guest timers): zero CPU, zero timer/RCU noise; wake latency ≈ a vCPU kick (sub-ms) plus guest clock catch-up. In a type-1 design this is nearly free to implement and should be the default seconds-scale idle state — the hypervisor can enter it transparently when the guest has been in HLT/WFI with only housekeeping timers pending, and wake on virtio RX / exec request. Needs a paravirtual "you were paused" time adjustment (stolen/suspended time) so watchdogs, RCU stall detectors and TCP timers do not fire.
  - (c) **Memory swapped/compressed** (paused + reclaim): zero CPU at rest, but reclaim and fault-in cost CPU (DSec: memory-saving mechanisms raised peak CPU 26.5% → 41.4% in one test); wake latency tens to hundreds of ms depending on working set and prefetch.
  - (d) **Snapshot to disk, VMM gone**: zero CPU/RAM; published resume 100 ms–1 s (Fly, E2B), pause cost ~4 s/GiB (E2B) unless incremental/dirty-page-tracked.
- Wake-on-activity requires the platform, not the guest, to hold the network endpoint: a proxy (Fly Proxy) or the hypervisor's virtio-net backend must accept/queue the SYN or exec RPC and trigger resume. Outbound long-lived connections from the sandbox (e.g. an agent's streaming LLM call) are the hard case: pausing (b) keeps host-side sockets only if TCP is terminated outside the guest; otherwise treat "has in-flight outbound request" as non-idle. For AI-agent sandboxes the LLM round-trip is normally driven by the orchestrator outside the sandbox, which makes state (b) safe during inference waits.
- Because E2B-style full-memory pause costs seconds per GiB and Fly discourages mass suspends, deep pause should be rate-limited and scheduled (it is itself a CPU/IO burst); cheap state (b) first, then (c)/(d) after minutes.

### Gaps
- No published latency for "paused with memory resident" as a product state; no published numbers for swap-backed resume latency in microVM sandboxes.
- No data found for Modal, Daytona, Morph, CodeSandbox, Cloudflare, Fly Sprites pause/wake latencies this session (CodeSandbox has published memory-snapshot/clone work that I recall but did not verify).
- The value of Fly's "suspension threshold" is not documented.
- E2B does not state billing while paused in the fetched page.

## 7. Per-VM fixed CPU-side overheads at scale

### Takeaway
Demonstrated scale points are 8,000 unikernel VMs on a 64-core Xen host (LightVM, 2017) and "thousands" of Firecracker microVMs per host, with real fleets today running ~500–800 microVMs per 192-core node (DSec) — far below hardware tag-space limits on x86, but an 8-bit Arm VMID space (255 VMs) would be exceeded, making 16-bit VMIDs and a rollover-safe allocator mandatory.

### Cited Findings
- [F] LightVM: up to 8,000 VMs (ClickOS unikernels, 8 MB each) on a 64-core AMD machine; instantiation ~10 ms; required replacing XenStore (noxs) and the toolstack because control-plane costs grew with VM count. (2017; dated) — [LightVM paper](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)
- [F] Firecracker: <5 MB memory overhead per microVM, up to 150 microVMs created per second per host, thousands of microVMs per host; 1,000 microVMs booted with 50 concurrent launches with p99 boot 146 ms (pre-configured). — [Firecracker NSDI'20](https://css.csail.mit.edu/6.566/2023/readings/firecracker.pdf)
- [F] DSec production: per-node one-day peaks of 524 microVMs / 1,048 containers; stable at 800 microVMs or 3,200 containers per node; fleet creation rate >5,000/s. — [DSec paper](https://arxiv.org/html/2609.22978v1)
- [F] Per-microVM host threads in Firecracker: one per vCPU + VMM thread + API thread (see §1). — [mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802)
- [S] KVM/arm64 VMID allocator (2021+): modelled on the arm64 ASID allocator with generations; on rollover it broadcasts a TLB flush + I-cache invalidation over the inner-shareable domain (unlike ASIDs, which mark CPUs for lazy local flush) because VMID rollover is expected to be rare; a capability detects 16-bit VMID support; allocation after rollover requires at least one more VMID than CPUs. — [PATCH v4 kvm/arm: New VMID allocator based on asid](https://lore.kernel.org/all/Yef65ng6pQK5yZDa@arm.com/T/), [vmid.c](https://android-kvm.googlesource.com/linux/+/refs/heads/debug/arch/arm64/kvm/vmid.c)
- [R] Tag-space sizes: Arm VMID is 8-bit baseline, 16-bit with FEAT_VMID16 (Armv8.1+; all current server cores); Intel VPID is 16-bit (65,535 usable; KVM allocates one VPID per vCPU from a global bitmap and falls back to VPID 0 = flush on every entry when exhausted); AMD ASID count is reported by CPUID 0x8000000A EBX (64 on some pre-Zen parts, 32,768 on Zen-era parts) and KVM/SVM assigns ASIDs per pCPU with a generation counter, flushing on wrap. Verify against SDM/APM. — [KVM VMX/SVM source](https://github.com/torvalds/linux/tree/master/arch/x86/kvm), [Arm ARM (VMID16)](https://developer.arm.com/documentation/ddi0487/latest)
- [F] IPI-type overheads visible even in an idle 2-vCPU guest: 11.3 function-call IPIs/s and ~3 reschedule IPIs/s. — [mvm issue #5802](https://github.com/tinylabscom/mvm/issues/5802)
- [F] Paratick: periodic guest ticks scale host timer-interrupt load with total vCPU count (Σ n_vCPU × f_tick) regardless of activity. — [Paratick](https://web.njit.edu/~dingxn/papers/paratick.pdf)

### Inferences
- Tag-space arithmetic for the target design: 5,000 two-vCPU sandboxes on a host = 5,000 VMIDs on Arm (fits 16-bit; does not fit 8-bit) and 10,000 VPIDs on Intel if allocated per vCPU as KVM does (fits 16-bit). A microhypervisor should allocate tags lazily to *runnable* VMs with generation-based recycling (as arm64 KVM does), so tag space scales with concurrently active VMs, not resident ones; rollover broadcast flush cost then scales with burstiness, not density. Older AMD parts with tiny ASID spaces are irrelevant for new deployments (Zen has 32K) — recalled, verify.
- With mostly idle guests, per-VM fixed CPU cost is dominated by timers and wakeups (§1), not by thread count; the hypervisor should have O(1) per-idle-VM cost: no per-VM periodic host timer, no per-VM polling thread in the deprivileged VMM (event-driven VMM that is fully blocked when the guest is idle), and no global broadcast operations (TLB shootdowns across all cores, stop-machine) on per-VM lifecycle events — LightVM's lesson was that control-plane paths that are O(#VMs) per operation (XenStore) become the scaling limit before the data plane does.
- Interrupt routing: virtio-only guests need only a handful of interrupts per VM; with GICv3 LPIs/ITS or x86 posted interrupts the limit is hypervisor data structures, not hardware vectors, if injection is software-mediated for descheduled vCPUs. (No source; design reasoning.)

### Gaps
- No published measurements of VMID/VPID rollover frequency or flush cost at thousands of VMs per host.
- No published hard limits "seen by Firecracker at N thousand VMs" beyond the paper's "thousands"; KVM-side scaling limits (e.g. memslot/irq-routing/eventfd counts, mmu notifier costs) not researched.
- IPI broadcast cost at 192–288 cores with thousands of VMs: no data found.
- Tag-size statements are recalled, not verified this session.

## 8. Density-relevant hardware economics and the binding constraint

### Takeaway
Current sockets offer 192–288 SMT-less cores (Clearwater Forest 288, AmpereOne/AmpereOne M 192, Graviton4 96) or 192 cores/384 threads with SMT (EPYC 9965), with 8–12 DDR5 channels; multiple operator sources (Lambda, Azure Coach, DeepSeek DSec) agree that once CPU is oversubscribed, **memory is the binding resource** for mostly-idle workloads.

### Inferences
- Memory-per-core arithmetic (from the cited specs; inference): a 12-channel socket with 64–128 GB DIMMs (1DPC) gives 768 GB–1.5 TB. On 288 cores that is 2.7–5.3 GB/core; on 192 cores 4–8 GB/core. At 10× CPU overcommit with 2-vCPU sandboxes, a 192-core socket could schedule ~960 sandboxes, leaving only 0.8–1.6 GB *resident* per sandbox — so memory binds first unless idle sandboxes' resident sets are driven far below their configured size (balloon/free-page reporting, page-cache dedup via DAX/shared images, swap/compression, snapshot-out). This matches DSec's observed 524–800 microVMs per 1.5 TB node.
- Hence CPU-side design should spend CPU to save memory where it is cheap (reclaim work done on idle cores at low priority), but bound it: reclaim CPU must run in the batch class and count against the tenant, since DSec saw peak CPU rise ~15 points with pmem/DAX.
- SMT-less high-core-count parts (AmpereOne, Graviton, Clearwater/Sierra Forest) suit this workload: one schedulable unit per core removes the core-scheduling tax and cross-thread side-channel exposure, and many slower cores map well to many small bursty guests. On EPYC Turin Dense, 384 threads are only fully usable if SMT siblings are shared within a trust domain. Per-core speed still matters for build-time usability (single-threaded link steps), so the trade-off is not purely cores-per-socket.
- Disk is rarely binding on CPU grounds but image pull/snapshot IO is a burst source (DSec: 700 GB vs 1,600 GB of writes for lazy vs eager pulls in one 8,192-container burst).

### Gaps
- No verified vendor-primary spec pages were fetched for Graviton4/5, Axion, Cobalt 200 or Sierra Forest 6900E; core counts above are secondary/recalled. Max memory per socket and DIMM-per-channel configurations were not verified.
- No published $/core or $/GB comparisons (x86 vs Arm) for sandbox fleets were found; "memory is 40% of capex" is a 2020 statement and DDR5 pricing has since moved.
- No operator has published a breakdown of the binding resource specifically for *dev-sandbox* (build-heavy) workloads other than DSec's agent-training workload, which may be lighter on CPU than interactive coding agents running large builds.
