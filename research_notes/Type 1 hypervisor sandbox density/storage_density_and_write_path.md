# Storage design for maximum density and optimized disk writes in a VM-based agent-sandbox platform

Scope: block/file storage stack for a type-1 microhypervisor (x86-64 + ARM64) with per-VM deprivileged VMM, a Linux driver/storage VM owning NVMe, and virtio-only Linux guests. Goes deeper than the "Storage" section of `Type 1 hypervisor for agent sandboxes/device_model_boot_snapshots.md` (which already established: every microVM platform gives the guest a plain virtio-blk root and does CoW below it; nobody uses virtio-fs for a snapshot-capable root).

Research date: 2026-11-26. Source labels on every finding:
- **[F]** = page or paper fetched and read this session.
- **[S]** = search-result snippet or secondary summary only (not opened, or numbers only visible in a chart).
- **[R]** = recalled from training knowledge; the link is where it should be verifiable, but it was not re-read.

Dated items are marked with their year. My own reasoning is confined to the "Inferences" subsections.

## 1. CoW block layer options and their write-path costs

### Takeaway
No fetched source gives a clean same-hardware comparison of first-write (allocate/CoW) cost across qcow2, dm-thin, reflink files, zvols, SPDK lvols and ublk backends; the numbers that exist are per-technology and mostly dated. What the sources do agree on is the shape of the cost: first-write to a shared chunk costs a read of the parent plus a write of the whole CoW unit plus a metadata update, so the CoW unit size (4K bitmap ... 16 MiB chunk) dominates amplification, and the 2025-2026 sandbox platforms (DigitalOcean, Modal, Cortex, E2B, BuildBuddy, Cognition) have all converged on a custom userspace "immutable chunked base + per-VM sparse overlay + dirty bitmap/manifest" layer rather than qcow2/dm-thin/ZFS.

### Cited Findings

**qcow2**
- QEMU always writes whole clusters, so a small write to an unallocated cluster with a backing file forces a read of the rest of the cluster from the backing file and a full-cluster write. Subcluster allocation (`extended_l2=on`, QEMU 5.2+) splits each cluster into 32 subclusters and avoids the copy when subcluster size equals the guest FS block size; the author reports "up to 10-15 times more I/O operations per second for the same cluster size" for 4 KB random writes to an empty 40 GB image with a fully populated backing file. No benefit without a backing file or on already-allocated clusters. Metadata: "sixteen times less metadata per unit of allocation". (2020) [F] — [Igalia: Subcluster allocation for qcow2 images](https://blogs.igalia.com/berto/2020/12/03/subcluster-allocation-for-qcow2-images/)
- User-reported in the comments of that post (not the author's data): fio 4k randwrite on a 1 TB image with a backing file went from about 4,000 to 22,000 IOPS with extended L2; without a backing file, default-L2-cache runs were only about 2,700 IOPS (64k clusters) and 1,500 IOPS (128k + extended_l2) until the L2 cache was enlarged to hold all metadata (128 MB), at which point both reached about 22,000 IOPS. (2020, single user report) [F] — [Igalia blog comments](https://blogs.igalia.com/berto/2020/12/03/subcluster-allocation-for-qcow2-images/)
- L2 cache sizing: `disk_size = l2_cache_size * cluster_size / 8` (1 MB of L2 cache covers 8 GB at 64 KB clusters); with extended L2 entries the divisor is 16 (twice the metadata). Default maximum L2 cache is 32 MB on Linux; `cache-clean-interval` default 600 s; refcount blocks are only touched on allocation and internal snapshots. [F] — [QEMU docs/qcow2-cache.txt](https://raw.githubusercontent.com/qemu/qemu/master/docs/qcow2-cache.txt)
- Cognition (Devin) rejected qcow2 because their hypervisor supports only raw images, and found `qemu-img convert` slow on large files and not metadata-only. (2025) [F] — [Cognition: Blockdiff](https://cognition.com/blog/blockdiff)

**dm-thin (LVM thin)**
- Data block size must be between 64 KiB and 1 GiB, a multiple of 64 KiB, fixed at pool creation; kernel doc suggests 64 KiB "for heavy snapshotting", 512 KiB for plain thin provisioning, and much larger if zeroing is skipped. Metadata device size is `48 * data_dev_size / data_block_size` bytes (more if sharing is heavy), maximum useful 16 GiB. [F] — [kernel.org: thin-provisioning](https://docs.kernel.org/admin-guide/device-mapper/thin-provisioning.html)
- Snapshots are thin devices sharing blocks; recursion depth is arbitrary and "this new implementation uses a single data structure to avoid this degradation with depth" (unlike old dm-snapshot whose chained lookups were O(depth)); "fragmentation may still be an issue". Creating a snapshot of an active origin requires suspending it first (not enforced by the kernel). [F] — [kernel.org: thin-provisioning](https://docs.kernel.org/admin-guide/device-mapper/thin-provisioning.html)
- Metadata is committed on every FLUSH or FUA bio, otherwise about once per second; the pool therefore behaves like a disk with a volatile write cache. Newly provisioned blocks are zeroed unless `skip_block_zeroing`. `ignore_discard` / `no_discard_passdown` control discards; `error_if_no_space` vs default queueing for 60 s (`no_space_timeout`). External read-only origin devices are supported (reads of unprovisioned areas pass through to the origin). [F] — [kernel.org: thin-provisioning](https://docs.kernel.org/admin-guide/device-mapper/thin-provisioning.html)
- Mailing-list measurements (old kernels, directional only): fully provisioned thin LV 177K random-write IOPS vs 416K on a thick LV (kernel 4.4, 2016); 4K random write about 132K thin vs 222K thick while 512k requests were equal (2017); with 64K chunks and 64K requests a snapshotted thin LV did 8,307 IOPS vs 9,381 unsnapshotted, and the poster concluded dm-thin is a poor fit for many small random writes plus frequent snapshots because of the 64K minimum chunk (2022). [S] — [dm-devel 2016: poor thin performance, relative to thick](https://listman.redhat.com/archives/dm-devel/2016-July/027359.html); [linux-lvm 2017](https://listman.redhat.com/archives/linux-lvm/2017-September/024285.html); [linux-lvm 2022](https://listman.redhat.com/archives/linux-lvm/2022-June/026211.html)
- Fly.io unpacks OCI layers into dm-thin snapshots for Firecracker root devices. [R, carried from earlier notes] — [Fly.io: Docker without Docker](https://fly.io/blog/docker-without-docker/)

**Reflink files (XFS/btrfs sparse raw + FICLONE)**
- `cp --reflink=always` of a 128 GB image on fast NVMe: 0.008 s vs 24.5 s (18.8 s sys) for a full copy. Cognition's production design is XFS-reflink on the hypervisor, ext4 in the guest, each VM disk a reflink copy of a base image; `blockdiff` reads FIEMAP extent maps (shared physical extents = identical data) to produce a diff file (`BDIFFv1` header + range list + data) without scanning data: about 200 ms to create a snapshot of a 20 GB disk vs about 6.5 s to read/write 20 GB; transfer about 2 GB/s; typical customer delta about 1 GB over a 15 GB OS image; EC2/EBS snapshots previously took 30+ minutes. The post acknowledges fragmentation into many extents but does not quantify it. (2025) [F] — [Cognition: Blockdiff](https://cognition.com/blog/blockdiff)
- XFS mitigates CoW fragmentation with the CoW extent size hint (`cowextsize`, default 32 blocks = 128K) so adjacent random CoW writes land in one extent; XFS developers flagged sparse-VM-image snapshotting as a fragmentation concern. No published overhead measurement found. [S] — [linux-xfs: cowextsize discussion](https://lore.kernel.org/all/20170110074524.GI14038@birch.djwong.org/T/); [linux-xfs: XFS reflink vs ThinLVM](https://lore.kernel.org/all/20200113180914.GI8247@magnolia/T/)
- CodeSandbox reported XFS fragmentation from random writes as a known bottleneck of file-level CoW (2022), and LXD documentation advises against VM images on btrfs because of random I/O on raw image files. [F earlier notes / S] — [CodeSandbox: how we clone a running VM in 2 seconds](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3); [LXD btrfs driver docs](https://documentation.ubuntu.com/lxd/latest/reference/storage_btrfs)
- E2B seals the per-sandbox CoW cache into a rootfs diff using reflink on pause. [F] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)

**ZFS zvols**
- Only forum-grade comparisons found: one 2018 test had qcow2-on-ZFS slightly ahead of a zvol on async 4K random writes (about 164 vs 139 MB/s); a Level1Techs NVMe test found qcow2 at 50-60% of zvol throughput at high queue depth. Treat as anecdote. [S] — [jrs-s.net: ZVOL vs QCOW2 with KVM (2018)](https://jrs-s.net/2018/03/13/zvol-vs-qcow2-with-kvm/); [Level1Techs forum](https://forum.level1techs.com/t/zvol-vs-file-as-vm-backing-huge-performance-difference-on-nvme-based-zpool/182074)
- Cognition did not benchmark ZFS send/recv but judged it would be slower end-to-end than blockdiff; ZFS inside the guest was rejected because it could only cover the home directory and exposed snapshot logic to the user. [F] — [Cognition: Blockdiff](https://cognition.com/blog/blockdiff)

**SPDK lvol + vhost-user-blk**
- Lvolstore cluster size defaults to 4 MiB; lvol block size is fixed at 4096. Thin lvols allocate a cluster on first write; a write to an unallocated cluster of a clone allocates a new cluster and copies the snapshot's cluster data before the write (full 4 MiB CoW at default). Snapshots are read-only; clones are thin; snapshot deletion merges cluster maps metadata-only when exactly one clone remains; "esnap clones" can use any external bdev as a read-only backing device; inflate/decouple-parent remove dependencies. No performance figures in the doc. [F] — [SPDK: Logical Volumes](https://spdk.io/doc/logical_volumes.html)
- With one SPDK core and four guest I/O queues, vhost-user-blk reached about 1002K IOPS (null bdev) vs 984K for vfio-user NVMe; in-guest fio reached roughly 91% of physical NVMe for vhost-user-blk and 84% for vfio-user. (KVM Forum 2021) [S] — [KVM Forum 2021: High Performance NVMe Virtualization with SPDK and vfio-user](https://kvm-forum.qemu.org/2021/Changpeng%20Liu%26Ben%20Walker_High%20Performance%20NVMe%20Virtualization%20with%20SPDK%20and%20vfio-user.pdf)
- Ubicloud started on SPDK (custom build v23.09-ubi) and wrote an SPDK module (`bdev_ubi`) to get copy-on-write from a base image without btrfs; it now also maintains `ubiblk`, a Rust vhost-user-blk backend (with an experimental ublk frontend) that lazily copies 1 MiB "stripes" (default `2^11` sectors) from a base image, with a metadata file of one byte per stripe (fetched / written / has-source flags), optional copy-on-read, background autofetch, a remote stripe server, and AES-XTS. No benchmarks published on the README. [S for SPDK docs/blog, F for ubiblk] — [Ubicloud block storage docs](https://www.mintlify.com/ubicloud/ubicloud/storage/block-storage); [ubicloud/ubiblk](https://github.com/ubicloud/ubiblk)

**ublk (userspace block driver over io_uring)**
- ublk exposes `/dev/ublkbN` as a blk-mq device; requests are forwarded and completed via io_uring passthrough commands (`UBLK_U_IO_FETCH_REQ`, `UBLK_IO_COMMIT_AND_FETCH_REQ`), with per-queue (or per-I/O with `UBLK_F_PER_IO_DAEMON`) server threads. Default path copies WRITE data into the server buffer. Zero-copy: `UBLK_F_SUPPORT_ZERO_COPY` (io_uring fixed buffers via `UBLK_IO_REGISTER_IO_BUF`), `UBLK_F_AUTO_BUF_REG` (automatic register/unregister), and `UBLK_F_SHMEM_ZC` (shared physical pages, O_DIRECT and contiguous data only). `UBLK_F_BATCH_IO` adds multishot per-queue batch fetch/commit. Recovery flags (`UBLK_F_USER_RECOVERY`, `_REISSUE`, `_FAIL_IO`) let a crashed server be replaced. "ublk server implementing zero copy or user copy has to be CAP_SYS_ADMIN and be trusted." (docs as of kernel 7.0 era) [F] — [kernel.org: ublk](https://docs.kernel.org/block/ublk.html)
- Performance data points: `UBLK_F_AUTO_BUF_REG` improved IOPS by 50% over `UBLK_F_SUPPORT_ZERO_COPY` in the author's test VM; the `UBLK_F_BATCH_IO` patchset (Nov 2025, null target, 16 fio jobs) reported 37.77M vs 42.40M IOPS with page copy (+12%) and 42.83M vs 44.43M with auto zero-copy (+3.7%); a single ublk queue thread caps at roughly 450K 4k-IOPS for a copy-based loop target; early zero-copy prototypes showed about 5x IOPS at 64k/512k block sizes on ublk-null; ublk-nbd was about 40% faster than the kernel nbd driver in one test (2023). [S] — [Linux commit 8ccebc19 (ublk selftests auto_zc)](https://tangled.org/tjh.dev/kernel/commit/8ccebc19ee3db03284504d340e5cd2de4141350b); [LKML: ublk UBLK_F_BATCH_IO V4](https://lkml.org/lkml/2025/11/21/97); [LWN 926376 comments](https://lwn.net/Articles/926376/); [ublk-nbd announcement](https://lkml.iu.edu/hypermail/linux/kernel/2301.3/02728.html)
- DigitalOcean's microVM platform (2026) uses a `microvm-ublk` daemon per execution: immutable base in content-addressed storage + host-local sparse delta file with one bitmap bit per 4 KiB block, exposed via ublk and attached to Firecracker as a file-backed drive. Host resource setup (sparse overlay + ublk device) has a 20 ms budget on a warm path targeting under 200 ms p50 end-to-end (budget, not measured per stage). [F] — [DigitalOcean: microVM architecture](https://www.digitalocean.com/blog/microvm-architecture)
- Vitastor reports its ublk frontend outperforms both NBD and VDUSE in 4K random tests even without zero copy. [S] — [Vitastor: UBLK](https://vitastor.io/en/docs/usage/ublk.html)

**NBD / FUSE-backed disks**
- E2B: in-process userspace NBD server per sandbox serving base + CoW cache; NBD netlink attach is serialized node-wide by the kernel (ioctl alternative parks one thread per device). [F] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- Cortex: custom userspace NBD server; disk split into fixed 16 MiB chunks addressed by SHA-256, per-sandbox manifest maps offsets to chunk hashes; first write to a base chunk makes a private dirty copy; "a session that dirties 20 chunks adds at most 320 MiB"; 128 GiB virtual disk; all-zero chunks skipped; host NVMe LRU cache in front of blob storage. (2026) [F] — [Cortex builders: Sandboxing agents, part 2](https://builders.cortex.io/blog/sandboxing-agents-part-2/)
- BuildBuddy: Firecracker disk file is a FUSE-backed virtual file (Go FUSE server) over content-hashed compressed chunks in a remote cache; a write copies the chunk to `<hash>.dirty`; only dirty chunks are uploaded at snapshot. Chunk size not stated. [F] — [BuildBuddy: fast runners at scale](https://www.buildbuddy.io/blog/fast-runners-at-scale)

**Log-structured virtual disks**
- LSVD (EuroSys'22): writes are logged to a local SSD write-cache journal and shipped to the object store as large batched objects (8 or 32 MB) whose names encode order; an in-memory extent map locates data; GC triggers when live-data ratio falls below 70%. A 16 KB client write generates 0.25 back-end disk I/Os vs 6 for Ceph RBD (24x); 50,000 client IOPS with back-end disks over 90% idle vs 12,000 IOPS for RBD; about 60K/50K IOPS for 4K/16K random writes on a device rated at 90K; up to 4x faster than bcache+RBD on sync-heavy (varmail) workloads; measured write amplification 1.046 (fileserver), 1.22 (varmail), 1.75 (oltp). Guarantees: all committed writes recovered after a client crash; prefix consistency if the local cache device is lost. Clones share an object-name prefix up to the clone point (O(1) fork), snapshots just pin a sequence number and defer GC deletion. [F] — [Hajkazemi et al., EuroSys'22 (LSVD)](https://rs3lab.github.io/assets/papers/2022/hajkazemi-aschenbrenner:lsvd.pdf)
- Fly.io shipped experimental LSVD "bottomless" volumes (NBD-era, 2023-2024) backed by S3/Tigris: "caching blocks while writing them to object storage ... continuously in snapshotted state". The original blog URL returned 404 when fetched; details here are from search snippets only. [S] — [Fly community: Bottomless S3-backed volumes](https://community.fly.io/t/bottomless-s3-backed-volumes/15648); [Fly infra log 2024-07-13](https://fly.io/infra-log/2024-07-13/)
- Fly Sprites (2026): 100 GB durable storage per Sprite rooted in S3-compatible object storage; "JuiceFS model" (immutable chunks in object store, metadata in SQLite made durable with Litestream), described as a "very hacked-up JuiceFS"; a sparse 100 GB NVMe volume acts as a dm-cache-style read-through cache and is not authoritative; checkpoint/restore "mostly shuffle metadata"; billing only for blocks written. [F] — [Fly.io: The Design & Implementation of Sprites](https://fly.io/blog/design-and-implementation/)
- Conflict/evolution: Fly's product page is quoted as saying Sprites present "an object storage bucket to the kernel as a real block device and runs ext4 on top, which is what makes checkpoints block-level snapshots", and community users report real restores taking 13-25 s and some restore failures ("failed to start overlay service tree"). The file-level JuiceFS description (design post) and the block-device description (product page) were not reconciled. [S] — [fly.io/sprites](https://fly.io/sprites.md); [Fly community: unrecoverable sprites after checkpoint restore](https://community.fly.io/t/unrecoverable-sprites-after-checkpoint-restore-failed-to-start-overlay-service-tree/27918)
- Elide: a side-project LSVD-inspired ublk block device with content-hash addressing over Tigris. No numbers. [F] — [Fly community: Elide](https://community.fly.io/t/elide-userspace-block-devices-lsvd-ublk-tigris/28256)
- AWS Lambda: flattened ext4 image split into fixed 512 KiB chunks, convergently encrypted, served by a local agent behind virtio-blk with a block overlay for writes (details in section 4). [F] — [Brooker et al., ATC'23](https://www.usenix.org/system/files/atc23-brooker.pdf)

**Modal ImageFS-blk (2026)**
- Host serves blocks over virtio-blk; the image is synthesized as a sparse ext4 (Modal writes ext4 inode/extent metadata itself and maps block ranges to lazily-fetched content-addressed file data); guest writes land in a sparse file with a dirty bitmap; CoW is block-granular ("worst-case overhead is one block") whereas OverlayFS copy-up over a FUSE lower "can cost gigabytes". [F] — [Modal: VM sandbox filesystem](https://modal.com/blog/vm-sandbox-filesystem)

### Inferences
- Ranking by fork cost and chain behaviour (reasoned from the mechanisms above, not measured): O(1)-fork with flat lookup regardless of chain depth = dm-thin (single shared btree), XFS reflink (shared extent refcounts), LSVD/manifest designs (fork = copy or reference a map). qcow2 backing chains and stacked sealed overlays (DigitalOcean, E2B header chains) have O(depth) lookup on miss unless periodically flattened/merged; DigitalOcean explicitly merges sealed overlays at publication and E2B resolves chains via `.header` files, which is the same remedy.
- First-write amplification is set by CoW granularity. For a 4 KiB guest write on a shared block: 4 KiB bitmap overlay (DigitalOcean, Modal) = 1x and no parent read if the write covers the block; qcow2 with 4K subclusters = 1x; dm-thin 64 KiB = 16x plus optional zeroing; ubiblk 1 MiB stripe = 256x; SPDK lvol 4 MiB = 1024x; Cortex 16 MiB = 4096x (their own "20 chunks = 320 MiB" example is exactly this). For agent sandboxes whose forks touch scattered small files (git objects, node_modules, sqlite pages), coarse chunks inflate both local disk and snapshot upload; fine local granularity with coarse (256K-1M) object-store packing is the better split.
- Metadata cost of fine granularity is small: a 100 GiB disk at 4 KiB granularity needs a 3.2 MiB presence bitmap per overlay layer (26.2M bits); a full 8-byte-per-block remap table would be 200 MiB, which is why bitmap + identity-mapped sparse file (offset in overlay == offset in disk) is the popular choice: the host filesystem's extent tree does the remapping and hole tracking for free. By the kernel formula dm-thin at 64 KiB needs about 75 MiB of metadata per 100 GiB mapped; qcow2 at 64 KiB needs 12.5 MiB of L2 per 100 GiB (and must be cached in RAM to avoid the IOPS collapse reported in the Igalia comments).
- qcow2's main risks for this platform are (a) per-image RAM for L2 caches at density (32 MB default max per image x thousands of VMs), (b) a large C/Rust parser in the per-VM VMM, and (c) chain depth. dm-thin's main risks are the 64 KiB floor, a single shared metadata device (pool-wide failure mode: metadata exhaustion flips the pool read-only), and suspend-required snapshots. Neither maps naturally onto "upload diff to object storage", which is why every recent platform built its own.
- ublk is the lowest-friction way to put a custom userspace CoW/lazy-fetch block layer under any VMM that only accepts files/block devices, and is now multi-million-IOPS capable on null targets; but inside this design the storage VM can serve virtqueues directly (vhost-user-blk style), so ublk's extra kernel block-layer round trip is unnecessary on the hot path. ublk remains useful in the storage VM for tooling (mounting an image to build or fsck it).

### Gaps
- No same-hardware 2024-2026 benchmark of first-write and steady-state overhead vs raw NVMe across qcow2 / dm-thin / reflink / zvol / lvol / ublk was found. All per-technology numbers above are from different rigs and mostly old. This needs to be measured in-house (fio: 4K randwrite QD1/QD32, pre-written vs fresh-fork regions, with fsync every N writes).
- bcachefs, Ceph RBD clones (beyond LSVD's RBD baseline), dm-snapshot specifics, VDUSE, and zvol first-write costs: no usable primary numbers found this session.
- Kernel versions in which ublk zero-copy (`UBLK_F_SUPPORT_ZERO_COPY` via io_uring kernel buffer registration), `UBLK_F_AUTO_BUF_REG`, `UBLK_F_BATCH_IO` and `UBLK_F_SHMEM_ZC` were merged were not confirmed (search suggested 6.15/6.16 for the first two but did not verify; the flags are all present in current kernel docs).
- E2B's rootfs block size, header format and CoW cache internals were not in the fetched portion of its architecture doc. Fly's LSVD blog post could not be fetched (404).
- SPDK lvol clone/snapshot performance overhead: no published measurement found.

## 2. "Optimized disk writes": avoiding double work on the write path

### Takeaway
The biggest levers found in primary sources are (1) keeping filesystem semantics in the guest on a block device (Modal measured 5-50x on metadata-heavy developer workloads vs virtio-fs), (2) making guest flush cheap or absent (Firecracker's default `Unsafe` cache mode does not even advertise FLUSH; DigitalOcean acks writes before host durability and syncs overlays periodically), and (3) using power-loss-protected NVMe where a real fsync costs single-digit to tens of microseconds instead of milliseconds. Double-caching and fine-vs-coarse CoW alignment are design choices with little published measurement.

### Cited Findings

**Block device vs shared filesystem for developer workloads**
- Modal (2026), same image, virtio-fs+ImageFS vs ImageFS-blk (virtio-blk + guest ext4): `bun install` 12.5 s vs 1.07 s; ripgrep on the Linux repo warm cache 6.03 s vs 0.18 s (cold cache 24.3 s vs 8.53 s; FUSE-in-container ImageFS was 4.47 s cold); SQLite speedtest1 543.4 s vs 43.2 s; pgbench read-write 8.3k vs 18.8k TPS, read-only 98.2k vs 230.1k TPS; 100,000 `chown` calls 9.87 s vs 0.21 s (about 99 µs vs 2.1 µs each; one chown over virtio-fs = three guest-host round trips and six host syscalls). Stated reason: "ext4 batches changes into its journal, committed every 5 seconds to the host over virtio-blk". [F] — [Modal: VM sandbox filesystem](https://modal.com/blog/vm-sandbox-filesystem)
- Kata docs: the devicemapper block path "gives much better I/O performance compared to using virtio-fs to share the container file system" (no numbers). [F] — [Kata Containers: storage architecture](https://kata-containers.github.io/kata-containers/design/architecture/storage/)
- virtio-fs DAX helps only while the working set fits the DAX window; reclaiming/remapping window ranges is expensive; estimated guest cost about 16 MB of struct page per GB of DAX window. (2020) [S] — [virtio-fs list: performance numbers for virtiofs, DAX and 9p](https://lore.kernel.org/all/20201211182956.GF3380@work-vm/T/)

**Flush/fsync semantics and what providers actually do**
- Firecracker `cache_type`: `Unsafe` (default) does not advertise the flush feature, so the guest never sends flushes and data is only as durable as the host page cache; recommended "for ephemeral storage, such as serverless environments". `Writeback` advertises flush and runs `fsync` on the backing file per guest flush, with slower boot and higher emulation latency. [F] — [Firecracker docs: block-caching.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/api_requests/block-caching.md)
- E2B's published Firecracker config uses `cache_type: "Unsafe"` on both the read-only squashfs root and the writable ext4 overlay drive. (2025) [F] — [E2B: Scaling Firecracker using OverlayFS](https://e2b.dev/blog/scaling-firecracker-using-overlayfs-to-save-disk-space)
- DigitalOcean: "a local write can be acknowledged before the host disk is durable, since overlays sync periodically"; sealing an overlay at checkpoint forces a sync of delta and bitmap; only published checkpoints count as durable. [F] — [DigitalOcean: microVM architecture](https://www.digitalocean.com/blog/microvm-architecture)
- LSVD's alternative: a local SSD journal makes commits durable locally (all committed writes recovered after client crash), with asynchronous batched upload and prefix consistency only if the cache device itself is lost; eliminating per-write metadata persistence made it up to 4x faster than bcache on sync-heavy workloads. [F] — [LSVD, EuroSys'22](https://rs3lab.github.io/assets/papers/2022/hajkazemi-aschenbrenner:lsvd.pdf)
- dm-thin commits metadata on every FLUSH/FUA bio, otherwise once per second. [F] — [kernel.org: thin-provisioning](https://docs.kernel.org/admin-guide/device-mapper/thin-provisioning.html)
- Raw device fsync cost (fio, O_DIRECT, one sync per write, ext4, Jan 2026): enterprise PLP drives 1.6 µs fsync / 0.7 µs fdatasync (Samsung PM9A3, 16 KB writes) and 12.4 / 9.8 µs (Intel D7-P5520); consumer non-PLP Samsung 990 Pro 2,974 / 2,783 µs; consumer Crucial T500 891 / 447 µs; GCP local NVMe 56 / 28 µs; GCP Hyperdisk Balanced 738 / 47 µs. After 2 MB writes the PM9A3 fsync rose to 139 µs. [F] — [Small Datum: SSDs, power loss protection and fsync latency](https://smalldatum.blogspot.com/2026/01/ssds-power-loss-protection-and-fsync.html)

**virtio-blk / backend engine features**
- Firecracker `io_engine`: `Sync` (default, blocking syscalls) vs `Async` (io_uring, host kernel >= 5.10.51, still labelled developer preview). On NVMe with a 5.10 host: reads not in host page cache 1.5-3x better IOPS-per-CPU and up to 30x total IOPS; writes 20-45% more total IOPS but lower efficiency (kernel workers burn CPU). Async adds up to about 110 ms to device creation (affects boot and snapshot-restore latency); io_uring workers can exhaust host PIDs and ran outside the VM's cgroup before 5.12. [F] — [Firecracker docs: block-io-engine.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/api_requests/block-io-engine.md)
- Firecracker in 2020 was limited to about 13,000 IOPS serial block I/O without flush; 4 kB read latency 49 µs worse than native at QD1. (2020) [F, carried from earlier notes] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- QEMU 9.0 / RHEL 9.4 added true multi-queue virtio-blk via IOThread-virtqueue mapping (round-robin virtqueues to multiple IOThreads); recommended 4-8 IOThreads pinned away from vCPUs, `cache=none io=native`; IOPS rise from 1 to 2 to 4 IOThreads at iodepth 1 and 64 on Optane (values only in chart); "extra IOThreads beyond the saturation point does not increase performance and may harm it"; a companion RHEL database study cites +13.82%. [F for config, S for the 13.82%] — [Red Hat: Scaling virtio-blk disk I/O with IOThread Virtqueue Mapping](https://developers.redhat.com/articles/2024/09/05/scaling-virtio-blk-disk-io-iothread-virtqueue-mapping)
- A FAST'26 paper's breakdown of a 4 KB random read through virtio-blk reports mean latency 35.5 µs with software overhead up to 87% of the total; LightIOV (2023) reports virtio with 51.2%-236.1% higher latency than its queue-passthrough design while SPDK-vhost matched VFIO. [S] — [RosenBridge, FAST'26](https://www.usenix.org/system/files/fast26-qiu.pdf); [LightIOV, arXiv 2304.05148](https://arxiv.org/pdf/2304.05148)
- Cloud Hypervisor added virtio-blk DISCARD and WRITE_ZEROES for qcow2 and raw only in v51.0 (2026). [F, carried from earlier notes] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- virtio-blk feature bits relevant here: `VIRTIO_BLK_F_FLUSH`, `F_DISCARD`, `F_WRITE_ZEROES`, `F_MQ`, `F_BLK_SIZE`/`F_TOPOLOGY` (advertise logical/physical block size and optimal I/O size), plus ring-level `VIRTIO_F_RING_PACKED`, `VIRTIO_RING_F_INDIRECT_DESC`, `VIRTIO_RING_F_EVENT_IDX`. [R] — [OASIS virtio 1.2 spec](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html)

**Guest filesystem and mount options**
- Deployed choices: guest ext4 on host XFS-reflink (Cognition); guest ext4 on synthesized sparse image (Modal); "ordinary ext4 disk" (Cortex); squashfs read-only root + ext4 overlay drive via overlayfs with `overlay-init` (E2B blog); EROFS lower + ext4 upper via overlayfs (Kata erofs snapshotter); flattened ext4 (Lambda). No platform in this set runs btrfs or XFS in the guest root. [F] — [Cognition](https://cognition.com/blog/blockdiff); [Modal](https://modal.com/blog/vm-sandbox-filesystem); [Cortex](https://builders.cortex.io/blog/sandboxing-agents-part-2/); [E2B](https://e2b.dev/blog/scaling-firecracker-using-overlayfs-to-save-disk-space); [Kata erofs how-to](https://github.com/kata-containers/kata-containers/blob/main/docs/how-to/how-to-use-erofs-snapshotter-with-kata.md)
- ext4 knobs: `commit=<sec>` (journal commit interval, default 5 s), `lazytime`, `noatime`, `data=ordered|writeback|journal`, `discard` (online) vs batched `fstrim`, `journal_async_commit`. [R] — [kernel.org: ext4 admin guide](https://docs.kernel.org/admin-guide/ext4.html)
- OverlayFS over a non-reflink lower copies the whole file on first modification; Cognition saw Docker fall back to the `vfs` driver in one nested configuration, using 17x more storage and running 6x slower. [F] — [Cognition: Blockdiff](https://cognition.com/blog/blockdiff); [Modal: VM sandbox filesystem](https://modal.com/blog/vm-sandbox-filesystem)

### Inferences
- Double journaling / double CoW: guest ext4 (in-place data, small journal) on a host CoW layer costs one CoW per first-touch block only; guest btrfs or ZFS would CoW every overwrite and turn every guest overwrite into a fresh host allocation plus a stale-block discard, defeating diff-size and GC goals. ext4 (or XFS without heavy reflink use) in the guest on a host CoW/bitmap layer is the consistent industry choice and should be the default. A host backend that is an identity-mapped sparse file on a non-CoW-per-write host FS (XFS used with reflink only at fork time, or ext4) avoids a second journal for data: only host extent-allocation metadata is journaled.
- Alignment: with a 4 KiB overlay granularity matching the guest ext4 block size, a block-aligned full-block guest write never needs a parent read (DigitalOcean notes only partial-block writes read the parent). Advertising `physical_block_size=4096` (and `logical_block_size=4096` if nothing needs 512e) via `F_BLK_SIZE` guarantees the guest never issues sub-4K writes, removing the read-modify-write path entirely. If a coarser unit is chosen, advertise it as optimal I/O size/discard granularity and use ext4 `stride`/`stripe_width` or bigalloc so allocations cluster.
- Double caching is primarily a memory-density problem: with buffered host I/O, every guest page-cache page can also exist in the storage VM's page cache. The storage backend should open overlay and base files `O_DIRECT` (cache=none equivalent) so the only cache is the guest's own (reclaimable via balloon/free-page-reporting), except for the shared read-only base, where a single host-side cached copy serving N guests (or DAX-mapped into them, section 5) is a net win.
- Safe cheap fsync, in order of preference for ephemeral-but-checkpointed sandboxes: (1) advertise FLUSH but implement it as "data is in the storage VM's power-loss-protected WAL/NVMe" — on PLP NVMe a real flush is about 2-60 µs, so honouring it costs little and avoids a per-sandbox lie; (2) group-commit flushes across virtqueues/VMs into one NVMe FLUSH per few hundred microseconds; (3) only for explicitly disposable sandboxes, Firecracker-style no-FLUSH. The actual durability boundary users care about is the checkpoint to object storage (DigitalOcean's stance), so local fsync needs to survive guest crash and VMM restart, and ideally host power loss, but not host loss.
- Guest mount defaults that reduce host writes without breaking fsync: `noatime,lazytime`, ext4 `commit=15..30` (fsync still forces a commit; only un-fsynced data is delayed), periodic `fstrim` instead of `discard`, journal sized small (64 MiB) to cap CoW churn in the journal region. `data=writeback` and `nobarrier`-style options are unnecessary once flush is cheap.
- Indirect descriptors and EVENT_IDX matter more than packed rings for this workload (small I/Os, bursty); request merging should be left to the guest block layer (`mq-deadline` or `none`), with the backend batching io_uring submissions per virtqueue kick.

### Gaps
- No published measurement of host page-cache double-caching memory cost per sandbox, or of cache=none vs buffered for forked-rootfs microVMs.
- No published group-commit design for virtio-blk flush across VMs; the inference above is untested.
- No primary numbers for guest mount-option effects (lazytime, commit interval) on host write volume for agent workloads.
- IOThread-vq-mapping IOPS values are only in a chart; io_uring passthrough (`IORING_OP_URING_CMD` to NVMe) backends for virtio-blk were not researched.

## 3. Space reclamation

### Takeaway
Reclamation is decided by three things the sources make explicit: whether the virtual disk passes DISCARD/WRITE_ZEROES at all (Cloud Hypervisor only since 2026), whether the overlay can distinguish "zeroed/discarded" from "not present, read parent" (DigitalOcean's bitmap rule), and, for log-structured backends, a GC whose write amplification was measured at 1.05-1.75x in LSVD.

### Cited Findings
- In a bitmap overlay over a parent, zeroing a block must set its presence bit even when the zeros are stored as a hole; otherwise reads fall through to the parent and old data reappears. [F] — [DigitalOcean: microVM architecture](https://www.digitalocean.com/blog/microvm-architecture)
- dm-thin: discards unmap blocks in the pool; `no_discard_passdown` stops them reaching the data device; `ignore_discard` disables discard entirely. vdo treats discarded addresses as unmapped. [F] — [kernel.org: thin-provisioning](https://docs.kernel.org/admin-guide/device-mapper/thin-provisioning.html); [kernel.org: dm-vdo design](https://docs.kernel.org/admin-guide/device-mapper/vdo-design.html)
- SPDK lvol: deleting or shrinking an lvol unmaps its clusters by default (`--clear-method unmap`). [F] — [SPDK: Logical Volumes](https://spdk.io/doc/logical_volumes.html)
- Firecracker `PATCH /drives` notes that if discard is enabled the new device's discard alignment must divide the advertised alignment (unchecked). [F] — [Firecracker docs: patch-block.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/api_requests/patch-block.md)
- LSVD GC: cleaning triggered when live/total falls below 70%; measured write amplification 1.046-1.75; GC also defragments the extent map; snapshots defer deletion of GC'd objects. [F] — [LSVD, EuroSys'22](https://rs3lab.github.io/assets/papers/2022/hajkazemi-aschenbrenner:lsvd.pdf)
- Lambda's chunk-store GC uses generational "roots" (active, retired, expired, deleted): new data goes to a new root periodically, live manifests+chunks are migrated forward, old roots are deleted wholesale; chosen because GC of a deduplicated store is "uniquely risky". [F] — [Brooker et al., ATC'23](https://www.usenix.org/system/files/atc23-brooker.pdf)
- Dirty tracking for diff snapshots in practice: 4 KiB dirty bitmap + sparse delta (DigitalOcean, Modal); per-chunk dirty set (Cortex 16 MiB, BuildBuddy); FIEMAP extent comparison against the base on reflink files (Cognition); CoW-cache contents (E2B). Cortex and Lambda skip all-zero chunks. [F] — [DigitalOcean](https://www.digitalocean.com/blog/microvm-architecture); [Modal](https://modal.com/blog/vm-sandbox-filesystem); [Cortex](https://builders.cortex.io/blog/sandboxing-agents-part-2/); [Cognition](https://cognition.com/blog/blockdiff); [E2B](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- Sprites bill only for blocks actually written out of the 100 GB thin volume. [F] — [Fly.io: Sprites design](https://fly.io/blog/design-and-implementation/)

### Inferences
- An overlay needs three per-block states, not two: absent (read parent), present (read overlay), and zero/discarded (read zeros, no storage). A 2-bit map, or a presence bitmap plus hole-punching, gives this; the zero state is what makes guest `fstrim` shrink both local usage and the next uploaded diff (a discarded block that was never in the parent can simply clear its presence bit; one that shadows parent data must become an explicit zero mark).
- Prefer agent-driven periodic `fstrim` (e.g. before each checkpoint and on idle) over the `discard` mount option: batched trims are large aligned ranges, cheap to turn into `fallocate(PUNCH_HOLE)`, and avoid per-unlink discard traffic on the virtqueue. Run fstrim before checkpoint so deleted build artifacts never get uploaded.
- "Truly dirty" tracking has a subtlety: a bitmap marks blocks written, not blocks changed. Rewrites of identical content (package reinstall, `git checkout` back) inflate diffs. Content-hashing chunks at upload time (Cortex/DigitalOcean/Lambda style) removes these for free and is where dedup against the base should happen, off the write path.
- Write-zeroes detection on the write path (dm-thin once had a patch for it) costs CPU per write; do it only at upload/chunking time, where the data is being hashed anyway.

### Gaps
- No measurements of online discard vs fstrim overhead through virtio-blk into a thin layer were found.
- No published numbers on how much of an agent-sandbox diff is reclaimable by fstrim-before-checkpoint.

## 4. Dedup, compression, and shared read-only base layers

### Takeaway
The strongest production evidence is that cross-image dedup of flattened images at 512 KiB fixed chunks is extremely effective (Lambda: about 80% of uploads add zero new chunks; the rest add a median 2.5%), and that dedup belongs at the immutable-chunk/object layer, not inline on the hot write path (inline dedup costs 25-50% throughput in ZFS even with fast dedup). No measured dedup or compression ratios for developer workspaces (node_modules, build artifacts) were found.

### Cited Findings
- AWS Lambda: container images flattened deterministically to ext4, split into fixed 512 KiB chunks; "approximately 80% of newly uploaded Lambda functions result in zero unique chunks"; of the remaining 20%, mean 4.3% and median 2.5% unique chunks; manifest under 3 MiB for a 16 GiB image (0.02%); convergent encryption with a rotating salt so dedup blast radius can be bounded; on-worker cache median hit rate 67%, AZ cache 99.9% of the remainder, 0.06% from S3; AZ-cache fetch median 550 µs vs 36 ms from S3 origin. Smaller chunks dedup better but 512 KiB balanced metadata and latency. [F] — [Brooker et al., ATC'23](https://www.usenix.org/system/files/atc23-brooker.pdf)
- Slacker (FAST'16): pulling packages accounts for 76% of container start time but only 6.4% of that data is read. (2016) [S] — [Harter et al., FAST'16](https://research.cs.wisc.edu/wind/Publications/slacker-fast16.pdf)
- Docker Hub studies: only about 3% of files across 167 TB of uncompressed images are unique; an earlier study estimated file-level dedup would eliminate 96.8% of files for a 6.9x capacity ratio. (2017-2020 datasets; file-level, not block-level) [S] — [Zhao et al., Large-Scale Analysis of Docker Images](https://par.nsf.gov/servlets/purl/10201736); [Slimmer study](https://par.nsf.gov/servlets/purl/10099559)
- DigitalOcean uses content-defined chunking (casync `.caibx` indexes; target 512 KiB, bounds 256-768 KiB), compressed remote chunks, uncompressed host-local cache; notes that a small edit can shift boundaries and rechunk a larger range when merging overlays. Cortex uses fixed 16 MiB SHA-256 chunks for disk and 512 KiB for memory. [F] — [DigitalOcean](https://www.digitalocean.com/blog/microvm-architecture); [Cortex](https://builders.cortex.io/blog/sandboxing-agents-part-2/)
- dm-vdo: 4K blocks; default dedup index holds 64 million records = about 256 GB dedup window, kept entirely in memory; sparse index gives 10x window for 10x index storage at the same memory and finds 97-99% of duplicates; compression packs up to 14 compressed blocks into one 4K block; 5-byte block-map entries (812 per 4K page); 1-byte refcount per data block; recovery journal written with FUA; a fixed pool of 2048 in-flight `data_vio`s. No throughput or CPU figures in the design doc. [F] — [kernel.org: dm-vdo design](https://docs.kernel.org/admin-guide/device-mapper/vdo-design.html)
- OpenZFS fast dedup (2.3): Klara's test with 96 GiB of 30%-dedupable data showed legacy dedup at about a 50% performance penalty and fast dedup at about 25%; Klara still discourages dedup for generic VM stores. [S] — [Klara Systems: fast dedup](https://klarasystems.com/?p=22086)
- Fedora measured about 40% space savings from btrfs zstd:1 on an installed root filesystem vs uncompressed ext4. (root FS, not workspaces) [S] — [Fedora: btrfs transparent compression](https://fedoraproject.org/wiki/Changes/BtrfsTransparentCompression)
- EROFS: block-aligned immutable FS (Linux 5.4+), per-file LZ4/LZMA/DEFLATE/Zstd compression, chunk-based dedup, FSDAX, file-backed mounts (6.12+); containerd has a native EROFS snapshotter since 2.1 (2.2 added parallel unpacking, writable-layer quota, block files as writable layer for VM-based containers, and never mounting on the host for VM runtimes); a user reported 2-3x faster launch in initial testing. AWS Bottlerocket's switch from ext4 to EROFS gave a "46% smaller root EBS volume". [F] — [LPC 2025: EROFS and containers (slides)](https://lpc.events/event/19/contributions/2238/attachments/1902/4089/LPC2025_erofs.pdf)
- EROFS page-cache sharing across images by content fingerprint (proposed, "aims to land in the next cycle" as of LPC 2025) cut memory when running two adjacent versions of the same image: redis 241 to 163 MB (-33%), postgres 872 to 630 MB (-28%), tensorflow 2771 to 2340 MB (-16%), mysql 926 to 735 MB (-21%), nginx 390 to 219 MB (-44%), tomcat 924 to 474 MB (-49%). [F] — [LPC 2025: EROFS and containers](https://lpc.events/event/19/contributions/2238/attachments/1902/4089/LPC2025_erofs.pdf)
- EROFS limitation relevant to DAX density: EROFS chunk dedup cannot be applied under FSDAX (FSDAX page sharing requires a filesystem reverse-mapping tree); the proposed alternative is layer-granular sharing, where each virtio-pmem region is composed of multiple sub-images so common layers map the same host memory. dm-verity cannot protect FSDAX mappings. [F] — [LPC 2025: EROFS and containers](https://lpc.events/event/19/contributions/2238/attachments/1902/4089/LPC2025_erofs.pdf)
- composefs = EROFS metadata image + overlayfs redirect xattrs into a content-addressed object store with fs-verity digests. [F] — [LPC 2025: EROFS and containers](https://lpc.events/event/19/contributions/2238/attachments/1902/4089/LPC2025_erofs.pdf)
- DADI/overlaybd (ATC'20): block-level layered image service; cold-started 10,000 containers on 1,000 hosts within 4 s; a project table shows 11.72 s service-available for an overlaybd-native image vs 30.77 s for OCIv1 gzip on one workload. [S] — [Li et al., ATC'20 (DADI)](https://usenix.org/conference/atc20/presentation/li-huiba); [accelerated-container-image TurboOCI doc](https://www.github.com/djdongjin/accelerated-container-image/blob/main/docs/TURBO_OCI.md)
- Modal ImageFS: read-only lazy-loading FS over a tiered content-addressed cache (memory, SSD/regional CDN, blob storage); index about 5 MiB mounted in about 2 ms; about 2.5 GB/s (512 MiB file in about 200 ms from disk cache, 300 ms from network). (2024) [S] — [Modal: jono containers talk](https://modal.com/blog/jono-containers-talk); [third-party notes](https://tinfoil-knight.github.io/notes/fast,-lazy-container-loading-in-modal-2024)
- Docker Sandboxes: each sandbox has its own Docker daemon, image cache and package installs; "sandboxes don't share images or layers" (only a read-only agent-skills store is shared). [F] — [Docker docs: Sandboxes architecture](https://docs.docker.com/ai/sandboxes/architecture/)
- Vercel Sandbox: snapshots are raw `.img` compressed into a framed `.vhs` format (one frame per allocated region), 200 MB to a few GB; restore p75 went from over 40 s to sub-second and p95 from 50 s to 5-10 s via ranged parallel S3 download, parallel decompression, streaming, and a local NVMe LRU cache of decompressed images with about 95% hit rate for base snapshots. No lazy loading. [F] — [Vercel: optimizing Vercel Sandbox snapshots](https://vercel.com/blog/optimizing-vercel-sandbox-snapshots)

### Inferences
- Where to dedup: (a) at image-build time, by flattening images deterministically (Lambda) so identical content lands at identical offsets and fixed-size chunks dedup well; (b) at checkpoint upload, by hashing dirty chunks against the fork parent's manifest and a global chunk index. Do not put VDO/ZFS-dedup under live overlays: per-write hashing and index lookups cost throughput and RAM (VDO's index is fully in-memory) for data that is mostly short-lived.
- Fixed vs content-defined chunking for block devices: block-device content is already 4K-aligned and in-place, so insertions do not shift subsequent data the way they do in a tar stream; fixed chunks aligned to the FS block size capture most duplication with trivial indexing and stable diffs. CDC helps mainly for file streams; DigitalOcean's own note that small edits rechunk larger ranges is the cost. Recommended: fixed 64-256 KiB object-store chunks (smaller than Lambda's 512 KiB because sandbox diffs are scattered small writes), packed into larger objects for PUT-cost efficiency, with per-chunk zstd.
- Compression belongs in the object/chunk tier (zstd at upload) and in the read-only base (EROFS zstd/LZ4 if the base is EROFS-over-blk; uncompressed if DAX-mapped). Leave the hot local overlay uncompressed: NVMe bytes are cheaper than the CPU and latency of inline compression, and the overlay is small by construction.
- Sharing package caches safely: publish them as additional read-only content-addressed base layers (e.g. a versioned npm/pip/cargo cache image attached as a second RO device and overlay-mounted or used as an offline mirror), never as a writable shared filesystem. This gives cross-tenant dedup of public artifacts on disk and, if DAX-mapped, in memory, without a cross-tenant write channel. Convergent-encryption-style salting (Lambda) is the model if tenant-private layers are ever deduplicated across tenants.
- Expected ratios for developer workspaces are unmeasured in public sources; the Docker Hub 3%-unique-files result and Lambda's 2.5% median-unique-chunks result suggest that sandboxes forked from common bases plus public package installs will be dominated by shared content, but this is an extrapolation.

### Gaps
- No measured block-level dedup or zstd ratios for developer workspaces (node_modules, build artifacts, package caches) were found. Needs an in-house measurement on real sandbox diffs.
- nydus, SOCI and stargz were not individually researched beyond mentions; the containerd `blockfile` and `devmapper` snapshotters were not read.
- dm-vdo and OpenZFS fast-dedup CPU/RAM costs: only one secondary benchmark (Klara) found; VDO memory-per-TB figures were not in the fetched design doc.
- DADI paper evaluation details were not read (only abstract-level claims).

## 5. Rootfs architecture choice for density

### Takeaway
Two block-based layouts dominate and both beat virtio-fs for sandbox roots: (A) one CoW block device per VM (base + overlay merged below the guest; Modal, Cortex, DigitalOcean, E2B current, Cognition, Lambda), and (B) a shared read-only base device plus a per-VM writable overlay device merged by guest overlayfs (E2B's earlier blog design, Kata's EROFS snapshotter). Only (B) with EROFS on virtio-pmem/DAX shares base-image page cache across guests, and that path has a recent security history (CVE-2026-24834) and file-level copy-up costs; (A) gives block-granular CoW and the simplest snapshot story but duplicates base pages in every guest's page cache unless handled at the memory layer.

### Cited Findings
- Modal moved from virtio-fs (guest FUSE to virtiofsd to ImageFS/OverlayFS) to virtio-blk + guest ext4 with host-side block CoW; virtio-fs was the slowest option on every tested operation, behind gVisor; "virtio-fs puts that authority on the far side of the VM boundary, to which the guest is only ever a client." (2026) [F] — [Modal: VM sandbox filesystem](https://modal.com/blog/vm-sandbox-filesystem)
- Kata: default without a block-based snapshotter is a virtio-fs overlay mount with one host `virtiofsd` per VM; with devicemapper the container's RW top layer is a block device hot-plugged into the VM (virtio-scsi/blk) and mounted directly. With the containerd EROFS snapshotter (containerd >= 2.2, runtime-rs): EROFS layer blobs are passed as virtio-blk (multiple layers merged into one disk via a VMDK flat-extent descriptor, QEMU-only), the upper is an ext4 block device sized by `default_size` (e.g. 6G/10G), and the agent builds overlayfs in the guest; `shared_fs = "none"` for pure block mode; dm-verity optional; claims "lower overhead, better performance, and smaller memory footprints" without numbers. [F] — [Kata: storage](https://kata-containers.github.io/kata-containers/design/architecture/storage/); [Kata: erofs snapshotter how-to](https://github.com/kata-containers/kata-containers/blob/main/docs/how-to/how-to-use-erofs-snapshotter-with-kata.md)
- EROFS maintainers' position: virtio-fs opens FDs on the host and has metadata-performance problems; pass container rootfs as block devices; fsmerge lets all layers be one mount/one device, "but most VMMs still do not support multi-part block devices". [F] — [LPC 2025: EROFS and containers](https://lpc.events/event/19/contributions/2238/attachments/1902/4089/LPC2025_erofs.pdf)
- CVE-2026-24834 (Kata < 3.27.0, reported by a third-party CVE write-up): the Linux virtio-pmem probe path cleared the region read-only flag, so `/dev/pmem0` holding the DAX-mapped guest rootfs was writable; on Cloud Hypervisor the file was `MAP_PRIVATE` so writes stayed in guest RAM (guest-root compromise, not host escape); the report says ARM64/QEMU NVDIMM read-only enforcement was missing so writes "might" reach the shared host file (unverified). Fix (3.27.0, 2026-02-19) moved the rootfs to virtio-blk and disabled DAX for it in some cases. [S, secondary report] — [cvereports: CVE-2026-24834](https://cvereports.com/reports/CVE-2026-24834)
- A 2026 open-source agent-sandbox project proposes attaching each image layer as read-only EROFS on virtio-pmem with DAX specifically because a host-merged rootfs makes every guest copy image bytes into its own page cache. [S] — [agent-substrate PR #2610](https://github.com/agent-substrate/substrate/pull/2610)
- E2B (2025 blog): squashfs read-only root shared by all VMs + per-VM sparse `overlay.ext4` (5 GB apparent, 0 bytes until written) merged by an `overlay-init` script (`overlay_root=vdb`, or `ram` for tmpfs). E2B (current infra doc): read-only template rootfs + per-sandbox CoW cache presented as a single NBD device. [F] — [E2B blog](https://e2b.dev/blog/scaling-firecracker-using-overlayfs-to-save-disk-space); [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- Lambda: two virtio-blk devices, a root device identical for all microVMs and the flattened function image with a block overlay for writes. [F] — [Brooker et al., ATC'23](https://www.usenix.org/system/files/atc23-brooker.pdf)
- Docker Sandboxes: private per-sandbox VM disk (own Docker daemon/image store, nothing shared) plus the host workspace via virtiofs passthrough with caching on by default; warns against network filesystems as workspaces. [F] — [Docker docs: Sandboxes architecture](https://docs.docker.com/ai/sandboxes/architecture/)
- Sprites: user code runs in an inner container; the VM root namespace runs the storage stack and service manager. [F] — [Fly.io: Sprites design](https://fly.io/blog/design-and-implementation/)
- Cortex measured base-memory sharing after making canonical guest memory a shared per-host file: ΣPSS/ΣRSS of 35% across three guests vs a 33% ideal; base shm 49 MiB physically allocated of 4 GiB apparent; lesson: "real agent workloads pull several GiB of pages into host RAM". [F] — [Cortex builders: Sandboxing agents, part 2](https://builders.cortex.io/blog/sandboxing-agents-part-2/)
- Firecracker added virtio-pmem in v1.14 (rate limiter in v1.16). [F, carried from earlier notes] — [Firecracker CHANGELOG](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)

### Inferences
- Disk density is equivalent in (A) and (B): both store one base plus per-VM deltas. The differences are: (A) CoW is 4 KiB-granular and invisible to the guest, any guest FS feature works (hardlinks, renames, xattrs, Docker's overlay2 on top without overlay-on-overlay problems), and one device = one snapshot object; (B) guest overlayfs copy-up copies whole files on first write (bad for large sqlite/db files, large binaries that get patched, and `chown -R`), nested Docker needs care (overlay2 on an overlayfs root requires the upper to be a real FS path), but the base can be DAX-mapped and base upgrades can swap a device.
- Memory density is where they diverge. In (A), base-image file pages read by N guests sit in N guest page caches. But when sandboxes are forked from a memory snapshot of a warm template, those page-cache pages are already shared CoW at the hypervisor level (Cortex's 35% PSS/RSS result is exactly this effect), so (A) + snapshot-fork recovers most of the sharing for pages touched before the fork point. Pages first read after the fork are duplicated. (B)+DAX shares those too, at the cost of guest-visible pmem, the EROFS-dedup-vs-FSDAX limitation, no dm-verity, struct-page overhead for the pmem range, and the CVE class above.
- Recommended default: (A) single CoW virtio-blk root with ext4, forked from warm memory snapshots so pre-fork page cache is shared; add an optional second device (B-style) only for large, read-mostly, cross-tenant content (toolchains, package caches, model weights) as EROFS on a read-only device, DAX-mapped where the hypervisor can enforce read-only in the stage-2 page tables. In a type-1 design read-only enforcement is a stage-2 permission, not a guest driver flag, which removes the CVE-2026-24834 failure mode by construction.
- virtio-fs should not be on the root or workspace path for cloud sandboxes (Modal's numbers, EROFS maintainers, earlier notes on snapshot state). It remains reasonable only for local-desktop products where the workspace must be the user's live host directory (Docker Sandboxes).

### Gaps
- No public measurement of guest page-cache duplication for forked single-device roots vs EROFS/DAX layouts in microVM sandboxes; Cortex's sharing figure is for memory snapshots generally, with only three guests.
- Firecracker-containerd's current rootfs layout and CodeSandbox's current disk design were not re-researched (CodeSandbox sources are from 2022-2023).
- The CVE details come from a secondary write-up; the Kata advisory itself was not read.

## 6. Snapshot/checkpoint/fork consistency, incremental upload, lazy restore

### Takeaway
The pattern with the most detailed public description is: pause the VM, seal the current writable overlay (forcing a sync of delta and bitmap), start a fresh overlay on top, resume, and upload the sealed layer in the background; the checkpoint is committed only when every artifact is published. Restore loads only a manifest and fetches chunks on demand through a host NVMe cache. Because memory is captured in the same pause, no guest filesystem freeze is used; fsfreeze is only needed for disk-only snapshots.

### Cited Findings
- DigitalOcean: checkpoint = disk + memory + device/vCPU state; capture pauses the VM, seals the overlay, switches writes to a fresh overlay, resumes, uploads in the background; sealed overlays become read-only parents; publication merges sealed overlays into a self-contained index reusing unchanged base chunks; completion is recorded in PostgreSQL only after all artifacts publish; forks reference immutable checkpoint content plus their own overlay; memory capture currently writes the full image without dirty tracking; restore uses userfaultfd with caches, coalesced fetches and read-ahead. [F] — [DigitalOcean: microVM architecture](https://www.digitalocean.com/blog/microvm-architecture)
- E2B: on pause, memory is diffed via dirty-page tracking and the rootfs from the CoW cache; snapshot cached locally and uploaded asynchronously with a retry budget; optional deferred rootfs export seals the CoW cache in the background via reflink (a seal failure is permanent); pause budget 80 s; snapshots have the same artifact shape as templates (`memfile`, `rootfs.ext4`, `snapfile`, `metadata.json`, `.header` indexes) stored as diffs against the parent build; templates fetched lazily with local-disk, shared NFS chunk cache and peer-to-peer tiers; an optional prefetcher warms known-hot pages; a pre-pause disk-headroom admission check exists. [F] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- Cortex: snapshot hashes and uploads dirty 16 MiB disk chunks and publishes a new manifest version; resume loads a small manifest and fetches chunks on demand; reads hit a host NVMe LRU cache first and fall back to blob storage; memory restored via userfaultfd in 512 KiB chunks (`UFFDIO_CONTINUE` for shared canonical pages, `UFFDIO_COPY` for private ones); worst-case snapshot before the redesign was about 144 GiB (128 GiB disk + 16 GiB RAM); retained sessions are snapshotted and evicted so host count follows active concurrency. [F] — [Cortex builders: Sandboxing agents, part 2](https://builders.cortex.io/blog/sandboxing-agents-part-2/)
- Firecracker drains and fsyncs block backing files on snapshot; vhost-user block devices cannot be snapshotted by Firecracker. [F, carried from earlier notes] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Firecracker `PATCH /drives` can repoint a drive's `path_on_host` at runtime but is non-atomic and only supported if the guest is not using the device; for vhost-user-blk a PATCH with only `drive_id` makes Firecracker re-read config from the backend. [F] — [Firecracker docs: patch-block.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/api_requests/patch-block.md)
- dm-thin requires suspending the origin before snapshotting an active device. [F] — [kernel.org: thin-provisioning](https://docs.kernel.org/admin-guide/device-mapper/thin-provisioning.html)
- Cognition: disk snapshot of a 20 GB disk in about 200 ms via FIEMAP diff, transfer about 2 GB/s; session-state snapshots about 50 MB vs multi-GB environment snapshots; open problems listed: hot-swapping the disk while running, caching dev-environment disks, incremental memory snapshots. [F] — [Cognition: Blockdiff](https://cognition.com/blog/blockdiff)
- Sprites: checkpoint/restore are metadata operations on object-store-rooted storage; a restore bounces the inner container without rebooting the VM; marketing says restore "in seconds"; users report 13-25 s. [F / S] — [Fly.io: Sprites design](https://fly.io/blog/design-and-implementation/); [Fly community thread](https://community.fly.io/t/unrecoverable-sprites-after-checkpoint-restore-failed-to-start-overlay-service-tree/27918)
- Lambda lazy-load path: 67% of chunks from the on-worker cache, 32% from the AZ cache (median 550 µs), 0.06% from S3 (median 36 ms). LSVD: asynchronous replication of a volume is plain object copy because objects are immutable and ordered. [F] — [Brooker et al., ATC'23](https://www.usenix.org/system/files/atc23-brooker.pdf); [LSVD, EuroSys'22](https://rs3lab.github.io/assets/papers/2022/hajkazemi-aschenbrenner:lsvd.pdf)
- Vercel: non-lazy restore needed ranged parallel download + parallel decompression + streaming to get p75 from over 40 s to sub-second, with a 95% local cache hit rate doing most of the work. [F] — [Vercel](https://vercel.com/blog/optimizing-vercel-sandbox-snapshots)

### Inferences
- Consistency rule for a combined memory+disk checkpoint: the disk image must reflect exactly the set of virtio-blk requests the guest has seen completed at the pause point. Procedure: stop vCPUs; stop popping new descriptors; drain in-flight backend I/O (or record in-flight descriptors as device state so they are re-issued on restore, which is safe for idempotent block writes); seal overlay generation N (durable bitmap + delta); record virtqueue indices in the device snapshot; open generation N+1; resume. No guest cooperation, no fsfreeze: guest page cache and journal state are in the memory image. Seal cost is O(bitmap flush), so pause time is dominated by memory capture, not disk.
- For a disk-only checkpoint (no memory image; used for hibernate-to-object-storage of idle sandboxes when memory is discarded) the result is merely crash-consistent unless the guest agent runs `sync` + `fsfreeze -f`, seals, then `fsfreeze -u`; ext4 journal replay makes crash-consistent acceptable, but databases with unflushed data benefit from the freeze. Run `fstrim` before the freeze.
- Fork = seal + two new empty overlays over the same sealed chain (parent continues on one, child on the other). With memory fork done by CoW of guest frames, both are O(metadata), and both must be keyed by one snapshot ID so the pair is atomic.
- Chain depth control: frequent checkpoints create many thin sealed layers. Merge policy: when a layer chain exceeds k (e.g. 8) or small layers accumulate, compact sealed layers in the background into one layer (bitmap OR + newest-wins copy); the published object-store form should always be a flat manifest (offset to chunk hash) so restore cost is independent of history (DigitalOcean's "self-contained index").
- Lazy restore needs three things to feel fast: a manifest-only attach (milliseconds), a local NVMe chunk cache shared by all sandboxes on the host keyed by content hash, and prefetch driven by a recorded access trace of the previous resume (E2B's prefetcher, DADI's trace replay). First-touch latency for a cold chunk is tens of ms from object storage (Lambda's 36 ms median), so background hydration of the hot set plus read-ahead on sequential faults is necessary; an AZ-level cache tier reduces this to sub-millisecond.
- Hibernation to object storage should upload only chunks not already present (hash check against parent manifest and global index), then drop the local overlay; the local NVMe cache copy is non-authoritative (Sprites model), so eviction is always safe and host loss never loses a committed checkpoint.

### Gaps
- No public description of how in-flight virtio-blk requests are handled at snapshot time beyond Firecracker's "drain and fsync"; the re-issue alternative is my inference.
- No published pause-time breakdown (ms) for overlay sealing in any platform; DigitalOcean's 20 ms is a setup budget, not a seal measurement.
- Prefetch effectiveness numbers for disk (as opposed to memory) were not found.

## 7. IOPS/throughput fairness, noisy neighbours, NVMe endurance

### Takeaway
Linux offers `io.max` (cheap, static caps, no proportional sharing) and `io.cost` (proportional, work-conserving, used fleet-wide at Meta), while I/O schedulers (BFQ, mq-deadline) add high overhead on NVMe; microVM platforms instead rate-limit per device in the VMM (Firecracker token buckets). Endurance data specific to CoW-layered sandbox storage was not found; the only measured write-amplification figures are LSVD's 1.05-1.75x.

### Cited Findings
- isol-bench (IISWC'25; Linux 6.9, direct I/O, Samsung 980 Pro and Intel Optane) evaluates five knobs (mq-deadline, BFQ, `io.max`, `io.latency`, `io.cost`) on overhead, proportional fairness, priority/utilization trade-off and burst support; headline slide: "Schedulers have high overhead!"; fairness depends on request-size mix (4 KiB vs 256 KiB). The per-knob result table was in chart form and not fully extracted; a search summary states `io.max` rated low-overhead but without proportional fairness, and `io.cost` providing fairness and priority handling. [F slides, partially; S for the ratings] — [Doekemeijer et al., IISWC'25 talk](https://krien.github.io/downloads/talk_iiswc_2025.pdf)
- IOCost (ASPLOS'22): per-device cost model from offline profiling, a cheap per-IO issue path plus a periodic planning path, budget donation between cgroups; deployed across Meta's fleet. A 2026 LWN article notes blk-iocost's model does not capture device behaviour that varies by I/O type or placement, and covers BPF-loadable cost models. [S] — [IOCost paper](https://par.nsf.gov/servlets/purl/10332478); [LWN 1093661](https://lwn.net/Articles/1093661/)
- cgroup v2 interfaces: `io.max` (per-device rbps/wbps/riops/wiops), `io.weight`/`io.cost.qos`/`io.cost.model`, `io.latency`. [R] — [kernel.org: cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)
- Firecracker rate limiters are per-device token buckets for bandwidth and ops, each with size, refill time and an optional one-time burst, applied to block (and now pmem) devices; its spec target is up to 1 GiB/s at <= 70% of one host core per device. [R for limiter shape; F in earlier notes for the spec and pmem limiter] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md); [Firecracker SPECIFICATION.md](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md)
- Firecracker's io_uring engine: kernel workers ran in the root cgroup (unaccountable per VM) before 5.12 and can exhaust the host PID limit at density. [F] — [Firecracker docs: block-io-engine.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/docs/api_requests/block-io-engine.md)
- CodeSandbox reported hibernation alone writing about 15 memory snapshots of 4 GiB per minute to disk (about 1 GiB/s of sequential writes) before it moved to compressed memory. (2023) [S] — [CodeSandbox: low-latency memory decompression](https://codesandbox.io/blog/how-we-scale-our-microvm-infrastructure-using-low-latency-memory-decompression)
- LSVD GC write amplification 1.046-1.75x; RBD-style replicated block stores turn one client write into about 6 back-end I/Os. [F] — [LSVD, EuroSys'22](https://rs3lab.github.io/assets/papers/2022/hajkazemi-aschenbrenner:lsvd.pdf)
- NVMe SR-IOV: secondary controllers as VFs since NVMe 1.3; practical ceiling around 254-255 VFs and vendor-dependent, much lower counts in shipping drives. [S] — [SNIA SDC'25: SSD virtualization](https://www.snia.org/sites/default/files/2025-09/SNIA-SDC25-Helmick-SSD-Virtualization.pdf); [KIOXIA blog on SR-IOV](https://blog-us.kioxia.com/post/2023/03/31/why-sr-iov-is-the-solution-to-help-efficiently-scale-your-data-center)

### Inferences
- Because the storage backend in this design is a single service (in the storage VM) that sees every request from every sandbox, fairness is best enforced there rather than by cgroup controllers: per-virtqueue token buckets (IOPS and bytes, with burst credits sized for `npm install`/`git clone` bursts) plus a weighted-fair dequeue across VMs when the device is saturated. This is Firecracker's limiter generalised with work-conserving sharing, and it avoids io.cost's reliance on blkcg attribution of io_uring/kernel-worker I/O. Cost accounting should charge first-write CoW (parent read + allocation) and flushes to the VM that caused them.
- NVMe queue mapping: backend worker threads pinned 1:1 to NVMe hardware queues in the storage VM, with thousands of virtqueues multiplexed onto a few tens of polling/interrupt-driven workers; idle sandboxes cost zero threads (no per-VM IOThread).
- Endurance: the write-amplification stack is guest journal (ext4 metadata journaling, roughly 1.1-2x on metadata-heavy workloads, estimate) x CoW granularity on first write (1x at 4 KiB, 16x at 64 KiB for small scattered writes) x host FS metadata x SSD FTL GC (worse with fragmented small random writes and TRIM lag). Fine-grained CoW, O_DIRECT, no inline dedup, and sequentialising hibernation/checkpoint writes (large appends, zstd-compressed) keep host WAF near 1; memory-snapshot writes (CodeSandbox's about 1 GiB/s example) will dominate drive wear unless memory checkpoints are incremental and compressed. Specify high-endurance PLP TLC drives and monitor per-drive WAF from SMART `data_units_written` vs backend-accounted guest bytes.

### Gaps
- No quantitative per-knob overhead numbers from isol-bench were extracted (charts only), and the IOCost paper's evaluation was not read.
- No published data on NVMe wear or WAF in CoW-layered microVM hosts.
- No data on per-VM IOPS budgets actually used by sandbox providers.

## 8. Type-1 with a storage service VM: cost of the extra hop, and passthrough alternatives

### Takeaway
I found no measurement of a guest-to-backend-VM virtio-blk path on a type-1 microhypervisor. The nearest evidence is that a userspace polling backend with direct shared-memory virtqueues (SPDK vhost-user-blk) reaches about 91% of bare NVMe and about 1M IOPS per backend core, while conventional virtio-blk software overhead is up to 87% of a 35.5 µs 4K read; this suggests the hop itself can be cheap if the storage VM maps the virtqueues directly and notifications are suppressed under load. NVMe SR-IOV/namespace passthrough cannot provide CoW, lazy restore or thousands of tenants per drive and does not fit this workload.

### Cited Findings
- SPDK vhost-user-blk: about 1002K IOPS with one backend core and four guest queues; in-guest fio at about 91% of physical NVMe; vfio-user NVMe 984K / 84%. (2021) [S] — [KVM Forum 2021 slides](https://kvm-forum.qemu.org/2021/Changpeng%20Liu%26Ben%20Walker_High%20Performance%20NVMe%20Virtualization%20with%20SPDK%20and%20vfio-user.pdf)
- virtio-blk 4 KB random read mean 35.5 µs with software overhead up to 87% (FAST'26); virtio 51-236% higher latency than queue-passthrough while SPDK-vhost matched VFIO in one test (LightIOV, 2023). [S] — [RosenBridge, FAST'26](https://www.usenix.org/system/files/fast26-qiu.pdf); [LightIOV](https://arxiv.org/pdf/2304.05148)
- Firecracker (in-VMM backend, no polling) added 49 µs to 4 kB read latency at QD1 in 2020. [F, earlier notes] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Xen: virtio backends can run in a non-dom0 driver domain using grant mappings (Linux `xen,dev-domid` / virtio-grant series, 2022; no performance numbers posted); for the classic blkfront/blkback protocol, grant map/unmap with TLB shootdowns was the dominant cost and persistent grants were introduced to remove it. [S] — [xen-devel/linux virtio-grant series](https://patchwork.kernel.org/project/xen-devel/cover/1650646263-22047-1-git-send-email-olekstysh@gmail.com/); [Xen Project: persistent grants](https://xenproject.org/blog/improving-block-protocol-scalability-with-persistent-grants/)
- vhost-user backends complicate snapshots in existing VMMs (Firecracker cannot snapshot vhost-user-blk; Cloud Hypervisor filled out vhost-user snapshot/restore in v52.0, 2026). [F, earlier notes] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md); [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- NVMe SR-IOV VF counts are vendor-specific with a practical ceiling near 254-255; SR-IOV "becomes awkward to scale" beyond that. [S] — [SNIA SDC'25: SSD virtualization](https://www.snia.org/sites/default/files/2025-09/SNIA-SDC25-Helmick-SSD-Virtualization.pdf)
- ublk docs: zero-copy servers "have to be trusted"; `UBLK_F_SHMEM_ZC` shares physical pages between client and server so matching O_DIRECT I/O needs no per-I/O registration. [F] — [kernel.org: ublk](https://docs.kernel.org/block/ublk.html)

### Inferences
- Path options and expected cost (analysis, not measurement):
  1. **Per-VM VMM proxies** (guest kick exits to the hypervisor, schedules the VMM, VMM forwards to the storage VM): two extra context switches and a copy or remap per request. Avoid for data; keep the VMM on the control path only (device config, feature negotiation, snapshot of queue indices).
  2. **Direct shared-memory virtqueues, vhost-user style**: the hypervisor maps the guest's virtqueue pages and data buffers into the storage VM (all guest RAM, or on demand); the guest's notify MMIO/hypercall is turned by the hypervisor into an event/IPI to a storage-VM worker without involving the VMM; completions inject the guest interrupt via a hypercall. Per-request overhead under load approaches SPDK-vhost numbers because EVENT_IDX suppresses most notifications while workers are busy; at QD1 the cost is one exit + one cross-VM wake + one interrupt injection (order of a few microseconds plus scheduling latency), small against an NVMe write of 10-20 µs and negligible against a flush on non-PLP media.
  3. **Bounce-buffer / restricted-DMA variant** of (2): the guest copies data into a pre-shared region (swiotlb-style) that is the only memory the storage VM can see. Costs one memcpy per byte (roughly 10 GB/s per core, i.e. about 0.4 µs per 4 KiB) but removes the storage VM's ability to read arbitrary guest memory, removes interaction with guest-memory CoW/dirty tracking for fork and snapshot (backend writes into guest RAM otherwise bypass stage-2 write-protect faults and need a separate dirty log), and makes fork trivial (the shared region is per-VM device state). For a multi-tenant sandbox host this is the better default; large sequential I/O is rare in the workload.
- Polling vs notification: at thousands of mostly idle sandboxes per host, per-VM polling is impossible; use a small fixed pool of storage-VM workers that adaptively busy-poll only the virtqueues that were active in the last few hundred microseconds and otherwise sleep on hypervisor events. Guest-side: `VIRTIO_RING_F_EVENT_IDX` on, one virtqueue per vCPU up to a small cap.
- NVMe namespace or SR-IOV VF passthrough gives near-native latency but: no CoW/fork, no thin provisioning or dedup across tenants, no lazy restore, tens-to-hundreds of functions per drive vs thousands of sandboxes, and passthrough devices block or complicate snapshot/migration. Reasonable only as a "performance volume" tier for a few database-heavy tenants, not for the sandbox root. What is worth passing through is the whole NVMe controller (all queues) to the storage VM, with one hardware queue pair per storage worker.
- Where the CoW map lives: keeping bitmap/manifest logic in the storage VM (Linux userspace, Rust) keeps the hypervisor TCB small; the hypervisor only needs "seal generation N for device D" as part of the atomic pause, which can be a synchronous call to the storage service while vCPUs are stopped. The earlier notes' alternative (CoW mapping inside the hypervisor) is not required for atomicity.

### Gaps
- No published performance or isolation evaluation of virtio backends in a separate VM on a type-1 microhypervisor (seL4/NOVA/pKVM/Xen virtio-grant) was found; all cost estimates above are inference and need prototyping (QD1 latency, IOPS per storage core, cross-VM wake latency on both x86-64 and ARM64).
- RosenBridge and LightIOV were seen only as snippets; their breakdowns should be read before quoting.
- SR-IOV VF counts for specific current enterprise SSDs were not found.

## 9. ARM64-specific considerations

### Takeaway
The main ARM64 risk is page-size coupling: a guest (or storage VM) kernel built with 16K or 64K pages changes page-cache granularity, the minimum efficient I/O unit, and DAX mapping granularity, while filesystem block sizes above the page size are only recently supported (XFS since 6.12, experimental; ext4 as a late-2025 patch series whose merge status I could not confirm). Keeping every on-disk and CoW unit at 4 KiB (or a multiple with 4 KiB addressing) keeps images portable across x86-64 and all ARM64 page sizes.

### Cited Findings
- XFS block size greater than page size (LBS) was merged for Linux 6.12 with an "EXPERIMENTAL: V5 Filesystem with Large Block Size" mount warning; it was motivated partly by testing 64K-block filesystems on 4K-page x86-64. [S] — [LWN 1009548](https://lwn.net/Articles/1009548); [LKML: enable bs > ps in XFS v13](https://lkml.iu.edu/hypermail/linux/kernel/2408.2/08517.html)
- ext4 "block size larger than page size" series (25 patches, Oct-Nov 2025, based on 6.18-rc2): 4K write performance unchanged; buffered writes about 50% faster than bigalloc on average; direct-I/O writes up to about 30% slower than bigalloc (checksum cost during allocation); all testing at PAGE_SIZE=4096; arm64 64K-page testing surfaced journal-credit and large-folio-order issues. Merge status not confirmed here. [F for the LWN mirror, S for the arm64 thread] — [LWN 1043513](https://lwn.net/Articles/1043513/); [LKML: ext4 LBS v2 discussion](https://lkml.iu.edu/2511.1/07563.html)
- The CVE-2026-24834 write-up indicates Kata's ARM64 path uses QEMU NVDIMM/DAX for the guest image and that read-only enforcement differed from x86 there (unverified claim), i.e. DAX rootfs is in use on arm64 but its protection semantics are platform-specific. [S] — [cvereports: CVE-2026-24834](https://cvereports.com/reports/CVE-2026-24834)
- virtio-fs DAX estimated at about 16 MB of guest struct-page memory per GB of DAX window with 4K pages. (2020, x86) [S] — [virtio-fs list](https://lore.kernel.org/all/20201211182956.GF3380@work-vm/T/)
- A ublk-over-SPDK tuning PR reports results on an RK3588 (ARM64) node: 4K randwrite QD32x4 from 125k to 187k IOPS, p99 from 6 ms to 1.6 ms, after poller and zero-copy changes, showing the userspace-backend path is viable but CPU-bound on small ARM cores. [S] — [Evariops/spdk PR #36](https://github.com/Evariops/spdk/pull/36)

### Inferences
- A filesystem with 4 KiB blocks mounts on 4K, 16K and 64K-page kernels; a filesystem made with 16K/64K blocks does not mount on a 4K-page kernel without LBS. Therefore: build all base images with 4 KiB FS blocks (ext4 `-b 4096`, EROFS 4K blocks), advertise 4096-byte logical blocks on virtio-blk, and keep the overlay bitmap at 4 KiB. Images and snapshots then move between x86-64 and ARM64 hosts and between guest kernels of different page size (disk snapshots only; memory snapshots are architecture- and page-size-specific).
- If a 16K- or 64K-page guest kernel is ever used (some ARM64 distros default to 64K; 16K is attractive for TLB reach), every buffered write dirties and writes back whole pages, so the effective minimum write becomes 16K/64K and a 4 KiB CoW granularity gives no benefit over 16K/64K for buffered I/O, while page-cache memory per small file rises (worse density for node_modules-style trees). Recommendation: 4K-page guest kernels on ARM64 for density; rely on stage-2 block mappings/THP for TLB reach instead.
- DAX on ARM64: mapping granularity equals the guest page size, and the pmem range needs struct pages in the guest (about 1.6% of the mapped size with 4K pages and 64-byte struct page); the EROFS image block size must equal PAGE_SIZE for FSDAX, so a DAX-mapped EROFS base built with 4K blocks is only DAX-usable by 4K-page guests. This is another reason to fix the guest page size at 4K on both architectures.
- The storage VM's own page size is independent of guests; with O_DIRECT backends, logical block size 4096 on the NVMe namespace, and io_uring fixed buffers, a 4K-page storage VM kernel is simplest. Stage-2 mappings of shared virtqueue/bounce regions should be 2 MiB blocks on both architectures (with 4K granule) to cut TLB misses in the storage VM.
- ARM64 server cores are generally weaker per-core than x86 for checksum/hash/zstd work; budget chunk hashing and compression at checkpoint time accordingly (use ARMv8 CRC32/SHA2 extensions; prefer BLAKE3 or SHA-256 with crypto extensions; zstd level 1-3).

### Gaps
- No primary source was read on virtio-pmem/DAX support status and performance on ARM64 guests, or on EROFS FSDAX with non-4K pages.
- ext4 LBS merge version unconfirmed; XFS LBS behaviour on 64K-page arm64 hosts not confirmed by the search results.
- No ARM64-vs-x86 measurements for virtio-blk backends or CoW layers were found.

## 10. Recommended design (synthesis)

### Takeaway
Build a purpose-made chunked CoW block service in the storage VM rather than adopting qcow2, dm-thin, ZFS or SPDK lvols: immutable content-addressed base images served lazily through a shared NVMe cache, a per-VM sparse overlay with a 4 KiB presence/zero map and stackable sealed generations, a small power-loss-protected write-ahead path so guest FLUSH is honest and cheap, and checkpoint/fork/hibernate implemented as "seal generation, publish hashed chunks, flat manifest". Guests run ext4 on a single virtio-blk root. Everything in this section is inference from the findings above.

### Cited Findings
- The component choices mirror designs that are in production and described in fetched sources: 4 KiB bitmap + sparse delta + sealed-overlay stacking + CAS chunk index (DigitalOcean); synthesized ext4 on virtio-blk with dirty bitmap replacing virtio-fs (Modal); manifest of content-hashed chunks with NVMe LRU cache and lazy restore (Cortex); 512 KiB chunk dedup with tiered caches and generational GC (Lambda); local journal + batched immutable objects with prefix consistency (LSVD); object-store-rooted durability with non-authoritative NVMe cache (Sprites). [F] — [DigitalOcean](https://www.digitalocean.com/blog/microvm-architecture); [Modal](https://modal.com/blog/vm-sandbox-filesystem); [Cortex](https://builders.cortex.io/blog/sandboxing-agents-part-2/); [Brooker et al., ATC'23](https://www.usenix.org/system/files/atc23-brooker.pdf); [LSVD](https://rs3lab.github.io/assets/papers/2022/hajkazemi-aschenbrenner:lsvd.pdf); [Fly.io Sprites](https://fly.io/blog/design-and-implementation/)

### Inferences
1. **Guest view**: one virtio-blk root (`/dev/vda`, ext4, 4 KiB blocks, logical/physical block size 4096 advertised, FLUSH + DISCARD + WRITE_ZEROES + MQ + EVENT_IDX + INDIRECT_DESC), thin-provisioned to a large apparent size (e.g. 64-128 GiB). Mount `noatime,lazytime,commit=15`; no `discard` mount option; guest agent runs `fstrim` on idle and before checkpoints. Optional extra read-only devices for shared toolchain/package-cache layers (EROFS), DAX-mapped only with stage-2-enforced read-only.
2. **Base images**: flatten OCI images deterministically into ext4 (Lambda/Modal style), chunk at a fixed 128-256 KiB aligned size, zstd-compress, store by content hash in object storage; a flat manifest (offset to hash) per image. Host-local uncompressed chunk cache on NVMe shared by all VMs (content-addressed, LRU, non-authoritative), plus an optional zone-level cache tier.
3. **Per-VM overlay**: identity-mapped sparse file (or raw extent region) per generation on a storage-VM XFS/ext4 volume opened `O_DIRECT`, with a 2-bit-per-4 KiB state map (absent / present / zero) kept in memory and persisted through the WAL; lookups are newest-generation-first with a merged in-memory index so chain depth does not add I/O. Full-block writes never read the parent.
4. **Write path and fsync**: backend workers batch virtqueue requests into io_uring submissions; data goes straight to the overlay with O_DIRECT; state-map updates are appended to a small per-host NVMe write-ahead log; guest FLUSH completes after one group-committed WAL sync (shared across VMs within a few-hundred-microsecond window). On PLP enterprise NVMe this makes fsync cost tens of microseconds while remaining crash- and power-safe on the host. A per-sandbox policy flag can downgrade to "no FLUSH advertised" for explicitly disposable sandboxes.
5. **Checkpoint / fork / hibernate**: with vCPUs paused, seal generation N (WAL sync), record virtqueue state, open N+1, resume; background job hashes dirty 4 KiB runs grouped into chunks, skips zero and already-known chunks, uploads, then publishes a flat manifest and marks the checkpoint complete. Fork = seal + two new generations. Hibernate = checkpoint, then drop local overlay generations once published. Restore = attach manifest, lazy fetch via cache, trace-driven prefetch. Background compaction merges sealed generations locally.
6. **Reclamation and GC**: discards set zero/absent state and punch holes; object-store GC by generational roots or mark-and-sweep over manifests with a grace period (immutable chunks make this safe to run offline).
7. **Fairness**: per-device token buckets (IOPS, bytes, burst) and weighted-fair dequeue in the storage service; charge CoW parent reads and flushes to the causing VM; cap hydration and checkpoint-upload I/O separately so background work cannot starve foreground guests.
8. **Transport**: virtqueues shared directly between guest and storage VM, notifications brokered by the hypervisor without the per-VM VMM on the data path; start with a per-VM pre-shared bounce region (storage VM never maps general guest RAM), measure, and only then consider direct mapping for large-I/O tenants. Whole-controller NVMe passthrough to the storage VM; no per-guest SR-IOV.
9. **What to measure first** (because public numbers are missing): QD1 4K write and fsync latency guest-to-NVMe through the storage VM on both architectures; fresh-fork first-write penalty vs steady state; diff size per checkpoint for real agent sessions at 4 KiB vs 64 KiB granularity; dedup/zstd ratio of uploaded diffs; guest page-cache duplication after fork; pause time attributable to sealing.

### Gaps
- This design is a synthesis; none of the cited platforms publishes end-to-end latency or density numbers for the equivalent of items 3-5, and the group-committed WAL flush path (item 4) has no public precedent among the sandbox providers surveyed (they relax durability instead).
- The choice of 128-256 KiB object-store chunk size is a judgment between Lambda's 512 KiB and the scattered-small-write profile of sandbox diffs; it needs validation against real diffs.
