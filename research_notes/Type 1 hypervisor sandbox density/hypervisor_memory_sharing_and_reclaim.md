## 1. CoW sharing from a common snapshot/template: persistence, what breaks it, data structures, page-table sharing

### Takeaway
Being "born shared" from a template is the cheapest and safest sharing there is, and the published production evidence (CodeSandbox, Cortex) says a resumed dev VM touches only a few hundred MB of a multi-GB guest and clones stay >90% shared, but nobody publishes a divergence-over-time curve for long-lived dev sandboxes, so the decay rate has to be measured. The mechanism a hypervisor needs is small: refcounted frames, a per-VM sparse map with "absent → look in parent layer" semantics, and a short layer chain that is flattened in the background; Xen's VM fork shows fork cost of ~0.75 ms when the child starts with an empty second-stage table.

### Cited Findings

**How much sharing persists (production and research evidence)**
- CodeSandbox (2022): clones share more than 90% of the source's data; a resumed VM typically touches only 300-400 MB even when the guest reports 3-4 GB in use. [F, from the earlier round] — [CodeSandbox: how we clone a running VM in 2 seconds](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3)
- CodeSandbox later post: Firecracker "only reads the memory that the VM needs to start", giving resume in ~200-300 ms; "most VMs load less than 1GB into memory". [S] — [CodeSandbox: cloning microVMs using userfaultfd](https://codesandbox.io/blog/cloning-microvms-using-userfaultfd)
- Cortex "Engrams" (2026, Firecracker): each host keeps one sparse shared-memory file per image (the "base shm"); every sandbox maps it `MAP_PRIVATE`, so clean pages share page-cache backing and writes get private pages by kernel CoW. A userfaultfd handler fills the base on demand: canonical chunks are populated once in the base shm and mapped with `UFFDIO_CONTINUE` (sharing preserved); chunks that differ in a session snapshot are installed privately with `UFFDIO_COPY`. Memory is content-addressed in 512 KiB chunks; faults fetch the surrounding 512 KiB chunk while CoW stays 4 KiB-granular. [F] — [Cortex builders: Snapshots, copy-on-write, and the economics of agent sandboxes](https://builders.cortex.io/blog/sandboxing-agents-part-2/)
- Cortex's only quantitative sharing datum: a visualization showing PSS/RSS of 35% across three guests (ideal with perfect sharing is 33%), and 49 MiB physically allocated against 4 GiB of apparent base shm "from a first canary". Their cost model after the change: RAM cost is proportional to "base shm + dirty RAM" rather than requested RAM. No time series of divergence is given. [F] — [Cortex builders blog](https://builders.cortex.io/blog/sandboxing-agents-part-2/)
- Cortex's motivating problem: "a 4 GiB guest could pull several GiB of pages into host RAM once real workloads ran", and a naive snapshot of a 16 GiB RAM / 128 GiB disk sandbox moved ~144 GiB to blob storage. [F] — [Cortex builders blog](https://builders.cortex.io/blog/sandboxing-agents-part-2/)
- E2B stores a paused sandbox as memory and rootfs diffs against the template with header files resolving diff chains (i.e. a layer chain, flattened by resolution at read time). [F, earlier round] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- Potemkin (SOSP'05, Xen; dated): "delta virtualization" is CoW sharing between VMs so that per-VM state is only the unique data; the number of VMs is limited by unique memory per VM. Deployed with 128 MB Linux honeypots; on 2 GB servers the authors estimated memory for about 1000 VMs per host and had tested about 100 at the time. [S, from a slide summary of the paper] — [Vrable et al., Potemkin, SOSP'05](https://www.eng.utah.edu/csl-sem/old/f05/papers/potemkin-sosp05.pdf)
- Waldspurger (OSDI'02, dated but still the reference measurement for "identical Linux VMs"): with 1-10 identically configured Red Hat Linux 7.2 VMs (40 MB each) running SPEC95, sharing approaches 67% of memory and nearly 60% of all VM memory is reclaimed for large VM counts; most of it is redundant code and read-only data, little is zero pages. [F] — [Waldspurger, Memory Resource Management in VMware ESX Server](https://research.cs.wisc.edu/areas/os/Qual/papers/vmware-memory.pdf)
- Difference Engine (OSDI'08): for homogeneous workloads savings of up to 90% (abstract); RUBiS VMs 65-75%; kernel-compile VMs about 40% with four or more VMs. Kernel compile is the closest of these to a coding-agent workload and is the lowest. [F] — [Gupta et al., Difference Engine](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/gupta/gupta_html/)
- Medes (EuroSys'22): warm serverless sandboxes have a high fraction of duplicated memory; a "dedup" sandbox state keeps only unique chunks and reduces function memory state by 16-58% (authors' figure). [S] — [Medes project page](https://utns.cs.utexas.edu/projects/medes/)
- Nephele (EuroSys'23, unikernel cloning on Xen): ~8x faster instantiation and ~3x more active unikernel VMs on the same hardware than booting separate unikernels. Per-clone memory and clone-time figures were not retrieved. [S] — [Nephele experiments repo](https://gh.r-mj.com/nephele-vm/experiments)

**Fork cost on a type-1 hypervisor**
- Xen VM fork (Lengyel, 2020): fork creation ~745 µs (~1300 forks/s) and fork reset ~111 µs (~9000 resets/s) on an i5-8350U; an early cover letter reported 0.0007 s fork and 0.0001 s reset, with the device-model launch (~1 s) being the slow part, which is why creation is split so the device model can be launched late or not at all. The first version (v2) measured 0.018 s. The feature is experimental and compiled out unless `XEN_CONFIG_EXPERT`. "For a fork that has a lot of memory it is likely more performant to create a new fork rather than reset one." [S] — [Lengyel, VM Forking & Hypervisor-based Fuzzing with Xen (slides)](https://www.slideshare.net/tklengyel/vm-forking-and-hypervisorbased-fuzzing-with-xen); [Xen-devel VM forking v8 cover letter](https://lore.kernel.org/all/cover.1581362050.git.tamas.lengyel@intel.com/T/)
- Difference Engine micro-costs (2008 hardware, useful as ratios): share_pages 6.2 µs, cow_break 25.1 µs, compress_page 29.7 µs, uncompress 10.4 µs, patch_page 338 µs, unpatch 18.6 µs. [F] — [Difference Engine](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/gupta/gupta_html/)

**What breaks sharing**
- Free-page reporting followed by host zeroing means reclaimed-then-reused pages come back as fresh private zero pages, and the guest then zeroes them again on allocation; a 2026 kernel series (Tsirkin, RFC April 2026, v9 late May 2026, merge status unconfirmed) adds a flag so a driver can declare "host already zeroed this" and the guest skips its own zeroing. [S] — [LWN 1073887](https://lwn.net/Articles/1073887/); [LKML RFC 2/9](https://lkml.iu.edu/2604.1/07454.html)
- Hildenbrand (2020) on pre-zeroing proposals: with reporting enabled, the host zeroes pages again each time they return to the guest, which hurts especially for huge pages. [S] — [lore: virtualization list](https://lore.kernel.org/virtualization/840ff69d-20d5-970a-1635-298000196f3e@redhat.com/)
- Firecracker: KVM dirty logging "negates most huge page benefits"; hugetlbfs-backed guests need the uffd restore path. [F, earlier round] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Difference Engine observation: savings from patching and compression are lost when the page is read or written, whereas a shared page can be read for free; only writes break full-page sharing. [F] — [Difference Engine](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/gupta/gupta_html/)

### Inferences
- **Expected shape of divergence for an agent dev sandbox** (no published curve; reasoning from the mechanisms): at fork, 100% shared. Within seconds, the pages written are kernel per-CPU data, slab, stacks, the agent's heap: tens of MB. The dominant long-run divergence is not anonymous memory but the **guest page cache**: every file the guest reads from a virtio-blk disk is copied into a guest-private page (a write, from the hypervisor's point of view, into a frame that was "free" in the template). A `git clone` plus `npm install` plus a build will write GBs of guest-physical memory that is private from the hypervisor's point of view even though half of it is byte-identical across sandboxes. So CoW sharing protects the template's resident set (kernel text/rodata, agent, runtimes already loaded, page cache already warm at snapshot time) and nothing else. This is the reason section 3 (shared page cache via DAX) matters at least as much as CoW.
- **Sharing breakers, by mechanism, and countermeasures:**
  - *Guest free-list churn.* Pages freed and reallocated in the guest are rewritten; the template's contents of "free" pages are garbage that is shared but worthless. Countermeasure: before snapshotting the template, have the template's guest drop caches selectively, compact, and (ideally) zero free memory so free pages are all zero; the hypervisor then represents them as "absent/zero" (no frame at all) rather than as shared frames.
  - *`init_on_free=1` / `init_on_alloc=1`.* `init_on_free` makes the guest write zeros on every free: this breaks CoW on a shared page merely to zero it (bad), but the result is a zero page that a zero-detecting hypervisor can drop (good). `init_on_alloc` zeroes on allocation and is a pure extra write from a sharing perspective. With a hypervisor that returns zero-filled pages on first touch, the right guest config is `init_on_alloc=0 init_on_free=0` plus free page reporting, and the pending "host-zeroed" flag once merged.
  - *ASLR/KASLR.* Irrelevant for snapshot forks: all clones inherit the snapshot's layout, so pages are identical. It matters for (a) security (all clones of a template share KASLR offsets and userspace layouts until processes re-exec) and (b) content-based dedup between independently booted VMs, where relocated kernel text and pointer-bearing data pages differ. This is another argument for "share by construction, not by scan".
  - *Guest THP and khugepaged.* A guest that collapses to 2 MiB pages writes 512 guest-physical frames to consolidate, turning shared 4 KiB pages into private ones, and a guest THP fault zero-fills 2 MiB where the app needed 4 KiB. For density, run guests with `transparent_hugepage=madvise` (or `never`) and keep khugepaged conservative. E2B's envd deliberately collapses its heap into THPs before pause to cut resume faults: this is a latency-for-density trade in the opposite direction, sensible only for a small hot heap.
  - *Guest compaction and page migration.* Moves contents between guest frames; each move is a write to a new frame and leaves the old one as stale garbage. Proactive compaction (`vm.compaction_proactiveness`) should be 0 in guests except right before a template snapshot.
  - *Page cache churn.* Addressed by not having a guest page cache for shared content (DAX) and by bounding the guest page cache for private content (small guest RAM plus a hypervisor-level cache, or cgroup limits in the guest).
  - *Guest kernel touching all memory at boot* (struct page init, `memblock` poisoning, memtest): avoided because clones never boot; only the template boots once.
- **Data structures for a multi-generation CoW page store** (design proposal, generalizing Xen mem_sharing, Cortex's base shm, and E2B's diff chains):
  - *Frame table*: one entry per host 4 KiB frame with a 32-bit refcount, a state (free / private / shared-RO / template / zero / swapped-in-progress) and an owner or reverse-map hint. A refcount per frame is the only thing strictly required for CoW; a reverse map (frame → list of (VM, GFN)) is needed only if the hypervisor wants to migrate or reclaim a shared frame, and can be avoided for template frames by never reclaiming them individually (reclaim the whole template layer when its last child dies).
  - *Layers*: a snapshot is an immutable layer = sparse map GFN → {frame, zero, absent-here, on-disk(extent)}. A running VM = one writable top layer (its second-stage table is the materialized index) + an ordered parent chain. A lookup on a second-stage fault walks the chain: top, parent, grandparent, base. Fork of a running VM freezes its top layer into a new immutable layer and gives parent and child fresh empty tops (this is exactly Xen's "empty EPT + parent pointer" generalized to chains).
  - *Chain length control*: lookups are only on faults, so a chain of 3-5 is harmless; bound it by background flattening (merge a layer into its sole child when its refcount is 1; or materialize a frequently hit ancestor mapping into the child's layer as a read-only reference). Because layers hold references to frames rather than copies, flattening is pointer copying plus refcount adjustment, not page copying.
  - *Zero and absent*: "zero" is an explicit map state backed by no frame; reads map a global read-only zero frame (or, better, leave unmapped until first write and then allocate a zeroed private frame, saving the read-only mapping step for the common write-first case).
  - *On-disk state*: the same map entry can point at an extent in a snapshot file or a swap slot, which is what makes hibernate, swap and lazy restore one mechanism (see section 4).
- **Can second-stage page-table subtrees be shared between forks?** Yes in principle, and it is the difference between O(resident memory) and O(1) fork. A leaf table page (512 PTEs, covering 2 MiB) whose entries are all read-only references to template frames is identical in every clone, so the PMD entries of many VMs can point at the same physical leaf table. Rules: (1) shared tables must be read-only and execute-only-as-permitted in every sharer; (2) on the first write fault under a shared table, copy the 4 KiB table page (table-level CoW), then do the normal data-page CoW; (3) accessed/dirty bits written by hardware into a shared table become meaningless per-VM (EPT A/D and Arm HAFDBS update the table in place), so either disable hardware A/D updates for shared subtrees (on x86 this is per-EPTP, not per-subtree, so in practice treat A bits in shared subtrees as "template-level" information and exclude shared subtrees from per-VM idle tracking, which is fine because those pages are not reclaimable per-VM anyway); (4) TLB/VPID invalidation on unshare is per-VM as usual. Savings: a fully populated 4 GiB guest at 4 KiB granularity needs 2048 leaf table pages = 8 MiB (0.2% of guest RAM, arithmetic) plus ~3 upper-level pages; with shared subtrees a fresh clone needs only its top-level page(s) until it writes. At 10,000 VMs this is the difference between ~80 GiB and well under 1 GiB of second-stage tables. Xen does not do this (child EPT is populated lazily instead); lazy population gets most of the benefit with far less complexity: a clone that touches 300 MB needs ~150 leaf tables = 0.6 MiB.
- **Recommendation**: lazy population first (simple, Xen-proven), shared read-only leaf tables as a later optimization only for the template's hot working set (where it also removes ~75k minor faults per clone for a 300 MB working set).
- Fork cost budget for this design: pausing vCPUs + freezing the top layer + allocating a root table + copying vCPU/virtio state. Xen's 745 µs on a 2017 laptop CPU suggests sub-millisecond is the right target; write-protecting the parent's existing mappings is the O(resident) part and can be done lazily with a generation counter (bump the layer generation; a writable mapping with a stale generation is treated as read-only on the next fault, with a TLB flush for the parent).

### Gaps
- No published measurement of CoW sharing versus time for long-lived dev/agent sandboxes. CodeSandbox (>90% at clone, 300-400 MB touched on resume) and Cortex (PSS/RSS 35% over three guests) are point values near fork time. This is the single most important number to measure in a prototype: private bytes per sandbox after 1 min, 1 h, 1 day of typical agent work, split into anonymous memory and guest page cache.
- SnowFlock (fraction of parent memory fetched by clones) and the Potemkin paper's own per-VM delta figures were not retrieved; the Potemkin figures above come from a slide summary.
- Nephele clone time and per-clone memory, Catalyzer sfork, and Lambda SnapStart internals were not retrieved. Recalled only: Lambda's on-demand loading paper uses fixed-size chunks with content-addressed dedup and convergent encryption [R] — [Brooker et al., ATC'23](https://www.usenix.org/conference/atc23/presentation/brooker).
- No measurements found of shared second-stage page-table subtrees in any production hypervisor; the analysis above is design reasoning.
- The CodeSandbox posts on uffd and compression returned HTTP 403; only snippets were used.

## 2. Content-based page sharing / dedup: savings, CPU cost, security history, safe policy

### Takeaway
Scanning dedup recovers real memory on similar VMs (roughly 7-33% in VMware's production samples, ~50% with zero pages in Difference Engine's mixed workload, 60%+ only for near-identical idle VMs), but every major vendor backed away from cross-tenant dedup after 2014-2016 because merge/unmerge timing leaks page contents and, combined with Rowhammer, lets an attacker corrupt a victim's page. For this design, scanning dedup should be limited to zero-page elimination and to matching guest pages against the trusted read-only template/base image (and only within one tenant's trust domain); the rest of the win is better obtained by construction (CoW fork and shared DAX page cache).

### Cited Findings

**Measured savings**
- VMware ESX (OSDI'02) production deployments: (A) 10 Windows NT VMs, 2048 MB total: 42.9% shared, 32.9% (673 MB) reclaimed; (B) 9 Linux VMs, 1846 MB: 29.2% shared, 18.7% (345 MB) reclaimed, of which 70 MB zero pages; (C) 5 Linux VMs, 1658 MB: 10.0% shared, 7.2% (120 MB) reclaimed, of which 25 MB zero pages. A single VM alone reclaimed ~5 MB, ~55% of it zero pages. [F] — [Waldspurger OSDI'02](https://research.cs.wisc.edu/areas/os/Qual/papers/vmware-memory.pdf)
- ESX mechanism: pages are scanned randomly, hashed with a 64-bit hash, looked up in a hash table; a match is confirmed by full comparison; an unshared scanned page is not marked CoW but recorded as a "hint" frame whose hash is re-checked on a later match (avoids CoW faults on pages that never get shared). Per-VM and system-wide scan rate limits are set so CPU overhead is negligible; "we measured no significant difference in the aggregate throughput" with sharing on vs off. ESX always attempts to share a page before paging it out to disk. [F] — [Waldspurger OSDI'02](https://research.cs.wisc.edu/areas/os/Qual/papers/vmware-memory.pdf)
- Difference Engine MIXED-1 snapshot (393,120 pages across heterogeneous VMs): 38% zero pages, 13% non-zero sharable, 49% unique. Full-page sharing alone: 50% reduction; adding sub-page patching: 77% reduction (patching covered 144,497 pages, average patch 1,070 bytes). Overall overhead claimed under 7%, though one benchmark in their Table 3 shows ~13% (620 s to 702 s). Versus ESX: ~1.5x the savings on homogeneous, 1.6-2.5x on heterogeneous workloads. [F] — [Difference Engine](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/gupta/gupta_html/)
- Medes: 16-58% memory reduction for deduplicated serverless sandboxes, with restore latency cost from reassembling chunks (uses modified CRIU and RDMA). [S] — [Medes project page](https://utns.cs.utexas.edu/projects/medes/)
- A follow-up ("User-guided Page Merging", arXiv 2311.13588) states KSM is "not designed to handle volatile and short-term workloads". [S] — [arXiv 2311.13588](https://arxiv.org/pdf/2311.13588)

**Linux KSM as of kernel 6.x/7.x**
- Opt-in per range via `madvise(MADV_MERGEABLE)`; ksmd started via `/sys/kernel/mm/ksm/run`. The docs state scans "may use a lot of processing power" and some installations disable KSM for that reason. [F] — [Kernel docs: KSM](https://docs.kernel.org/admin-guide/mm/ksm.html)
- `smart_scan` (default on): pages that previously failed to dedup are skipped, with skip count growing with repeated failure; `pages_skipped` shows effectiveness. [F] — [Kernel docs: KSM](https://docs.kernel.org/admin-guide/mm/ksm.html)
- Scan-time advisor (`advisor_mode=scan-time`, default `none`): auto-tunes `pages_to_scan` to hit `advisor_target_scan_time` (default 200 s for a full pass) bounded by `advisor_max_cpu` (default 70% of one CPU) and `advisor_min/max_pages_to_scan` (500 / 30000). [F] — [Kernel docs: KSM](https://docs.kernel.org/admin-guide/mm/ksm.html)
- `use_zero_pages` (default 0): merge all-zero pages with the kernel zero page instead of with each other. `max_page_sharing` bounds how many mappings share one KSM page to bound rmap-walk latency (minimum 2). `general_profit` = saved pages x page size minus rmap_item metadata; if rmap_items per merged page exceeds ~64 the policy is not paying for itself. [F] — [Kernel docs: KSM](https://docs.kernel.org/admin-guide/mm/ksm.html)
- Recalled, not on the fetched page: `max_page_sharing` default is 256; process-wide enablement via `prctl(PR_SET_MEMORY_MERGE)` arrived in Linux 6.4; smart scan in 6.7 and the advisor in 6.8. [R] — [Kernel docs: KSM](https://docs.kernel.org/admin-guide/mm/ksm.html)

**Security history and vendor responses**
- VMware KB 2080735 (Oct 2014) announced that ESXi update releases would no longer allow inter-VM TPS by default; rationale: risk judged low but products should ship with the most secure defaults. The mechanism is salting: `Mem.ShareForceSalting=2` by default, each VM gets a distinct salt, so sharing only happens within a VM (and for zero pages [R]); VMs given the same salt (`sched.mem.pshare.salt`) can share with each other; setting it to 0 re-enables global inter-VM sharing. VMware advised watching free memory, ballooning and swapping after the change because free memory can drop. [S] — [Broadcom KB 318959 (formerly 2080735)](https://knowledge.broadcom.com/external/article/318959/security-considerations-and-disallowing.html); [Broadcom KB 323624 (formerly 2097593)](https://knowledge.broadcom.com/external/article/323624/additional-transparent-page-sharing-mana.html)
- Flip Feng Shui (USENIX Security'16): an attacker VM uses dedup to get a victim's page physically placed on a Rowhammer-vulnerable frame the attacker has profiled, then flips a bit in the victim's page without writing to it (so no CoW). The authors' primary recommendation is disabling memory deduplication (KSM, TPS, content-based sharing); press coverage of the paper mentions "less efficient zero-page deduplication" as a fallback. [S] — [VUSec Flip Feng Shui project page](https://vusec.net/projects/flip-feng-shui); [Razavi et al., USENIX Security'16](https://usenix.org/conference/usenixsecurity16/technical-sessions/presentation/razavi)
- Recalled details of FFS: demonstrated against OpenSSH `authorized_keys` (flipping a bit in an RSA public key to make it factorable) and apt/GPG trust; works because KSM keeps the attacker-controlled physical page as the merged copy when the attacker's page reaches the stable tree first. [R] — [Razavi et al.](https://usenix.org/conference/usenixsecurity16/technical-sessions/presentation/razavi)
- Dedup Est Machina (IEEE S&P'16) used dedup timing to leak randomized addresses (ASLR) rather than to place data, per the VUSec page. [S] — [VUSec Flip Feng Shui project page](https://vusec.net/projects/flip-feng-shui)
- Suzaki et al., "Memory deduplication as a threat to the guest OS" (EuroSec'11): write-latency difference on a CoW-merged page reveals whether another VM holds an identical page, enough to detect which applications/files another guest has loaded. [R] — [Suzaki et al., EuroSec'11](https://dl.acm.org/doi/10.1145/1972551.1972552)
- Firecracker's pmem documentation (2025-2026) applies the same reasoning to explicitly shared mappings: sharing a backing file lets multiple VMs map the same physical pages, "which could be used as a side channel by an attacker inside a microVM"; operators must evaluate against their threat model. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- The Firecracker NSDI'20 paper lists dedup that does not sacrifice side-channel isolation as open future work. [F, earlier round] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)

### Inferences
- **What each attack class needs, and which policies remove it:**
  1. *Existence oracle by CoW timing* (Suzaki, CAIN, Dedup Est Machina): attacker crafts a page, waits for the scanner, times a write. Needs: attacker-chosen content can be merged with a victim's secret-dependent page. Removed by: never merging pages across trust domains; or merging only against content that is public anyway (the base image), where "does the victim have this page of the public base image loaded" still leaks *which* base-image pages a victim touched (activity fingerprinting), a weaker leak equivalent to what any shared page cache gives (Flush+Reload-style cache probing on shared frames is the remaining channel).
  2. *Flip Feng Shui placement*: needs the attacker's physical frame to become the backing frame of a victim mapping. Removed by: when merging against the template, always keep the *template's* frame (hypervisor-owned, never guest-chosen) and free the guest's; never let a tenant-supplied frame back another tenant's mapping. Zero-page-only dedup satisfies this trivially (backing frame is a hypervisor zero frame). Template frames should come from memory with ECC and, if paranoid, a dedicated physical region.
  3. *Read-side cache channels on shared frames* (Flush+Reload/Prime+Probe on a shared read-only page): present for any shared frame, including CoW-from-template and DAX page cache. Accepting it for public base-image content is the industry norm (it is what container hosts do with shared image layers) but it should be a stated decision; per-tenant templates should never be shared across tenants.
- **Safe policy for this design** (ordered by value/risk):
  - Zero-page elimination: always on, all tenants. No cross-tenant information (any tenant can already infer a zero page is zero).
  - Template-relative dedup ("re-share with parent"): when a private guest page is found equal to the page at the *same GFN* in its own ancestor layer (e.g. after hibernate/restore, or after the guest wrote identical contents back), drop the private frame and re-point at the ancestor. This needs no hash table and no cross-VM matching: one memcmp against a known candidate. It is the natural product of diffing at hibernate time and is side-channel-neutral relative to plain CoW.
  - Content-hash dedup against the trusted base-image corpus (any GFN): optional, tenant-scoped or public-base-only, hypervisor frame always wins. Good for catching guest page cache pages of base-image files if DAX is not used.
  - Arbitrary cross-VM KSM-style merging: off across tenants; possibly on within one tenant's fleet as an explicit opt-in.
- **Scan cost model**: KSM's own defaults imply the scale: a 200 s full-pass target capped at 70% of a core. For a 512 GiB host that is ~134M pages per pass; at ~1-2 µs per page for a cheap checksum that is several core-minutes per pass. The hypervisor can do much better than a blind scan because it knows which pages are private and recently dirtied (second-stage dirty bits): only private pages that have been clean for N seconds are candidates, and template-relative compare needs no global index. Doing the compare at hibernate/pause time (when the page is being read anyway to write it out) costs almost nothing extra.
- Sub-page patching (Difference Engine) is not worth its complexity here: 338 µs to patch in 2008, any access (even read) faults, and the fork model already captures identical pages. Compression of cold pages (section 4) captures most of the remaining win with a simpler invariant.
- KASLR and per-boot randomization reduce scanning dedup between independently booted VMs but not between forks; another reason scan-based savings measured on "identical VMs booted separately" (Waldspurger's 60%) overstate what scanning would add on top of CoW fork.

### Gaps
- VMware KB text was seen only via search snippets (the snippets disagree on which default applied at which patch level; the stable reading is: late-2014 patches added the salting capability with it off, the following update releases turned it on by default).

## 3. Shared page cache for common files: virtio-pmem/DAX, virtio-fs DAX, EROFS, pitfalls

### Takeaway
Mapping a read-only base image into every guest as a DAX device makes the base image's file data exist once on the host and zero times in guest RAM, and it is now mainstream for microVMs (Firecracker has virtio-pmem with root-device support; the kernel community is actively cutting its per-device metadata cost specifically for AI sandbox microVMs). The costs are guest struct-page metadata (~1.56% of device size today), per-VM second-stage mappings for the window, 2 MiB alignment rules, and an explicit cross-VM shared-frame side channel that must be accepted only for public content.

### Cited Findings

**Firecracker virtio-pmem (fetched docs, 2026)**
- virtio-pmem is backed by an mmap'd host file exposed as a guest-physical region; guest sees `/dev/pmemN`; it can be the root device (`root_device`, `rootflags=dax`). DAX "avoids using the guest page cache, since the device is already in memory"; the docs recommend DAX to reduce duplicated data in guest page cache. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- Measured in the doc: a 128 MB VM booted from pmem without DAX has RSS ~120 MB; with DAX ~96 MB, similar to a virtio-block root. Two 128 MB VMs sharing a 100 MB pmem file have a worst-case footprint of ~356 MB instead of 456 MB because the shared file is counted once. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- The backing is a `MAP_SHARED` file, so the host can page it out (it is ordinary host page cache); pmem raises the VM's maximum possible memory use (RAM + pmem region). [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- Read-only pitfall: the host maps the file read-only but the guest kernel still believes the device is writable; a guest write on x86-64 is typically discarded by KVM with a warning, on aarch64 it causes a KVM internal error (ENOSYS) and Firecracker stops the VM. Guests must mount `-o ro`. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- Alignment: the guest region must be 2 MiB-aligned; the tail between end-of-file and the next 2 MiB boundary is filled with private anonymous pages. aarch64 guests need `CONFIG_ARM64_PMEM` for DAX. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- DoS surface: guest flush requests become `msync(MS_SYNC)` on the host; needs a rate limiter or cgroup `io.max`. First access to each page is slow (KVM builds the mapping); huge pages (tmpfs THP or hugetlbfs) reduce fault counts. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- Snapshots store pmem configuration only; on restore the same backing file must be at the same path unless `pmem_overrides` is used. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- A Firecracker feature request proposes a userfaultfd/on-demand backend for pmem so microVMs can share host page cache for lazily loaded images; it notes the alternatives are virtio-block (no DAX, double buffering) or vhost-user-fs (more complex). Proposal, not shipped. [S] — [Firecracker issue 5740](https://github-users.yhajoa.workers.dev/firecracker-microvm/firecracker/issues/5740)

**Guest-side metadata cost of DAX devices**
- Muchun Song (ByteDance), "[PATCH 0/4] mm: Reduce struct page overhead for FS-DAX pmem", 3 Sep 2026: with virtio-pmem FS-DAX the guest allocates and initializes struct pages for every advertised PFN up front; the vmemmap is "about 1.56% of the pmem device size" (~16 MiB per GiB) and its initialization "can noticeably slow down startup for lightweight VMs". The series maps the vmemmap to a shared read-only page and materializes private metadata only when a DAX fault inserts a PFN into a user mapping. Stated target: short-lived sandbox microVMs run by AI and code-execution services, small, densely packed, sparse disk images. Posted, not confirmed merged. [F] — [LWN 1092485](https://lwn.net/Articles/1092485/)
- virtio-fs DAX window: Vivek Goyal estimated ~16 MB of guest memory for page descriptors per 1 GB of DAX window, and warned that this can offset the benefit of eliminating guest page cache; when the data set exceeds the window, reclaiming and re-establishing mappings is very expensive; files under 32 KB are better without DAX because each can occupy a full 2 MB window slot (motivation for per-file DAX). "There is no sharing between dax windows unless they map the same file on the host." (2020-2021) [S] — [kata-dev: virtiofs cache and dax](https://lists.katacontainers.io/pipermail/kata-dev/2021-May/001931.html); [Alibaba: virtiofs per-inode DAX](https://developer.aliyun.com/article/863752)

**EROFS**
- EROFS page cache sharing (`-o inode_share,domain_id=...`): files with identical content (identified by a fingerprint xattr written at mkfs time, e.g. `mkfs.erofs --xattr-inode-digest=trusted.erofs.fingerprint`) share one page cache copy across mounts, scoped by `domain_id` for security; privileged mounts only. Cover-letter measurements, two minor versions of the same container image: page cache after reading all files reduced 16-49% (redis 241→163 MB, postgres 872→630, tensorflow 2771→2340, mysql 926→735, nginx 390→219, tomcat 924→474); runtime container memory reduced 4-47% (e.g. postgres 149.1→95 MB, tomcat 186→99 MB, redis 34.9→33.6 MB). v14 was applied to the `vfs-7.0.iomap` branch in Jan 2026 (so Linux 7.0-era); mainline release status not independently confirmed; Christoph Hellwig objected to the design. [F for numbers, S for merge status] — [patchew: erofs page cache sharing v14](https://patchew.org/linux/20260109102856.598531-1-lihongbo22@huawei.com); [linux-erofs list](https://lists.ozlabs.org/pipermail/linux-erofs/2026-January/014780.html)
- This is an *in-guest* (or in-host) mechanism: it dedups page cache across mounts within one kernel. It helps a hypervisor only where one kernel serves many images (host side, or inside one guest running several containers). [F, by the cover letter's description] — [patchew](https://patchew.org/linux/20260109102856.598531-1-lihongbo22@huawei.com)
- A kernel maintainer noted in a 2026 DAXFS thread that EROFS on DAX is already used by various users for shared read-only images. [S] — [LKML DAXFS thread](https://lkml.iu.edu/2601.3/02273.html)
- Blaxel/Baseten-style layout (vendor blog, 2026): reads go to a read-only EROFS base, writes go to a tmpfs upper layer through overlayfs; the base image is kept out of the memory snapshot; moving a Next.js base image from an in-memory initramfs to this layout cut memory "from four GB to one GB, a 75% reduction". [F, vendor claim] — [Blaxel blog: sandbox snapshot/hibernate/resume](https://blaxel.ai/blog/sandbox-snapshot-hibernate-resume-ai-agents)

### Inferences
- **Why this matters more than it looks for coding sandboxes**: toolchains, language runtimes, `node_modules`-style base layers and the distro are GBs of read-mostly files. Via virtio-blk, each sandbox that uses them holds a private guest page cache copy (and after fork these are exactly the pages that diverge, section 1). Via a DAX-mapped read-only image, file pages are host frames mapped read-only into each guest: resident once per host regardless of sandbox count, reclaimable by the hypervisor at any time without guest involvement (drop the second-stage mapping, re-fault from the image later), and never part of any snapshot.
- **In a hypervisor that owns stage-2 tables, "virtio-pmem" collapses to a very small mechanism**: a read-only image store (content-addressed 2 MiB or 4 KiB extents held in hypervisor frames, shared by all VMs using that image) plus a guest-physical window whose stage-2 entries point at those frames read+execute, no write. No host page cache, no VMM mmap, no msync path for read-only images (so Firecracker's flush-DoS concern disappears; simply fail or ignore flush on read-only devices). The guest-visible device should be advertised read-only where the guest driver allows; a guest write to the window should inject a fault or be ignored consistently on both architectures (Firecracker's x86/arm64 divergence is a KVM artifact to avoid).
- **The DAX image window is the ideal place for 2 MiB mappings and shared stage-2 subtrees**: contents are immutable, identical in every VM, never CoW'd, never dirty-tracked. A 4 GiB image window mapped with 2 MiB blocks costs 2048 PMD entries = 16 KiB of tables per VM (or zero if the PMD table itself is shared). This needs the image store to hold file data in 2 MiB-contiguous physical extents and EROFS laid out uncompressed and 2 MiB-aligned for large files; small files then share frames at 4 KiB granularity.
- **EROFS compression vs DAX**: DAX requires uncompressed data on the device (compressed extents must be decompressed into guest page cache, which defeats the purpose). So the base image costs more "disk" (host RAM, when resident) but is shared; host-side cold image pages can still be compressed or dropped by the hypervisor since they are re-readable.
- **Writable layer**: overlayfs with the DAX EROFS lower and a private upper (virtio-blk ext4/xfs or tmpfs). Copy-up of a large file on first write is the classic overlayfs cost; base images should be organized so mutable trees (workspace, caches) live on the upper from the start.
- **Guest struct-page cost**: until the Muchun Song series (or equivalent) lands in guest kernels, an N GiB pmem window costs ~16 MiB/GiB of guest RAM for vmemmap, written at device probe. For forked guests this is paid once in the template (shared by CoW afterwards) as long as the guest does not write those struct pages; DAX faults do write refcounts/mapcounts into struct pages of mapped PFNs, so the vmemmap for the *used* part of the image diverges per clone (~1.56% of the image bytes each sandbox actually maps). Still two orders of magnitude better than private page cache.
- **Snapshots and DAX**: a memory snapshot of a guest with DAX mappings contains guest PTEs pointing into the window, so the window must be re-established at the same guest-physical address with the *same image version* on restore/fork; image identity (content hash) must be part of snapshot metadata and images must be immutable and refcounted by snapshots. Image garbage collection is therefore tied to snapshot lifetime.
- **Page size pitfall on arm64**: a guest built with 16K or 64K pages needs the window, image block size and alignment to be compatible; a 4K-block EROFS image cannot be DAX-mapped by a 64K-page guest. Standardize on 4K-granule guests on both architectures (also best for CoW granularity), or build per-granule images.
- **virtio-fs with DAX** gives the same sharing with file-level granularity and a mutable shared tree, but needs a filesystem server per VM (or in the hypervisor), a window manager, and has the window-thrash and small-file pathologies cited above; for immutable base images a block-like pmem/EROFS image is simpler and has a smaller TCB. Recalled, unverified: the Rust `virtiofsd` does not implement the DAX window and Cloud Hypervisor dropped virtio-fs DAX for that reason [R] — [virtio-fs project](https://virtio-fs.gitlab.io).
- **Side channel**: every sandbox mapping the same image frame can run cache-timing probes on it. Policy: public base images shared across tenants (equivalent to a public container layer); tenant-private images shared only within the tenant.
- Expected saving (rough, to be measured): if a typical sandbox has 0.5-2 GiB of base-image file pages hot in its page cache, DAX sharing removes that entirely from the per-sandbox private set. For mostly idle sandboxes it is plausibly the largest single reduction after lazy allocation.

### Gaps

## 4. Hypervisor-level reclaim of cold guest memory; hibernate-to-disk and wake

### Takeaway
Fleet evidence says 20-32% of memory is cold enough to offload even in busy services (Google, Meta), and far more in idle sandboxes, where a resumed VM needs only a few hundred MB; the cheap tier is compression at microsecond fault cost, the deep tier is NVMe at ~100 µs per fault, and whole-VM hibernate is what every sandbox provider actually ships, with ~1 s resume being typical and pause cost of seconds per GiB being the weak spot of KVM/Firecracker designs. A hypervisor that owns stage-2 tables can unify lazy restore, swap, compression and hibernate as states of one page map, track idleness with hardware accessed bits at no exit cost, and avoid double paging by keeping guests from swapping at all.

### Cited Findings

**Fleet-scale cold-memory offload**
- Google far memory (ASPLOS'19): 32% of memory in Google's WSCs is cold on average at a 120 s threshold, ranging 1-52% per machine; applications touch 15% of their cold memory per minute at that threshold, hence a control plane rather than a fixed threshold. Tier is zswap: 67% or more memory cost reduction for the compressed part at ~6 µs access; promotion-rate SLO of 0.2% of working set per minute; about 20% of data stored far on average; CPU overhead 0.001% for compression and 0.005% for decompression; 4-5% memory TCO reduction; an ML autotuner added ~20% coverage. [F, via detailed secondary summary] — [the morning paper: Software-defined far memory](https://blog.acolyer.org/2019/05/22/sw-far-memory/); [Google Research publication page](https://research.google/pubs/software-defined-far-memory-in-warehouse-scale-computers/)
- Recalled from the paper: cold-page identification is a kernel thread (kstaled) scanning accessed bits at a fixed period (120 s) into per-page age histograms; ~3x compression ratio; a substantial fraction of cold pages is incompressible and is left uncompressed. [R] — [Lagar-Cavilla et al., ASPLOS'19](https://research.google/pubs/software-defined-far-memory-in-warehouse-scale-computers/)
- Meta TMO (ASPLOS'22): saves 20-32% of total memory across millions of servers (7-19% from application containers, ~13% from sidecars); driven by PSI (measured stall time) through the Senpai agent, which adjusts reclaim about every 6 s; supports both zswap and SSD tiers without offline profiling; SSD at iso-capacity is under 1% of server cost, ~10x cheaper per byte than compressed memory. [S] — [TMO paper](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf); [Meta engineering blog](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/)
- TierScape (Intel, 2024): on average 20-30% of data is cold in production; placing ~50% of data in compressed tiers yields 16% memory TCO savings at 13.5% slowdown, i.e. pushing past the cold set gets expensive quickly. [S] — [arXiv 2404.13886](https://arxiv.org/html/2404.13886v1)

**Working-set estimation without guest help**
- VMware ESX statistical sampling: each period, select n random guest-physical pages, invalidate their mappings, count how many are re-touched (t); active fraction f = t/n. Default 100 pages per 30 s period (of VM execution time), i.e. at most 100 minor faults per period; estimates are smoothed with fast and slow moving averages and the max is used. The idle memory tax (default 75%) charges idle pages more so reclaim prefers VMs not using their allocation. [F] — [Waldspurger OSDI'02](https://research.cs.wisc.edu/areas/os/Qual/papers/vmware-memory.pdf)
- Difference Engine: a not-recently-used clock over referenced/modified bits plus two extra bits for long-idle pages, scans at least 4 s apart; ~80% of victim pages stayed untouched for at least 10 s and ~50% for more than 100 s. [F] — [Difference Engine](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/gupta/gupta_html/)
- Linux/KVM state of the art (2024-2025): MGLRU can now walk secondary-MMU (KVM) page tables during aging, not only at eviction (Houghton series); motivation from ChromeOS: KVM SPTE accessed bits were being cleared only via rmap walks at eviction time, skewing reclaim decisions for VMs. A Feb 2025 v9 series ages SPTEs locklessly so neither vCPUs nor reclaim stall. Reviewers noted idle-page-tracking interactions were broken with MGLRU and that as of 6.13 KVM no longer propagates the accessed bit when zapping an SPTE. [S] — [LKML: MGLRU walk secondary MMU](https://lkml.iu.edu/hypermail/linux/kernel/2410.1/10436.html); [LKML: KVM age sptes locklessly v9](https://lkml.iu.edu/hypermail/linux/kernel/2502.2/04290.html)
- Hardware support, recalled: Intel EPT accessed/dirty bits (Haswell and later) and Page Modification Logging (Broadwell and later); Arm stage-2 Access Flag with hardware management via FEAT_HAFDBS (Armv8.1, also hardware dirty state via DBM); no PML equivalent on Arm until FEAT_HDBSS (Armv9.5) which is not yet in common server silicon. [R] — [Kernel docs: KVM MMU](https://docs.kernel.org/virt/kvm/x86/mmu.html)

### Inferences
- **One page-state machine covers everything.** Per (VM, GFN): `absent-zero` → `mapped-private` ⇄ `compressed` ⇄ `on-nvme`; and `inherited(layer)` → (on write) `mapped-private`. "Lazy restore" is `on-nvme`/`inherited` at start; "swap" is the transition of cold private pages to `compressed`/`on-nvme`; "hibernate" is driving all private pages to `on-nvme` and freeing the vCPU/VMM; "pause-to-zero" additionally uploads the extents to object storage. Clean-relative-to-parent pages are simply dropped (they are `inherited` again). Building diff snapshots first yields swap nearly for free, as the earlier round noted; the new point is that *compression* slots in as an intermediate state with the same fault path.
- **Idle tracking design.** Use hardware A bits in stage-2 leaf entries (EPT A/D on x86; AF with FEAT_HAFDBS on Arm so that clearing AF does not cost a fault per re-access). A scanner per VM clears A bits and ages pages into a small number of generations (MGLRU-style) at a period that adapts to state: e.g. 5-10 s for running VMs, stopped entirely for paused ones. Scan cost is proportional to *populated private* stage-2 entries, not guest RAM, so shared template subtrees and DAX windows are skipped. A 1 GiB private set is 262k PTEs = 512 table pages to walk: well under a millisecond per pass. Clearing A bits requires a TLB invalidation for precision, but skipping the flush (as Linux does for young-bit clearing on x86) only delays detection; batch one flush per pass. Waldspurger sampling (100 pages / 30 s) is the fallback for hardware without stage-2 A bits and is useful anyway as a cheap WSS estimate for the admission controller.
- **2 MiB mappings hide idleness**: one A bit per 2 MiB. Private guest RAM is better mapped at 4 KiB while it is a candidate for reclaim (see section 5).
- **Avoiding double paging.** (1) Give guests no swap device, so the guest never pages anonymous memory itself. (2) The guest's own page-cache writeback of a page the hypervisor swapped out forces a swap-in just to write the page to virtual disk: minimized because DAX removes most file pages from guest RAM and the remaining dirty file pages are recent (not cold) by nature. (3) Guest reclaim scanning (kswapd) touching PTEs does not touch page contents, so does not fault pages in; guest THP collapse, compaction, KSM-in-guest and `init_on_free` *do* touch contents of cold pages and should be off. (4) Free page reporting tells the hypervisor which swapped/compressed pages are now garbage so they are discarded rather than ever swapped in.
- **Tiering policy for mostly-idle sandboxes** (latency budget reasoning): compressed tier fault ≈ decompress (single-digit µs for LZ4/zstd-fast on 4 KiB today; Google reports ~6 µs) + stage-2 exit/entry (~1-2 µs) = invisible to interactive use. NVMe tier fault ≈ 75-100 µs device + software = ~100-150 µs each; a resume that needs 300-400 MB (CodeSandbox's figure; ~75k-100k pages) would take ~8-15 s if faulted serially at 4 KiB, versus ~0.2-0.4 s if read as sequential extents at 1-2 GB/s. Hence: (a) record the post-wake working set per sandbox (REAP-style, but using A bits harvested in the first seconds after each resume: free for a stage-2-owning hypervisor) and store hibernated pages *ordered by last working-set membership* so the wake prefetch is one sequential read; (b) fault granularity for on-NVMe pages should be 64-512 KiB clusters (Cortex uses 512 KiB chunks), while CoW stays 4 KiB; (c) run the vCPU concurrently with the prefetcher (FaaSnap) rather than blocking on it.
- **Recommended idle ladder for one sandbox** (time since last activity; thresholds to be tuned by measured promotion rate, Google-style): 0-30 s: nothing. 30 s-5 min: age pages; compress private pages idle > ~60 s subject to a promotion-rate SLO (start from Google's 0.2%/min of working set). 5-30 min idle: "soft hibernate": vCPUs descheduled, timers frozen, all private pages compressed, incompressible ones written to NVMe; VMM process state compacted or freed; wake is tens of ms because everything is local and the working set is prefetched. Hours: flush compressed pages to NVMe extents (they are already compressed: write the compressed bytes); wake ~100-300 ms. Days: extents to object storage; wake ≥ 1 s (matches E2B/Fly/Modal-class numbers).
- **Pause cost is where a type-1 design can beat the field.** E2B's ~4 s/GiB pause comes from serializing guest memory after pausing; Fly claims background write-back instead. With continuous background cleaning (private pages idle for > N seconds are compressed/written while the VM runs, using stage-2 dirty bits to know what changed since), hibernate at idle time only has to flush the recently dirtied remainder: pause cost becomes proportional to the dirty rate of an idle VM (near zero), not to RAM size.
- **Compression ratio expectation**: 2.5-3x on general memory (Sabre 2.5x on diff snapshots; Google ~3x; CodeSandbox 8 GiB → 745 MiB = ~11x, but that includes zero and never-touched pages, which a sparse map already elides). Budget 2.5x for private non-zero pages and treat anything better as upside. Same-filled-page detection (zswap-style) should precede compression.
- **Where the compressed pool lives**: a per-host hypervisor zpool with per-VM accounting (compressed bytes are charged to the VM); cross-VM dedup of compressed objects is the same side-channel question as section 2, so do not content-address the pool across tenants.
- **Security of hibernated state**: swap/hibernate extents contain tenant secrets; encrypt per-VM (key held in hypervisor memory, destroyed on VM delete). Convergent encryption (Lambda) is only appropriate for public base-image chunks.

### Gaps
- No public description found of a production microVM platform doing *per-page* hypervisor swap/compression of running guests (as opposed to whole-VM pause). Google and Meta numbers are for containers/processes; applicability to guest-physical memory rests on KVM's MGLRU integration, for which I found only patch discussions, not fleet results.
- DAMON on guest-physical memory / DAMON_RECLAIM for VMs: not researched this session; no cited facts.
- VMware's memory compression tier is recalled only (pages compressible to ≤ 2 KiB go to a per-VM compression cache, default up to 10% of VM memory, before host swap) [R] — [vSphere resource management docs](https://docs.vmware.com/en/VMware-vSphere/6.7/com.vmware.vsphere.resmgmt.doc/GUID-F9111E35-E197-46EC-8350-77827A5A2DEC.html).
- Blaxel's "<25 ms" and "~25 ms standby" claims are unverified vendor numbers and the fetched page attributes them to "Baseten Sandboxes"; Fly publishes no wake-latency measurement in its design post; Morph, Daytona, Runloop not checked.
- Current (2025-2026) zstd/LZ4 per-4KiB-page compress/decompress times on Zen 5 / Graviton4 / AmpereOne were not retrieved; the µs figures above are Google's 2019 number and a 2008 measurement.
- CXL/memory-tiering papers (2023-2026) for VM memory were not researched.
- REAP/FaaSnap numbers come via a vendor blog's citations, not the papers.

## 5. Huge pages vs 4K in the second stage

### Takeaway
2 MiB second-stage mappings buy a workload-dependent 3-22% (occasionally more for TLB-hostile workloads) but cost exactly the things density depends on: page-granular CoW, dirty and idle tracking, zero-page elision and reclaim. The workable compromise is by region, not global: 2 MiB (even shared tables) for immutable shared regions (DAX base image, template kernel text), 4 KiB for private guest RAM by default, with opportunistic promotion to 2 MiB only for hot, fully private, fully populated ranges of active VMs and demotion again on idle.

### Cited Findings
- A two-dimensional (nested) page walk with 4-level guest and 4-level host tables makes six times as many page-table references as a native 4-level walk (24 vs 4 [R for the absolute count]); TLB misses can cost up to ~6x native. [S] — [Gandhi et al., MICRO'14](https://scail.cs.wisc.edu/papers/micro14-virtualization.pdf)
- VMware's EPT evaluation: using large pages in the hypervisor "can ... further improve the guest performance by 3%-22%" depending on workload. (Dated: Nehalem era, ~2009.) [S] — [VMware: Performance Evaluation of Intel EPT Hardware Assist](https://www.cs.miami.edu/~burt/learning/Csc521.121/docs/Perf_ESX_Intel-EPT-eval.pdf)
- Misaligned huge pages (guest 2 MiB over host 4 KiB or vice versa) do not reduce TLB misses, because the TLB caches the smaller of the two sizes; benefit requires both stages to be huge and aligned. [S] — [Gemini / HugeGPT line of work](https://cs.hofstra.edu/~jshan/papers/xgemini.pdf)
- SpOT (ISCA'20) quotes nested-paging translation overhead of ~16.5% for its workloads (big-memory, TLB-intensive) before its contiguity-based fix. [S] — [Alverti et al., ISCA'20](https://pages.cs.wisc.edu/~jayneel/papers/isca20_capaging_spot.pdf)
- Firecracker: KVM dirty tracking "negates most huge page benefits"; hugetlbfs pages cannot be used with file-backed (`MAP_PRIVATE`) restore, only uffd; balloon discards on hugetlbfs must free whole huge pages. [F, earlier round] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md); [Firecracker CHANGELOG](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)
- E2B places sandboxes by hugepage-pool load (hugetlbfs-backed guests) and collapses the agent heap into THPs before pause to reduce resume faults. [F/S, earlier round] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- Free page reporting only reports blocks of `pageblock_order` (2 MiB on x86-64) precisely so it does not break guest THP. [F, earlier round] — [LWN 808807](https://lwn.net/Articles/808807/)
- Firecracker pmem docs: huge pages (tmpfs THP or hugetlbfs) reduce first-access fault counts for the pmem window. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- Recalled (ESX): on hardware-MMU hosts ESX backs guests with 2 MiB pages and does not TPS-share them; under memory pressure it breaks large pages into 4 KiB and then shares, which is why TPS savings appear only under pressure on modern hosts. [R] — [Broadcom KB: TPS](https://knowledge.broadcom.com/external/article/323624/additional-transparent-page-sharing-mana.html)
- Recalled (Arm): stage-2 block sizes are 2 MiB/1 GiB with a 4K granule, 32 MiB with 16K, 512 MiB with 64K; the contiguous bit lets 16 adjacent 4K entries (64 KiB) share one TLB entry; Linux multi-size THP (mTHP, from 6.8) uses this on arm64. [R] — [Kernel docs: transparent hugepage / mTHP](https://docs.kernel.org/admin-guide/mm/transhuge.html)

### Inferences
- **Cost accounting of a 2 MiB private mapping in this design**: (a) the first write after fork copies 2 MiB instead of 4 KiB (512x; at ~10 GB/s memcpy that is ~200 µs vs <1 µs, and 2 MiB of private memory for a one-byte write); (b) one A bit and one D bit per 2 MiB, so idle tracking and incremental hibernate see the whole block as hot/dirty; (c) zero sub-pages inside the block cannot be elided; (d) a compressed/swapped block must come back whole. For a mostly idle sandbox whose private set should be a few hundred MB, these dominate any TLB win.
- **Region policy:**
  - *DAX base-image window*: 2 MiB (or 1 GiB where the image store is contiguous) blocks, read-only, shared tables. No downside: immutable, never tracked.
  - *Template-inherited guest RAM*: map read-only at 2 MiB where the template layer holds a fully populated, physically contiguous 2 MiB extent (the hypervisor can arrange this when sealing a template: copy the template's resident set into 2 MiB-contiguous frames). First write to the block splits the stage-2 entry into a 4 KiB table (pointing at the same frames) and CoWs only the written 4 KiB page. Split is cheap (allocate one table page, fill 512 entries, no data copy).
  - *Private guest RAM*: 4 KiB by default. Promotion ("khugepaged for stage 2"): for a running, CPU-active VM, a 2 MiB-aligned range whose 512 pages are all private, present and recently accessed may be migrated into a contiguous 2 MiB frame and mapped as a block; demote (split the mapping; no data movement needed) when the VM goes idle so the scanner regains 4 KiB resolution. Promotion needs a compaction-capable frame allocator (movable private frames, which a hypervisor with a full reverse map for private frames can do).
  - On Arm, the contiguous bit gives a middle option (64 KiB TLB reach with 4 KiB frames) for private RAM with only 16x coarser A/D information if used; treat as an optimization after measurement.
- **Guest side**: the guest may use THP internally irrespective of stage-2 granularity, but (per the misalignment result) gets full benefit only when stage 2 is also 2 MiB there; guest THP at `madvise` plus stage-2 promotion driven by observed hotness lines the two up where it matters (big build/JIT heaps) without bloating idle guests.
- **How much performance is at stake for this workload**: coding-agent workloads (compilers, interpreters, git, package managers) are moderately TLB-sensitive; published 3-22% figures are for 2009-era CPUs with small second-level TLBs and no paging-structure caches for nested walks comparable to today's. Modern cores (thousands of L2 TLB entries that hold 4K and 2M, EPT paging-structure caches) should shrink the gap, but I found no current measurement, so the honest planning number is "single-digit to low-double-digit percent on TLB-heavy phases, near zero when idle", and the design should make promotion a tunable policy and measure.
- 16K/64K granule guests on Arm reduce TLB pressure but multiply CoW/dirty granularity by 4x/16x and break DAX image compatibility with 4K images; not recommended for density.

### Gaps
- No 2023-2026 measurement of 4 KiB-only vs 2 MiB second-stage mappings on current x86 (Zen 4/5, Sapphire/Granite Rapids) or Arm (Neoverse V2/V3, AmpereOne) server cores for build/dev workloads was found. This needs a benchmark (kernel compile, `npm install`, test suites) in the prototype.
- No source retrieved on Arm stage-2 walk caching behaviour or measured nested-walk cost on Neoverse cores.
- The MICRO'14, VMware EPT, Gemini and SpOT numbers are from search snippets, not read in full.

## 6. Zero pages, lazy allocation, and not touching memory at boot

### Takeaway
Never allocating what was never written is the largest and cheapest saving: guest-physical memory should be a sparse map in which "zero/absent" costs no frame and no page-table page, populated on first touch, with guests configured (and templates prepared) so that the kernel does not sweep memory at boot or on free. Zero pages were 38% of memory in Difference Engine's mixed snapshot and a visible share of all VMware sharing, so explicit zero handling is worth doing even before any dedup.

### Cited Findings
- Difference Engine MIXED-1: 149,038 of 393,120 pages (~38%) were zero pages. [F] — [Difference Engine](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/gupta/gupta_html/)
- VMware ESX: zero pages were 70 of 345 MB reclaimed (workload B) and 25 of 120 MB (workload C); in the single-VM case ~55% of sharing was the zero page; the paper notes a spike in Windows guests' apparent activity from the "zero page thread" that zeroes free pages. [F] — [Waldspurger OSDI'02](https://research.cs.wisc.edu/areas/os/Qual/papers/vmware-memory.pdf)
- KSM `use_zero_pages` merges empty pages with the kernel zero page; the docs count `ksm_zero_pages` as savings. [F] — [Kernel docs: KSM](https://docs.kernel.org/admin-guide/mm/ksm.html)
- Lazy restore in practice: Firecracker reads only memory the VM needs; most CodeSandbox VMs load less than 1 GB; Cortex saw 49 MiB allocated against 4 GiB apparent base. [S/F] — [CodeSandbox uffd post](https://codesandbox.io/blog/cloning-microvms-using-userfaultfd); [Cortex builders blog](https://builders.cortex.io/blog/sandboxing-agents-part-2/)
- Free page reporting returns guest-free blocks ≥ 2 MiB to the host continuously at ~0-2% overhead; the host then gives zeroed pages back on re-touch; a 2026 series removes the guest's redundant re-zeroing of host-zeroed pages. [F earlier round; S] — [LWN 808807](https://lwn.net/Articles/808807/); [LWN 1073887](https://lwn.net/Articles/1073887/)
- virtio-pmem FS-DAX initializes struct pages for the whole device at probe (1.56% of device size), an example of a guest kernel touching memory proportional to configured size rather than use. [F] — [LWN 1092485](https://lwn.net/Articles/1092485/)
- Cloud Hypervisor snapshot files are sparse-aware (SEEK_DATA/SEEK_HOLE), and postcopy restores ballooned pages as zero pages. [F, earlier round] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)

### Inferences
- **Zero handling rules for the hypervisor:**
  1. Unpopulated GFN: no stage-2 entry. Read fault → map shared read-only zero frame (or populate privately if the guest's pattern is read-then-write, which it usually is for anonymous memory: prefer allocating directly on *any* first touch for RAM regions to save a second fault, and use the read-only zero frame only when under memory pressure). Write fault → allocate a pre-zeroed frame from a per-CPU zeroed pool (zeroing done in the background by idle cores, so the fault path does not pay ~100-200 ns/4 KiB... or 2 MiB zeroing cost).
  2. Detect zero pages at every point a page's contents are read anyway: compression (same-filled check), hibernate write-out, template sealing, template-relative compare. A zero private page is freed and its entry returned to absent.
  3. On free-page-report/balloon discard: entry returns to **absent-zero**, never to "inherited from parent" (returning stale parent contents would both leak template data into a fresh allocation, harmless for a same-tenant template but wrong, and resurrect the bug class behind the 2026 Firecracker file-backend + balloon advisory noted in the earlier round).
- **Keeping the guest from touching all memory:**
  - Boot happens once per template, so boot-time sweeps (struct page init for all RAM, ~1.6% of RAM written; `memblock` debug; memtest; `init_on_alloc`; KASAN) cost the template only. But *configured RAM size* still matters per clone through structures that are later written (struct pages are written whenever a page changes state): keep guest RAM modest and grow by virtio-mem hot-add (earlier round), or accept ~16 MiB/GiB of eventually-private struct pages for memory the guest actually cycles through.
  - Guest config for density: `init_on_alloc=0 init_on_free=0`, no `page_poison`, THP `madvise`, `vm.compaction_proactiveness=0`, no in-guest KSM, no swap, `vm.min_free_kbytes` small, free page reporting on; avoid `hugetlbfs` reservations; avoid `mlockall`-style prefaulting in agents; deferred struct page init is irrelevant after fork.
  - Before sealing a template: drop caches not wanted in clones, `sync`, compact memory once, zero free pages (a one-off balloon inflate/deflate or a kernel "zero free pages" pass), then snapshot. The result: template resident set = kernel + warmed processes + deliberately warm page cache; everything else absent.
- **Lazy allocation has a latency face**: each first touch is a stage-2 fault (~1-2 µs exit/entry + alloc). A build that touches 2 GiB of fresh memory takes ~524k faults ≈ 1 s of fault overhead spread over the build; fault-around (populate 16-64 KiB per fault for RAM regions of *active* VMs) cuts this by 4-16x at a small density cost, and is a natural knob tied to host memory pressure.

### Gaps
- No source quantifies how much of a modern Linux guest's RAM is written during boot as a function of configured size with current kernels (struct page init, per-CPU areas, etc.); the 1.56% struct-page figure is from the DAX context but is the same structure.
- No measurement retrieved of stage-2 fault cost on current CPUs (the 1-2 µs figure is a rule of thumb, not a cited number).
- The interaction between `init_on_free`, free page reporting and host zero detection has no published density measurement that I found.

## 7. Overcommit policy and real-world ratios

### Takeaway
Published operator numbers span from "don't" (Red Hat found 25% oversubscription disruptive without care) through VMware-style modest overcommit backed by ballooning and sharing, to Lambda/Firecracker's "10x in production, 20x tested" for small, mostly idle microVMs; sandbox providers avoid quoting a ratio and instead scale idle sandboxes to zero so that hosts are sized to active concurrency. The policy that fits agent sandboxes is: account real (private + pool) memory, admit against measured working sets with headroom, and treat hibernation of the coldest low-priority sandbox as the pressure-relief valve instead of an OOM kill.

### Cited Findings
- Firecracker/Lambda (NSDI'20): oversubscription tested up to 20x and run in production at up to 10x (CPU and memory are "soft allocated"); memory overhead target expressed as a few percent. [S for the 20x/10x via a paper summary; F earlier round for soft allocation] — [Justin Lin's review of the Firecracker paper](https://justinlinkk.github.io/blog/fire_cracker_review); [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- VMware ESX's reclamation stack and policy vocabulary (still the template for hypervisor overcommit): shares-based proportional allocation with min-funding revocation, an idle memory tax (default 75%: up to 75% of a VM's idle memory may be reclaimed when memory is scarce), ballooning preferred, hypervisor paging as last resort, content sharing attempted before paging out. Overhead memory is reserved per VM on top of its minimum (admission control on min + overhead). [F] — [Waldspurger OSDI'02](https://research.cs.wisc.edu/areas/os/Qual/papers/vmware-memory.pdf)
- VMware's own warning when it turned off inter-VM TPS: monitor free memory, ballooning and swapping, since effective overcommit capacity drops. [S] — [Broadcom KB 318959](https://knowledge.broadcom.com/external/article/318959/security-considerations-and-disallowing.html)
- Red Hat OpenShift Virtualization (2025): tests at 25% memory oversubscription on a host; fine for the MariaDB case with the right mechanisms, but "memory oversubscription is found to be very disruptive in general, and it can lead to VMs being killed by the OOM killer". [S] — [Red Hat Developer: evaluating memory overcommitment](https://developers.redhat.com/articles/2025/04/24/evaluating-memory-overcommitment-openshift-virtualization)
- Overdriver (IBM, 2011): in oversubscribed clouds memory overload is mostly transient: up to 88.1% of overloads last under 2 minutes, arguing for a fast temporary relief mechanism (they used network swap) rather than migration for every overload. [S] — [Overdriver](https://researcher.draco.res.ibm.com/publications/overdriver-handling-memory-overload-in-an-oversubscribed-cloud--1)
- Google: promotion-rate SLO (0.2% of working set per minute) as the safety metric for offloading; Meta: PSI stall time as the feedback signal, adjusted every ~6 s. [F/S] — [the morning paper: far memory](https://blog.acolyer.org/2019/05/22/sw-far-memory/); [TMO](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)
- Sandbox providers' implicit policy is scale-to-zero rather than a published ratio: Cortex sizes hosts to active concurrency (18 retained / 6 active sessions on 3 nodes; a 16 vCPU / 64 GiB node "saturates at 9 to 24 parallel agents" for 2 vCPU/8 GiB coding agents and 4 vCPU/16 GiB build agents); E2B bills allocated resources while running and offers auto-pause; Fly bills Sprites for CPU time and memory actually used; Blaxel/Baseten standby after ~15 s of network inactivity. [F] — [Cortex builders blog](https://builders.cortex.io/blog/sandboxing-agents-part-2/); [E2B docs](https://docs.e2b.dev/sandbox/persistence); [Fly vs E2B](https://fly.io/learn/fly-vs-e2b/); [Blaxel blog](https://blaxel.ai/blog/sandbox-snapshot-hibernate-resume-ai-agents)
- E2B operational detail relevant to admission control: nodes can refuse a pause while a previous snapshot is still being written (HTTP 503), i.e. snapshot I/O throughput is itself a bottleneck resource during mass idle transitions. [F] — [E2B docs](https://docs.e2b.dev/sandbox/persistence)
- Ampere's marketing density claim (2023): a 42U/16.5 kW rack of 192-core AmpereOne 1S servers supports up to 7,926 VMs vs 2,496 for 96-core EPYC 9654; trade press flagged the comparison as carrying "a pretty big asterisk". Vendor claim, CPU-bound not memory-bound. [S] — [Tom's Hardware](https://www.tomshardware.com/news/ampere-unveils-192-core-cpu); [The Register](https://www.theregister.com/2023/05/18/ampere_one_cpu/)

### Inferences
- **Define the ratio carefully.** "Overcommit ratio" = sum of guest-configured RAM / host RAM is nearly meaningless here: with lazy allocation, CoW and DAX a 4 GiB guest may cost 100 MiB. The controllable quantity is **committed private memory**: Σ over VMs of (private resident frames + compressed bytes + page tables + VMM overhead) + shared pools (templates, images) charged once. Report configured-RAM overcommit as an outcome (it could legitimately be 10-30x for idle-heavy fleets, consistent with Lambda's 10x for a far more active workload), but admit and schedule on private memory.
- **Admission control**: a host admits a new or waking sandbox if `Σ WSS_estimate(active) + Σ floor(idle) + shared + reserve ≤ RAM`, where WSS comes from A-bit aging (section 4), `floor(idle)` is the post-compression residual for soft-hibernated sandboxes, and `reserve` covers burst (e.g. the P99 of fleet-wide 1-minute growth in private memory, measured). Waking a hibernated sandbox is an admission event: if the host cannot admit, wake it on another host from object storage (latency penalty) rather than overload this one.
- **Pressure ladder** (cheapest and least visible first): (1) drop clean shared pages with no cost (cold DAX image pages, cold template pages are re-readable); (2) compress cold private pages of idle VMs past the normal threshold; (3) write compressed/incompressible cold pages to NVMe; (4) soft-hibernate idle sandboxes in priority order (longest idle, lowest tier first); (5) throttle the allocation rate of the fastest-growing sandboxes (stall their stage-2 allocation faults briefly: back-pressure instead of failure); (6) hard-hibernate (freeze) *active* low-priority sandboxes: the VM is paused, state intact, resumes when memory is available or on another host; (7) never OOM-kill: there is always a consistent state to freeze to because the hypervisor, not the guest, owns the memory. Freeze-instead-of-kill is the key usability property; Overdriver's finding that most overloads are transient supports short freezes over migration.
- **Per-VM limits and DoS resistance**: each sandbox has a hard cap on private memory (= its configured RAM, which the guest cannot exceed anyway) and, more importantly, a cap on *rate of private growth* and on fault-driven swap-in I/O (a guest touching its pages in a pattern that defeats the idle tracker can otherwise thrash the host: charge swap-in I/O and decompression CPU to the VM's own CPU/IO budget so thrashing slows only the thrasher). Per-tenant quotas on Σ private memory bound a tenant's ability to squeeze others. Page-table memory and VMM memory are charged to the VM. Compressed-pool usage is charged to the VM.
- **Fairness**: ESX's shares + idle tax is a good fit conceptually: reclaim preferentially from VMs with the most idle memory per unit of entitlement. For sandboxes a simpler rule is defensible: reclaim strictly by page age across the host (global LRU by generation) with a per-VM protected minimum (its recent working set), which is what Google's and Meta's systems amount to.
- **What ratio to expect** (reasoning, to be validated): if an active sandbox averages 300-500 MiB private (CodeSandbox-like working set) with bursts to several GiB, and an idle soft-hibernated one costs ~20-60 MiB compressed plus ~1 MiB fixed, then a 512 GiB host could hold on the order of 500-1000 active plus several thousand soft-hibernated sandboxes; configured-RAM overcommit (at 4-8 GiB configured each) would then be in the tens. The binding constraints become CPU for bursts and NVMe throughput for wake storms, not RAM.
- **Correlated bursts** are the real risk (a tenant fans out 500 agents that all start building at once): admission should be per-tenant burst-aware, and the scheduler should spread a tenant's sandboxes across hosts.

### Gaps
- I could not fetch the Firecracker paper PDF this session (redirect), so the "20x tested / 10x production" figures are from a secondary summary and match my recollection of the paper; verify the exact wording and whether it refers to CPU, memory, or both.
- No published memory-overcommit ratio found for Azure, GCP, fly.io, E2B, Modal, Daytona or Blaxel. Google Borg/Autopilot figures are recalled only (Borg runs lower-priority work in reclaimed resources; Autopilot cut memory slack roughly in half versus manual limits) [R] — [Rzadca et al., Autopilot, EuroSys'20](https://research.google/pubs/autopilot-workload-autoscaling-at-google-scale/).
- VMware's current official overcommit guidance was not fetched.
- No data found on real agent-sandbox burst correlation or idle fractions; "mostly idle" is the brief's premise, not a measured figure here.

## 8. Per-VM fixed overhead and the density floor

### Takeaway
Published floors are ~5 MiB per microVM for Firecracker's VMM, 12 MB per gVisor sandbox at Modal, and a few MB total for unikernel guests in LightVM; with a Linux guest the kernel's own unshared footprint is the larger term, and it is exactly what template CoW removes. At 1,000-10,000 sandboxes per host the dominant terms are, in order: private (diverged) guest pages, guest-side metadata that diverges (struct pages, slab), then per-VM VMM memory, with second-stage tables and vCPU state small if tables are lazily populated.

### Cited Findings
- Firecracker specification: VMM threads have a memory overhead ≤ 5 MiB for a microVM with 1 vCPU and 128 MiB RAM with a Firecracker-tuned guest kernel; workload dependent (e.g. many vsock connections raise it). [S, from the SPECIFICATION.md snippet] — [Firecracker SPECIFICATION.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/SPECIFICATION.md)
- Recalled from the NSDI'20 paper: measured VMM overhead of ~3 MB for Firecracker vs ~13 MB for Cloud Hypervisor vs ~131 MB for QEMU per VM, independent of guest size. [R] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Firecracker pmem doc: a 128 MB VM booted to idle has RSS ~96 MB (virtio-block or pmem+DAX root) and ~120 MB with pmem without DAX: i.e. a booted minimal Linux guest touches ~75% of a 128 MB allocation, and double caching of the rootfs costs ~24 MB in this tiny example. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- Modal (2026): ~12 MB overhead and ~25 ms boot per gVisor sandbox. [S] — [Modal blog](https://modal.com/blog/modal-gvisor-maintainer)
- LightVM (SOSP'17), recalled: 8,000 guests on a 64-core host using Tinyx/unikernel guests; a minimal unikernel image of ~480 KB needing ~3.6 MB RAM and booting in ~2.3 ms; the paper's point was that toolstack/XenStore overhead, not the hypervisor, limited density. [R] — [Manco et al., My VM is Lighter (and Safer) than your Container](https://dl.acm.org/doi/10.1145/3132747.3132763)
- Potemkin estimated ~1000 128 MB honeypot VMs on a 2 GB host from delta virtualization, limited by unique memory per VM. (2005) [S] — [Potemkin](https://www.eng.utah.edu/csl-sem/old/f05/papers/potemkin-sosp05.pdf)
- Xen VM fork: the device model is the heavy part (≈1 s to launch) and forks can run without one. [S] — [Xen-devel VM forking v8](https://lore.kernel.org/all/cover.1581362050.git.tamas.lengyel@intel.com/T/)
- Guest metadata: struct page ≈ 1.56% of covered memory (64 B per 4 KiB). [F] — [LWN 1092485](https://lwn.net/Articles/1092485/)

### Inferences
- **Budget per sandbox in the proposed design (estimates from arithmetic and the cited figures; to be measured):**

  | Item | Running, lightly used | Soft-hibernated | Notes |
  |---|---|---|---|
  | Stage-2 tables | 4 KiB root + ~2 KiB per MiB of *privately mapped or lazily referenced* RAM at 4 KiB (0.2%) | freed (rebuilt on wake) | 300 MiB touched → ~0.6 MiB; DAX window ~16 KiB with 2 MiB blocks; near zero with shared subtrees |
  | Hypervisor per-VM structs | vCPU state: x86 VMCS 4 KiB + XSAVE area up to ~11 KiB with AVX-512/AMX state (more with AMX tile data, 8 KiB) + MSR lists; Arm: sysreg context + SVE state (size depends on VL) | same (tiny) | tens of KiB per vCPU |
  | GFN map / layer index | 8 B per populated GFN if a flat array is used (0.2%), less with extents | extent list, a few KiB-100s of KiB | can be the stage-2 table itself for mapped pages |
  | Frame-table share | 8-16 B per host frame (global, 0.2-0.4% of host RAM) | n/a | global, not per VM |
  | virtio queues | in guest memory (already counted): 256-entry split queue ≈ 10 KiB per queue | same | VMM-side shadow state ~KiBs |
  | Deprivileged VMM | target ≤ 1-2 MiB private (Firecracker shows ≤ 5 MiB, ~3 MiB measured, is achievable in a general-purpose host process; a purpose-built VMM with shared text and no libc heap growth can be far below) | can be torn down entirely and recreated on wake, or swapped as ordinary cold memory | text pages shared across all VMMs |
  | Guest kernel + userspace unshared | tens of MiB after fork, growing (slab, per-CPU, page tables, struct pages of cycled memory) | compressed 2.5-3x | this is the term to measure |
  | Guest private data | workload dependent (100s of MiB active) | compressed or on NVMe | dominated by page cache unless DAX |

- **Floor**: a soft-hibernated sandbox can be driven to roughly its compressed private pages + ~100 KiB of hypervisor metadata; a fully (hard) hibernated one to a few KiB of in-memory metadata (an index entry and keys). So "10,000 sandboxes per host" is feasible only as a mix dominated by hibernated ones; the *running-idle* floor per sandbox is set by the guest kernel's unshared footprint, which CoW from a template reduces from ~96 MB (Firecracker's booted 128 MB example) to whatever diverges (timers, RCU, slab churn, logs): plausibly 5-20 MiB before compression, the number to measure first.
- **What dominates at scale**: at 1,000 running sandboxes × 300 MiB private = 300 GiB, private pages dominate by two orders of magnitude over fixed overhead (1,000 × ~3 MiB). At 10,000 mostly hibernated, fixed per-VM in-memory metadata (10,000 × 100 KiB = 1 GiB) and timer/housekeeping CPU matter more than memory: idle guests must be truly tickless (`nohz_idle`, no periodic agent polling) or frozen, since 10,000 guests × even 10 wakeups/s is 100k exits/s.
- **Non-memory per-VM limits to watch**: VPID/ASID space (x86 VPID is 16-bit: 65,535; Arm VMID is 8 or 16-bit depending on FEAT_VMID16, so 8-bit-VMID cores would require VMID recycling beyond 255 concurrently *running* VMs per... rollover generation), interrupt vectors/GIC LPIs/ITS tables per device, NVMe queue depth for swap, host file descriptors or their equivalent, and network namespaces/TAP-equivalents. [VMID width recalled; R] — [Kernel docs: KVM/arm64](https://docs.kernel.org/virt/kvm/arm/index.html)
- Hyperlight-class "micro-VMs without a kernel" reach sub-MiB per instance by not having a guest OS; not applicable to Linux dev sandboxes but indicates the hypervisor-side floor (VM + vCPU structures) is tens of KiB.

### Gaps
- Hyperlight's published per-VM memory/startup figures were not retrieved this session.
- LightVM numbers are recalled, not re-read; the earlier round cited only its checkpoint timings.
- No published breakdown of what diverges in an idle forked Linux guest over time (which kernel structures dirty pages while idle). Needs measurement: fork, idle 10 min, count private pages by owner.
- vCPU state sizes are from architecture knowledge, not a fetched source.

## 9. Density-relevant differences between x86-64 and ARM64 servers

### Takeaway
Arm servers offer one hardware thread per core (no SMT sibling leakage to manage, no core-scheduling tax, but also no 2-for-1 thread count), high core counts at low power, and flexible stage-2 granules; x86 offers more threads per socket, PML for dirty logging, and mature EPT A/D. For memory density the architectures are close; the practical differences are GB of RAM per schedulable vCPU, the cost of A/D tracking without FEAT_HAFDBS-capable cores, VMID width, and page-granule compatibility of images and snapshots.

### Cited Findings
- AmpereOne A192-32X: 192 cores, no SMT (one thread per core), 2 MB L2 per core, 8 DDR5 channels, "just over 2 W/core". AMD EPYC 9965 (Turin Dense): 192 cores / 384 threads; test platform used 12 DIMMs (12 channels). Phoronix found the EPYC 9965 ahead on both performance and performance-per-watt in its suite. [S] — [ServeTheHome AmpereOne review](https://www.servethehome.com/ampere-ampereone-a192-32x-review-a-192-arm-core-supermicro-nvidia-broadcom-kioxia-server-cpu/); [Phoronix: EPYC 9965 vs AmpereOne](https://phoronix.com/review/amd-epyc-9965-ampereone)
- Jeff Geerling's framing of AmpereOne: like "48 dedicated 4-core servers in one box, each with 10 gigs of high-speed RAM": i.e. ~2.67 GB/core in his 512 GB configuration. [S] — [Jeff Geerling: AmpereOne](https://www.jeffgeerling.com/blog/2024/ampereone-cores-are-new-mhz/)
- Firecracker pmem: a guest write to a read-only-mapped region behaves differently by architecture under KVM (x86-64: write discarded with warning; aarch64: KVM internal error, VM stopped); aarch64 guests need `CONFIG_ARM64_PMEM` for DAX. [F] — [Firecracker docs/pmem.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)
- virtio-mem is supported on x86-64 and aarch64 (and RISC-V, s390x). [F, earlier round] — [virtio-mem](https://virtio-mem.gitlab.io/)
- Recalled: Firecracker's production host guidance recommends disabling SMT (or using core scheduling) and disabling KSM for multi-tenant hosts; on Arm servers without SMT the first recommendation is moot. [R] — [Firecracker prod-host-setup.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/prod-host-setup.md)
- Recalled hardware facts: EPT A/D bits and PML on Intel; AMD NPT has A/D bits but no PML equivalent; Arm stage-2 AF/dirty hardware management requires FEAT_HAFDBS (present on Neoverse N1 and later [R]); Arm supports 4K/16K/64K granules and the contiguous hint; x86 has 4K/2M/1G only; Arm TLB invalidation is by broadcast instruction (no IPI needed for TLBI broadcast, FEAT_TLBIRANGE for ranges) whereas x86 needs IPIs or INVEPT on each CPU. [R] — [Kernel docs: arm64 memory](https://docs.kernel.org/arch/arm64/memory.html)

### Inferences
- **Threads vs cores for mostly idle sandboxes**: density here is memory- and burst-bound. With SMT on x86, cross-tenant safety requires either SMT off or core scheduling (siblings only run vCPUs of the same trust domain), which wastes capacity when a core's two siblings cannot be filled by the same tenant; at high CPU overcommit with many small tenants this tax is real. Arm's one-thread-per-core removes the policy and the tax; a 192-core Arm part gives 192 isolation-safe run slots versus 192 (SMT off) or up to 384 (same-tenant pairing possible) on Turin Dense. For bursty short builds, per-thread performance matters to usability (Phoronix shows Turin Dense ahead of AmpereOne), so "more cores" is not automatically "better sandboxes".
- **Memory per host**: both platform classes reach 1.5-3 TB per socket with 8-12 DDR5 channels at 2 DIMMs per channel; memory capacity per socket is not architecture-limited. Because sandboxes are memory-bound when idle and CPU-bound when bursting, the ratio to choose is roughly: (expected active fraction × private WSS) + (idle fraction × compressed residual) per core of burst capacity. Platforms with 12 channels per socket give more headroom for the idle population.
- **Stage-2 specifics to design for:**
  - Abstract page-table code over: block sizes (x86 2M/1G; Arm 4K-granule 2M/1G plus contiguous 64K/32M), A/D semantics (EPT A/D per EPTP; Arm per-VTCR HA/HD enable, and on cores without HAFDBS AF faults must be taken, making idle scanning cost one fault per re-accessed page: budget for sampling, Waldspurger-style, on such cores), and dirty logging (PML on Intel; write-protect or D-bit scan elsewhere).
  - Arm requires break-before-make when changing block/table mappings (e.g. splitting a 2 MiB block to 4 KiB) unless FEAT_BBM level 2 is present; splitting a shared read-only block for CoW therefore needs either BBM2 or a brief unmap + TLBI with concurrent vCPUs faulting and retrying. x86 can replace entries atomically followed by INVEPT. This affects the cost of the "start huge, split on write" strategy on Arm.
  - VMID is 8 or 16 bits on Arm depending on the core; VPID is 16 bits on x86. With >255 runnable VMs on 8-bit-VMID cores, VMID rollover and TLB flushes are needed (as KVM does); require FEAT_VMID16 on target hardware.
  - Snapshots are not portable across architectures and should be treated as specific to CPU model/feature set even within one (Firecracker's rule, earlier round); templates and DAX images are therefore per-architecture artifacts, and base images must use a 4K granule on both for the same CoW/dedup granularity.
- **Cache-timing isolation**: Arm cores in this class have private L2 and shared L3/SLC like x86; shared-frame Flush+Reload-style channels (sections 2-3) exist on both. No architecture advantage.

### Gaps
- No independent, like-for-like VM-density benchmark between current Arm (AmpereOne M, Graviton4, Axion, Cobalt) and x86 (Turin, Granite Rapids/Sierra Forest) servers was found; Ampere's rack-density claim is marketing.
- Channel counts and max memory for the latest parts (AmpereOne M 12-channel, Graviton4) are recalled only and were not verified this session.
- No measurement retrieved of stage-2 fault cost, TLBI cost or A/D-scan cost on Neoverse versus x86 cores.
- Sierra Forest/Clearwater Forest (x86 E-core, no SMT) change the "x86 has SMT" generalization; not researched.

## 10. Recommended combination (synthesis for the design)

### Takeaway
Layer the techniques so that each handles what the previous cannot: (1) lazy, sparse guest memory with explicit zero state; (2) fork from sealed templates with page-granular CoW and layered snapshots; (3) a shared read-only DAX base image so base-image file pages never enter guest RAM; (4) A-bit-driven aging feeding a compressed tier, then NVMe, with continuous background cleaning so that idle sandboxes hibernate at near-zero pause cost and wake with a recorded working-set prefetch; (5) only zero-page and template-relative dedup, no cross-tenant content scanning; (6) admission on measured private memory with freeze-instead-of-kill under pressure.

### Cited Findings
- Each element has production or research precedent cited above: lazy restore and small resume working sets ([CodeSandbox](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3)); shared base + private CoW with content-addressed chunks ([Cortex](https://builders.cortex.io/blog/sandboxing-agents-part-2/)); empty-EPT fork in a type-1 hypervisor at ~745 µs ([Lengyel/Xen](https://www.slideshare.net/tklengyel/vm-forking-and-hypervisorbased-fuzzing-with-xen)); DAX rootfs sharing counted once per host ([Firecracker pmem](https://github.com/firecracker-microvm/firecracker/blob/main/docs/pmem.md)); 20-32% cold memory offload at fleet scale with compressed and SSD tiers ([Google far memory](https://blog.acolyer.org/2019/05/22/sw-far-memory/), [TMO](https://www.pdl.cmu.edu/PDL-FTP/NVM/tmo_asplos22.pdf)); working-set prefetch on wake ([REAP/FaaSnap via Blaxel blog](https://blaxel.ai/blog/sandbox-snapshot-hibernate-resume-ai-agents)); cross-tenant dedup abandoned by default ([VMware KB](https://knowledge.broadcom.com/external/article/318959/security-considerations-and-disallowing.html), [Flip Feng Shui](https://vusec.net/projects/flip-feng-shui)); ~1 s resume and ~4 s/GiB pause as the incumbent baseline to beat ([E2B docs](https://docs.e2b.dev/sandbox/persistence)).

### Inferences
- **Priority order by (saving × certainty) / complexity:**
  1. Sparse lazy allocation + zero state + guest config that avoids sweeping memory. Saves "configured minus touched", typically the majority. Trivial for a stage-2 owner.
  2. Template fork with 4 KiB CoW and lazy stage-2 population. Saves the template's resident set (kernel, runtimes, warm caches) × (N-1). Fork < 1 ms.
  3. DAX read-only base image (EROFS, uncompressed, 2 MiB-aligned large files) + overlay upper. Saves the base-image page cache × N and removes the main source of post-fork divergence. Requires guest kernel config and image build pipeline; side channel accepted for public images only.
  4. Free page reporting (guest-cooperative but stock Linux; from the earlier round) with absent-zero semantics, so guest-freed memory returns continuously.
  5. Idle aging via stage-2 A bits → compressed tier (same-filled check, LZ4/zstd) under a promotion-rate SLO → NVMe extents, with background cleaning. Saves ~60-70% of cold private memory in RAM (compression) or ~100% (NVMe).
  6. Soft hibernate on idle (minutes), hard hibernate to NVMe/object store on long idle, with working-set-ordered extents and concurrent prefetch on wake; target wake < 50 ms local-compressed, < 300 ms local-NVMe, ~1 s remote.
  7. Template-relative re-share at hibernate/restore and zero detection; optional tenant-scoped content dedup against base-image corpus.
  8. 2 MiB mappings for the DAX window and for intact template extents; later, hotness-driven promotion for private RAM of active VMs; shared stage-2 subtrees for immutable regions.
  9. Overcommit control loop: per-VM WSS estimates, private-memory admission, pressure ladder ending in freeze, per-tenant quotas and rate limits.
- **Explicitly not recommended**: cross-tenant KSM-style scanning; sub-page patching; hugetlbfs-style 2 MiB-only guest RAM; guest swap; relying on classic balloon inflation for reclaim (unverifiable, guest OOM risk) except as an emergency lever.
- **Measurements the prototype must produce before the numbers in this file are trusted for capacity planning:** private pages per sandbox vs time since fork (idle and under a scripted agent workload), split by anonymous / page cache / kernel; compressibility of that private set; post-wake working set size and its stability between wakes; 4 KiB vs 2 MiB stage-2 throughput delta on build workloads per CPU family; stage-2 fault, CoW-break and decompress-fault latencies; NVMe wake-storm throughput.

### Gaps
- The combination has no single published end-to-end precedent with measured density; the closest public descriptions (Cortex, E2B, CodeSandbox) are KVM/Firecracker designs using userfaultfd and host page cache, and none publishes sandboxes-per-host.
- Interactions most likely to produce bugs, none with a published treatment specific to this stack: free page reporting × CoW layers × hibernate (the zero-vs-inherited rule), DAX window identity × snapshot/fork × image GC, A-bit tracking × shared table subtrees, and block splitting on Arm without FEAT_BBM2.
