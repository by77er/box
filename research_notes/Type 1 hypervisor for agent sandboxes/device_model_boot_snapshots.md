## 1. Minimal device model: what a modern Linux guest needs, and what existing VMMs chose

### Takeaway
The proven minimal set is: virtio-blk, virtio-net, virtio-vsock, a console (16550 serial or virtio-console), an entropy source, a "reboot" signal (i8042 stub or ACPI), paravirt clock, and in-kernel interrupt controller/timer emulation; everything else (balloon, virtio-mem, pmem, RTC, VMGenID/VMClock) is optional and was added later by Firecracker as density and snapshot features demanded it. Firecracker started MMIO-only and added an optional PCI transport in v1.13 (2025), so a new design should pick one transport deliberately: MMIO is the smallest code, PCI gives MSI-X per-queue interrupts and hotplug.

### Cited Findings

**Firecracker (KVM, Rust)**
- Device list per the design doc: virtio-net (backed by host TAP, "no traffic filtering"), virtio-block (backed by host files), virtio-vsock (runs on the VMM thread), serial console (development builds only), a partial i8042 keyboard controller "used only to signal the host that the guest requested a reboot", and PIC/IOAPIC/PIT provided by KVM. Clocksources: kvm-clock and tsc on x86_64 (guests >= 5.10 default to tsc if stable); arch_sys_counter on aarch64. [F] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)
- Threading: one API thread (control plane, off the fast path), one VMM thread (single epoll loop hosting the machine model, legacy devices, MMDS and virtio devices), one thread per vCPU running `KVM_RUN` and handling synchronous PIO/MMIO exits. [F] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)
- Token-bucket rate limiters per block device and per NIC, two buckets each (ops/s and bytes/s), separately for ingress/egress. [F] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)
- Rationale from the NSDI'20 paper: Firecracker "does not offer a BIOS, cannot boot arbitrary kernels, does not emulate legacy devices nor PCI, and does not support VM migration"; virtio was chosen because it "is simple, scalable, and offers sufficiently good overhead and performance for our needs". Code size at the time: about 50k lines of Rust total (96% fewer than QEMU); the i8042 driver is under 50 lines, the serial driver around 250, and "the entire virtio block implementation (including MMIO and data structures) is around 1400 lines of Rust". The seccomp profile whitelisted 24 syscalls plus 30 ioctls (22 required by the KVM API). (2020) [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Evolution of the device model, from the changelog (versions, no dates in the file): PVH boot added in v1.12.0; "PCI support in Firecracker" (`--enable-pci`) in v1.13.0; virtio-pmem, virtio-mem memory hot-plug, and virtio-balloon free page reporting and hinting in v1.14.0 (reporting is developer preview); VMClock device in v1.15.0; developer-preview hot(un)plug of PCI virtio devices in v1.16.0; virtio device reset and a `Transparent` huge page option in v1.17.0; "Nitro Sandboxes" in v1.18.0. Earlier: virtio-rng in v1.4.0, vhost-user-blk developer preview in v1.6.0, ACPI and VMGenID in v1.8.0/1.9.0, io_uring async block engine in v1.0.0. [F] — [Firecracker CHANGELOG.md](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)
- A secondary source dates v1.14 to December 2025. [2nd] — [search summary of Firecracker releases](https://github.com/firecracker-microvm/firecracker/releases)

**Cloud Hypervisor (KVM/MSHV, Rust)**
- Always-on legacy devices: 16550A serial (PL011 on arm64), RTC/CMOS (PL031 on arm64), I/O APIC (split irqchip: part in userspace), i8042 (single reboot/shutdown key), and an ACPI device (shutdown/reboot normally go via ACPI). [F] — [Cloud Hypervisor device_model.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/device_model.md)
- Virtio devices are virtio-pci only (no MMIO mentioned): virtio-blk, virtio-console (on by default), virtio-iommu, virtio-net, virtio-pmem, virtio-rng (always enabled), virtio-vsock; plus vhost-user-blk, vhost-user-fs (this is how virtio-fs is provided), vhost-user-net, a generic vhost-user device, and VFIO passthrough. [F] — [Cloud Hypervisor device_model.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/device_model.md)
- With ACPI, wall-clock comes from an ACPI Time and Alarm Device (ACPI000E), usable by Linux 7.1 or newer with the right config. `virtio-rtc` (`--rtc`) is on by default for MSHV guests as of v53.0. ACPI memory hotplug is deprecated in favor of virtio-mem in v55.0. [F] — [Cloud Hypervisor device_model.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/device_model.md); [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)

**QEMU microvm, crosvm, Xen PVH (recalled)**
- QEMU `microvm` machine: no PCI and no ACPI by default; ISA bus with i8259 PIC, i8254 PIT, MC146818 RTC, one ISA serial, LAPIC + IOAPIC, and up to 8 virtio-mmio slots (24 with a second IOAPIC); `pic=off`, `pit=off`, `rtc=off` machine options exist because a guest with kvmclock and LAPIC TSC-deadline timer needs neither PIT nor PIC. [R] — [QEMU microvm docs](https://www.qemu.org/docs/master/system/i386/microvm.html)
- crosvm uses virtio-pci and runs each device in its own sandboxed process (minijail: namespaces + seccomp), i.e. it trades process count and memory for per-device isolation. [R] — [crosvm book](https://crosvm.dev/book/)
- Xen PVH: the guest is an HVM container with no emulated legacy platform; it enters in 32-bit protected mode with paging off, `ebx` = physical address of `hvm_start_info`, `cr0` = PE only, `cr4` = 0, flat 32-bit segments; the RSDP address (if any) is passed in `rsdp_paddr`; APs are started with VCPUOP hypercalls or via the local APIC; PV device descriptions come from XenStore. Entry point is advertised via ELF note `XEN_ELFNOTE_PHYS32_ENTRY`. [F] — [Xen x86 PVH guest ABI](https://xenbits.xen.org/docs/unstable/misc/pvh.html)

**virtio spec details for a from-scratch implementation (recalled from the spec)**
- Transports: virtio-mmio is a ~0x200-byte register window (magic `0x74726976` "virt", version 2 for non-legacy, DeviceID, feature select/bits, QueueSel/QueueNumMax/QueueNum/QueueReady, QueueNotify at 0x050, InterruptStatus/ACK at 0x060/0x064, Status at 0x070, 64-bit queue address registers, ConfigGeneration, config space at 0x100) with a single level-style interrupt per device and no discovery mechanism: devices are announced by device tree, ACPI, or the Linux command line `virtio_mmio.device=<size>@<base>:<irq>`. virtio-pci exposes vendor capabilities (common cfg, notify cfg with per-queue notify offsets, ISR, device cfg) and supports MSI-X with a config vector plus per-queue vectors. [R] — [OASIS virtio v1.3](https://docs.oasis-open.org/virtio/virtio/v1.3/virtio-v1.3.html)
- Split virtqueue: descriptor table (16-byte entries: addr, len, flags NEXT/WRITE/INDIRECT, next), driver-written available ring, device-written used ring (id+len pairs). Packed virtqueue (`VIRTIO_F_RING_PACKED`, bit 34): a single ring of 16-byte descriptors where AVAIL/USED flag bits plus wrap counters replace the separate rings; better cache behavior and friendlier to hardware implementations, but more state to snapshot (wrap counters, last avail/used positions). [R] — [OASIS virtio v1.3](https://docs.oasis-open.org/virtio/virtio/v1.3/virtio-v1.3.html)
- Notification suppression: without `VIRTIO_F_EVENT_IDX` (bit 29) it is a coarse flag (`VIRTQ_USED_F_NO_NOTIFY` / `VIRTQ_AVAIL_F_NO_INTERRUPT`); with EVENT_IDX each side publishes an index (`used_event`, `avail_event`) and the other side notifies only when crossing it, which is the key mechanism for batching exits and interrupts. Other feature bits worth implementing: `VIRTIO_F_VERSION_1` (32, mandatory), `VIRTIO_F_INDIRECT_DESC` (28), `VIRTIO_F_IN_ORDER` (35), `VIRTIO_F_NOTIFICATION_DATA` (38), `VIRTIO_F_ACCESS_PLATFORM` (33, needed when the device may not touch all guest memory, e.g. grant/swiotlb designs). [R] — [OASIS virtio v1.3](https://docs.oasis-open.org/virtio/virtio/v1.3/virtio-v1.3.html)
- virtio-mem is specified in virtio v1.2 as the "Memory Device". [F] — [virtio-mem project page](https://virtio-mem.gitlab.io/)

### Inferences
- Smallest viable x86-64 device set for an agent sandbox on a new hypervisor: LAPIC in x2APIC mode with TSC-deadline timer emulated in the hypervisor, an IOAPIC only if using virtio-mmio wired interrupts (MSI-X with virtio-pci removes the need for IOAPIC routing on the data path), kvmclock-style pvclock page or just invariant TSC with a TSC-frequency CPUID leaf, virtio-blk (rootfs), virtio-vsock (control channel), virtio-net or none, virtio-rng or RDRAND passthrough, a write-only debug console port, and a reset/shutdown mechanism (a hypercall or a one-register stub is enough; i8042 exists in Firecracker and Cloud Hypervisor only as a reboot signal).
- Firecracker's own trajectory (MMIO-only in 2018-2024, PCI in 2025, hotplug in 2026) suggests MMIO's limits (one shared interrupt per device, no hotplug, IRQ-count ceiling) were eventually worth the PCI code. A new design that needs multi-queue block/net and device hotplug should plan for virtio-pci with MSI-X; one that wants the smallest trusted code and only 3-4 devices can stay on MMIO.
- Implement split virtqueues with EVENT_IDX and INDIRECT_DESC first: every Linux guest supports them, and packed rings add snapshot state and code for modest gain with software backends.
- PIC and PIT can be omitted only if the guest kernel is configured and booted so that it never calibrates against them (TSC frequency from CPUID 0x15/0x16 or the hypervisor timing leaf 0x40000010, `no_timer_check`, LAPIC timer). The Firecracker paper notes that a distro kernel wasted time "probing for legacy devices not emulated by Firecracker", so absent devices must be paired with a kernel config that does not probe them.

### Gaps
- QEMU microvm, crosvm, and virtio-spec facts above are recalled, not re-fetched; register offsets and feature-bit numbers should be checked against the v1.3 (or newer) spec text.
- I did not verify whether a virtio 1.4 spec has been published by late 2026, nor the upstream status of virtio-rtc beyond Cloud Hypervisor enabling it on MSHV.
- I found no primary source this session describing what "Nitro Sandboxes" (Firecracker v1.18) are beyond the snapshot doc stating they "have no paused state and do not support snapshots".

## 2. Fast boot: direct kernel boot, kernel config, where time goes, published numbers

### Takeaway
Published cold-boot floors for a real Linux guest are roughly 100-150 ms to `init` (Firecracker, Cloud Hypervisor, 2020 data) and are dominated by guest-kernel work, not VMM work (VMM startup is ~8 CPU-ms); getting to "tens of milliseconds" for a Linux guest in practice means restoring a snapshot rather than booting, which every agent-sandbox provider examined does.

### Cited Findings
- Firecracker specification targets (m5d.metal / m6g.metal, SMT off): VMM start "within 8 CPU ms" of CPU time, 6-60 ms wall-clock with ~12 ms typical; boot "<= 125 ms" from `InstanceStart` to guest `/sbin/init`; VMM memory overhead "<= 5 MiB" for a 1 vCPU / 128 MiB microVM; network up to 14.5 Gbps at <= 80% of one host core (25 Gbps at 100%); storage up to 1 GiB/s at <= 70% of a core; average added network latency 0.06 ms. [F] — [Firecracker SPECIFICATION.md](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md)
- NSDI'20 measurement method: time from VMM process fork to the guest kernel forking init, minimal init that writes to an I/O port, Linux 4.14.94 loaded directly, 1 vCPU / 256 MB, 500 serial samples, Firecracker v0.20.0 vs QEMU v4.2.0 vs Cloud Hypervisor. Pre-configured Firecracker and Cloud Hypervisor boot about twice as fast as QEMU; with 50 concurrent launches the 99th percentile was 146 ms (pre-configured Firecracker) vs 158 ms (Cloud Hypervisor); with 100 concurrent, 153 ms. (2020) [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Where time goes, per the same paper: decompressing a compressed kernel "adds around 40ms" (Firecracker and Cloud Hypervisor boot uncompressed kernels); the stock Ubuntu 18.04 kernel "takes an additional 900ms", partly from "timeouts when probing for legacy devices not emulated" and partly from loading unneeded drivers; disabling serial console logging saves "up to 70ms"; a statically configured network interface adds about 20 ms (35 ms on QEMU); qboot instead of the default BIOS saves about 20 ms on QEMU. The minimal compressed kernel was 4.0 MB with no modules vs 6.7 MB plus 44 MB of modules for Ubuntu's. (2020) [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Creation rate: "up to 150 MicroVMs per second per host". At 125 ms creation time, one pooled microVM is needed per 8 creations per second. (2020) [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Memory overhead measured in the paper: about 3 MB per VM for Firecracker, about 13 MB for Cloud Hypervisor, about 131 MB for QEMU, constant across VM sizes. (2020) [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- LightVM (SOSP'17, Xen): abstract claims a unikernel VM boots in 2.3 ms (vs ~1 ms for fork/exec), up to 8000 VMs per host, per-VM footprints as low as 480 KB on disk and 3.6 MB running, and migration / suspend / resume of 60 ms / 30 ms / 25 ms. Key changes were replacing XenStore with shared-memory device setup ("noxs"), a split toolstack that pre-creates VM shells, and a minimal Linux build (Tinyx). [2nd, search summary of the paper] — [Manco et al., SOSP'17](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)
- LightVM at scale: creating the 1000th guest takes 42 s (Debian), 10 s (Tinyx), 700 ms (unikernel) on stock tooling; a blog summary quotes 4 ms for the minimal unikernel, conflicting with the abstract's 2.3 ms. [2nd] — [the morning paper summary](https://blog.acolyer.org/2017/11/02/my-vm-is-lighter-and-safer-than-your-container/)
- The Firecracker paper cites LightVM as reporting 180 ms boot for an unmodified Linux kernel. [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Firecracker added PVH boot in v1.12.0. [F] — [Firecracker CHANGELOG.md](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)
- PVH entry state (32-bit protected mode, paging off, `ebx` -> `hvm_start_info`) as in section 1. [F] — [Xen x86 PVH guest ABI](https://xenbits.xen.org/docs/unstable/misc/pvh.html)
- Linux 64-bit boot protocol: the loader places the kernel, builds a `boot_params` "zero page" (setup header copied from the image, e820 map, cmdline pointer, initrd address/size), enters at the 64-bit entry point (load address + 0x200 for a bzImage) in long mode with identity-mapped page tables, interrupts off, and `%rsi` pointing at `boot_params`. An uncompressed `vmlinux` ELF can be loaded segment-by-segment and entered directly, skipping the decompressor. [R] — [Linux x86 boot protocol](https://docs.kernel.org/arch/x86/boot.html)
- CodeSandbox reports a "normal VM" at ~5 s to boot vs ~300 ms for a Firecracker microVM, and 200-300 ms to resume from a memory snapshot. (2022) [F] — [CodeSandbox: how we clone a running VM in 2 seconds](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3)
- Cloud Hypervisor v54.0 parallelized memory prefault per NUMA node: a 3 TiB guest's prefault dropped from 51.8 s to 7.4 s, i.e. roughly 58 GiB/s -> 415 GiB/s of page population; this bounds what "pre-faulted memory" costs at boot. [F] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)

### Inferences
- Boot-time budget for a ~100 ms Linux boot is mostly guest-side: kernel decompression (~40 ms, avoid with uncompressed vmlinux or PVH ELF), console output (~70 ms, use `quiet`/no serial), device probing and timer calibration (avoid with a kernel config matched exactly to the device model), network bring-up (~20 ms, defer or do statically), then userspace init. The hypervisor-side cost (create VM, map memory, load kernel) is single-digit milliseconds if memory is not eagerly zeroed or faulted.
- For a type-1 hypervisor the equivalents of host-kernel costs are: allocating and zeroing guest frames (keep a pool of pre-zeroed frames, or map lazily and zero on first EPT violation), building EPT (use 2 MiB/1 GiB mappings for cold boot to cut EPT build and TLB cost), and loading the kernel image (map it CoW from a shared, already-resident copy instead of copying).
- ACPI is avoidable for the boot path: PVH or the 64-bit protocol gives memory map, cmdline, and initrd directly; virtio-mmio devices can be declared on the kernel command line. ACPI becomes useful only for VMGenID, PCI hotplug, and CPU/memory topology, which is why Firecracker added it late (v1.8).
- LightVM's lesson for a type-1 design is about the control plane, not the guest: device setup through a central store (XenStore) and toolstack work scaled worse than the hypervisor itself. Device configuration should be handed to the guest in a single pre-built structure (cmdline / start-info / shared page) with pre-created VM shells.
- A sub-50 ms "start" is therefore a restore problem (section 3). Cold boot matters only for template builds and kernel updates.

### Gaps
- I did not obtain primary, recent (2024-2026) cold-boot measurements for Firecracker, Cloud Hypervisor, or QEMU microvm on current kernels (6.x/7.x); all the solid numbers are from 2020 or earlier.
- Unikraft boot-time figures (the project claims millisecond-scale boots) were not fetched; the Unikraft Cloud page I read gives only "pauses for a few milliseconds" for branching.
- LightVM numbers come from a search summary and a blog, not from reading the PDF; the 2.3 ms vs 4 ms discrepancy is unresolved.
- No published per-phase breakdown of a modern minimal kernel boot (e.g. time in `start_kernel`, SMP bring-up, initcalls) was retrieved.
- PVH boot on Linux requires `CONFIG_PVH`; exact kernel config recommendations (Firecracker's microvm configs) were not fetched.

## 3. Snapshot / restore / fork

### Takeaway
State of practice on KVM is: write vCPU+device state to a small file, keep guest RAM as a (sparse) file, restore by mapping it lazily (MAP_PRIVATE or userfaultfd), and track dirty pages for diffs; production forks (CodeSandbox, E2B) layer CoW on top with shared mmaps, reflinks and uffd handlers. A hypervisor that owns EPT directly can do what Xen's VM fork does: create a child with an empty EPT pointing at a frozen parent and populate or copy pages on EPT violations, with no file, no userfaultfd round-trip and no per-clone page-cache duplication.

### Cited Findings

**Firecracker snapshot mechanics**
- A snapshot is: a guest memory file (full or diff), a microVM state file (device model + KVM state, 64-bit CRC that detects corruption but not tampering), and user-managed disk files. MMDS data store contents are not saved. [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Full snapshots write all guest memory (faulting in every page). Diff snapshots write the state plus pages dirtied since the last snapshot into a sparse file and must be merged into a base with `snapshot-editor edit-memory rebase`; diff snapshots are still developer preview while full snapshots went GA in v1.13.0. [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md); [Firecracker CHANGELOG.md](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)
- Dirty tracking has two modes: with `track_dirty_pages: true`, KVM's dirty page log (adds CPU overhead and "negates most huge page benefits"); without it, `mincore(2)` on the memory mapping to find resident pages (requires swap disabled; no runtime overhead but larger diffs). [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Restore with the `File` backend creates a `MAP_PRIVATE` mapping of the memory file: pages load on demand via kernel page faults and writes go to anonymous CoW memory; the file must stay immutable for the VM's lifetime. With the `Uffd` backend a separate userspace process serves faults over a Unix socket. 2 MiB hugetlbfs pages require `Uffd`; combining `2M` with `File` is an error. [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- On pause, in-flight async block I/O is drained; on snapshot create the vsock device sends a transport reset event and (x86) a KVM-clock notification is injected. On resume, open vsock connections are closed but listening sockets survive; network packets may be lost. [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Clocks: guest wall clock continues from snapshot time unless `clock_realtime: true` (host Linux >= 5.16, kvm-clock) advances it. A vCPU whose `MSR_IA32_TSC_DEADLINE` is 0 has it set to the current TSC so timer interrupts continue. [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Entropy/uniqueness: VMGenID exposes a 16-byte random ID that Firecracker changes and signals before vCPUs resume; Linux 5.18+ (ACPI) and 6.10+ (DeviceTree) reseed the kernel PRNG on change. VMClock adds a `vm_generation_counter` in a shared page that userspace can mmap/poll (support in Linux v7.0; backported to Amazon Linux microVM kernels). Application-level state (cached random numbers, UUIDs, tokens) is still duplicated and must be handled by applications. [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Firecracker's stated safety rule: resuming the same snapshot more than once (multiple clones, or source continues plus a clone) is "insecure" from a uniqueness standpoint unless mitigated. Snapshots taken very early in boot may crash the guest. [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Compatibility: snapshots should be resumed on identical hardware and software; e.g. Ice Lake to Cascade Lake is not supported. cgroups v1 causes high restore latency. [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- A 2026 security advisory (reported as CVE-2026-122192) affects VMs restored with the File memory backend together with a balloon or virtio-mem device, Firecracker v0.23.0 through v1.16.1, fixed in v1.16.2 / v1.17.0. I did not read the bulletin itself; the interaction of discard-style memory reclaim with file-backed private restore mappings is evidently error-prone. [2nd] — [AWS security bulletin 2026-169](https://aws.amazon.com/security/security-bulletins/2026-169-aws/)

**Network identity for clones**
- Firecracker restores NICs with the TAP names stored in the snapshot and every clone resumes with the same guest IP/MAC. The documented approach: one network namespace per clone (identical TAP names coexist), a veth pair to the host, MASQUERADE NAT inside the namespace and on the host, optional per-clone DNAT address for ingress; alternatively `network_overrides` at load time remaps TAP names. The doc gives no cost figures and says the example is not claimed to be performant or secure. [F] — [Firecracker network-for-clones.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/network-for-clones.md)

**Cloud Hypervisor (2026 releases; page shows day/month only)**
- v52.0: `memory_restore_mode` enables userfaultfd demand-paged restore; snapshot memory files are sparse-aware (SEEK_DATA/SEEK_HOLE); vsock connections reset on restore. v53.0: snapshot/restore can run in an external "offload daemon"; background prefaulting after a uffd restore fully populates memory shortly after resume. v54.0: `memory_restore_mode=copyonwrite`; vCPU state save/restore 5-9x faster on many-vCPU VMs. v55.0: snapshots of VMs restored copy-on-write write only pages changed since restore on reflink-capable filesystems; an on-demand mode without background fetch. [F] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)

**Production fork implementations**
- CodeSandbox (2022): original clone path was pause ~16 ms + save snapshot ~4 s + copy memory and disk ~6 s + start ~300 ms = ~10 s; snapshot save cost about 1 s per GB of guest RAM. Mapping guest memory `MAP_SHARED` to a file (kernel flushes dirty pages in the background) cut save to 30-100 ms, and CoW file copies (reflink-style) cut the copy to ~50 ms, giving under 2 s total (pause ~16 ms, save ~100 ms, copy ~800 ms, start ~400 ms). Clones share more than 90% of the source's data. A resumed VM typically touches only 300-400 MB even when the guest reports 3-4 GB in use. Memory-snapshot resume of a Next.js dev environment: 0.6 s vs 132 s cold. [F] — [CodeSandbox: how we clone a running VM in 2 seconds](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3)
- That article does not mention memfd or userfaultfd; CodeSandbox's later uffd-based design is described in follow-up posts I did not fetch. [F] — [CodeSandbox: how we clone a running VM in 2 seconds](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3)
- E2B (open-source infra, 2026): templates are pre-booted snapshots (memfile, rootfs, snapfile) in object storage; sandbox creation restores rather than boots. Firecracker restores without loading memory and a userfaultfd handler serves faults from the template memfile, with an optional prefetcher. The prefetch list is harvested by resuming a network-isolated throwaway copy of the snapshot and recording which pages the resume touches. Pause diffs memory (dirty tracking) and the rootfs CoW cache against the template; a snapshot is a new "build" stored as diffs with `.header` index files resolving diff chains. Placement scores nodes by hugepage-pool load, implying hugetlbfs-backed guests. [F] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- E2B's envd has a documented step that collapses its own heap into 2 MiB transparent huge pages before pause "so on resume envd touches fewer distinct guest-physical frames, each a cold fault". [2nd, from a search-result title only] — [E2B docs](https://e2b.dev/docs/sandbox/snapshots)
- Morph Cloud markets "Infinibranch": snapshot, branch and restore in under 250 ms; branching launches N instances from an instance's latest snapshot. No architectural description or independent benchmark was found. [2nd] — [Morph Cloud docs](https://cloud.morph.so/docs/developers)
- Unikraft Cloud "branching": an asynchronous CoW snapshot of memory and volume state; the source "pauses for a few milliseconds before it resumes running"; only Firecracker-based micro instances and block-based volumes are supported; same-metro only. [F] — [Unikraft Cloud branching docs](https://unikraft.com/docs/features/branching)

**Xen VM forking (type-1 precedent)**
- Design: "VM forking is the process of creating a domain with an empty memory space and a parent domain specified from which to populate the memory when necessary"; it is built on Xen's memory-sharing subsystem, i.e. a VM with an empty EPT plus a parent pointer. The series has a hypervisor part (fork + fork reset) and a toolstack part. Fork reset was measured at 0.011 s "under the optimal circumstances". (2020) [2nd, search summary of the cover letters and slides] — [Xen-devel VM forking series](https://lore.kernel.org/xen-devel/cover.1584981438.git.tamas.lengyel@intel.com/); [Lengyel, VM Forking & Hypervisor-based Fuzzing with Xen](https://www.slideshare.net/tklengyel/vm-forking-and-hypervisorbased-fuzzing-with-xen)

**Research systems**
- REAP (ASPLOS'21, Firecracker): records the guest-physical pages touched on the first invocation after restore and prefetches that working set on later restores; cuts cold-start delay ~3.7x on average vs baseline lazy snapshot restore. Limitation: if the working set changes between runs it falls back to slow faults from the memory file. [2nd] — [Ustiugov et al., REAP](https://infoscience.epfl.ch/record/283308/files/asplos21-reap.pdf)
- FaaSnap (EuroSys'22, Firecracker): concurrent paging (guest runs while a loader populates), per-region memory mapping, compact loading-set files; on average 3.5% slower than snapshots fully cached in memory and up to 3.5x faster than REAP. [2nd] — [Ao et al., FaaSnap](https://www.sysnet.ucsd.edu/~voelker/pubs/faasnap-eurosys22.pdf)
- LightVM checkpointing: save ~30 ms and restore ~20 ms vs 128 ms / 550 ms on stock Xen. (2017) [2nd] — [the morning paper summary](https://blog.acolyer.org/2017/11/02/my-vm-is-lighter-and-safer-than-your-container/)
- SnowFlock (EuroSys'09, Xen): VM fork to many hosts in under a second by shipping a small VM descriptor and fetching memory on demand, with guest-assisted avoidance of fetches for pages about to be overwritten. [R] — [Lagar-Cavilla et al., SnowFlock](https://www.cs.toronto.edu/~brudno/snowflock_eurosys.pdf)
- Potemkin (SOSP'05, Xen): "flash cloning" from a reference image plus "delta virtualization" (CoW sharing of memory) to run very large numbers of short-lived honeypot VMs per host. [R] — [Vrable et al., Potemkin](https://cseweb.ucsd.edu/~savage/papers/Sosp05.pdf)
- Restoring uniqueness after snapshot clone (duplicate PRNG state, UUIDs) is analyzed by the Firecracker/Lambda authors; the proposed remedy is a generation-ID mechanism visible to kernel and userspace. [R] — [Brooker et al., Restoring Uniqueness in MicroVM Snapshots](https://arxiv.org/abs/2102.12892)
- AWS Lambda loads snapshot/image data on demand as fixed-size chunks from a content-addressed, deduplicated, tiered cache with convergent encryption. [R] — [Brooker et al., On-demand Container Loading in AWS Lambda, ATC'23](https://www.usenix.org/conference/atc23/presentation/brooker)

### Inferences
- **CoW fork in a type-1 hypervisor that owns EPT** (generalizing Xen's design):
  1. Pause parent vCPUs (CodeSandbox measured ~16 ms for the KVM pause path; a hypervisor IPI-based pause is far less).
  2. Write-protect the parent's EPT leaf entries (or mark the parent frozen so that it too takes CoW faults), and bump a reference count on each backing frame or, cheaper, on each page-table page so that EPT subtrees are shared and themselves copied on write.
  3. Create the child with an empty or subtree-shared EPT, copy vCPU state (registers, MSRs, XSAVE area, LAPIC, pending events) and virtio device state (feature bits, queue addresses, last-avail/used indices, device config), then resume both.
  4. On an EPT write violation: allocate a frame, copy 4 KiB, install a writable mapping; on a read violation in a lazily populated child, install a read-only mapping to the shared frame.
  This needs no memory file, no page-cache copies, no userspace fault handler, and fork cost is O(number of EPT pages touched), not O(guest RAM). The KVM+userfaultfd equivalent pays a user/kernel round trip per first-touch fault and needs memfd/shared-mapping tricks to avoid a full memory write-out.
- Shared-subtree EPT forking makes huge pages awkward: a 2 MiB mapping must either be copied whole on first write (512x the copy cost, fast density loss) or be split to 4 KiB at fork time. Firecracker's own doc says dirty tracking "negates most huge page benefits", and E2B's THP-collapse-before-pause trick shows the opposite pressure (fewer distinct frames touched on resume). A reasonable policy: 2 MiB mappings for read-mostly template memory shared across clones, split on first write.
- Dirty tracking options for a hypervisor owning EPT: (a) write-protect and catch faults (precise, exit per first write to each page); (b) Intel PML, where the CPU logs dirtied GPAs to a 512-entry buffer and exits when full (no source fetched; general knowledge); (c) scan and clear EPT dirty bits periodically (no exits, cost proportional to mapped memory). Firecracker's `mincore` mode is the "no tracking" extreme: treat every resident page as dirty.
- Fork-safe device state rules implied by Firecracker's behavior: drain in-flight block I/O before capturing, reset vsock connections (keep listeners), accept packet loss on net, never include host-side handles (TAP names, socket paths, backing file paths) in the portable state without an override mechanism (Firecracker added `network_overrides`, `vsock_override`, `drive_overrides`, `pmem_overrides` over time).
- Identity after fork needs a guest-agent step regardless of hypervisor: new MAC/IP (or identical guest IP behind per-VM NAT, as Firecracker and E2B do), flush ARP, VMGenID bump for the kernel RNG, VMClock generation counter for userspace, wall-clock step, and application-level regeneration of secrets. Keeping the guest IP identical and translating outside the VM avoids any in-guest reconfiguration on the fork path.
- Working-set prefetch (REAP/FaaSnap/E2B) matters when snapshot memory lives on disk or remote storage. For same-host forks from an in-memory parent, pages are already resident and shared, so prefetch is unnecessary; it matters again for restore-from-cold-storage and cross-host clone.
- KSM-style after-the-fact dedup is redundant when clones are born sharing pages, and avoids KSM's timing side channel (write latency reveals whether another tenant has an identical page). Sharing only between forks of the same tenant's template preserves that property. The Firecracker paper lists "memory deduplication without sacrificing isolation against ... side-channel attacks" as open future work, i.e. they did not consider cross-tenant dedup safe in 2020.

## 4. Memory elasticity

### Takeaway
The current toolkit is: virtio-balloon free page reporting (guest proactively returns free high-order blocks, ~0-2% overhead), virtio-mem for coarse 2 MiB-granular resize, and hypervisor-side reclaim of whatever the guest gave back; Firecracker shipped all three in v1.14 (late 2025), and Cloud Hypervisor is deprecating ACPI hotplug for virtio-mem. Every one of these interacts badly with file-backed private snapshot mappings and with huge pages, and needs to be designed together with the snapshot path.

### Cited Findings
- Free page reporting (Linux, merged 2020): while pages of sufficiently high order are being freed, the guest scans free lists every 2 seconds and reports batches via a scatterlist; the minimum order reported is `pageblock_order` so it does not break up transparent huge pages; each pass covers at least 1/16 of each free list; a repurposed page flag marks already-reported buddy pages. virtio-balloon is the only user. In QEMU the host applies `MADV_DONTNEED` to reported ranges (pages are zero-filled on next touch); an RFC used `MADV_FREE`. [F] — [LWN: free page reporting cover letter](https://lwn.net/Articles/808807/)
- Measured overhead on will-it-scale page_fault1/page_fault2 in a 32 GB guest: roughly 0.2% to 1.7% below baseline with reporting enabled (computed from the posted table); the author attributes the cost to re-faulting reported pages and host zeroing. (2020) [F] — [LWN: free page reporting cover letter](https://lwn.net/Articles/808807/)
- Firecracker v1.14.0 added virtio-balloon free page reporting and hinting (reporting is developer preview) and virtio-mem hot-plug; unreleased work adds "balloon and virtio-mem memory reclamation for shared memfd-backed guest memory" and makes balloon discards on hugetlbfs free whole huge pages, with the note that reporting or hinting is recommended over the traditional balloon when using hugetlbfs. [F] — [Firecracker CHANGELOG.md](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)
- virtio-mem: resizes a running Linux VM in 2 MiB granularity "in most configurations"; supported on x86-64, aarch64, RISC-V, s390x; Linux guest support since v5.8, QEMU since 5.1, also in Cloud Hypervisor. [F] — [virtio-mem project page](https://virtio-mem.gitlab.io/)
- Cloud Hypervisor: `vm.balloon-stats` API (v54.0); postcopy migration restores ballooned pages as zero pages (v55.0); a `pvmemcontrol` device lets the guest issue madvise-like requests (MADV_HUGEPAGE etc.) to the host; THP now covers shared memory under `madvise` (v51.0). [F] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- Firecracker restore observation relevant to density: memory is loaded on demand, and CodeSandbox saw resumed VMs touching only 300-400 MB of a 4 GB guest. [F] — [CodeSandbox: how we clone a running VM in 2 seconds](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3)
- The Lambda economic framing: memory and CPU are "soft allocated" (overcommitted), and the overhead target is expressed as a percentage (about 3% memory for Firecracker). [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- virtio-mem design per the VEE'21 paper: the device exposes a large region with a `requested_size`; the guest plugs/unplugs fixed-size blocks and the hypervisor can verify that unplugged blocks are not accessed, which a balloon cannot enforce; unplug reliability depends on the guest keeping hotplugged memory movable (ZONE_MOVABLE). [R] — [Hildenbrand & Schulz, virtio-mem, VEE'21](https://dl.acm.org/doi/10.1145/3453933.3454010)

### Inferences
- For idle agent sandboxes the cheapest state is "paused or stopped with memory mostly not resident": (1) enable free page reporting so guest-freed memory returns to the hypervisor continuously, (2) have the guest agent drop caches / compact before idle, (3) on idle timeout, snapshot dirty pages to storage and release frames (E2B's pause; CodeSandbox hibernates after 5-30 minutes with ~300 ms wake). In a type-1 design, "release" is simply unmapping EPT entries and freeing frames, with re-population on EPT violation from the snapshot store.
- With CoW-forked guests, a reported free page that is still shared with the parent costs nothing to release (drop the mapping); a privately-owned page frees a frame. The hypervisor must make the re-fault path return a zero page, not the parent's stale content, otherwise guest-freed-then-reused memory leaks parent data into fresh allocations (this class of bug is what the 2026 Firecracker File-backend + balloon/virtio-mem advisory appears to be about; inferred, bulletin not read).
- Free page reporting only reports blocks of `pageblock_order` (2 MiB on x86-64), so a fragmented guest returns little; periodic guest compaction or virtio-mem unplug is the complement. Classic balloon inflation is the only mechanism that forces a guest to give memory back but risks guest OOM and is not verifiable by the hypervisor.
- Hypervisor-level swap of guest memory is a natural extension of lazy restore: any page that is clean relative to a snapshot can be dropped and re-fetched; dirty pages need a swap/diff store. This is the same machinery as diff snapshots, so building incremental snapshots first gives swap almost for free.
- 4 KiB vs 2 MiB: huge pages cut EPT walk and TLB cost and reduce fault count on restore (E2B uses a hugepage pool; Firecracker needs uffd for hugetlbfs restore), but they make dirty tracking coarse (a single byte written dirties 2 MiB in a diff), make CoW copies 512x larger, and defeat reporting granularity below 2 MiB. Density-first designs use 4 KiB for private/dirty memory and may use 2 MiB only for shared read-only template regions.

### Gaps
- DAMON-based reclaim (DAMON_RECLAIM, proactive reclaim inside guests or on host) was not researched this session; no cited facts.
- No numbers were retrieved for balloon inflate/deflate rates, virtio-mem plug/unplug throughput (MiB/s), or the latency of re-faulting reported pages.
- Free page hinting (the older, migration-oriented virtio-balloon feature) vs reporting: the LWN item fetched does not compare them.
- The virtio-mem VEE'21 details above are recalled, not re-read.
- No source found on hypervisor-managed swap of guest memory in microVM platforms beyond the snapshot-diff designs above.

## 5. Storage

### Takeaway
All examined microVM platforms give the guest a plain virtio-blk root device and implement copy-on-write below it on the host (reflink files, userspace NBD with a CoW cache, device-mapper thin pools); nobody in this set relies on virtio-fs for the root, and Firecracker never adopted virtio-fs in-tree. Disk CoW must be snapshot-consistent with memory, which is easiest when the hypervisor-side block layer itself is a chunked overlay keyed to the same snapshot ID.

### Cited Findings
- Firecracker virtio-block is backed by host files; it gained an io_uring async engine (v1.0.0), vhost-user-blk in developer preview (v1.6.0), and virtio-pmem (v1.14.0, with rate limiter in v1.16.0). vhost-user block devices cannot be snapshotted or overridden at load. Block backing files are drained and fsync'd on snapshot. [F] — [Firecracker CHANGELOG.md](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md); [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Firecracker block I/O in 2020 was serial and did not implement flush: about 13,000 IOPS (52 MB/s at 4 kB) on hardware capable of over 340,000 read IOPS; 4 kB read latency was only 49 us worse than native at queue depth 1. (2020; since improved by the io_uring engine) [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Firecracker spec target: up to 1 GiB/s storage throughput at <= 70% of one host core. [F] — [Firecracker SPECIFICATION.md](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md)
- E2B: template rootfs is read-only; writes go to a per-sandbox CoW cache exposed to Firecracker as an NBD block device served by an in-process userspace NBD server; attach uses the NBD netlink interface, which the kernel serializes node-wide (an ioctl-based alternative costs one parked thread per device). On pause the CoW cache is sealed into a rootfs diff (reflink). Artifacts are fetched lazily from object storage (GCS/S3) with local-disk, shared NFS chunk cache, and peer-to-peer caches. Templates are built from Docker images. [F] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- CodeSandbox applies the same CoW idea to disks ("if a fork changes one file, only that file is stored for the fork") and reports XFS fragmentation from random writes as a known bottleneck of file-level CoW. (2022) [F] — [CodeSandbox: how we clone a running VM in 2 seconds](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3)
- Cloud Hypervisor: virtio-blk supports DISCARD and WRITE_ZEROES for QCOW2 and RAW (v51.0); virtio-fs is provided via an external vhost-user-fs daemon; virtio-pmem is built in (and had a use-after-free security fix in v53.1/v54.1). [F] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases); [Cloud Hypervisor device_model.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/device_model.md)
- Unikraft Cloud branching supports only block-based volumes (e.g. ext4), not shared filesystems. [F] — [Unikraft Cloud branching docs](https://unikraft.com/docs/features/branching)
- Fly.io converts OCI images to a root block device by unpacking layers with containerd into device-mapper thin-provisioned snapshots, then hands the device to Firecracker. [R] — [Fly.io: Docker without Docker](https://fly.io/blog/docker-without-docker/)
- AWS Lambda flattens container images to a block device, splits it into chunks stored in a deduplicated content-addressed store, and loads chunks on demand through a local cache. [R] — [Brooker et al., ATC'23](https://www.usenix.org/conference/atc23/presentation/brooker)

### Inferences
- For a type-1 hypervisor the natural design is a chunked CoW block layer in the storage backend: an immutable base image (flattened OCI layers -> ext4/erofs) plus a per-VM overlay keyed by chunk, with fork = snapshot the overlay's chunk map (O(metadata)). This is equivalent to E2B's `.header` diff chains and Lambda's chunk store, and it makes VM fork consistent across memory and disk because both are "base + diff" keyed by the same snapshot ID.
- virtio-fs/DAX gives shared page cache between host and guests and easy host-side workspace sync, but it puts a large filesystem server in the trust path, has host-side state that is hard to snapshot/fork atomically with guest memory (open handles, inode maps), and Firecracker/Unikraft/E2B all avoided it for snapshot-capable guests. For agent sandboxes that need fork, prefer block devices; expose host files via a sync protocol over vsock or a second read-only block device.
- virtio-pmem with DAX is the block-device way to share a read-only base image's pages across VMs without guest page-cache duplication (the guest maps host pages directly); Firecracker adding it in v1.14 alongside snapshot overrides suggests this density use case. In a type-1 design this is just mapping the same frames read-only into many guests' EPTs.
- Discard support in the virtual disk matters for CoW overlays (otherwise deleted files keep overlay chunks allocated); Cloud Hypervisor added DISCARD/WRITE_ZEROES only in 2026.
- Userspace NBD attach is a control-plane scalability limit on Linux hosts (node-wide serialization per E2B); a hypervisor-native backend avoids the host block layer entirely.

### Gaps
- qcow2 vs dm-thin vs reflink performance comparisons, ublk and SPDK vhost-user-blk numbers were not researched this session; no cited figures.
- 9p vs virtio-fs benchmarks and DAX window behavior were not fetched.
- The Firecracker project's stated reasons for not merging virtio-fs (GitHub issue discussion) were not re-read; treat "never adopted in-tree" as accurate as of the device list and changelog I read, which contain no virtio-fs entry.

## 6. Networking

### Takeaway
The standard pattern is virtio-net over a TAP device inside a per-VM network namespace with veth + NAT, pooled and pre-created because namespace/tap/iptables setup is the slow part of VM creation; policy is enforced outside the VMM (nftables, SNI/Host-inspecting proxies). Keeping the guest's IP/MAC identical across clones and translating outside the VM is what makes snapshot-clone networking work without guest reconfiguration.

### Cited Findings
- Firecracker's virtio-net is backed by a host TAP and "does no traffic filtering"; rate limiting is the only in-VMM policy. [F] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)
- Throughput (2020, iperf3 over tap, 1500 MTU, Gb/s, 1 stream RX/TX): loopback 44.14/44.14; Firecracker 15.61/14.15; Cloud Hypervisor 23.12/20.96; QEMU 23.76/20.43. A statically configured NIC adds about 20 ms to boot. [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Firecracker spec: up to 14.5 Gbps at <= 80% of a host core, 25 Gbps at 100%; 0.06 ms average added latency. [F] — [Firecracker SPECIFICATION.md](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md)
- Clone networking recipe: per-clone netns with identically named TAP and identical guest subnet (example `192.168.241.1/29`), veth pair to host, MASQUERADE in the namespace and on the host, optional DNAT "clone address" for ingress; guest must flush ARP or wait for timeout. [F] — [Firecracker network-for-clones.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/network-for-clones.md)
- E2B: each sandbox gets a "slot" = network namespace + veth pair + tap + unique host-side IP from a /16 + NAT; slots are pooled and reused (`NETWORK_REUSED_SLOTS_POOL_SIZE`); each slot has an nftables egress firewall, and a TCP firewall inspects TLS SNI and HTTP Host to enforce domain allow/deny lists; inbound traffic goes through a reverse proxy that enforces per-sandbox access tokens. [F] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- Cloud Hypervisor disabled virtio-net offloads by default in v54.0, supports vhost-user-net, and sends post-migration network announcements to shorten connectivity recovery (v53.0). [F] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- Firecracker's MMDS is a metadata service reached by the guest over its network interface, implemented inside the VMM (no host network involved); E2B delivers the envd access token through it. [F] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md); [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- passt/pasta implement user-mode networking by translating guest L2 frames to host L4 sockets without privileges or a tap device, the modern replacement for slirp. [R] — [passt project](https://passt.top/passt/about/)

### Inferences
- In a type-1 design there is no host TAP: the choices are (a) an in-hypervisor or service-VM virtual switch with per-VM ports, (b) terminating guest traffic in a per-VM user-mode L4 stack (passt-like: guest frames -> sockets in a network service VM), or (c) no NIC at all, vsock-only with an egress proxy. For AI-agent sandboxes whose traffic is overwhelmingly outbound HTTP(S) to package registries and APIs, (b) or (c) put all policy (domain allow-lists, credential injection, logging) in one place and eliminate per-VM netns/tap/veth/iptables setup entirely, at the cost of throughput and of breaking raw-socket/ICMP/UDP-heavy workloads.
- If a real NIC is kept, give every VM the same guest MAC/IP and identify the VM by its virtual-switch port; NAT/policy is keyed on the port. This makes network identity a hypervisor-side attribute, so forks need no guest-visible change (matches Firecracker's and E2B's same-guest-IP approach).
- E2B's pooling of slots implies that namespace + veth + nftables creation is expensive relative to snapshot restore; no figure is published in what I read. A hypervisor-native switch port is a table insert.
- An SNI/Host-based filter (E2B) is bypassable by non-HTTP protocols and by encrypted client hello; a strict design allows only proxy-mediated egress (vsock or forced proxy) and drops everything else at the port.
- virtio-net throughput of 15-25 Gb/s per core (2020 software backends) is far above agent-sandbox needs; vhost-user/DPDK-class backends are unnecessary complexity for this use case.

### Gaps
- No measured per-VM network setup cost (ms for netns + tap + veth + rules) was found in primary sources.
- vhost-net vs userspace virtio-net vs vhost-user/DPDK comparisons and passt throughput numbers were not researched.
- Fly.io's networking design (WireGuard mesh, per-VM tap + eBPF) was not fetched.
- passt description is recalled, not re-fetched.

## 7. Host-guest control channel

### Takeaway
The dominant pattern is a small in-guest agent reached over virtio-vsock (or plain TCP on the VM's private interface) exposing process exec with PTY, filesystem operations, and lifecycle hooks (init, freeze/thaw around snapshots), with a metadata side-channel for bootstrap secrets. The agent must be snapshot-aware: connections die on restore, and "ready" should be a single blocking handshake rather than polling.

### Cited Findings
- Firecracker vsock: device runs on the VMM thread; on snapshot a transport reset is sent, open connections are closed on resume, listen sockets stay active and the CID is updated; `vsock_override` can change the host Unix socket path at load. [F] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md); [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Cloud Hypervisor vsock: connections reset on restore (v52.0); SEQPACKET support added (v55.0). [F] — [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- E2B envd: runs in every VM on port 49983 using Connect RPC (over HTTP, on the VM's network interface, not vsock). Process service: start/list/connect, stream stdout/stderr, send stdin and signals, PTYs. Filesystem service: stat/list/mkdir/move/remove/watch. REST endpoints: `/health`, `/metrics`, `/envs`, `/files` (upload/download, also via signed URLs), `/init`, `/upgrade`, plus freeze/thaw hooks for pause. Auth is an `X-Access-Token` header checked against a token delivered via Firecracker MMDS. Sandbox create blocks on envd's `/init` (one held request in envd >= 0.10.0, replacing a retry loop). Process starts are refused while workload cgroups are frozen for a pause. Live upgrade re-execs envd in place, handing state through a tmpfs blob. Before a memory snapshot the node probes envd health and records unresponsive guests so a plain resume is refused. [F] — [E2B infra ARCHITECTURE.md](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
- Firecracker's host-side vsock is a Unix domain socket: the host connects and sends `CONNECT <port>\n`, and guest-initiated connections land on `<uds_path>_<port>`. [R] — [Firecracker vsock.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/vsock.md)
- Kata Containers' agent speaks ttRPC (a lightweight gRPC-like protocol) over vsock to the runtime shim. [R] — [Kata Containers architecture](https://github.com/kata-containers/kata-containers/tree/main/docs/design/architecture)
- CodeSandbox used Fly.io's `init` as the reference for its in-guest init. [F] — [CodeSandbox: how we clone a running VM in 2 seconds](https://dev.to/codesandboxio/how-we-clone-a-running-vm-in-2-seconds-39m3)

### Inferences
- Agent API surface that the examined systems converge on: exec (argv, env, cwd, uid) with stdio streams and PTY resize/signals; file read/write/stat/list/watch and bulk upload/download; port forwarding; health; snapshot hooks (quiesce: freeze workload cgroup, sync filesystems, optionally compact memory; thaw: fix clock, reseed, re-announce network, reopen control connections).
- vsock is the better transport for a hypervisor-controlled channel: no IP configuration, not reachable from the guest's network peers, survives network policy changes, and the hypervisor can authenticate by construction (the channel endpoint is the VM). E2B's use of TCP + MMDS token shows the alternative works but needs a token and a proxy.
- A type-1 hypervisor can implement vsock (or an even simpler hypercall/shared-ring channel) directly as the control path and treat "agent ready" as an event (guest writes to a doorbell), which removes polling from the start path; E2B's change from a retry loop to a single held `/init` request indicates polling was a measurable cost.
- Because every clone resumes with the same agent state, the agent protocol should be connectionless-on-restore: the host reconnects and issues a "you were forked, new identity = X" message that triggers the identity steps in section 3.

### Gaps
- Kata agent and Firecracker vsock handshake details are recalled, not re-fetched.
- No latency figures for exec round-trips over vsock vs TCP were found.
- Daytona, Modal, and other sandbox vendors' agent protocols were not researched.

## 8. Where device backends run in a type-1 design

### Takeaway
I did not retrieve dedicated primary sources on this question within the tool budget; the cited facts below are limited to what the fetched documents say about backend placement in existing systems, and the rest is reasoned inference that the report writer should treat as design analysis, not sourced fact.

### Cited Findings
- Firecracker (type-2 on KVM) runs all device emulation in one deprivileged userspace process per VM (jailer: chroot, namespaces, cgroups, per-thread seccomp), with interrupt controllers and timers in the kernel (KVM). "One Firecracker process runs per MicroVM, providing a simple model for security isolation." [F] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md); [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Cloud Hypervisor uses a split irqchip (part of IOAPIC emulation in userspace) and supports moving block/net/fs backends into separate processes via vhost-user; it also runs on Microsoft's hypervisor (MSHV), i.e. as a per-VM userspace VMM in the root partition of a type-1 hypervisor. [F] — [Cloud Hypervisor device_model.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/device_model.md); [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- vhost-user devices complicate snapshot/fork: Firecracker cannot snapshot vhost-user block devices; Cloud Hypervisor only "filled out" vhost-user snapshot/restore (including virtio-fs migration) in v52.0 (2026). [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md); [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- Xen PVH guests get PV device descriptions from XenStore and use event channels/hypercalls set up via HVM params; backends live in dom0 or driver domains. LightVM found XenStore to be the scaling bottleneck and replaced it with direct shared-memory setup between frontend and backend ("noxs"). [F] — [Xen x86 PVH guest ABI](https://xenbits.xen.org/docs/unstable/misc/pvh.html); [2nd] [the morning paper summary of LightVM](https://blog.acolyer.org/2017/11/02/my-vm-is-lighter-and-safer-than-your-container/)
- The Firecracker authors state that virtio "will not yield the near-bare-metal performance offered by PCI pass-through", and that hardware "is not yet up to the task of supporting thousands of ephemeral VMs". (2020) [F] — [Agache et al., NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- crosvm isolates each device backend in its own sandboxed process. [R] — [crosvm book](https://crosvm.dev/book/)

### Inferences
- Three placements and their consequences:
  1. **In-hypervisor backends** (virtqueue processing at the highest privilege level): fastest path (an exit, no world switch), simplest fork (device state is hypervisor state), but every parser of guest-controlled descriptors is in the TCB. Reasonable only for tiny, fixed-function devices: console, RNG, vsock transport, a memory-backed or chunk-mapped block device, VMGenID/clock pages, and interrupt/timer emulation.
  2. **Per-VM deprivileged user-mode VMM** (the NOVA/seL4-style and MSHV+Cloud Hypervisor model): each guest gets its own unprivileged emulator component that sees only that guest's memory; a compromise is contained to one VM. Cost: a context switch per MMIO exit or notification (mitigated by EVENT_IDX batching and ioeventfd-like doorbells that wake the backend without a synchronous exit), per-VM memory overhead (Firecracker's ~3-5 MiB shows how small this can be), and fork must also clone the VMM's state.
  3. **Shared driver/service VM** (Xen dom0/driver domain model): reuses Linux drivers and network stack, one backend instance multiplexes many guests, but it is a shared fate and shared attack surface, needs a cross-VM memory-sharing mechanism (grants, or pre-shared/bounce buffers with `VIRTIO_F_ACCESS_PLATFORM`), and adds a second scheduling hop per I/O.
- For agent sandboxes a hybrid is likely best: hypervisor-internal vsock/console/RNG/clock plus a hypervisor-level CoW block mapping layer (so fork is atomic across memory and disk), with networking and any object-storage access in a deprivileged service domain reached via virtio with restricted memory access. This keeps the fork path free of external processes while keeping the largest parsers (TCP/IP, TLS proxy, filesystems) out of the TCB.
- Cross-VM virtio options in principle: (a) backend maps all guest memory (vhost-user model; simple and fast but the backend can read/write the whole guest), (b) grant-style per-request mappings (Xen grants; fine-grained, map/unmap cost and TLB shootdowns), (c) a pre-shared bounce region with copies (swiotlb/restricted-DMA style; fixed cost per byte, no dynamic mapping, simplest to reason about and fork-friendly because the shared region is the only cross-VM state), (d) hypervisor-mediated copy channels (Argo-style; no shared memory at all, hypervisor copies messages). For CoW-forked guests, (c) and (d) avoid the problem that a backend's mapping of guest pages pins or bypasses CoW/dirty tracking: with (a), backend writes into guest memory do not fault through the guest's EPT and must be tracked separately (the same reason KVM needs vhost dirty logs).

### Gaps
- Not researched this session (no sources fetched): Xen grant tables vs virtio with grant-based DMA, virtio-over-Argo proposals, ACRN's device model/ioreq architecture, Jailhouse ivshmem v2, pKVM's restricted-DMA virtio, seL4/NOVA user-level VMM measurements, and any performance comparison (exits/sec, latency) between in-hypervisor, per-VM VMM, and driver-domain backends. The inferences above rest on general architecture knowledge and the limited cited findings; they need sourcing before being presented as established fact.
- No published isolation or performance evaluation of vhost-user-style backends across VMs on a type-1 hypervisor was found.
- crosvm item is recalled, not re-fetched.

## 9. AArch64 differences (scope addition: arm64 is a confirmed target alongside x86-64)

### Takeaway
On arm64 the guest contract is simpler and more uniform than x86 (flat `Image` + devicetree in `x0`, PSCI for vCPU bring-up, architected virtual timer, GICv3), but snapshot and fork are harder in three places: interrupt-controller state (the virtual ITS keeps its tables in guest RAM), stage-2 dirty tracking (no PML analogue in deployed CPUs; hardware dirty logging FEAT_HDBSS is Armv9.5 and its KVM support was still in patch review in 2026), and register-state portability (Firecracker cannot restore arm64 snapshots across host kernel versions or GIC versions). I found no published arm64-specific microVM boot or snapshot latency figures.

### Cited Findings

**Boot protocol**
- The arm64 `Image` has a 64-byte header: `code0`/`code1` (branch to `stext`), `text_offset` (u64 at offset 8), `image_size` (16), `flags` (24), magic `0x644d5241` ("ARM\x64") at offset 56, PE header offset at 60. Flags bit 0 = endianness, bits 1-2 = kernel page size (1 = 4K, 2 = 16K, 3 = 64K), bit 3 = placement (0 = 2 MB-aligned base near start of DRAM; 1 = anywhere in the 48-bit physical range). [F] — [Linux: Booting AArch64 Linux](https://docs.kernel.org/arch/arm64/booting.html)
- Placement: load the Image `text_offset` bytes above a 2 MB-aligned base, with `image_size` bytes free from the image start. An initrd must lie within a 1 GB-aligned window of up to 32 GB that also covers the image. The DTB must be 8-byte aligned, at most 2 MB, and is mapped cacheable in blocks of up to 2 MB. [F] — [Linux: Booting AArch64 Linux](https://docs.kernel.org/arch/arm64/booting.html)
- Entry state: primary CPU `x0` = physical address of the DTB, `x1`-`x3` = 0; MMU off; all of DAIF masked; entered at EL2 or EL1 (all CPUs at the same EL); kernel image range cleaned to the point of coherency in the data cache; instruction cache free of stale entries. [F] — [Linux: Booting AArch64 Linux](https://docs.kernel.org/arch/arm64/booting.html)
- There is no in-kernel decompressor on arm64: "If you use a compressed target such as `Image.gz`, the boot loader must decompress it." [F] — [Linux: Booting AArch64 Linux](https://docs.kernel.org/arch/arm64/booting.html)
- Secondary CPUs: each CPU node needs an `enable-method`; with PSCI the DT has a `psci` node and the kernel issues `CPU_ON`; the alternative is spin-table with a `cpu-release-addr`. [F] — [Linux: Booting AArch64 Linux](https://docs.kernel.org/arch/arm64/booting.html)
- Timers: `CNTFRQ` must hold the timer frequency and `CNTVOFF` must be identical on all CPUs. [F] — [Linux: Booting AArch64 Linux](https://docs.kernel.org/arch/arm64/booting.html)
- GIC: the DT or ACPI tables must describe the GIC version in use; for a GICv3 guest entered at EL1, system-register access (`ICC_SRE_EL2` Enable and SRE) must be enabled. The current document also specifies requirements for GICv5. [F] — [Linux: Booting AArch64 Linux](https://docs.kernel.org/arch/arm64/booting.html)

**Device model on arm64 in existing VMMs**
- Firecracker arm64 clocksource is `arch_sys_counter` (no kvm-clock). [F] — [Firecracker design.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)
- Cloud Hypervisor on AArch64 uses a PL011 UART (`console=ttyAMA0`), a PL031 RTC (used from FDT when `acpi=off`), and a PL061 GPIO; v54.0 added firmware-aided direct kernel boot via `fw_cfg` on AArch64. [F] — [Cloud Hypervisor device_model.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/device_model.md); [Cloud Hypervisor releases](https://github.com/cloud-hypervisor/cloud-hypervisor/releases)
- Firecracker: VMGenID-driven PRNG reseed works via DeviceTree on Linux 6.10+ (ACPI path is 5.18+); a changelog entry adds an `rng-seed` FDT node for aarch64 guests to provide an initial seed (reported as also covering post-restore; second part is from a search summary). [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md); [2nd] [Firecracker CHANGELOG.md](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)
- Firecracker saves and restores aarch64 PL061 GPIO state as of the unreleased snapshot format 13.0.0. [F] — [Firecracker CHANGELOG.md](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)
- A Firecracker changelog entry gives a maximum of 92 devices on aarch64 vs 17 on x86 (likely the virtio-mmio interrupt-line budget; the snippet does not state the reason). [2nd] — [Firecracker CHANGELOG.md](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)

**Interrupt delivery: SPIs vs MSIs through a virtual ITS**
- KVM's virtual ITS translates guest MSI(-X) to LPIs; it is optional, needs a host GICv3 but not physical ITS hardware, occupies a 64K-aligned 128K MMIO region, and a guest may have several. [F] — [KVM: ARM vGIC ITS device](https://docs.kernel.org/virt/kvm/devices/arm-vgic-its.html)
- ITS snapshot semantics: `KVM_DEV_ARM_ITS_SAVE_TABLES` writes the device/ITT/collection tables into guest RAM at the locations the guest provisioned ("the layout of the tables in guest memory defines an ABI"; 8-byte little-endian entries), so the save itself dirties guest pages. Restore order is strict: guest memory and vCPUs, then redistributors, then ITS base address, then `GITS_CBASER`, other GITS registers, tables, and `GITS_CTLR` last; `GITS_CREADR` must be restored after CBASER or queued commands may re-execute. With a physical GICv4 ITS backing, state is unavailable without GICv4.1. [F] — [KVM: ARM vGIC ITS device](https://docs.kernel.org/virt/kvm/devices/arm-vgic-its.html)
- Firecracker supports GICv2 and GICv3 guests on arm64 but "snapshots cannot be restored across GIC versions". [F] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)

**Snapshot portability**
- Firecracker on aarch64 saved only the lower 128 bits of any register (wider SVE-class registers truncated, risking guest failure on restore), and "on ARM, snapshot restore between kernel versions is not possible due to registers incompatibility". These statements come from Firecracker docs surfaced via search snippets; the version in which they apply was not confirmed. [2nd] — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)

**Stage-2 dirty tracking**
- KVM/arm64 classic dirty logging is write-protection of stage-2 entries plus faults; eager huge-page splitting (Koller, 2022-2023 series) splits block mappings when dirty logging is enabled rather than at fault time, and relies on FEAT_BBM level 2 to avoid break-before-make when breaking huge pages. [2nd] — [KVM: arm64 eager huge-page splitting series](https://lore.kernel.org/all/Y3Qms0lbCiLFJvG+@google.com/T/)
- FEAT_HDBSS (Armv9.5, a hardware dirty-state tracking structure, i.e. the closest thing to Intel PML) had KVM support in patch review during 2026 (v4/v5 series by Tian Zheng, combined with Leonardo Bras's HAFDBS descriptor rework); the series claims lower live-migration overhead than write-protect or scanning stage-2 tables, and sets the stage-2 DBM bit at MMU creation. A separate HACDBS (hardware-accelerated dirty-bit cleaning) series was also posted. Merge status was not confirmed. [2nd] — [LWN: FEAT_HDBSS series](https://lwn.net/Articles/1097350/); [LKML: Support the FEAT_HDBSS introduced in Armv9.5](https://lkml.iu.edu/2607.1/11384.html)

**Published arm64 numbers**
- Firecracker's specification numbers (boot <= 125 ms, <= 5 MiB overhead, 8 CPU-ms VMM start) are stated for both M5D.metal and M6G.metal (Graviton2) hosts without per-architecture breakdown. [F] — [Firecracker SPECIFICATION.md](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md)
- Marc Brooker's 2022 SnapStart post says Firecracker can restore a microVM snapshot "in as little as 4ms (or about 10ms for a full decent-sized Linux system)"; architecture is not stated. (2022) [2nd, search snippet] — [Brooker: Lambda SnapStart](https://brooker.co.za/blog/2022/11/29/snapstart/)
- An AWS write-up describes a "Lambda microVMs" product as ARM64 (Graviton) only. [2nd] — [AWS Builder Center](https://builder.aws.com/content/32UgWHH0glOmtSkkAFjjoLu9Jfj/aws-lambda-microvms-aws-turned-its-best-kept-infrastructure-secret-into-a-product)

### Inferences
- **Boot path**: arm64 direct boot is "copy Image to a 2 MB-aligned base + text_offset, build an FDT, set x0, enter at EL1 with MMU off". There is no decompression stage to skip if the hypervisor loads an uncompressed `Image`, and no equivalent of x86 real-mode/zero-page/e820 or of legacy-device probing; the FDT is the whole platform description. A hypervisor must do the cache maintenance the protocol demands (clean the loaded image to PoC), which is easy to miss when the image pages are mapped CoW from a shared copy.
- **DT vs ACPI**: devicetree is sufficient and smaller for a microVM guest (memory, cpus + `psci`, GIC, timer, virtio-mmio nodes, `chosen` with bootargs/initrd/`rng-seed`, VMGenID since 6.10). ACPI on arm64 implies UEFI-style tables and is needed only for guests that insist on it. This also means virtio-mmio devices are discovered via FDT nodes, not the command line as on x86.
- **vCPU bring-up**: the hypervisor implements PSCI (`CPU_ON`, `CPU_OFF`, `SYSTEM_OFF`, `SYSTEM_RESET`, and `CPU_SUSPEND`/WFI idling) as SMC/HVC handlers. PSCI `SYSTEM_OFF/RESET` replaces the x86 i8042/ACPI reboot stub, so no reset device is needed. vCPU power state (on/off, pending `CPU_ON` entry point and context ID) is part of snapshot state.
- **Transport and interrupts**: virtio-mmio with one SPI per device needs only a GICv3 distributor + redistributors, no ITS, and has far simpler snapshot state. virtio-pci with MSI-X needs either a virtual ITS (MSI -> LPI; tables and pending tables live in guest memory and must be flushed there before snapshot, then re-parsed on restore in a strict order) or a GICv2m-style MSI frame mapping MSIs onto SPIs. For a from-scratch hypervisor that wants fast fork, MMIO + SPIs on arm64 avoids the ITS entirely; if PCI is wanted for parity with x86, an SPI-backed MSI frame is the lower-complexity option (inference from the ITS save/restore complexity above; no source compared the two).
- **Timer and clock after restore**: the guest reads the virtual counter (`CNTVCT = CNTPCT - CNTVOFF`). On restore/fork the hypervisor sets `CNTVOFF` per VM so the virtual counter continues from the snapshot value (no guest-visible jump), and re-arms `CNTV_CVAL`/`CNTV_CTL` per vCPU; `CNTVOFF` must be equal across the VM's vCPUs per the boot protocol. There is no kvm-clock on arm64, so wall-clock correction after restore must come from the guest agent, a PL031 RTC read, PTP-style paravirt time, or the VMClock page (Linux 7.0+). `CNTFRQ` differences between hosts make cross-host restore visible to the guest unless the counter is trapped or scaled, which is one more reason snapshots are host-model-specific.
- **Dirty tracking / CoW fork without PML**: the baseline that works on every Armv8 core is stage-2 write-protection (clear S2AP write permission, take a permission fault, copy or mark dirty, restore write access). For CoW fork this is not a penalty relative to x86, because fork needs the write fault anyway to copy the page; PML/HDBSS only help diff-snapshot dirty logging. With FEAT_HAFDBS (hardware Access/Dirty state at stage 2, Armv8.1), the hypervisor can set DBM on writable-clean entries and let hardware flip them to writable-dirty, then harvest by scanning stage-2 tables, the analogue of EPT dirty-bit scanning; HDBSS (Armv9.5) adds a PML-like log but is not in deployed fleets or mainline KVM as far as I could confirm.
- **Break-before-make**: changing a live stage-2 block mapping into a table (splitting 2 MiB to 4 KiB at fork or on first write) architecturally requires break-before-make unless FEAT_BBM level 2 is present, meaning a window where the mapping is invalid and other vCPUs may fault. On x86 an EPT large page can be replaced in place. An arm64 fork implementation should either map guest memory at 4 KiB from the start for forkable VMs, or split under a per-VM pause.
- **Granule choice**: the stage-2 granule and the guest's stage-1 page size are independent, but density depends on both. A 64K-page guest kernel dirties and frees memory in 64 KiB units (larger diffs, more memory per small allocation, less sharing between forks); a 16K guest is a middle ground with 32 MiB block size at level 2; 4K gives the finest CoW/dedup granularity and 2 MiB blocks matching x86 tooling. The Image header's page-size flag lets the loader detect the guest granule. For sandbox density and snapshot size, 4K guest + 4K stage-2 (with optional 2 MiB blocks for shared read-only template memory) is the conservative choice; 16K/64K trade density for TLB reach.
- **Snapshot state surface** on arm64 is wider and less stable than on x86: system registers (ID registers must match or be sanitized on the destination), SVE/SME vector state of variable length, pointer-auth keys, GIC redistributor/distributor/ITS state, PSCI state, and timer registers. Firecracker's restrictions (same kernel, same GIC version, truncated wide registers) show this is a practical source of breakage; a new hypervisor should version the vCPU state format per feature and pin a per-template CPU feature mask.

### Gaps
- No arm64-specific cold-boot or snapshot-restore latency measurements (Graviton or otherwise) were found; the Firecracker spec does not split numbers by architecture, and the 4 ms / 10 ms restore figures are from a 2022 blog snippet with no architecture stated.
- Whether Firecracker's PCI transport (v1.13+) on aarch64 uses a virtual ITS, a GICv2m frame, or is x86-only was not determined.
- FEAT_HDBSS / HACDBS mainline status and measured pages/sec or migration-overhead numbers were not retrieved; the 2026 threads are patch postings.
- FEAT_HAFDBS stage-2 DBM behavior, FEAT_BBM levels, and `CNTVOFF`/`CNTFRQ` semantics in the inferences are from architecture knowledge, not from a source fetched this session (the Arm ARM was not consulted).
- No source was found comparing 4K/16K/64K granules for snapshot size or VM density.
- The "lower 128 bits" and "no restore across kernel versions on ARM" statements come from search snippets of Firecracker docs and may reflect older doc versions; the current snapshot doc I read mentions only the GIC-version restriction.
- Paravirtualized time on arm64 (stolen time, PTP KVM) and how hypervisors expose wall-clock steps after restore were not researched.
