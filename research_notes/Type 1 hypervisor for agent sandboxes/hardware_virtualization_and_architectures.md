## 1. Essential CPU virtualization mechanisms (x86-64 VT-x / AMD-V, ARM64, RISC-V) and which architecture to target first

### Takeaway
All three architectures now provide the same four building blocks (a deprivileged guest mode with trap-to-hypervisor, hardware two-stage paging with tagged TLBs, hardware-assisted interrupt-controller virtualization, and an IOMMU), but x86 carries by far the largest amount of mandatory legacy and optional-feature surface (VMCS with hundreds of fields, real-mode boot, APIC/x2APIC, MSR/CPUID/IO-port interception), whereas ARM64 and RISC-V were designed to be "classically virtualizable" with a small trap interface. ARM64 is now a confirmed target for this project (see section 1b for the full-depth AArch64 treatment and the portability plan). ARM64 (EL2, GICv3, stage-2) is the simplest *commercially relevant* first target for the CPU/memory/interrupt core; RISC-V H is the simplest on paper but lacks server hardware; x86-64 is the most work but is the largest installed base, and can be cut down sharply by requiring a modern feature baseline (EPT + unrestricted guest + VPID + APICv/x2APIC, PVH-style direct 64-bit boot, no real-mode/BIOS emulation).

### Cited Findings

**Intel VT-x (VMX)**
- [spec, not re-fetched] VMX adds root / non-root operation; per-vCPU state and controls live in a 4 KiB VMCS accessed by VMREAD/VMWRITE; VMLAUNCH/VMRESUME enter the guest; VM exits return to the host RIP in the VMCS with an exit reason + qualification. Guest-state area, host-state area, pin-based / primary / secondary / tertiary execution controls, exit and entry controls, MSR bitmaps and I/O bitmaps decide what traps. Capability MSRs (IA32_VMX_*) must be consulted because allowed-0/allowed-1 settings differ per CPU. — [Intel SDM Vol. 3C, ch. 24–29](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)
- EPT: hardware second-stage paging; cost is that a TLB miss needs an extra EPT walk for each level of guest translation (2-D walk). VPID: 16-bit tag in the VMCS for cached linear translations so TLBs need not be flushed on VM entry/exit. [secondary] — [Univ. of Crete x86 virtualization lecture, May 2025](https://www.csd.uoc.gr/~hy428/vm-labs/hw-x86-virt-may5_2025.pdf)
- Unrestricted guest (Westmere, 2010) allows the guest to run real mode / unpaged protected mode directly and requires EPT; without it a hypervisor must emulate real mode (vm86 or instruction emulator). Feature availability varies per CPU model, so capability MSRs must be checked. [secondary] — [Wikipedia x86 virtualization](https://en.wikipedia.com/wiki/VT-d); [Intel community thread](https://community.intel.com/t5/Software-Archive/Core-i7-Processor-description-listing-VT-x2-features/m-p/889708)
- PML (page-modification logging): when enabled, a guest write that sets an EPT dirty bit first appends the GPA to a 512-entry log page; a full log causes a VM exit. This replaces write-protect-fault-based dirty tracking. [secondary, SDM mirror] — [SDM Vol. 3C mirror](https://xem.github.io/minix86/manual/intel-x86-and-64-manual-vol3/o_fe12b1e2a880e0ce-1096.html)
- MBEC (mode-based execute control): splits EPT execute permission into supervisor-execute and user-execute, based on the mode of the guest linear address translating to the GPA. [secondary] — [Intel Core Series 3 datasheet](https://edc.intel.com/content/www/us/en/design/platforms/core-processor-series-3-datasheet-volume-1-of-2/intel-virtualization-technology-intel-vt-for-intel-64-and-intel-archit/)
- VMFUNC leaf 0 (EPTP switching) lets guest code switch among up to 512 pre-registered EPT hierarchies without a VM exit. Research systems use it for exit-less cross-domain calls: ELISA (ASPLOS 2023) reports overhead 3.5x smaller than a VMCALL-based host-interposition path. — [ELISA slides, ASPLOS 2023](https://yasukata.github.io/presentation/2023/03/asplos2023/asplosc23main-p814-slides.pdf); [LVDs, VEE 2020](https://users.cs.utah.edu/~aburtsev/doc/lvds-vee20.pdf)
- APICv / posted interrupts: "process posted interrupts" is a secondary VM-execution control; the CPU delivers interrupts recorded in a posted-interrupt descriptor to a running guest without an exit. IPI virtualization (eliminates exits when a vCPU *sends* an IPI) was merged in Linux 6.0 and targets Sapphire Rapids and later. — [SDM mirror](https://xem.github.io/minix86/manual/intel-x86-and-64-manual-vol3/o_fe12b1e2a880e0ce-1057.html); [Phoronix, Linux 6.0 KVM](https://www.phoronix.com/news/Linux-6.0-KVM)

**AMD-V (SVM)**
- [spec, not re-fetched] SVM uses a VMCB (control area with intercept bit-vectors + state-save area) accessed as ordinary memory; VMRUN enters, #VMEXIT returns to the instruction after VMRUN; VMLOAD/VMSAVE handle the remaining state lazily; NPT is the nested paging equivalent of EPT (it reuses the normal x86 page-table format); ASIDs tag the TLB; AVIC virtualizes the local APIC via a backing page and physical/logical ID tables. SVM is generally regarded as simpler to program than VMX (no VMREAD/VMWRITE, "paged real mode" available from the start). — [AMD64 APM Vol. 2, ch. 15](https://docs.amd.com/v/u/en-US/24593_3.43)
- AVIC maturity: Linux 6.18 (Oct 2025) made KVM enable AVIC by default only on Zen 4+ when x2AVIC is supported; on Zen 1/Zen 2 IPI virtualization is disabled due to erratum #1235 (AVIC without IPI virtualization still benchmarks much better than no AVIC). Before 6.18 AVIC was off by default. Implication: a new hypervisor should treat AVIC as usable only on Zen 4+. — [Phoronix Linux 6.18 KVM](https://phoronix.com/news/Linux-6.18-KVM); [patch series](https://patchew.org/linux/20250919002136.1349663-1-seanjc@google.com); [erratum patch](https://lkml.iu.edu/hypermail/linux/kernel/2506.1/05890.html)

**ARM64**
- Stage-2 translation: guest accesses not permitted by stage-2 cause a precise trap to EL2; with the 4 KiB granule, 2 MiB and 1 GiB block mappings (superpages) are available. The GIC virtual interface (list registers) lets the hypervisor inject virtual interrupts that the guest acks/EOIs without trapping. **[verified]** — [Martins & Pinto, RTAS 2023, arXiv:2303.11186](https://arxiv.org/abs/2303.11186)
- nVHE vs VHE: in nVHE mode the hypervisor runs at EL2 while host and guest kernels run at EL1; VHE (ARMv8.1) lets the host kernel itself run at EL2, removing the double world-switch for hosted hypervisors. A true type-1 lives entirely at EL2 and needs neither trick. — [LWN, pKVM article](https://lwn.net/Articles/836693/); [Dall et al., ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)
- pKVM model: at boot pKVM installs a stage-2 *identity map for the host*, isolating the EL2 hypervisor from the host kernel at EL1; metadata pages are *donated* host -> hypervisor at VM creation; guest pages are lazily mapped on stage-2 faults, pinned, and unmapped from the host; the guest can share pages back via hypercalls. Only GICv3 is supported. As of the current kernel docs: CPU memory isolation implemented (anonymous memory only), CPU state isolation implemented (EL2 performs the full context switch for protected vCPUs), FF-A/PSCI proxying implemented, **DMA isolation via IOMMU unimplemented, pvmfw unimplemented**; "experimental ... subject to breaking changes". **[verified]** — [kernel.org pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html)
- pKVM upstream timeline: protected-guest support landed in Linux 7.1 (April 2026) as "very experimental", gated by `kvm-arm.mode=protected`; a KVM pull request dated 2026-10-23 says "years after pKVM started being enabled upstream, we finally get the basics in the form of state isolation." [secondary] — [Phoronix Linux 7.1 KVM](https://phoronix.com/news/linux-7.1-kvm); [Will Deacon series](https://lists.infradead.org/pipermail/linux-arm-kernel/2026-January/1091563.html); [LWN 1055029](https://lwn.net/Articles/1055029)
- GICv3/v4: [spec, not re-fetched] GICv3 exposes the CPU interface as system registers (ICH_* list registers at EL2); GICv4/4.1 adds direct injection of virtual LPIs (and vSGIs in 4.1) via the ITS without hypervisor involvement. — [Arm AArch64 virtualization guide](https://developer.arm.com/documentation/102142/latest/)

**RISC-V**
- H extension 1.0: S-mode becomes HS-mode; guests run in VS/VU-mode with V=1 enabling two-stage translation; the second ("G-stage") translates guest-physical to host-physical. The design explicitly accommodates type-1, type-2 and hybrid hypervisors, and S-mode OSes run unmodified in HS or VS mode. — [RISC-V Privileged Spec, Hypervisor chapter](https://docs.riscv.org/reference/isa/priv/hypervisor); [CVA6 virtualization paper](https://arxiv.org/pdf/2302.02969)
- AIA: an IMSIC provides per-hart *guest interrupt files* so MSIs (and IPIs) are delivered straight to a VS-mode guest; an IOMMU with an MSI page table redirects device MSIs to guest interrupt files "without hypervisor involvement". Limit: up to 63 guest interrupt files per hart on RV64 (31 on RV32) unless memory-resident interrupt files (MRIF) are used. KVM irqbypass support for this was still RFC in Sept 2025. Without hardware guest files KVM trap-and-emulates IMSIC/APLIC. — [RISC-V AIA spec, IOMMU chapter](https://docs.riscv.org/reference/aia/IOMMU.html); [KVM RFC irqbypass](https://lists.infradead.org/pipermail/kvm-riscv/2025-September/010148.html); [KVM Forum 2022 AIA slides](https://kvm-forum.qemu.org/2022/AIA_Virtualization_in_KVM_RISCV_final.pdf)

**Relative architectural cost (measured)**
- ISCA 2016 microbenchmarks, cycle counts, order KVM-ARM / Xen-ARM / KVM-x86 / Xen-x86 **[verified, dated 2016: ARMv8.0 without VHE, Xeon of that era]**: Hypercall 6,500 / 376 / 1,300 / 1,228; interrupt-controller trap 7,370 / 1,356 / 2,384 / 1,734; virtual IPI 11,557 / 5,978 / 5,230 / 5,562; virtual IRQ completion 71 / 71 / 1,556 / 1,464; VM switch 10,387 / 8,799 / 4,812 / 10,534; I/O latency out 6,024 / 16,491 / 560 / 11,262; I/O latency in 13,872 / 15,650 / 18,923 / 10,050. The paper's conclusion: a type-1 on ARM has a ~3x cheaper bare transition than x86 (376 vs ~1,230 cycles) because EL2 has its own register bank and the trap does not save/restore state automatically, but Xen's I/O path through dom0 is far slower than KVM's (16,491 vs 560 cycles I/O-out). — [Dall et al., ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)

### Inferences
- "Simplest first" ranking by mandatory hypervisor code: RISC-V H < ARM64 EL2 < AMD SVM < Intel VMX. NOVA's own numbers support ARM < x86: 11,008 SLOC for Arm vs 13,996 SLOC for x86 in a shared code base (release 24.17; see section 2).
- For the agent-sandbox goal, a defensible x86 minimum baseline is: EPT/NPT, VPID/ASID, unrestricted guest, x2APIC + APICv (Intel) / x2AVIC on Zen 4+ (AMD), TSC-deadline timer + invariant TSC, VT-d/AMD-Vi. Requiring this lets the hypervisor omit shadow paging, real-mode emulation, a full instruction emulator, and PIC/PIT/IOAPIC emulation if guests boot via a PVH-style 64-bit entry with virtio-mmio or a paravirtual bus (this is the Firecracker/Xen-PVH device model philosophy; see sections 2 and 4).
- VMFUNC/EPTP switching and MBEC are *optional* accelerators: useful for exit-less service calls and in-guest isolation, not needed for a first version.
- ARM64 first is attractive if the deployment fleet has Graviton/Ampere-class servers; note pKVM's own gap (no IOMMU DMA isolation upstream) shows device isolation is where even ARM designs remain unfinished.

## 1b. AArch64 in full depth (confirmed target) and keeping one codebase portable across ARM64 and x86-64

Scope update (2026-11-26): ARM64 is a *confirmed* target, not an option. This section supersedes the hedged wording in section 1 and gives AArch64 the same depth as x86-64.

### Takeaway
**ARM64 is the simpler architecture to bring up first, stated plainly.** A type-1 hypervisor lives entirely at EL2 with its own banked registers and translation regime, guest entry/exit is an ordinary exception return/exception (no VMCS, no capability-MSR negotiation, no real-mode or instruction-emulation legacy), stage-2 uses the same page-table format as stage-1, the virtual timer and GICv3 virtual CPU interface are architectural, and guests boot with a flat devicetree + PSCI. The measured trap cost for a type-1 on Arm is ~3x cheaper than x86 (376 vs ~1,230 cycles, 2016 hardware). What ARM64 makes *harder* is everything outside the CPU: platform discovery (ACPI on servers vs devicetree elsewhere), GIC ITS/LPI and SMMUv3 drivers that are larger than their x86 counterparts' minimum, firmware dependencies (TF-A at EL3, PSCI/SMCCC pass-through), implementation-defined differences between SoCs, and — critically for development and deployment — **access to EL2 in the cloud: Graviton VMs do not offer nested virtualization as of 2026, so the hypervisor needs bare-metal instances or owned Ampere-class hardware**, whereas on x86 it can be developed and even deployed nested on ordinary cloud VMs. Recommended order: bring up on QEMU `virt` (EL2 enabled, GICv3) -> one SystemReady server platform (Ampere or Graviton .metal) -> then x86-64 on the same portable core. NOVA is the existence proof that one small codebase can serve both (Arm 11,008 SLOC / x86 13,996 SLOC, shared code base).

### Cited Findings

**EL2 with and without VHE**
- Architecture: ARM virtualization support runs the hypervisor in a separate CPU mode, EL2, with its own register state; stage-2 translation configured from EL2 translates IPA -> PA; Xen as a type-1 runs entirely in EL2, whereas KVM (pre-VHE) splits into an EL2 "lowvisor" and the EL1 host kernel and must context-switch all EL1 register state on every transition between VM and host. **[verified]** — [Dall et al., ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)
- nVHE: hypervisor at EL2, host and guest kernels at EL1. VHE (ARMv8.1): the host kernel itself runs at EL2. All arm64 CPUs can still run nVHE. pKVM uses the nVHE split and is ignored when VHE mode is selected. — [LWN pKVM article](https://lwn.net/Articles/836693/); [Will Deacon, pKVM base support series](https://lwn.net/Articles/895790/)
- [spec, not re-fetched] VHE mechanics: `HCR_EL2.E2H=1` gives EL2 a two-VA-range (TTBR0/TTBR1) translation regime and redirects EL1 system-register encodings to their EL2 counterparts when executing at EL2 (guest EL1 state is reached via `*_EL12` aliases); `TGE=1` routes EL0 exceptions to EL2 so EL2 can host EL0 applications. **Relevance to a new type-1:** VHE is not required (a hypervisor written for EL2 uses EL2 registers natively), but E2H=1 is still useful because it allows EL2 to run its own EL0 user processes (per-VM VMMs) *without* an EL1 kernel, i.e. microhypervisor user space runs at EL0 under EL2. Armv9 cores may implement E2H as RES1 (always-on), so new code should be written for E2H=1. — [Arm AArch64 virtualization guide](https://developer.arm.com/documentation/102142/latest/) (fetch failed this session; from background knowledge)
- Measured effect of redesigning the world switch for VHE (AMD Seattle A1100, 2.0 GHz, cycles; non-VHE / VHE-optimized / x86 Xeon): hypercall 3,181 / 752 / 1,437; I/O handled in kernel 3,992 / 1,604 / 2,565; I/O handled in user space 6,665 / 7,630 / 6,732; virtual IPI 14,155 / 2,526 / 3,102. Merely enabling VHE without restructuring gave only 3,181 -> 3,045. Key technique: move register save/restore out of the per-exit path into vcpu_load/vcpu_put (lazy switching). **[verified from slides; 2017, old core]** — [Linaro SFO17-403, Dall](https://static.linaro.org/connect/sfo17/Presentations/SFO17-403%20Optimizing%20the%20Design%20and%20Implementation%20of%20KVM_ARM.pdf)

**Stage-2 translation, dirty tracking, CoW**
- Stage-2 faults are precise traps to EL2; with 4 KiB granule, 2 MiB and 1 GiB block mappings; 16 KiB and 64 KiB granules also exist. Not using 2 MiB stage-2 blocks measurably hurts (up to ~20% on MiBench when forced to 4 KiB). **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- [spec, not re-fetched] VMID (8 or 16 bit, in VTTBR_EL2) tags TLB entries so no flush is needed on VM switch; MMIO emulation relies on stage-2 data aborts with `ESR_EL2.ISV=1` giving the access size/register/direction, so no general instruction decoder is needed for normal load/store MMIO (unlike x86). pKVM documents the limit: only single-register loads/stores can be emulated; other accesses inject an external abort. — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html) **[verified for the emulation restriction]**
- Dirty tracking state of the art (2026): baseline is write-protecting stage-2 and taking a permission fault per first write (requires splitting blocks to pages). Hardware options: FEAT_HAFDBS (hardware Access flag / dirty state via the DBM bit in stage-2 descriptors) and FEAT_HDBSS (Armv9.5 "hardware dirty state tracking structure": the CPU logs dirtied IPAs into a buffer — the direct analogue of Intel PML). KVM support for HDBSS was still in review in 2026 (v4 July 2026, v5 Sept 2026); because DBM removes the write fault, lazy huge-page splitting cannot work and *eager* block splitting becomes mandatory. — [HDBSS v4 thread](https://lkml.iu.edu/2607.1/12868.html); [LWN 1097350](https://lwn.net/Articles/1097350/); [eager split patch](https://lkml.iu.edu/hypermail/linux/kernel/2603.3/04431.html)
- pKVM's stage-2 ownership model (donate/share/unshare state per page, host identity-mapped at stage-2) shows stage-2 can also confine a *host/driver VM*, at the cost of no dirty logging, no read-only memslots, and no runtime reclaim today. **[verified]** — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html)

**GICv3 / GICv4 / GICv4.1**
- GICv2/v3 virtual interface: list registers (LRs) hold pending virtual interrupts; the guest acknowledges and EOIs through the virtual CPU interface without trapping (virtual IRQ completion = 71 cycles on ARM vs ~1,500 on pre-APICv x86). The number of LRs is small (the RTAS study notes four on its platform), so a higher-priority interrupt arriving with full LRs forces hypervisor intervention; only Xen and Bao respected interrupt priority in that study. Physical interrupts still trap to EL2 first unless direct injection is used; sending an SGI (IPI) traps for emulation. **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186); [ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)
- GICv4.0: the ITS can inject virtual LPIs (MSIs from passthrough devices) directly into a *resident* vCPU; one doorbell interrupt per vLPI wakes non-resident vCPUs. GICv4.1 improvements (Marc Zyngier's series, merged Linux 5.6–5.7): one architectural doorbell per vCPU managed by hardware with at-most-once delivery; RVPEID makes vCPU residency switching much cheaper; ITS and redistributors share vPE tables (fewer VMOVP commands); **direct virtual SGI delivery** (16 vSGIs per vPE) so guest IPIs no longer trap — trade-off: the guest loses the SGI active state. Developed against FVP models; public docs lagged. — [GICv4.1 series cover letter](https://lore.kernel.org/lkml/20191228104147.0e658aa9@why/T/); [v5 series](https://lkml.indiana.edu/hypermail/linux/kernel/2003.0/05018.html)
- pKVM supports only GICv3 guests (not GICv2, not GICv5). GICv5 is arriving: KVM 6.18 added nested support on GICv5 hosts with FEAT_GCIE_LEGACY. **[verified / secondary]** — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html); [KVM/arm64 6.18 pull](https://lists.infradead.org/pipermail/linux-arm-kernel/2025-September/1066162.html)

**Virtual timers**
- [spec, not re-fetched] Generic timer: each PE has an EL1 physical timer, an EL1 virtual timer (CNTV, count = physical count − `CNTVOFF_EL2`), an EL2 physical timer, and with VHE an EL2 virtual timer. Standard design: the guest owns the virtual timer and programs it without trapping; the hypervisor uses the EL2 timer for its own scheduling tick; the hypervisor only traps the timer *interrupt* (a PPI) and reinjects it via an LR (hardware-linked "HW" LR so the guest's EOI deactivates the physical interrupt). FEAT_ECV adds `CNTPOFF_EL2` so the guest physical timer can also be offset without trapping. Compared with x86 this removes the TSC-deadline MSR-write exit on each timer re-arm; the remaining cost is saving/restoring CNTV_CTL/CVAL on vCPU switch and one trap per expiry. — [Arm AArch64 virtualization guide](https://developer.arm.com/documentation/102142/latest/) (not re-fetched)
- Measured: KVM ARM hypercall analysis attributes ~104–106 cycles to save/restore of timer registers out of the 6,500-cycle nVHE world switch (vs 3,250+ for the VGIC registers on GICv2-era hardware — GIC register access dominated). **[verified, 2016]** — [ISCA 2016, Table III](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)

**PSCI / SMCCC**
- For protected guests pKVM implements PSCI 1.1 at EL2: only the primary vCPU starts runnable with just PC (entry) and x0 (DTB pointer) set; secondaries are started by the guest via PSCI `CPU_ON`; guest SMCCC calls are handled by the hypervisor; host FF-A and PSCI calls are proxied by pKVM to TrustZone firmware. **[verified]** — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html)
- [spec, not re-fetched] Implications for a new type-1: (i) guest side — trap HVC (and SMC via `HCR_EL2.TSC`) and implement a small PSCI subset (CPU_ON/OFF/SUSPEND, SYSTEM_OFF/RESET, VERSION, FEATURES) plus SMCCC arch calls (ARCH_WORKAROUND_1/2/3 discovery for Spectre mitigations, TRNG optional); this *replaces* x86's INIT/SIPI/AP-trampoline emulation and ACPI power-off emulation and is a few hundred lines. (ii) host side — the hypervisor itself uses PSCI over SMC to EL3 firmware (TF-A) to bring up secondary cores and for idle/suspend/reset; it is a client of firmware it cannot replace. — [Arm PSCI / SMCCC specifications](https://developer.arm.com/Architectures/Power%20State%20Coordination%20Interface)

**FEAT_NV / NV2 (nested virtualization)**
- KVM/arm64 nested virtualization went upstream for Linux 6.16 (mid-2025) and supports only FEAT_NV2 (Armv8.4+; plain FEAT_NV dropped); with Armv9.5 NV can be implemented as NV2 alone ("NV_frac"). Arm's guide: NV requires FEAT_NV2 on a *bare-metal* host and the log line "VHE+NV2 mode initialized"; a standard cloud VM does not expose it. Recursive NV series followed in 2025. — [KVM/arm64 6.16 pull](https://lists.infradead.org/pipermail/linux-arm-kernel/2025-May/1030962.html); [Arm learning path](https://learn.arm.com/learning-paths/servers-and-cloud-computing/nested-virtualization/); [NV2-only commit](https://mirrors.lzu.edu.cn/git/linux-nf/-/commit/7f3225fe8bc2b4a406160d3efdb900bd01037aea); [KVM Forum 2025 talk](https://pretalx.com/kvm-forum-2025/talk/XBVDHS)
- Cloud reality: AWS launched nested virtualization on *virtual* EC2 instances in Feb 2026 for Intel families only (C8i/M8i/R8i, extended June 2026 to C7i/M7i/R7i etc.); **Graviton instances are not supported**; running your own hypervisor on Graviton requires `*.metal` instances. Azure states Cobalt 100 VMs offer no bare-metal instances. — [AWS What's New Feb 2026](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-ec2-nested-virtualization-on-virtual); [AWS June 2026](https://aws.amazon.com/about-aws/whats-new/2026/06/nested-virtualization-intel-us-gov-cloud/); [InfoQ](https://www.infoq.com/news/2026/03/aws-ec2-nested-virtualization/); [Arm migration guide](https://learn.arm.com/migration/)

**SMMUv3 (passthrough / DMA isolation)**
- NOVA added an SMMU abstraction layer and SMMUv3 support, the GIC ITS, and LPIs across releases 25.08–25.26, with device/DMA/interrupt assignment as capabilities (`assign_dev`, `assign_int`). **[verified from slides]** — [FOSDEM 2026 NOVA slides](https://fosdem.org/2026/events/attachments/SUMHNW-nova/slides/267403/nova_-_fo_yup0qhf.pdf)
- pKVM still has no upstream DMA isolation; the "KVM: Arm SMMUv3 driver for pKVM" series reached RFC v2 at 58 patches — an indicator of SMMUv3 complexity even when most of the driver stays in the host. — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html); [SMMUv3 pKVM RFC](https://patchew.org/linux/BN9PR11MB52760686ABB3145E44BAD95A8C1A2@BN9PR11MB5276.namprd11.prod.outlook.com)
- Xen on Arm: ACPI boot is "mostly implemented" but *experimental*; the remaining blocker is IORT handling for proper IOMMU support; devicetree boot is recommended where both exist (Sept 2025). — [xen-devel, Aug 2025](https://lists.xen.org/archives/html/xen-devel/2025-08/msg01497.html); [SUPPORT.md discussion](https://mid.mail-archive.com/xen-devel@lists.xenproject.org/msg198280.html)
- [spec, not re-fetched] SMMUv3 essentials: stream table (StreamID -> stream table entry selecting stage-1 and/or stage-2 config), in-memory command and event queues, stage-2 tables can share format (and, with care, the actual tables) with CPU stage-2; MSIs from passthrough devices go through the GIC ITS (DeviceID/EventID -> LPI), so interrupt isolation needs ITS command-queue mediation rather than x86-style interrupt remapping tables; topology comes from ACPI IORT (or DT `iommus`/`msi-map`). — [Arm SMMUv3 specification](https://developer.arm.com/documentation/ihi0070/latest/)

**Arm-side designs (pKVM / Hafnium / Gunyah / Bao / seL4 / Xen)**
- pKVM: details in section 1; summary — deprivileged Linux host under a small EL2 hypervisor sharing the kernel image, page donation/sharing, GICv3 only, experimental upstream, no DMA isolation. — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html)
- Hafnium: the reference **S-EL2** Secure Partition Manager Core in the TF-A stack — the SPMD at EL3 relays FF-A messages from the normal world (hypervisor or OS) to the SPMC at S-EL1 or S-EL2; Hafnium manages secure partitions in the secure world; TF-A docs list only Arm FVP as supported for the reference stack; NVIDIA ships it on Jetson. It is a secure-world partition manager, not a general normal-world VM host. — [TF-A SPM docs](https://trustedfirmware-a.readthedocs.io/en/v2.6/components/secure-partition-manager.html); [NVIDIA Jetson docs](https://docs.nvidia.com/jetson/archives/r38.4/DeveloperGuide/SD/Security/Hafnium.html)
- Gunyah: Qualcomm's type-1 for Arm; Linux VMM driver not yet merged (v17 Feb 2024; new 34-patch RFC April 2025). — [Qualcomm blog](https://www.qualcomm.com/developer/blog/2024/08/learn-about-gunyah--qualcomm-s-open-source--lightweight-hypervis); [RFC](https://lists.infradead.org/pipermail/linux-arm-kernel/2025-April/1022032.html)
- Bao / Jailhouse / Xen dom0less / seL4 CAmkES VMM on the same Arm board: sizes 8.4 K / 9.9 K / 67 K / 14.8 K+40 K SLoC; base interrupt latency ~840 ns / ~1 us / higher / 9,400 ns vs 200 ns native; Bao adds +1.8% to Linux boot. Bao was evaluated on GICv2 (ZCU104) and GICv3 (i.MX8QM). **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- seL4 on Arm: verified configurations exist for AArch64 hypervisor mode (kernel at EL2); Microkit requires EL2 for VMs; libvmm 0.2.0 (Aug 2026). — [seL4 16.0.0 notes](https://docs.sel4.systems/releases/sel4/16.0.0); [libvmm](https://github.com/au-ts/libvmm)
- NOVA on Arm: 11,008 SLOC (release 24.17), runs on Raspberry Pi 4 and NVIDIA DGX Spark per FOSDEM 2026 slides; boots as Multiboot2 or Linux-image payload from UEFI/GRUB/U-Boot. — [FOSDEM 2026 slides](https://fosdem.org/2026/events/attachments/SUMHNW-nova/slides/267403/nova_-_fo_yup0qhf.pdf)

**Trap costs on Arm**

- A 2025 blog gives an "expected" 200–800 cycles per exit on Neoverse N1 without measurement data — not reliable. — [PandaStack blog](https://www.pandastack.ai/blog/kvm-vm-exits-explained/)

**Server platform reality**
- Cores: AWS Graviton4 and Google Axion are Neoverse V2 designs; Azure Cobalt 100 is Neoverse N2. [secondary] — [Wikipedia: ARM Neoverse](https://wikipedia.com/wiki/ARM_Neoverse); [Arm newsroom, Graviton4](https://newsroom.arm.com/blog/aws-graviton4)
- Standards: Arm SystemReady = common BSA hardware spec + market supplements; the server band (SystemReady SR) = BSA + SBSA + SBBR boot recipe (UEFI + ACPI). Linux's ACPI-on-Arm assumes BSA/BBR compliance and servers additionally follow SBSA. A SystemReady-SR OS sees UEFI, ACPI tables, PSCI over SMC, GICv3 and SMMUv3. — [kernel.org ACPI on Arm](https://docs.kernel.org/6.16/arch/arm64/arm-acpi.html); [UEFI Forum SystemReady deck](https://uefi.org/sites/default/files/resources/15.%20Integrate%20Arm%20SystemReady_Arm_Wang_FINAL.pdf)
- Guest side is the opposite: Firecracker on aarch64 configures only a GICv3 vGIC and boots guests with virtio-mmio and devicetree — its kernel policy lists `CONFIG_ACPI`/`CONFIG_PCI` as required on x86_64 but not on aarch64. — [Firecracker kernel policy](https://www.github.com/firecracker-microvm/firecracker/blob/main/docs/kernel-policy.md); [Firecracker issue 1196](https://github.com/firecracker-microvm/firecracker/issues/1196)

### Inferences
- **Which is simpler to bring up first: ARM64.** Evidence: smaller arch-specific code in the one shared-codebase data point (NOVA 11.0 K vs 14.0 K SLOC), 8.4 KSLoC Bao boots Linux guests on Arm, cheaper traps for an EL2-resident hypervisor, no trap needed for guest timer programming or EOI, ISV-decoded MMIO aborts instead of an instruction emulator, PSCI instead of INIT/SIPI. Counter-evidence to state honestly: (a) GICv3 ITS + SMMUv3 + ACPI/IORT is more code than x86's minimum (x2APIC + VT-d DMAR), and both Xen (ACPI/IORT experimental) and pKVM (no IOMMU) are still unfinished exactly there; (b) no nested-virt development path on Graviton cloud VMs; (c) x86 hardware is cheaper and ubiquitous for CI. Net: ARM64 first for the CPU/memory/interrupt core; expect platform/IO work to dominate.
- **Minimum ARM64 baseline to mandate** (keeps the code small, matches Neoverse N1+/V1+ servers): Armv8.2+ with VHE (write for E2H=1), 16-bit VMID, GICv3 with system-register CPU interface (no GICv2, no MMIO GICC), ≥ GICv4.1 treated as an optional accelerator (vSGI/vLPI direct injection), generic timers with ECV optional, SMMUv3, PSCI ≥ 1.0 via SMC, UEFI + ACPI (MADT/GTDT/IORT/MCFG/SPCR/DBG2) on hosts. Guests: devicetree + PSCI + virtio-mmio (or virtio-pci via ECAM) — no ACPI/UEFI in the guest for fast boot.
- **Host discovery strategy**: servers (Ampere, Graviton metal, Axion/Cobalt class) are UEFI+ACPI; do not plan on host devicetree except for QEMU `virt` and dev boards. A small static-table ACPI parser (no AML interpreter) is sufficient for MADT/GTDT/IORT/MCFG/SPCR; anything needing AML (PCI `_OSC`, power management) should be delegated to the Linux driver VM. This is identical in spirit to x86 (MADT/DMAR/MCFG) and should be one shared ACPI module.
- **CoW / snapshot-clone on stage-2** works as on EPT (read-only stage-2 mapping -> permission fault -> copy -> remap) with two Arm-specific points: (i) break-before-make — changing a live stage-2 block to a table or changing output address requires invalidate + TLBI + remap unless FEAT_BBM level 2 is present, which matters when splitting 2 MiB blocks under running multi-vCPU guests; (ii) TLB invalidation is a broadcast instruction (TLBI ...IS) rather than IPI shootdown, which simplifies SMP code. For dirty tracking, design the page-table layer so "hardware log" (PML on Intel, HDBSS on Armv9.5) and "write-protect fault" are interchangeable backends; neither is needed for clone-from-snapshot, only for incremental snapshots/migration. (Break-before-make/BBM statements are from background knowledge of the Arm ARM, not verified this session.)
- **Interrupts for many small guests**: GICv3 LRs + in-kernel vGIC emulation is the baseline and is cheap for the common case (timer PPI, a few virtio SPIs); the expensive case is guest IPIs (SGI trap, ~2,500–6,000 cycles in the dated data), which GICv4.1 vSGIs eliminate. For 1–2 vCPU agent sandboxes IPI cost is secondary; do not depend on GICv4.1.
- **Portability architecture (one codebase, two ISAs)** — what it takes:
  1. A narrow arch interface with exactly these seams: `vcpu_enter()/exit reason decode`, guest register frame, stage-2/EPT page-table ops (map/unmap/protect/split/query-dirty + TLB invalidate), interrupt-controller virtualization (inject/EOI/IPI/timer), physical IRQ controller + timer drivers, IOMMU ops, CPU bring-up, and feature discovery. NOVA and Bao both follow this split; Bao also adds RISC-V behind the same interface.
  2. Normalize exits into a small architecture-neutral set handled by generic code: stage-2 fault (IPA, access type, size, value-register for MMIO), hypercall, halt/WFI, virtual-timer expiry, system-register/MSR trap, shutdown/reset. ARM's ISV syndrome and x86 EPT-violation + (rare) instruction decode both reduce to the same "MMIO access" event if the guest ABI is restricted to virtio-mmio with simple MOV/LDR/STR accesses.
  3. **Converge the guest ABI rather than the host**: same paravirtual device set (virtio-mmio blk/net/vsock/rng/console), same direct-kernel boot contract (x86: PVH 64-bit entry; arm64: Image + DTB), paravirtual clock, no firmware in the guest. Then the per-VM user-mode VMM is >90% shared; only boot-info generation (DTB vs PVH start_info/E820) and CPU-ID/feature-register policy differ.
  4. Keep policy (scheduler, memory allocator, capability/object model, VM lifecycle, snapshot/CoW logic) strictly arch-independent and operating on an abstract "second-stage address space" object. Page-table code can be one generic 4-level radix walker parameterized by PTE encode/decode (EPT bits vs stage-2 descriptor bits) — both use 4 KiB/2 MiB/1 GiB at the same levels with a 4 KiB granule, so mandate the 4 KiB granule on Arm.
  5. Per-arch items that will *not* unify and should not be forced: CPUID/MSR emulation and feature masking (x86) vs ID-register sanitization and `HCR_EL2`/fine-grained-trap configuration (Arm); APIC/x2APIC/APICv vs GICv3/v4.1; VT-d vs SMMUv3+ITS; speculative-execution mitigations; SMP boot (INIT/SIPI vs PSCI); firmware interface (none vs SMCCC to EL3).
  6. CI on both from day one: QEMU TCG can emulate EL2 (and NV2 on `max`/Neoverse models) on x86 hosts; x86 nested KVM for the other side; one real SystemReady box for GIC ITS/SMMUv3 since emulation hides errata.
  7. Language: the arch seam is small enough that Rust traits or C++ templates (NOVA's approach) with zero dynamic dispatch on the exit path work; the hard part is discipline, not mechanism.
- **Deployment consequence of the Graviton nested-virt gap**: on x86 the product could run nested on commodity cloud VMs (now including EC2 Intel instances since Feb 2026); on ARM64 it must own EL2, i.e. Graviton `.metal`, Ampere bare metal (OCI A1/A2-class, Hetzner, colo), or on-prem. This asymmetry should be surfaced in the final report as a go-to-market constraint.

## 2. How existing type-1 hypervisors are architected (size, language, license, maturity, 2026 status)

### Takeaway
Small type-1 hypervisors cluster into three families: (1) microhypervisors with per-VM user-mode VMMs (NOVA and its forks, seL4) at roughly 10–15 KSLOC of privileged code; (2) static partitioners (Bao, Jailhouse, Muen, hvisor) at roughly 8–10 KSLOC with no scheduler and no dynamic VM lifecycle; and (3) "monolithic-plus-control-domain" systems (Xen ~67 KSLOC for a minimal Arm config and far more on x86, Hyper-V, ESXi) that are the only true type-1s proven at cloud scale. Nothing in families (1) and (2) is known to run thousands of short-lived Linux guests in production today.

Additional architecture details:
- NOVA exit path: a VM exit costs ~3,900 cycles on average in the 2010 evaluation, of which 1,016 cycles (26%) is the hardware guest/host transition, ~600 cycles (15%) is the IPC to and from the user-mode VMM, and 59% is instruction/device emulation in the VMM. "Only ... 15% of the total cost ... is a direct consequence" of the microhypervisor split. **[verified, dated 2010 hardware]** — [NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)
- seL4-VMM measured costs on Arm (Zynq UltraScale+): interrupt latency 9,400 ns vs ~840 ns for Bao and ~200 ns bare metal, because every interrupt goes kernel -> user VMM -> kernel; Bao/Jailhouse execute ~200 instructions on the interrupt path vs ~1,050 for Xen. With GIC direct injection latency returns to near-native. **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- TCB caveat from the same paper: "The hypervisor SLoC does not directly reflect the VM TCB" — with seL4 the *shared* TCB is only the verified kernel since each VM has its own isolated VMM; with Jailhouse the Linux root cell is in the critical path and arguably in the TCB. **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- Xen LightVM (SOSP 2017): by replacing XenStore with shared-memory "noxs" and a leaner toolstack, a unikernel VM boots in 2.3 ms (fork/exec ~1 ms), up to 8,000 VMs per host, unikernel image 480 KB using 3.6 MB RAM. Shows the bottleneck for fast VM creation in Xen was the dom0 toolstack/XenStore, not the hypervisor. **[verified, dated 2017; never upstreamed]** — [LightVM, SOSP 2017](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)

### Inferences
- The realistic reference designs for a *dynamic* lightweight type-1 are NOVA (object/capability model, per-VM VMM, ~11–14 KSLOC, now with public proofs) and Xen-PVH-with-noxs-style toolstack; static partitioners (Bao, Jailhouse, Muen) are instructive for minimal bring-up code (8–10 KSLOC proves how little is needed to drive EL2/VMX) but lack everything the sandbox workload needs (scheduler, memory allocator, overcommit, VM lifecycle).
- The microhypervisor's IPC tax is small relative to emulation cost on x86 (15% in NOVA's data), but is very visible on interrupt paths that could otherwise be handled in-kernel or by hardware (seL4-VMM 9.4 us). Conclusion: keep interrupt injection/timers in the kernel or rely on APICv/GIC direct injection; put device models in user space.
- The embedded/static type-1 ecosystem looks stagnant or shrinking in 2026 (Jailhouse, ACRN quiet; Hedron effectively closed development; Cyberus pivoting to KVM), while momentum is in KVM-derived designs (pKVM, Nitro, mshv with Linux root) and in NOVA/seL4 verification.

## 3. Monolithic vs microhypervisor vs static partitioning: robustness and thousands of short-lived VMs

### Takeaway
Static partitioning gives the smallest code and best determinism but is structurally unsuited to churn; monolithic designs give the fastest exit paths but put emulation and often drivers in the most privileged layer; the microhypervisor pattern (minimal kernel: vCPU/VMCS handling, stage-2 tables, scheduling, IPC, interrupt routing; everything else in one deprivileged VMM per VM) best fits "many mutually-distrusting short-lived guests" because a VMM compromise or crash is contained to one VM, at a measured cost of roughly 15% of exit-handling time on exits that need the VMM.

### Cited Findings
- Static partitioning hypervisors are defined by 1:1 vCPU-to-pCPU mapping (no scheduler), static memory assignment, and passthrough/exclusive device assignment; they are built for mixed-criticality embedded systems. **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- Code size ordering (same paper, Arm): Bao 8.4 K < Jailhouse 9.9 K (+2.2 K driver) < seL4 14.8 K (+40 K VMM) < Xen 67 K SLoC. **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- Boot overhead in that study is dominated by image loading, not hypervisor logic: Linux guest (59 MiB image) boot 7,665 ms native vs 7,806 ms on Bao (+1.8%), 8,534 ms on Xen (+11.3%), 12,285 ms on Jailhouse (+60%), 12,630 ms on seL4-VMM (+65%); seL4's overhead is in user-level capability/kernel-object setup. **[verified; embedded board, includes U-Boot]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- NOVA's thesis: with nested paging, >99% of vTLB-related exits vanish, so a decomposed design reaches ~1–3% overhead; microhypervisor-to-VMM communication is 15% of average exit handling. Each vCPU has its own handler EC so exits on different vCPUs are handled in parallel without a global VMM lock. **[verified, 2010]** — [NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)
- Monolithic counter-examples: ESXi "implements device drivers and VMM functionality inside the hypervisor"; Hyper-V and Xen push drivers and device emulation into a privileged parent domain that inflates the TCB. **[verified, 2010]** — [NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)
- Firecracker applies the same per-VM-VMM decomposition on top of KVM: one VMM process per microVM, jailed with chroot/namespaces and a seccomp-bpf filter that whitelists 24 syscalls and 30 ioctls (22 required by the KVM API). **[verified]** — [Firecracker NSDI 2020](https://files.usenix.org/s3fs-public/cdn/nsdi20-paper-agache.pdf)
- LightVM shows dynamic-workload scalability depends on control-plane design: Xen's centralized XenStore made creation time grow with the number of guests; removing it gave 2.3 ms boots and 8,000 VMs/host. **[verified]** — [LightVM SOSP 2017](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)

### Inferences
- For thousands of short-lived VMs the design-critical paths are not steady-state exits but VM create/destroy: allocating and zeroing memory, building stage-2 tables, creating kernel objects, wiring devices, and reclaiming everything reliably on teardown. seL4's +65% boot overhead from capability setup and Xen's XenStore bottleneck are both warnings: the object model and control plane must be O(1) per VM and avoid any global registry or lock.
- A capability/object model (NOVA, seL4) makes teardown of a dead VM's resources tractable (revoke the PD), which is a robustness advantage for churn-heavy workloads over ad hoc reference counting.
- Recommended split for the project: in-kernel = vCPU run loop, EPT/stage-2 fault fast path, LAPIC/GIC + timer virtualization (or hardware APICv/vGIC), scheduler, IOMMU programming; per-VM user VMM = virtio device models, boot loader, snapshot/restore logic; separate driver domain(s) = physical NIC/NVMe.
- Static partitioning ideas worth borrowing even in a dynamic design: per-core hypervisor data with no cross-core locks on the exit path, and optional core pinning for latency-sensitive tenants.

### Gaps
- No published measurements found of VM creation/destruction rates on NOVA, seL4, or Hedron (create-rate analogues to Firecracker's 150 microVMs/s/host).
- No data found on long-running stability of microhypervisors under high VM churn (memory fragmentation, capability-space exhaustion).

## 4. KVM-based "type-1.5" designs vs true type-1: the honest argument

### Takeaway
The honest case *against* building a true type-1 is strong: KVM plus a minimal host and a Rust VMM (Firecracker) already delivers <=125 ms boots, <=5 MiB per-VM overhead, 150 creations/s/host, millisecond-scale snapshot restores, and free reuse of Linux's scheduler, memory manager, drivers and tooling; AWS explicitly chose this for implementation cost and operational familiarity. The honest case *for* a true type-1 is narrower: a privileged TCB of ~10–15 KSLOC (potentially formally verified) instead of KVM's ~120 KLOC plus the reachable parts of a multi-million-line host kernel, strict containment of drivers and VMMs outside the TCB, and freedom to redesign the VM lifecycle and memory model (snapshot/fork, CoW, sharing) as first-class primitives rather than through Linux mm abstractions.

### Cited Findings
- Firecracker rationale (quote): "we chose to keep KVM, but entirely replace QEMU"; relying on Linux components was chosen for "implementation cost" and because Linux's scheduler/memory manager etc. are "well-proven" and operators already know the tooling. Firecracker is ~50 KLOC of Rust, "96% fewer lines than QEMU"; QEMU is >1.4 M LOC and "the KVM code in Linux adds another 120,000 lines". Results: <5 MB memory overhead per microVM, boot to application code in <125 ms, up to 150 microVMs/s/host. Measured VMM overhead ~3 MB Firecracker vs ~13 MB Cloud Hypervisor vs ~131 MB QEMU per VM. **[verified; 2020]** — [Firecracker NSDI 2020](https://files.usenix.org/s3fs-public/cdn/nsdi20-paper-agache.pdf)
- Firecracker spec (current): <=125 ms from InstanceStart API call to guest `/sbin/init`; VMM memory overhead <=5 MiB for a 1 vCPU / 128 MiB VM. — [Firecracker SPECIFICATION.md](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/SPECIFICATION.md)
- Snapshot restore: Firecracker can restore a microVM snapshot "in as little as 4 ms (or about 10 ms for a full decent-sized Linux system)" per Marc Brooker (AWS). A third-party sandbox builder self-reports ~28 ms end-to-end restores (5 ms process start, 8 ms mmap of memory file, 10 ms CPU/device state, 5 ms vsock reconnect). — [Brooker, 2022](https://brooker.co.za/blog/2022/11/29/snapstart/); [dev.to blog, self-reported](https://dev.to/adwitiya/how-i-built-sandboxes-that-boot-in-28ms-using-firecracker-snapshots-i0k)
- TCB comparison from the NOVA paper: even assuming Linux stripped to ~200 KLOC, KVM (+20 KLOC then) + QEMU (~140 KLOC) is an order of magnitude larger than NOVA's 9 KLOC privileged core; in NOVA the VMM (20 KLOC) is per-VM and unprivileged. **[verified; 2010 numbers]** — [NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)
- AWS Nitro went the other direction from Xen: it "entirely eliminated the need for Dom0" using a custom minimized KVM-based hypervisor with device functions offloaded to Nitro cards. — [AWS Nitro whitepaper](https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/the-nitro-system-journey.html)
- pKVM shows the hybrid end-state: keep Linux for drivers/scheduling but remove it from the confidentiality/integrity TCB of guests with a small EL2 layer; yet upstream it remains experimental after ~5 years, with DMA isolation unimplemented and restrictions such as no dirty logging, no memslot changes after start, no runtime page reclaim (pages stay mlocked). **[verified]** — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html)
- Microsoft now supports Linux as the Hyper-V root partition (`mshv_root` in mainline), i.e. a true type-1 with a Linux control domain exposed via ioctls much like KVM. — [LWN](https://lwn.net/Articles/1014239/); [mshv_root.h, v6.19](https://tangled.org/tjh.dev/kernel/blob/v6.19/drivers/hv/mshv_root.h)
- ARM data point that hosted designs are not inherently slow on I/O: KVM x86 I/O-latency-out 560 cycles vs Xen x86 11,262 cycles, because Xen must switch to dom0. **[verified; 2016]** — [Dall et al., ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)

### Inferences
- Arguments against true type-1 (to be stated plainly in the report): (a) performance parity is the best case, not an improvement — exits cost the same hardware transition; (b) the driver problem (section 6) forces either a Linux driver domain (so Linux is still on the box) or a narrow hardware compatibility list; (c) loss of the Linux ecosystem: perf, eBPF, cgroups, live patching, kdump, NUMA balancing, KSM, THP, userfaultfd, io_uring; (d) years of hardening work for CPU errata, side-channel mitigations (L1TF, MDS, Retbleed, etc.), microcode loading, power management, hotplug, RAS — all already in Linux; (e) the precedents: AWS moved Xen -> KVM, Cyberus added a KVM product, Jailhouse/ACRN stagnated.
- Arguments for: (a) host-kernel attack surface — a guest-to-host escape in KVM lands in ring 0 of a general-purpose kernel; in a microhypervisor design most guest-reachable code (device models, instruction emulation) is in a per-VM unprivileged process and the kernel-reachable surface is ~10 KSLOC; this matters for AI-agent sandboxes that run adversarial/untrusted code by design; (b) the workload is narrow (Linux guests only, virtio only, no legacy), which is exactly the condition under which a small purpose-built system is feasible; (c) VM fork/snapshot/CoW memory sharing and sub-10 ms creation can be kernel primitives; (d) formal verification is becoming practical for this size (NOVA proofs public in 2026; seL4).
- Middle paths worth naming: pKVM-style deprivileged Linux host; NOVA/seL4 as the kernel with a custom VMM (reuse rather than build); Hyper-V with Linux root + OpenVMM/Cloud Hypervisor; or type-1 with a Linux *driver VM* only (no dom0 control plane).
- Caveat on the security argument: the microhypervisor still needs the same speculative-execution mitigations and must itself get them right; a small TCB is not automatically a hardened one.

### Gaps
- No independent head-to-head benchmark (boot latency, density, exit cost) of a microhypervisor vs Firecracker/KVM on the same hardware was found.
- No quantitative data found on KVM escape CVE counts vs Xen/Hyper-V for 2020–2026 to ground the attack-surface argument.
- Cloud Hypervisor boot-time figures and Firecracker 2025–2026 feature/status (e.g. current snapshot/UFFD capabilities) were not verified.

## 5. Memory virtualization, vCPU scheduling, timer/interrupt virtualization costs, VM-exit costs

### Takeaway
With nested paging the steady-state cost of virtualization is dominated by exit *frequency* (I/O, timers, IPIs, EPT faults during boot/first-touch), not per-exit cost; a bare hardware round trip is on the order of ~1,000 cycles on x86 (roughly 0.3–0.5 us at 2–3 GHz) and a few hundred cycles on ARM for a type-1, while exits that involve a user-mode VMM or another domain cost 3–10x more. Huge pages in the second stage and hardware interrupt virtualization are the two biggest levers; fast boot for short-lived VMs is mainly about avoiding per-page EPT faults and memory zeroing.

### Cited Findings
- Hardware exit-cost trend (cycles for a VM exit+entry pair by microarchitecture): 3,963 on Prescott falling to 761 on Westmere; ~80% reduction from Prescott to Sandy Bridge. **[secondary summary of VMware ATC 2012 paper; dated]** — [Agesen et al., USENIX ATC 2012](https://www.usenix.org/conference/atc12/technical-sessions/presentation/agesen)
- Measured hypercall round trip: KVM x86 1,300 cycles, Xen x86 1,228, Xen ARM 376, KVM ARM (nVHE) 6,500 cycles. **[verified; 2016]** — [Dall et al., ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)
- NOVA: average handled exit ~3,900 cycles (1,016 hardware transition; ~600 IPC to user VMM; rest emulation); disk I/O request needing 6 exits = 21,500 cycles; network interrupt path ~16,300 cycles with 6 exits per interrupt (pre-APICv; mask/ack/EOI all exit). **[verified; 2010, 2.67 GHz Nehalem-era]** — [NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)
- KVM-unit-tests sample (2012, unnamed CPU): vmcall 3,898 cycles; in-kernel PIO read 7,237; PIO handled in userspace 20,574 — i.e. the round trip to a user-space VMM adds ~13,000 cycles there. **[secondary; dated]** — [kvm patch, Bonzini 2012](https://patchwork.kernel.org/project/kvm/patch/1355402437-21935-1-git-send-email-pbonzini@redhat.com/)
- Interrupt virtualization: without direct injection all Arm hypervisors raise interrupt latency by at least an order of magnitude over bare metal (200 ns -> 840 ns Bao, ~1 us Jailhouse, more for Xen, 9,400 ns seL4-VMM); under cache interference latencies rise a further ~10x; with direct injection latency is near native. Virtual IPIs require a trap to emulate the GIC distributor write and forwarding to the target core. Inter-VM notification latency: ~1,500 ns (Jailhouse) to ~1,900 ns (Bao). **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- Virtual IRQ completion (EOI): 71 cycles on ARM (hardware vGIC, no trap) vs ~1,500 cycles on x86 without APICv (trap). Virtual IPI: ~5,200–5,600 cycles on x86, 5,978 (Xen) / 11,557 (KVM) on ARM. VM switch: 4,812 (KVM x86) to 10,534 (Xen x86) cycles. **[verified; 2016, pre-APICv-era measurements]** — [Dall et al., ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)
- Superpages: "more than 99% of native performance can be achieved when nested paging (EPT/NPT), tagged TLBs (VPID/ASID), and large host pages are used"; nested paging cut exits by two orders of magnitude and overhead from >20% to 1–3%. **[verified; 2010]** — [NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)
- Superpages on Arm: hypervisors without 2 MiB stage-2 mappings show clearly higher overhead; forcing 4 KiB pages (e.g. for cache coloring) costs up to ~20% on MiBench. **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- Dirty logging: PML logs GPAs of pages whose EPT dirty bit gets set into a log page instead of taking a write-protection fault per page. [secondary] — [SDM mirror](https://xem.github.io/minix86/manual/intel-x86-and-64-manual-vol3/o_fe12b1e2a880e0ce-1096.html)
- pKVM as a cautionary data point on memory features in a small hypervisor: no dirty logging, no read-only memslots, no runtime reclaim of donated pages, only anonymous/swap-backed memory. **[verified]** — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html)
- Overcommit/density in practice: Firecracker's stated design target was thousands of microVMs per host (e.g. up to 8,000 functions filling RAM, more with soft allocation), with per-VM overhead ~3 MB. LightVM: 8,000 unikernel VMs/host at 3.6 MB each. **[verified]** — [Firecracker NSDI 2020](https://files.usenix.org/s3fs-public/cdn/nsdi20-paper-agache.pdf); [LightVM](https://www.cs.utexas.edu/~witchel/S25-380L/papers/manco17sosp-lightvm.pdf)
- Scheduling: NOVA separates execution contexts (ECs) from scheduling contexts (SCs: priority + time quantum) with donation across IPC, so a VMM handling an exit runs on the vCPU's time budget; static partitioners avoid a scheduler entirely via 1:1 pinning. — [NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf); [RTAS 2023](https://arxiv.org/abs/2303.11186)

### Inferences
- Rule-of-thumb budget for 2026 planning (inference, not a verified modern measurement): bare VMX/SVM round trip ~1,000–2,000 cycles (~0.3–0.7 us) including the speculative-execution mitigations (IBRS/IBPB/RSB stuffing, L1D flush where needed) that postdate all of the cited measurements and typically add hundreds of cycles; exit handled by a same-core user-mode VMM ~3,000–6,000 cycles; exit requiring a cross-core/cross-VM hop ~10,000+ cycles. The report should present these as estimates and recommend measuring on target hardware (kvm-unit-tests `vmexit.flat` is the standard tool).
- Timer cost: with a TSC-deadline LAPIC timer each guest timer re-arm is an MSR write exit unless the MSR is passed through or APICv timer virtualization is used; with a tickless (NO_HZ) guest kernel and idle guests this is small, but thousands of idle guests each ticking at 100–1000 Hz would be a real load — enforce tickless guest kernels and paravirtual idle (HLT exiting + long deadlines).
- EPT-violation handling for fast boot: back guest RAM with pre-zeroed 2 MiB (or 1 GiB) pages from a per-core pool so a booting guest takes hundreds rather than hundreds of thousands of EPT faults; for snapshot-clone, map the snapshot image read-only with CoW at 2 MiB granularity where possible and fall back to 4 KiB on write. Huge pages conflict with fine-grained CoW/dedup/ballooning — this is the central memory-design trade-off for sandbox density.
- Overcommit options for a type-1 without Linux mm: free-page reporting / virtio-balloon, CoW sharing of a common base snapshot (page-cache and kernel text shared across thousands of clones), and lazy population; swapping is likely not worth implementing.
- PML matters only if incremental/diff snapshots or live migration are wanted; EPT accessed/dirty bits scanned at snapshot time may be sufficient for short-lived guests.

### Gaps
- No verified 2023–2026 published measurement of VM-exit round-trip cost (cycles or ns) on Sapphire Rapids / Emerald Rapids / Zen 4–5 / Neoverse V2 was found despite targeted searches; the most recent hard numbers are 2010–2016. Quantified exit-reduction figures for APICv/IPI-virtualization/AVIC were also not found.
- No source retrieved on EPT 2-D page-walk cost with 5-level paging or on current hardware walk caches.
- No sourced data on vCPU scheduler designs suited to thousands of mostly idle vCPUs (e.g. Xen credit2, Hyper-V root scheduler) was collected.

## 6. The device driver problem

### Takeaway
No general-purpose type-1 hypervisor writes its own broad driver set except ESXi (drivers in the vmkernel, at the cost of an HCL and a large TCB); everyone else reuses an existing OS's drivers by running it deprivileged — Xen's dom0 / driver domains, Hyper-V's root partition, ACRN's Service VM, Jailhouse's root cell, NOVA/seL4 user-level drivers or Linux driver VMs — or avoids the problem with passthrough/SR-IOV behind an IOMMU, or pushes it into hardware (Nitro cards). For the sandbox project the minimal viable approach is a small in-hypervisor set (UART, timer, interrupt controller, IOMMU) plus a Linux driver VM owning NIC/NVMe via VT-d passthrough and exporting virtio/vhost-user backends to per-VM VMMs.

### Cited Findings
- Hyper-V: the root partition "manages machine-level functions such as device drivers, power management, and device hot addition/removal" and is "the only partition that has direct access to physical memory and devices"; children use VSCs talking over VMBus to VSPs in the root; "Enlightened I/O" bypasses device emulation. **[verified]** — [Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/architecture)
- Xen: dom0 hosts drivers, backends, XenStore and the toolstack; device-model *stub domains* (since Xen 3.3, 2008, mostly Mini-OS based) and driver domains disaggregate dom0; Qubes OS moved net and USB (and storage backends) out of dom0. Caveat: Mini-OS frontends are not hardened against malicious backends. PVH guests need no QEMU at all. — [Xen wiki: Device Model Stub Domains](https://wiki.xen.org/wiki/Device_Model_Stub_Domains); [xen-devel, June 2024](https://lists.xen.org/archives/html/xen-devel/2024-06/msg01638.html); [Rutkowska on xen-devel, 2012](https://lore.kernel.org/all/4F0EE07C.2070603@invisiblethingslab.com/)
- Xen I/O cost of the dom0 model: I/O-latency-out 11,262 cycles (x86) / 16,491 (ARM) vs KVM x86 560 cycles, since each I/O signal requires a switch to dom0. **[verified; 2016]** — [Dall et al., ISCA 2016](https://www.cs.columbia.edu/~nieh/pubs/isca2016_armvirt.pdf)
- ESXi: device drivers and VMM functionality are implemented inside the hypervisor. **[verified; 2010 description]** — [NOVA EuroSys 2010](https://hypervisor.org/eurosys2010.pdf)
- NOVA: drivers run in user mode; 2025–2026 releases added explicit *device capabilities* — `assign_dev` (device as a source of DMA into a DMA space, enforced by IOMMU/SMMUv3) and `assign_int` (device as a source of MSI/LPI targeting an interrupt semaphore) — specifically to scale to "thousands of devices and interrupts". **[verified from slides]** — [FOSDEM 2026 NOVA slides](https://fosdem.org/2026/events/attachments/SUMHNW-nova/slides/267403/nova_-_fo_yup0qhf.pdf)
- Static partitioners: devices are passed through and exclusively assigned to one VM; Bao has no privileged VM; Jailhouse relies on the Linux root cell to boot and initialize hardware. **[verified]** — [RTAS 2023](https://arxiv.org/abs/2303.11186)
- Nitro: device models that dom0 used to provide are moved onto dedicated Nitro cards presenting NVMe/ENA to guests; the hypervisor has no dom0. — [AWS Nitro whitepaper](https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/the-nitro-system-journey.html)
- Firecracker (KVM): relies entirely on host Linux drivers; emulates only virtio-net, virtio-block (chosen over a filesystem passthrough to limit attack surface), serial and a minimal keyboard controller; virtio-block implementation ~1,400 lines of Rust, serial ~250 lines. **[verified]** — [Firecracker NSDI 2020](https://files.usenix.org/s3fs-public/cdn/nsdi20-paper-agache.pdf)
- pKVM: Linux host keeps all drivers, but DMA isolation via IOMMU is still unimplemented upstream (an Arm SMMUv3 driver for pKVM has been through multiple RFC rounds) — the host's devices can in principle DMA into protected memory until this lands. **[verified]** — [pKVM docs](https://docs.kernel.org/virt/kvm/arm/pkvm.html); [SMMUv3 for pKVM RFC](https://patchew.org/linux/BN9PR11MB52760686ABB3145E44BAD95A8C1A2@BN9PR11MB5276.namprd11.prod.outlook.com)
- IOMMU-based interrupt delivery on RISC-V: IOMMU MSI page tables redirect device MSIs to guest interrupt files for direct delivery. — [RISC-V AIA spec](https://docs.riscv.org/reference/aia/IOMMU.html)

### Inferences
- Options ranked for the sandbox project:
  1. **Linux driver VM(s) with VT-d passthrough of NIC and NVMe, exporting virtio backends** (vhost-user-style shared memory rings to guests). Reuses Linux drivers outside the TCB for isolation between guests *if* the hypervisor controls memory grants and the IOMMU; the driver VM is in the availability TCB and the data-path TCB (it sees guest I/O unless encrypted). Cost: every I/O crosses VM boundaries (cf. Xen's ~11K-cycle path) unless polling/shared-ring batching hides it.
  2. **SR-IOV VFs passed directly to guests**: near-native performance, no driver VM on the data path, but VF count limits (typically tens to low hundreds per port) conflict with "thousands of VMs", VF setup time affects boot latency, and snapshot/clone of device state is hard. Suited to premium/long-lived sandboxes only.
  3. **Native drivers for a tiny HCL** (e.g. one NVMe + one NIC family, or virtio only when running nested on a cloud): NVMe is a simple, well-specified interface and is feasible in user mode; modern NICs are not. Running nested on cloud instances (where the "hardware" is virtio/ENA/NVMe) narrows the HCL drastically but requires nested-virt support from the cloud.
  4. **SmartNIC/DPU offload** (Nitro pattern): out of reach for a new project except by targeting off-the-shelf DPUs that present virtio/NVMe to the host.
- The hypervisor itself cannot avoid: IOMMU (VT-d/AMD-Vi/SMMUv3) driver with interrupt remapping, PCI config-space mediation for passthrough, ACPI table parsing (MADT/DMAR/MCFG at minimum; AML interpretation should be delegated to the driver VM), and x2APIC/GIC/timer drivers. These are a meaningful fraction of a ~10–15 KSLOC kernel (NOVA's 2025–26 release notes are dominated by exactly this work).
- For AI-agent sandboxes the I/O profile (package downloads, git, builds, small files) is throughput-moderate and latency-tolerant, so option 1 with batching is likely adequate; a filesystem-sharing device (virtiofs-like) for workspace mounts would be a larger attack surface than virtio-blk, mirroring Firecracker's reasoning.

### Gaps
- No measurements found comparing driver-VM virtio backends vs SR-IOV vs in-host vhost on current (2024–2026) hardware.
- No sources collected on SR-IOV / Scalable IOV (SIOV) VF limits or on IOMMU (VT-d scalable mode, posted-interrupt remapping) programming cost per VM creation.
- Did not research existing reusable user-mode driver frameworks (e.g. seL4 sDDF, Genode DDE, SPDK/DPDK inside a driver VM) that could shortcut this work.
